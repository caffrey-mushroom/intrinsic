Datadog 是怎么运转的

从客户机器上的探针开始，跟着一条数据走完六站：采集、发送、进门处理、存储、分析、使用。每一站在干什么、在哪收钱、谁能替代。

一张图看懂

一句话：Datadog 是一条"数据流水线 + 一套看数据的工具"。它在客户的每台机器上装一个小程序 (探针)，持续把机器和程序的状态拍下来，传到 Datadog 自己的云上，在那里整理、对齐、存好，然后用告警、图表和 AI 帮工程师在出事时几分钟内找到原因。

怎么收钱：主要在流水线的入口和仓库收：装了多少台机器 (按主机)、送进来多少数据 (按 GB)、要保留多少可快速搜索的数据 (按条数和天数)。看数据本身，不管是人看还是 agent 看，基本不另收钱。

为什么难替代：难的不是图表，是第 3 站和第 5 站：数据一进门就被盖上统一的"身份证"并互相串好，然后在几秒内被告警引擎和 AI 用上。其余几站 (采集、传输、存储、界面) 都有更便宜的替代品，正在被一站一站地蚕食。

深色两站 (第 3 站进门处理、第 5 站分析) 是 Datadog 最难被替代的部分。第二行是每一站怎么收钱，第三行是谁在那一站切进来。收费为公开标价，大客户有折扣。

跟着一次故障走一遍

用一次真实感的故障，看数据在六站之间怎么走。

时间发生了什么在 Datadog 的哪一站
20:00:00某电商的"支付"服务发布新版本 v1.4.2，新版本多调用了一个风控接口第 1 站：探针记下"支付服务换版本了"，这条发布事件带着 version:1.4.2 标签进来
20:00 起每个结账请求经过：结账 → 购物车 (20 毫秒) → 库存 (30 毫秒) → 支付 (原来 200 毫秒，现在 1.8 秒)第 1 站：代码里的追踪库给每个请求一个编号，记下它在每个服务停留多久 (这一段叫 span)；第 2 站每几秒打包上传
20:00 起支付服务打出日志："fraud-check timeout after 1500ms"第 1 站：日志自动带上同一个请求编号；第 3 站进门时被解析出"超时""1500ms"这些字段
20:03结账接口的慢请求比例从 1% 升到 12%第 5 站：告警引擎每分钟检查一次规则 "结账 p99 延迟 > 1 秒持续 3 分钟"
20:05值班工程师的手机响了 (告警推到 Slack 和值班系统)第 6 站：告警消息里带着链接，点开直接看到出问题的那一段
20:06Bits AI 自动开始调查：哪个服务变慢 → 慢在哪个下游调用 → 那一刻有没有发布 → 相关日志写了什么第 5 站：因为数据在第 3 站已经按编号和标签串好，AI 每一步都是精确跳转，不用猜
20:09Bits 给出结论："支付 v1.4.2 新增的风控调用超时，建议回滚"；工程师确认回滚第 6 站：人在网页上确认；也可以是工程师在 Claude Code 里通过 MCP 问同样的问题
20:12延迟恢复第 5 站：告警自动关闭，整个过程被记进事故记录

12 分钟。如果数据分在六个工具里、没有统一编号，20:06 那一步会变成人或 agent 在几十万行日志里按时间去捞，通常要半小时到一小时。

六站分别在做什么

每一站展开说。收费是公开标价，大客户按年承诺有折扣；查询是否另收费以 Datadog 定价页为准，就我们所知基本不单独收。

站具体在干什么例子收费谁能替代
1. 采集客户在每台机器上装 Datadog Agent (一个后台小程序，Kubernetes 里每个节点一份)；在代码里加一个追踪库 (dd-trace)；打开几百个现成集成，自动读 AWS、MySQL、Nginx、Kafka 的状态。三种数据：指标 (每 10–15 秒一个数，如 CPU 63%)、链路 (一个请求经过每个服务的耗时)、日志 (程序自己写的每一行文字)一台机器每分钟产生几百个指标点、几千行日志按主机：基础设施 ~$15/台/月，APM ~$31/台/月OpenTelemetry 开源探针，所有厂商通用。采集在变成免费标准
2. 发送探针把数据压缩，几秒一批，通过 HTTPS 发到 Datadog 在某个地区的数据中心 (美国、欧洲等)。链路通常先在机器上采样，只留一部分100 个请求里留 10 个完整链路，出错和慢的全留不单独收费Cribl、管道产品：入库前先过滤、去重，直接减少后面按 GB 收的钱
3. 进门处理数据进门后：把日志拆成字段 (状态码、用户 ID、耗时)；给所有数据统一盖上服务名、环境、版本、主机这套标签；把请求编号对齐，让日志能链接到链路；从日志里生成指标；把信用卡号等敏感信息打码；同时计量"fraud-check timeout after 1500ms" 被拆成 error=timeout、duration=1500日志按摄入 GB 收，~$0.10/GB最难替代。对齐和串联是 Datadog 的核心，开源组合要客户自己配，配不好就串不起来
4. 存储三种数据分开存。指标：自研的时间序列数据库，按"指标名 + 标签组合"存，保留 15 个月。链路：选中的保留 15 天。日志分三档：可秒级搜索的热索引 (贵)，Flex Logs (便宜一些、查得慢一些)，归档到客户自己的 S3 (几乎免费，要用时再取回)。新出的 Federated Logs 干脆不搬，直接去客户的 ClickHouse / Databricks 里查15 天热日志 ~$1.70/百万条；自定义指标按序列数另收按条数、保留天数、指标序列数正在被蚕食：ClickHouse、S3、湖仓、Chronosphere (指标) 都更便宜；OpenAI 就是在这一站搬走的
5. 分析告警引擎每分钟跑一遍几百万条规则；从链路自动画出"谁调用谁"的服务地图；Watchdog 找异常；自研的时间序列模型 Toto 预测；Bits AI SRE 自动调查根因"结账 p99 > 1 秒持续 3 分钟" → 告警大部分含在主机费里；Bits 按 AI credit (~$1/credit)较难替代，要实时、要串好的数据。Dynatrace 的自动根因在这里更强
6. 使用告警推到 Slack / 值班系统；工程师在网页上看仪表盘、点链接排查；Bits 给出结论；外部 agent 通过 Datadog 的 MCP server (给 AI 用的标准接口) 来查数据工程师在 Claude Code 里问："结账为什么变慢？"值班等少数产品按人头 ($20–40/人)；查询本身基本不另收Claude Code / Cursor 经 MCP 绕过网页；Grafana 也能做仪表盘

护城河在哪一站

把上面的表压成一张"护城河在哪"的表：

站能被替代吗收入占比的直觉趋势
1. 采集容易 (OTel)按主机收的那部分 (基础设施约 41%、APM 一部分)探针不再锁客户，但主机费还在，因为后面几站仍要 Datadog
2. 发送容易 (管道)不收费管道越普及，进 3 4 的量越少
3. 进门处理难藏在摄入费里核心护城河之一；OTel 统一字段会慢慢削弱它
4. 存储容易，且最贵日志约 26% 的大头在这里大客户最先搬走的一站；Datadog 主动让出 (Flex、Federated、BYOC)
5. 分析较难大部分捆在主机费里；Bits 刚开始收下一代利润池，看 Bits 能否单独收费
6. 使用在变容易 (MCP)很少，按人头的部分小界面价值被 agent 摊薄，但 agent 仍要读 3 串好的数据

所以回答"仪表盘被 AI 绕过怎么办"：仪表盘是第 6 站，本来就不怎么收钱。Datadog 收钱的是第 1 站和第 4 站 (主机、数据量)，值钱的是第 3 站和第 5 站 (串好、实时)。AI 绕过 6 不伤收入；真正的风险是 4 被更便宜的存储搬走，以及 3 的"串好"被 OTel 标准化。

收入占比来自我们用 ARR 门槛推算的产品结构 (Q4'25：基础设施约 41%、APM + 用户体验约 26%、日志约 26%、其他约 8%)。

为什么别人做不了

严格说，不是"别人做不了"，而是每一块别人都能做，但要同时做好五件事，而且要做很多年。拆开看：

难在哪具体是什么对手为什么追不上
1. 从第一天就是一套底座Datadog 2010 年生在云上，指标、链路、日志从一开始就存在同一个后台、用同一套标签。后来加的 26 个产品都长在这个底座上，新产品一上线就能和老数据串起来Cisco 的 Splunk (日志)、AppDynamics (链路)、ThousandEyes (网络) 是三次收购拼起来的，三套数据库、三套标签，只能事后打补丁去连。New Relic 后来重写了底座，但那几年增长已经掉下来了
2. 上千个集成，一个一个磨出来AWS 每个服务、每种数据库、每个消息队列、每个框架，都要有人写好"怎么读它的数据、读出来叫什么名字"，还要跟着对方版本更新一直维护。Datadog 磨了 15 年，现在有上千个这件事没有捷径，也不性感。开源社区有一部分，但质量和命名不统一，正好落在第 3 站"对齐"的问题上
3. 实时、多租户的规模同时接住 3 万多家客户的数据，几秒内入库、告警。固定成本由所有客户分摊，所以单个客户自建很难更便宜自建要养一个团队。Coinbase 2021 年付了约 $6,500 万后组团队准备自建，最后拿着大折扣留下。能自建的只有"规模极大但应用很少"的公司 (Harzog)，也就是 AI 实验室
4. 自下而上的销售工程师刷信用卡就能开通，从几百、几千美元一个月用起，再一个产品一个产品往上加。58% 的客户用 4 个以上产品，每多卖一个，几乎不用新的获客成本Dynatrace 走自上而下的大单 (平均新单 >$20 万/年)，进不了中型公司；Grafana 有开发者口碑，但产品要客户自己拼
5. 越用越聪明 (正在形成)它看到 3 万多家客户的真实故障，可以训练自己的时间序列模型 (Toto) 和调查 AI (Bits)单个客户自建只看得到自己的数据；外部的通用大模型也看不到这些运维数据

谁离它最近：技术上是 Dynatrace。它也有统一的底座 (Grail)，自动根因比 Datadog 强，差在打法：它只卖大企业，进不了中型市场。云厂商 (AWS CloudWatch) 有数据，但客户普遍多云，没人愿意让 AWS 来监控 Azure。Grafana 每一块都有，可是要客户自己组装，前面说的"对齐"就落在客户头上。

所以真正的威胁不是"有人复制一个 Datadog"，而是"拆开 Datadog"：采集被 OTel 标准化，存储被便宜的数据库拿走，界面被 agent 绕过。每一站单独看都有更便宜的替代品，Datadog 要证明的是"串起来"这件事值它收的溢价。这也是竞争格局页里三层分化的来由。

同一条流水线，Dynatrace 长什么样

同样六站，Dynatrace 的每一站也都是自己的，所以它也能把数据串起来。区别在串的方法和强在哪一站：

深色 = 这家公司在这一站更强。Datadog 强在两头 (1、6)，Dynatrace 强在中间 (1、3、4、5)。Source: 两家公开产品文档；Dynatrace FY27 Q1 业绩会 (DPS、MCP 计费)；DT - 101 专家纪要。

站DatadogDynatrace谁更强
1. 采集一个 Agent + 代码里加追踪库 (dd-trace) + 按需打开上千个集成。服务名、环境、版本这套标签要客户按规范设好 (近两年也推了一键自动埋点，差距在缩小)OneAgent：一个探针装上，自动钻进机器上每个程序里埋点，不用改代码、不用配标签。也支持 OTelDynatrace (更自动)；Datadog 胜在覆盖的来源更多
2. 发送探针直接发；Observability Pipelines (Vector) 帮客户在路上过滤经 ActiveGate (客户网络里的中转站) 汇总再发；收购 BindPlane 做 OTel 管道差不多
3. 进门处理统一标签 + 请求编号把三种数据串起来；日志按规则解析OpenPipeline 解析处理，同时把每条数据挂到 Smartscape 依赖图上的具体"实体" (哪台机器、哪个进程、哪个服务)。它串数据靠的是一张自动画出来的图，Datadog 靠的是标签各有所长：Dynatrace 的图更自动、更精确；Datadog 的标签更灵活、覆盖更广
4. 存储三种数据分三套存储；日志分热索引 / Flex / 归档到 S3，再加 Federated LogsGrail：一个统一的数据湖装所有数据，先存后解析 (存的时候不用想好怎么查)。主打日志更便宜，专门去抢 Splunk 的日志Dynatrace 架构更新、日志更便宜；Datadog 的分层选项更多
5. 分析告警引擎 + Watchdog 找异常 + Bits AI 调查。把线索摆出来，由人或 Bits 判断Davis AI：顺着依赖图推因果，直接给出"根因是 X"。专家说用满 Dynatrace 的大企业"告警检查不需要人工"。Datadog 的 Watchdog 本身就是对标 Davis 做的Dynatrace (行业标杆)
6. 使用网页界面最好用、开发者最熟；值班、事故管理、安全等 26 个产品都在一个界面里；MCP server网页 + Notebooks；Workflows 自动执行修复动作 (重启、回滚)；也有 MCP。MCP 调用和 agent 操作直接扣 DPS 额度Datadog (产品更全、更好上手)
收费方式每个产品单独计价：按主机、按 GB、按条数、按 credit。查询基本不另收DPS：客户先承诺一笔年度额度 (比如 $100 万)，所有产品按消费从额度里扣，包括存储、查询和 AI 调用。DPS 已占 ARR 75% 以上方向不同：Datadog 卖"一个个产品"，Dynatrace 卖"一个总额度"

一句话：Datadog 强在两头，第 1 站覆盖最广、第 6 站产品最全最好用，所以从中小公司一路卖上去；Dynatrace 强在中间，第 1 站最自动、第 5 站最准，所以适合复杂的大企业。

和 agent 有关的一个区别值得注意：Dynatrace 的 MCP 调用和 agent 操作会直接扣客户的 DPS 额度 (管理层在业绩会上说的)，也就是 agent 查得越多，Dynatrace 收得越多。Datadog 目前主要按数据进来的量收费，agent 多查几次不一定多收钱。如果以后大部分查询都由 agent 来做，这个计费差别会变得重要。
