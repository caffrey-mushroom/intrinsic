结论

一句话判断：不买，放观察；买点 $40-45 (现价 $54.13，2026-10-30 收盘)。GitLab 是一家在受监管大客户里有真实护城河的公司，但它是 B 类增长 (靠新产品带动提价)，不是 A 类 (用量驱动)：过去三年的增长主要来自客户从 Premium 升级到 Ultimate 和 2023 年的涨价，"老客户加席位"已经从 ~10pt 掉到 ~2pt。AI 让流经 GitLab 的代码和流水线暴增，但 GitLab 按人收钱，这些量今天大部分不进收入。现价隐含未来 5 年每年 ~17% 增长 (口径 B)，我们的基本情景只有 ~14%；扣掉 SBC 后公司过去 12 个月的现金是 ~0。

为什么不是现在。(1) 增长引擎会到头：Ultimate 已经占 ARR 59%，每年 +35%，按这个速度 FY29-30 前后升级就做得差不多了，那时增长要靠新的提价理由 (AI Credits) 接上；(2) AI 这条杠杆还没证明是新钱：Paid CRR 从 $1,500 万跳到 $4,000 万+，主要靠新合同形式 Flex，CEO 承认客户可能先用原来的席位钱给 Flex 出资；(3) Q2 的大加速 (net ARR +42%、账单 +24%) 管理层自己说不会在下半年重复，Q3 指引只隐含 +15%；(4) SBC 吃掉全部 FCF：TTM FCF $226M (~21%)，SBC $230M (~22%)。

什么会让我们改变主意。下季度 (12 月初) 盯三个数：收入、cRPO、Paid CRR 的质量 (见下表)。真正的转折点是 2027 年 3 月的 FY28 指引：≥ +14% 且 Paid CRR 年底 ≥$1 亿、多数是新钱，买点可以上移到 ~$50；如果 DBNR 跌破 115% 或 Paid CRR 被证明多是换名，买点降到 ~$30-35 (接近 MS 悲观目标 $28)。股价跌到买点区间时，被收购的期权 (创始人 2026-05 放弃超级投票权；前 Field CTO 认为 AI 实验室或云厂商是潜在买家) 也开始提供下方保护。

1. 产品：它是什么、怎么运转、凭什么赢

1.1 一句话 + 一个例子

一句话：GitLab 卖的是"软件工厂的流水线"：一个软件从"有人提出要改什么"，到"代码写好、测试、扫漏洞、审批、上线、留证据"，每一步都在 GitLab 里完成并留下记录。行业把这件事叫 DevOps (开发 + 运维)，加上安全叫 DevSecOps。

日常例子：一家银行的手机 App 团队，200 名工程师。客户投诉"转账页面输入金额有 bug"。产品经理开工单；工程师在"支线"(branch) 上改代码，存回 GitLab 的代码仓库 (repository，记得每一次修改、谁改的、为什么改的共享文件夹)；然后申请"把支线并回主代码"(merge request)，同事在这里审；每次推送，GitLab 自动在一台机器 (runner) 上编译、跑测试、扫安全漏洞，这一步叫 CI/CD 流水线；审批人点同意后自动上线；监管来查时，银行从 GitLab 导出这次修改的完整证据链。

AI 进来以后，第 2 站越来越多由 agent (Claude Code、Cursor、Codex，或 GitLab 自己的 Duo) 来做。agent 写代码比人快得多，于是第 3-5 站的量暴增。这就是多头的核心论点："AI 写的代码越多，越需要流水线和治理"。空头的论点是：钱最多的第 2 站被别人拿走了，GitLab 变成被调用的后端；而且需要登录 GitLab 的"人"在变少。下面这张图把两种说法放在同一个 bug 上：

1.2 行业背景：客户为什么需要它

十年前一家公司的软件流水线由很多小工具拼起来：代码放 GitHub 或 Bitbucket，自动化用 Jenkins，安全扫描用 Snyk 或 Checkmarx，部署用别的工具。每多一个工具，就多一份采购合同、一套权限、一份审计材料。GitLab 的卖点是一个产品全包，这在行业里叫"工具整合"(toolchain consolidation)。前 GitLab Field CTO (2026-03 离职，Third Bridge 10-19) 说得很实际：大企业很少真的端到端全用，"他们拿自己想要的那几块，其余继续插别的工具"，小公司反而用得更全；但"不用在六个工具之间跳来跳去"的价值是真的。

客户真正离不开它的场景是受监管行业：银行、政府、国防要把代码放在自己机房或单租户云上，审计要能导出"谁改的、谁批的、扫过没有"。这种场景里 GitLab 做得最完整，GitHub 的自建版 (Enterprise Server) 功能更少；GitHub 2025-12 想对客户自建的 CI 机器收费，遭到反弹后第二天就推迟了。

1.3 怎么收费

1. 一句话商业模式：订阅为主、用量刚起步。FY27E 收入 ~$1144M 里，~89% 是按人头的年度席位订阅 (预付、按月分摊确认)，~8% 是自建版签约时一次确认的许可证部分加专业服务，按用量收的只有 ~2%。部署方式是另一条轴：~2/3 收入来自客户自己机房的版本，~1/3 来自 SaaS (GitLab.com + Dedicated)，SaaS 涨得快 (+36%)。

2. 一张日常账单：一家区域银行，1,000 名工程师用自建版 GitLab。750 个核心开发者买 Ultimate (要安全扫描和合规审批)，250 个外包和测试人员买 Premium；产品经理、审计这些只看不改的人在 Ultimate 下是免费的 guest。团队开始用 GitLab Duo 的 agent 做代码审查和修漏洞，每月超出赠送额度 ~3,000 个 Credits。流水线每天跑几千次，但都在银行自己的 runner 上。

4. 收入按收费方式拆分：

5. 承诺 vs 按需：几乎所有收入都是年度承诺 (席位预付，按月分摊确认)，所以季度收入很平滑、cRPO 很好用。有两处例外：(1) 自建版合同签约时有 ~15% 作为许可证一次确认 (license 行)，大单集中的季度会被抬高；(2) 按需 Credits ($1 / 个) 是唯一随用随付的部分，今天很小。Flex 改了两件事：自建许可证改为按合同期分摊确认 (FY27 最多推迟 ~$13M 收入，指引里没算)；Flex 承诺不计入 cRPO (Q2 拖累 cRPO 增速约 3pt)。含义：报告的收入和 cRPO 在 Flex 推广期会比真实签约看起来差，而 Paid CRR 会比真实"新用量"看起来好。

1.5 核心竞争力

1. 先说它在哪一步不是最强。入口两站都不在它手里：计划 (大企业多用 Jira)、写代码 (Claude Code、Cursor、Copilot)。审查体验 GitHub 更好，安全扫描 Snyk 这类专业厂商更强 (一位矿业 CIO 的代码安全招标短名单里没有 GitLab)。它真正最强的是自建场景下的仓库、CI 引擎和合规审计：

2. 为什么只有它能做成"一套正本做完"。GitLab 从 2011 年起就是一个应用、一个数据模型：工单、代码、合并请求、流水线、扫描结果、审批记录都在同一个库里，审计时一次导出。GitHub 的 Actions (2019)、Advanced Security 是后加的，Atlassian 是 Jira + Bitbucket + Bamboo 拼起来的。前 Field CTO 说 CI 引擎是"GitLab 最被客户喜欢的部分"，在 AI 自动化里"更有用"。

3. 为什么它的位置最难替代：它装在客户自己机房里。12,000+ 份企业协议 (前 Field CTO)、$5K+ 客户 11,114 家、$100K+ 客户 1,571 家 (+17%)。对手要替代的不是一个 SaaS 账号，而是一家银行几千条写进流程的流水线和多年的审计证据。

4. 为什么可持续：

飞轮保护不了三样：席位数、写代码那一层的钱、价格敏感的中小客户 (Guggenheim 引用管理层说法，约 20% ARR 是价格敏感客群)。对手卡在哪里：GitHub 技术和开发者入口更强，但自建版功能少、在受监管客户那里背着 MSFT 的"不中立"(前 Field CTO：AWS、Google 这类公司更需要一个独立于云厂商的代码平台)；AI 原生厂商有入口但没有 12,000 份企业协议和合规认证。

3.4 行业分层和粘性

3.5 客户自建

从几个维度看：(1) 账单规模：一个 1,000 人工程团队一年付 GitLab ~$80 万，自己维护一套 Git + CI + 合规的人力成本远高于此；(2) 应用种类：要同时覆盖仓库、CI、扫描、审批、审计，自建的范围很大；(3) 实时性：流水线停一小时全公司停工；(4) 人才：维护 CI 平台的工程师不便宜，这正是银行转 Dedicated 的原因；(5) 数据：代码正本本来就在 GitLab 里，搬出去的成本最高。门槛：只有上万工程师、而且在做"agent 规模"开发的公司 (AI 实验室、超大科技公司) 才可能自建，而且通常只自建 Git 层，CI 和合规仍用平台。受监管银行和政府几乎不会自建。

是否伤 moat：自建不是主要风险，"留下但缩席位、增量预算给写代码那一层"才是。丢掉价格敏感的中小 Premium 客户 (~20% ARR) 是低质量收入，Ultimate 和 Dedicated 的高质量增长可以抵消一段时间。和第 1 节连起来：客户真实需求是"一个可信、可审计、装在自己地盘上的代码正本 + 流水线"，AI 让这个需求更强；GitLab 的问题不是需求，而是收费单位。
