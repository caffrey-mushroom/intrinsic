这是 Anthropic 工程博客 11 月 6 日的一篇文章，讲 Claude 做长任务时怎么"记事"。你问的 "memory structure" 按这篇理解：它把 agent 的记忆拆成四层，再用一个叫 dreaming 的离线步骤去整理。文章不是产品发布，是方法论加一组自家实验。

Claude 的"记忆"不是改模型本身，而是像分析师一样往文件夹里写东西：原始记录、随手笔记、整理好的 wiki、每天开工先看的一页纸，一共四层。dreaming 就是空闲时回头翻原始记录，把记错的笔记改对，把零散的笔记整理成 wiki。

Anthropic 自己的测试里，越新的模型越会判断该记什么。有记忆的 Opus 5.5 得分从 0.655 升到 0.838。wiki 在答案要跨几份文件拼起来时有用 (87% 对 73%)，一份文件就能搜到答案时没用。

对我们的议题，dreaming 是一块新的离线 token 需求，可以放在闲时跑：一个实验里光整理一个语料就花了 1.28 亿 token。记忆本身存在文件里，吃的是存储，不是 HBM。这块需求有多大，目前没有任何产品数据。

Follow-up (复查 2026.12.08)

  • dreaming 什么时候变成收费功能。这决定它是不是真实的 token 需求。现在文章只说有 cookbook 可以上手，没有说 Managed Agents 里按什么计费。如果出现"按 dreaming token 计费"或"后台整理默认开启"，离线需求这条就有了落点；如果一直只是 cookbook，就只是方法论
  • Claude Code / Claude app 的记忆是否开始自动整理。Claude Code 的 auto memory 现在是会话里边干活边维护索引文件。如果它加上定时的后台整理，每个用户每天会多出一批离线调用，这是规模最大的落点
  • dreaming 花的算力和省下的算力能不能算平。文章里唯一的账是：wiki 加搜索每题省约 2 万 token，建 wiki 花了 1.28 亿 token。按这个比例要问约 6,400 个问题才回本 (我算的，见第 6 节)。如果后续数据显示回本问题数降到几百，说明 dreaming 会被大规模默认打开
  • 其他家有没有跟。Letta 和 UC Berkeley 先提过 sleep-time compute，文章引用了它。看 OpenAI、Google 的 agent 平台有没有类似的"离线整理记忆"功能。跟的人多，说明这是 agent 的标配环节，不是 Anthropic 一家的实验

1. 是什么

一句话：Claude 跨会话"记住"东西的办法，是把经验写进一组分层的文件里；dreaming 是让它在空闲时回头整理这些文件。

先说清"记忆"指什么

  • 大模型本身每次对话都从零开始。它在训练时学到的东西存在权重里，聊天时不会变
  • 文章说的 agent memory，是 Claude 从做过的任务和与人的交互里得到、并留到下一次会话还能读到的知识。它就是文件，存在一个文件夹或数据库里，下次开工时去读
  • 它明确不包括三样东西：改权重 (重新训练)、单次对话里的现学现用、以及 compaction (对话太长时把前面的轮次压成摘要接着干)

一个比喻贯穿全篇：分析师的资料体系

想象一个研究员怎么管资料。所有 expert call 的录音和转写都存着，要用时能搜。每次听完会随手记几条要点。花时间整理出一份行业 wiki，把公司、产品、价格串起来。还有一页纸贴在桌上，每天开工先看：当前在跟的三件事、几条不能忘的规矩。

Claude 的记忆就是这四样。dreaming 相当于周末把这一周的录音翻一遍，发现某条笔记记错了就改掉，把散落的笔记并进 wiki，把真正重要的一条提到那页纸上。

它现在在哪些产品里

  • Claude Code 的 auto memory：边干活边维护一个叫 MEMORY.md 的索引文件，每次开新会话只加载它的前 200 行或 25KB。这就是第 ④ 层。我们这个项目的 project memory 也是这个形状：每次开工先看到"Remote Control 一律用 Mac mini"那几行
  • Claude Managed Agents：给 agent 挂一个跨会话保留的记忆文件夹 (memory directory) 和读写它的工具。文章里的 CL-Bench 和宝可梦实验都在这上面跑
  • dreaming：文章说"见我们的 cookbook"，也就是开发者可以照着示例代码自己搭。文章没说它已经是一个默认开启的产品功能
  • 文章还提到 Claude Duet (一个助手产品) 的记忆适合"围绕这个人来组织"，没有更多细节

一句话：记忆是写在文件里的四层资料，dreaming 是离线整理这些资料。目前在 Claude Code 和 Managed Agents 里有前三层的用法，dreaming 还停在示例代码阶段。

2. 机制：dreaming 干的五件事

为什么需要 dreaming？因为 Claude 在会话里写笔记时，只看得到这一次会话，也不知道以后会发生什么。笔记可能一开始就记错，也可能因为环境变了而过时，下次 Claude 读到还会照信不误。dreaming 用原始记录当"真值"来核对，再把东西在四层之间搬上搬下。

dreaming 干什么文章里的例子结果
① 改错：拿笔记对原始记录宝可梦里 Claude 把 Mt. Moon 的宝可梦中心记到了东边 (其实在西边)，以为山已经过了，结果三次掉下单向的悬崖回到原路改对笔记后，第 1,935 步走到下一座城。没改的那次和没有记忆的那次都没过山
② 建 wiki：把零散笔记整理成互相链接的页面Stainless (5 月收购的软件公司) 内部约 35 万个文件、4.2 亿 token，128 轮 dreaming 建 wiki只看 wiki 能答对的比例 13% → 48%。wiki 从 103 页 766 条链接长到 222 页 12,893 条
③ 往上提：把重要的提到第 ④ 层Claude Code 的 MEMORY.md 只加载前 200 行或 25KB第 ④ 层必须小。塞多了占 token，错的一条会传染到每次会话，指令文件越长模型越不照做
④ 定方向：按目标决定 wiki 长什么样收购案的合同条款。几个 agent 同时往一张共享表里写，互相覆盖Claude 反思失败后自己改了建 wiki 的指令：一份合同一页、一个 agent 写、条款逐字抄。保留下来的关键事实 41/57 → 57/57
⑤ 补缝：跨多个会话找共同的漏洞wiki 里 9 个链接指向一个不存在的页面第二轮 dreaming 把 9 个链接改到正确页面，补了 3 个新页面 (含索引)

Source: Anthropic, The components of agent memory, Figures 6–15

一句话：会话里写笔记是"当场判断"，dreaming 是"事后核对"。两者分工，就像人白天记、睡觉时整理。

3. 实验在说什么 (都是自测)

新模型会自己闭环：记规则、写证据、标陷阱

CL-Bench 1.0 的数据库题：Claude 每答一题，就被告知正确答案，可以写一条记忆。每题都在全新会话里做，唯一能带过去的是记忆文件夹。

  • Sonnet 4.6 只会猜"为什么错了"，文件夹里是一堆没验证过的猜测
  • Opus 4.7 开始把笔记并成一份参考文档，标出哪些核实过、哪些没有
  • Opus 5 第一个"闭环"：每条记忆写规则、写它怎么知道这条规则是对的、写踩过的坑
  • Opus 5.5 和 Sonnet 5.5 也闭环了。有记忆时得分和 Opus 5 差不多，但它们不靠记忆时本来就更高，所以记忆带来的增量反而小一些

会判断什么值得记

宝可梦测试，跑到约 1 万步时对比。Sonnet 3.7 什么都记：每场战斗、每件道具、每个 NPC 一个文件，共 413 个文件、约 98 万字符，拿 1 个徽章。到第 1 万步左右，它连续 17 步在建文件、删文件，一步游戏都没走。Fable 5 只有 10 个文件、约 4.3 万字符，拿 4 个徽章。

差别在于 Fable 5 只记屏幕上看不到的东西：钱和位置每回合都能从屏幕读，不用记；策略、计划、试出来的规则不写下来就没了。比如连扔 7 个球没抓到鲤鱼王后，它记了一条"连续 3 个以上失败就改节奏"。Opus 5.5 用类似的小文件夹打通了整个游戏。

告诉它记忆是干嘛的，不要规定怎么记

  • 只说"有个记忆文件夹可用"，Opus 4.7 和 Opus 5 就能用好
  • 加一条死规则"只记失败"，记忆带来的提升反而少了：Opus 5 少 0.234，Opus 4.7 少 0.150，Sonnet 4.6 只少 0.020
  • 老模型反而需要手把手：提示 Sonnet 4.6"答题前先读记忆、再验证你的猜测"，得分从 0.330 (有记忆但不提示是 0.364) 升到 0.641，接近翻倍。Sonnet 5 不用提示，10 次里 9 次会先读记忆；Sonnet 4.6 不到一半

wiki 什么时候有用

  • wiki 加搜索最好 (61%)，比只搜索 (53%) 高 8 个百分点，还每题省约 2 万 token
  • 收购案 24 个问题，一半以上要跨几份文件拼、还要算数：用 wiki 87%，只搜索 73%
  • 另一个法律任务，大部分答案在一份文件里就能搜到：wiki 没有明显帮助
  • 还有一次 wiki 越建越大：10 份文件 115KB，wiki 写了 68 页 203KB，是原文的 1.77 倍。文章自己用了博尔赫斯"和帝国一样大的地图"来形容，等于什么也没抽象

4. 一句话规则

值不值得花算力去整理记忆，看两件事：答案平均要从几份材料里拼出来，以及这些材料变得有多快。

  • 答案在一份文件里就能搜到 → 直接搜原始记录，不用 wiki (法律任务里 wiki 没帮上)
  • 答案要跨 2 份以上文件拼 → wiki 有用 (收购案 87% 对 73%)
  • 环境每一步都在变、而且能直接看到 (宝可梦里的钱和位置) → 不记，记了反而过时
  • 环境变、但看不到 (宝可梦中心在哪边) → 要记，而且要靠 dreaming 定期核对

拿我们自己的工作套一下：问"某个 expert 上周怎么说 HBM 价格"，一份纪要就能搜到，不需要 wiki。问"过去三个月所有 call 里对 HBM4 价格的说法怎么变的"，要拼十几份，这时一份按公司、按产品整理好的 wiki 才省事。

一句话：跨文件拼答案用 wiki，单文件能搜到就直接搜；看得见的不记，看不见的要记还要定期核对。

5. 反过来想：它做不到什么

能力现在有没有缺的性质说明
真正"学会"，下次不看笔记也会无天生记忆是文件，不改权重。删掉文件夹，模型就回到原样
预知以后需要什么部分天生文章原话：没有模型真的知道以后会发生什么。只能靠事后 dreaming 补
保证记忆不出错部分能补但吃掉优势dreaming 能改错，但要算力。把所有记忆都持续核对一遍不现实，文章建议只核对容易变的、按访问频率定节奏
多个 agent 同时写同一份记忆差没适配合同实验里互相覆盖，丢了 16 条。改成一人一页就好了，是工程问题
记忆越多越好否天生注入的那层每多一行都占 token，还会降低模型照做的程度。wiki 也会膨胀到比原文还大
新老模型都能用好否没适配Sonnet 4.6 不提示就不读记忆。靠提示词能补一半，靠换新模型能补全
  • "天生"的三条 (不改权重、不知未来、不是越多越好) 不会因为下一代模型翻掉，它们决定了 dreaming 这种"事后整理"会一直存在
  • "没适配"的两条 (并发写、老模型不会用) 会随工程和模型迭代消失
  • "能补但吃掉优势"的一条最关键：核对得越勤，记忆越准，但花的 token 越多。这正是第 6 节的需求来源

一句话：记忆永远是"外挂的笔记"，不会变成模型本身的能力，所以"花算力维护笔记"这件事不会消失。

6. 对 token、算力和存储的含义

以下是我的推演，文章本身没有谈需求。

token：多出一块离线需求

  • 以前 agent 的 token 只花在"干活"时。dreaming 是在没人用的时候，让 Claude 回头读原始记录、写 wiki、改笔记。这是一块新的、和用户请求不挂钩的调用
  • 它可以排在闲时跑，类似批处理。对算力集群来说是填谷，能提高夜间利用率
  • 读原始记录为主，读多写少，主要是 prefill (把输入读进模型)
账怎么算 (我算的)：建 Stainless wiki 用了约 1.28 亿 dreaming token。wiki 加搜索每题省约 2 万 token。
回本问题数 ≈ 128,000,000 ÷ 20,000 ≈ 6,400 题。
这还没算准确率从 53% 升到 61% 的价值，也没算 dreaming 和答题用的模型、价格可能不同。意思是：只有一份资料会被反复问几千次，建 wiki 才在 token 上划算。语料本身约 4.2 亿 token，dreaming 花的约是它的 30%。

注入层被刻意压小

  • MEMORY.md 只加载 25KB，大约 6–8 千 token (按英文约 3–4 字节一个 token 估)。相对动辄几十万 token 的长会话，这一项很小
  • 所以"有了记忆，每次请求的输入都变长"这条加项不大。Anthropic 是在主动控制这块

存储：记忆住在硬盘上，不在 HBM 里

  • 四层都是文件。原始记录要留着当"真值"，agent 用得越多，会话日志越多，要可搜索地存着。这是给 SSD 和对象存储的加项，和 KV cache 那种要贴着 GPU 的"短期记忆"不是一回事
  • 对 HBM 和 DRAM 的影响是间接的：只有 dreaming 跑起来时，那些 token 才和普通推理一样吃 HBM

怎么判断大小

  • 没有任何产品数据。dreaming 目前是 cookbook，不是默认功能
  • 真正能放大的是 Claude Code 和消费端 app：如果每个活跃用户每天都在后台跑一次记忆整理，那是一块按用户数线性增长的需求。这是 Follow-up 第 2 条要盯的

一句话：对 token 是加项但现在量不明，可以闲时跑；对存储是明确但温和的加项；对 HBM 只有间接影响。

7. 最容易被误读的几点

大家可能以为实际
Claude 会"自我学习"、在线训练了没有改权重。所有记忆都是它自己写的文件，能看、能改、能删
dreaming 是模型在"睡觉"时训练dreaming 就是普通的推理调用，只是放在会话之外跑，用来整理文件。"做梦"是借海马体的比喻
记得越多越聪明宝可梦里记得最多的那个打得最差。注入层被刻意限制在 25KB
有了 wiki 就不用搜索最好的组合是 wiki 加搜索。单文件能答的问题 wiki 没用，还可能比原文更大
规则定得越细越好对新模型反而有害："只记失败"让 Opus 5 少了 0.234 的提升
这是一个新产品发布是工程博客，讲方法和自测结果。产品里现成的是 Claude Code auto memory 和 Managed Agents 的记忆文件夹

一句话：这是"让模型自己管笔记"的方法论，不是模型会自我进化了。
