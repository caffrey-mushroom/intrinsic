Super-agent 是 DeepSeek Harness 团队 10 月 31 日发的一篇设计文章，加一份开源原型代码 (dsh-superagent，MIT)。它不是新模型，是一种组织 agent 的方式：一个常驻的"领班"接所有消息、派活，一群"工人"各自在隔离的会话里并行干活，人只在需要拍板或验收时被叫到。DeepSeek 自己说这篇文章是"架构思路探讨，不是现有产品功能介绍"，原型是研究代码，文章里的一部分设计没有写进开源代码。v2 起所有数字以 DeepSeek 公众号原文为准。

它解决的是"人盯不过来"：今天一个人最多同时跟 3–5 个 agent 会话，Super-agent 把盯会话的活交给一个常驻的领班 agent，人只看结果。这个思路不新，GitHub、OpenAI、Anthropic 都有类似产品，DeepSeek 的新东西是"主动找活"和"尽量少占人的注意力"这两条设计原则，并且全部开源。

DeepSeek 的实验测的是调度：真正写代码的部分被换成了一个只耗时间的假工具。结果是同一批活做得更稳 (最慢那 5% 的任务从约 29 分钟降到 16 分钟)，代价是协调开销，每个任务多读约 60–90 万缓存 token。真实编码任务本身要读几百万缓存 token，所以协调开销大约只让每个任务贵 10–20% (我们的假设)。

DeepSeek 没有给任务完成率、每人多交付多少活、总 token 用量涨多少。token 的加项主要不在单个任务，而在三处：人能交出去的活变多；没人吩咐也主动干的活；原文明说的"投机执行"，先在后台试着做，有用就交、没用就丢。

对 token、算力、内存和存储都是加项，对电力跟着算力走，但量级比我们 v1 写的小。Base 给 2027 年全行业推理算力加约 2%，Bull 约 15%，都建立在我们的假设上。卡住它的不是成本，是人能验收多少结果、敢放多少权限。

Follow-up (复查 2026.12.01)

DeepSeek 会不会公布内部实例的生产数据。 这是"它真能干活"和"每人多用多少 token"两个判断的唯一硬证据。现在只有一组合成负载的调度实验，编码本身是假工具，内部实例每天处理多少单、合并率多少、每单多少 token、每人每天交付多少都没有。如果公布的每人交付量是单会话的 1.5 倍以上，第 9 节的 Bull 更可信；如果和单会话差不多，说明它只是让活更稳，不是更多，Base 要下调。

DeepSeek API 的缓存命中占比和缓存价格。 Super-agent 的 token 主要是缓存读。DeepSeek 8 月已经把缓存命中价提到原来的约 6 倍 (二手报道，$0.0036→$0.022 每百万，闲时)。如果命中占比从 DeepInfer 披露的 96% 继续上升，同时缓存价再涨，说明缓存读确实在吃硬件，内存和存储的加项成立；如果缓存价反而降，说明这部分负载比我们想的轻。

OpenRouter 上 DeepSeek Harness 和同类 agent 应用的 token。 这是第三方能看到的最快信号，可以接进现有的 OpenRouter tracker。原型发布当天约 2,000 star，Harness 本身据称 20 万以上 (未独立核实)。一个月后如果 Harness 类应用的 token 份额明显抬升，说明常驻 agent 在被真用；如果 star 涨、token 不涨，就是围观。

主动干活出事的案例。 原型默认只记录"本来会做什么"，要团队写规则才放开；权限上它以操作者身份全权限运行，DeepSeek 明说这不是安全边界。一个月内如果出现常驻 agent 误操作或被注入指令的公开事故，企业会把它锁在"只听吩咐"模式，第 9 节的采用率要下调。

1. 是什么

一句话：Super-agent 是一套"领班 + 工人 + 值班经理"的 agent 组织方式，让 AI 能同时推进很多件事、人不在也继续干，人只在要拍板或验收时被叫到。

今天的 agent 怎么工作

  • 今天的编程 agent (Claude Code、Codex、DeepSeek Harness 本身) 是"一个会话一件事"。你开一个会话，说要干什么，它干，你看着，它问你，你答
  • 想同时做五件事，就开五个会话，自己记住哪个在干什么、哪个在等你。DeepSeek 观察到一个人通常只能同时跟 3–5 个活跃会话
  • 你的电脑一关或断网，本地会话就停了。会话越长，上下文越乱，几件事搅在一起

Super-agent 改了什么：用一家餐馆来比

把今天的 agent 想成一个厨师，你得站在灶台边一道一道点菜。Super-agent 把它改成一家餐馆：

  • 领班 (Router)：常驻，所有客人的话都先到他这里。他判断这是不是要做的单、交给谁、什么时候回客人话。他自己不下厨
  • 厨师 (Worker)：每人一张单、一个灶台。在 Super-agent 里就是每个任务一个独立会话、一个独立工作目录，互相不串味。厨师做完、卡住或要问客人，都先报给领班，由领班统一对外说
  • 订单本 (状态)：哪张单在做、做到哪、客人说过什么，写在店里的本子上 (数据库)，不在厨师脑子里。厨师换班或店里断电，单子不丢
  • 灶台可以在你家 (执行环境)：思考在云端跑，代码、文件、工具可以留在你本地，本地只装一个"执行命令、回传结果"的小程序
  • 值班经理 (Watchdog)：一个独立的 agent 会话，定时被唤醒，除了查接口报错、恢复失败，还判断每个工人是否真有进展、是否偏离目标，必要时介入。维护者可以直接问它故障原因，也能让它改提示词、调触发规则
  • 先做着 (投机执行)：原文的说法是"通过消耗额外的后台算力来减少人类的等待与介入成本，结果有价值就交付，没有价值就丢弃"。DeepSeek 内部群里配了一条"静默复现并修复"的规则：群里还在讨论，它已经在后台复现、提了修复 PR
  • 门铃 (事件驱动)：群聊消息、代码评论、CI 结果、邮件都是"门铃"(Trigger)。先用写死的规则过滤一遍，再让领班判断要不要处理。领班不用一直盯着门口

核心指标是什么意思

  • 缓存读取 token：agent 每走一步，都要把这件事到目前为止的全部记录重新"读"一遍给模型。重复的部分模型服务商会缓存起来，读缓存比重新算便宜得多 (DeepSeek 价格便宜约 30 倍)。像厨师每次回到这张单都要把整张单从头扫一眼：扫一眼很快，但扫的次数多了也是工作量
  • 完成时间 p50 / p95：一批任务里，一半任务在 p50 之内完成，95% 在 p95 之内完成。p95 看的是"最慢的那几件拖多久"
  • 并发槽：同时最多有几个厨师在灶台上。原型默认 3 个，可以设到 16 个，另外永远留 1 个给人的消息，保证新活再多也不会让你插不上话

做成了什么

  • 设计文章：《Super-agent 设计探索：迈向更自主的 Agent 系统》，讲四个目标 (持续、高效、主动、持久) 和五个部件 (双层结构、事件驱动、以人为中心的交互、计算 / 状态 / 环境分离、Watchdog)
  • 开源原型 dsh-superagent：一个只盯一个 GitHub 仓库的编程 agent，跑在 DeepSeek Harness 上，听 GitHub 和 (可选) 飞书。TypeScript，MIT 协议，10 月 31 日建库，带 9 篇按顺序读的设计文档
  • 内部实例：DeepSeek 内部有一个一直在跑的实例，在 IM 和 GitHub 之间推进开发任务：复现和修 issue、回复 code review、迭代 Harness 本身。据报道它会看公开群聊里的反馈，没人 @ 它也会去找根因、提修复 PR

拿来干什么：一个例子

今天：群里有人说"导出按钮在 Safari 上没反应"。你看到后开一个 agent 会话，把描述贴进去，等它复现、改代码、跑测试，中间回答它两三个问题，最后自己去开 PR，再回群里说一声。这期间你没法同时盯太多别的事。

用 Super-agent：群消息本身就是一个门铃。领班判断这是一个 bug 报告、发消息的人在允许名单里 (或者团队写过"bug 报告可以主动处理"的规则)，就开一张单，回一句"我来看"。一个厨师在自己的目录里复现、修、跑测试、开 PR。PR 上有人评论，评论自动送到这个厨师手里，不用再 @ 谁。你只在 PR 好了要 review 时被叫一次。

现在到哪一步

  • 是研究原型，DeepSeek 说可能有 bug，不是正式产品。开源版和内部版不一样
  • 开源版里有：领班 / 工人两层、事件过滤、授权规则、并发槽、单子的状态机、SQLite 存状态、重启恢复、一个网页面板
  • 原文说的其他实现状态：异步执行 (工具在后台跑、agent 能同时接新消息) 已经在 Harness 里实现，但默认没开；领班在 IM 里每条回复不超过 100 字是一条硬规则
  • 开源版里没有或很弱：文章说的云端 / 本地分离 (原型跑在操作者自己机器的 tmux 里)、会判断"有没有进展"的 Watchdog (原型只有一个每小时检查服务是否活着的定时任务)、安全隔离

2. 机制：快从哪来，卡在哪

快从哪来

  • 并行：几张单同时做，不排队等人。DeepSeek 的对照实验里，单会话即使给了"开子 agent"的工具，中性提示下 5 次运行一次都没有委派，所以几件事还是一件一件做
  • 不等人：工人做完一步不用等人回话，PR 评论和 CI 结果直接送达。人只出现在必须拍板的地方
  • 上下文干净：每张单一个会话，不会把五件事搅在一个越来越长的对话里

把一件事从发生到交付拆成串联的五段，最弱的说了算

段决定什么谁定义今天的状态
1 门铃能听到哪些事 (GitHub、飞书、邮件、CI)各平台的 API 和权限原型只接 GitHub 和飞书，加别的要自己写
2 领班判断接不接、交给谁、要不要回话团队写的规则 + 底座模型默认只记录不真接；规则写得好坏决定噪音多少
3 工人干活活干得对不对底座模型能力 + 工具和单会话 agent 一样，框架不提升模型本身
4 验证结果靠不靠谱仓库自己的测试 / CI有测试的仓库能自动验一遍，没有就全靠人
5 人验收能交付多少人的时间和信任最窄的一段：原型的整个设计都在省这一段

今天卡在第 5 段。第 1–4 段可以靠加机器、加工具、换更强的模型变宽；第 5 段只能靠"让结果更容易验收" (测试、小 PR、清楚的说明)。这也是为什么原型把"尽量少占人的注意力"写成第一原则：每一条消息、每一个通知都要证明它值得人看一眼。

谁定义瓶颈段：第 3 段归模型公司，第 4 段归用户自己的工程习惯，第 5 段归组织。框架本身 (第 1、2 段) 是谁都能做的胶水，DeepSeek 把它开源，说明它不打算靠这一层赚钱，而是想让更多 token 跑在自己的模型和 Harness 上。

一句话：它快是因为并行、不等人；它卡在人能验收多少结果，框架本身没有壁垒。

3. 数字打折

公开的数字只有 DeepSeek 原文第 7 节的两组初步实验和原型源码里的参数。原文自己说"实验基于合成负载与简化环境，结果仅作为初步参考"。

实验怎么做的

  • 负载：群聊和 GitHub CI 消息流同时驱动四种方案。每次实验约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息
  • 编码被换成假工具：原文写"编码工作用一个只消耗时间的工具代替，因此实验衡量的是系统的调度与协作能力，而非针对单个任务的执行能力"。所以 token 数只代表领班和工人之间的协调开销，不包括真正写代码的 token
  • 时间压缩：消息间隔和工作时长按 1/4 缩放，模型调用耗时为真实值。每种方案跑 5 次取平均。完成时间 = 从工作请求到结果消息

怎么读这张表

  • 中性提示：5 次里模型一次都没用子 agent，所有活在一个会话里做，还不断被新消息打断，所以中位数 20.4、最慢的 29.5
  • 提示优先委派：5 次里有 4 次真的分了活，中位数 13.8，已经接近 Super-agent 的 12.4。剩下 1 次判断"活很小"全部自己做，拖出 29.0 的长尾。所以 Super-agent 主要赢在稳定，不是普遍更快；原文的解释是单会话靠模型临场判断分不分工，双层架构让领班根本不干活，从结构上避免了这一点
  • 去掉直通：完成时间几乎一样，但领班多做约 30% 的决策，读缓存多 37%。直通是省钱的设计，不是提速的设计
  • 读缓存：Super-agent 读的缓存是会委派的单会话的 2.1 倍、中性提示的 3.8 倍。原文的说法是"以更多的 token 消耗换取更短且更稳定的完成时间"。前者是更公平的对比，因为两边都在并行

领班扛得住多少消息 (原文 7.2 节)

单独给领班做压力测试 (领班用真实模型，工人用假模型)：需要决策的消息从每分钟 1 条加到约 40 条，领班会把攒下的消息并成一批处理，平均每批从 1.0 条升到 2.8 条，单次请求耗时从 2.5 秒只增加到 3.9 秒，摊到每个决策的推理时间从 6.4 秒降到 1.6 秒。结论是在他们的团队规模下，一个常驻领班够用。领班可以用较轻的模型，工人要用能力最强的模型。

把协调开销折成每个任务

多出来的读缓存全部是协调开销，因为编码本身是假的。每次实验约 20 个工作请求：

vs 中性提示1,718 万约 86 万+17%

500 万是我们的假设：DeepInfer 披露 DeepSeek 平均每次调用输入 7.7 万 token、96% 命中缓存，一个真实编码任务走 50–100 步，就是 400–800 万缓存读。真实任务越小，协调开销占比越大。按价格算，每个任务多出来的 60–90 万缓存 token，按 V4-Pro 闲时缓存价 ($0.022/百万) 约 $0.02，可以忽略。

v1 的错误：v1 把 2,323 万 vs 605 万当成每个任务的总 token，再按"一个缓存 token 约占 1/25 个普通 token 的 GPU 时间"折出"每任务 GPU 工作量约 2.4 倍"。原文说明编码是假工具，所以这 2.4 倍是错的，实际每任务约多 10–20%。

能。这是设计取舍，不是技术壁垒。GitHub Copilot coding agent (把 issue 指派给 agent，它开 PR)、OpenAI Codex 云端并行任务、Cursor 后台 agent、Claude Code 的云端会话和 GitHub 集成，都是"多个隔离会话并行 + 结果回到原对话"这一类。DeepSeek 比较新的是三点：领班常驻并统一对外说话；主动接没人派的活 (有规则时)；把"省人的注意力"写成硬原则，并且全部开源。所以只能说"DeepSeek 是第一个把完整一套开源出来的"，不能说"独家"。

一句话：实验测的是调度，不是写代码；Super-agent 赢在没有长尾，代价是每个任务多读约 60–90 万缓存 token，折成真实任务约贵 10–20%。

4. 一句话规则

一件活值不值得交给常驻 agent，看"人验收它要几分钟"除以"人自己盯着做要几分钟"。这个比例低于约 1/5 才划算，代码有测试和 CI 的活最容易做到。

为什么是这条：Super-agent 省的是人的注意力，不是机器时间。如果验收一个结果和自己做差不多累 (比如判断一段财务分析的数字对不对)，交给它只是把"盯着做"换成"仔细查"，没有省。1/5 是我们的经验门槛，不是 DeepSeek 给的数。

  • 修一个能复现的 bug，测试通过、PR 30 行：做要 1 小时，看 PR 5 分钟。比例 1/12，划算
  • 回复 code review 里的小修改：做 15 分钟，看 2 分钟。划算
  • 重构一个模块的接口：做半天，但 review 要理解全部设计，至少 1 小时。比例约 1/4，勉强
  • 写一份投资 memo 的核心判断：做 1 天，验收要逐个核数和逻辑，半天。比例 1/2，不划算，交给它做初稿和更新数据才划算

一句话：结果能被机器先验一遍、人几分钟能看完的活，才是常驻 agent 的活。

企业业务流程 (发票例外、理赔)看审计要求暂不适合—要跨 8 个系统、审计和责任，见我们的"Agent 进大企业"一篇

拿你自己的工作举例。Knowledge Base 里每周进来几十篇纪要，今天是你开会话说"读一下这周的 memory 纪要，对照 thesis"。放进 Super-agent：新文件就是门铃，领班判断这篇和哪篇 memo 有关 (HBM 定价、某家公司)，派一个工人去更新那篇 memo 的数据和证据表，做完在聊天里说一句"XL-Flash memo 的 KV 证据表加了两条，结论没变"。你只在它说"这篇和我们的判断相反"时去看。省下的是"每周开会话、贴路径、等它读"这部分注意力。

为什么它对编程最合适

编程是唯一一个"机器能先验一遍"的大场景：测试、类型检查、CI 都是现成的自动验收。其他领域的结果大多只能人看，所以第 4 节的比例很难压到 1/5 以下。这也是 DeepSeek、GitHub、OpenAI 都先在代码仓库里做这件事的原因。

一句话：先赢的是代码仓库里的小活 (bug、review、CI)，研究和业务流程要等验收变快、权限问题解决。

8. 最容易被误读的几点

比喻：这不是"雇了一个会自己找活的员工"，而是"给你的项目配了一个前台和几个临时工"。前台只按你写的规矩接活，临时工干完要你签字。

大家以为实际

开源了 DeepSeek 内部用的那个开源版和内部版不同；云端常驻、会判断进展的 Watchdog 不在开源代码里

多 agent = token 爆炸，成本扛不住多的主要是缓存读，按 DeepSeek 价格一个任务多几毛钱；成本不是障碍，人的验收才是

9. 落到核心议题：token、算力、内存、存储、电力

取代谁、谁拿钱

  • 取代人的"盯会话"时间，不取代模型。底座模型的调用量是加项
  • 被挤压的：做 agent 编排、多 agent 调度的创业公司。这一层被 DeepSeek 免费开源，很难单独收费
  • 拿钱的：卖 token 的模型公司 (DeepSeek 想让 token 跑在自己的模型和 Harness 上)；GPU 和 HBM (缓存读也要算)；DRAM 和 SSD (存 KV 和会话状态)；CPU (每个工人一个工作目录、一个执行环境，跑测试和命令)

算式

每个采用者的 token 倍数 = 任务数倍数 × (1 + 主动 / 投机工作占比) × (真实任务 token + 协调开销) ÷ 真实任务 token

全行业推理算力增幅 = 工程类 agent 占推理 token 的比例 × 用上常驻多 agent 的比例 × (每个采用者的 token 倍数 − 1)

  • 任务数倍数：人从"盯着做"变成"只验收"之后，每人每天交出去的活多了几倍。受第 4 节的验收比例限制。DeepSeek 没给，这是最关键也最软的假设
  • 主动 / 投机工作占比：没人吩咐、它按规则主动做的活，以及先在后台试做、可能被丢掉的活，占正常任务的比例
  • 真实任务读多少缓存：一个真实编码任务本身读的缓存 token。按 DeepInfer 的每次调用 7.7 万输入、50–100 步，约 400–800 万
  • 协调开销：固定用 86 万 (原文实验 vs 中性提示，每个任务多读的缓存)。假设协调开销和真实任务的"缓存 / 要算"比例一样，所以 token 倍数也就是 GPU 工作量倍数

三个预设改了什么

  • Base：任务数 1.2 倍、主动 / 投机 5%、真实任务读 500 万缓存、15% 采用、工程类占 30%。每个采用者约 1.5 倍，全行业推理算力约 +2%
  • Bull：任务数 1.5 倍、主动 / 投机 30%、真实任务读 300 万、25% 采用、工程类占 40%。每个采用者约 2.5 倍，全行业约 +15%
  • 长期上限：任务数 2.5 倍、主动 / 投机 50%、真实任务读 200 万、60% 采用、工程类占 50%。不设年份，用来看天花板
  • 人验收的门：任务数倍数受"人一天能看多少 PR"限制。一个工程师一天认真 review 10 个小 PR 已经很多
  • 权限的门：原型默认只记录主动活，企业会长期停在"只听吩咐"模式，主动活带来的那部分 token 进不来
  • 设计会变省的门：消融实验里"直通"这一个设计就让缓存读少了 27%；原文还说领班可以用较轻的模型。协调开销会越做越小

对每一项是加还是减

议题方向为什么量级 (Base)
Token加每人交出去的活更多；主动和投机执行是"没人发起"的新 token；每个任务的协调开销约 +10–20%采用者每人约 1.5 倍
算力 (GPU)加和 token 同比例；领班可用轻模型，工人用最强模型全行业约 +2%
内存 (HBM / DRAM)加同时活着的会话更多 (领班 + 3–16 个工人 + 值班经理)，领班常驻、上下文一直在；每次读缓存都要把 KV 搬进 HBM略大于 GPU 的加项，未量化
存储 (SSD)加工人经常停下来等 review、等 CI，几小时到几天后再接着干，KV 要存着等它回来；单子关闭后还要盯 2 周。不存就得重算，一个缓存 token 重算要 25 倍 GPU方向确定 (存得更久)，量级没有数据
CPU / 沙箱加每张单一个工作目录和执行环境，跑测试、编译。DeepSeek 另有一篇沙箱基础设施论文 (DSec) 讲的就是这层和并发工人数成正比，未量化
电力加跟着 GPU 工作量走同算力

为什么 DeepSeek 要做、还要开源

不是因为这套框架能卖钱。DeepSeek 的生意是卖 token，而且 token 便宜：一次实验多出来的 1,700 多万缓存 token 按它的价格只要几毛钱，海外前沿模型 (按 Sonnet 级缓存价 $0.10/百万) 贵约 5–30 倍，看是和 V4-Pro 还是 V4.1 Flash 比。常驻多 agent 是最能放大 token 用量的用法之一，DeepSeek 用自己的价格优势去推这种用法，同时让 Harness 成为默认的运行环境。原文也写明，下一步想让模型和架构"协同设计"，专门训练领班的判断、批量分派和上下文召回。

一句话：Super-agent 对 token、GPU、内存、存储、电力全是加项，主要来自活变多、主动干活和投机执行，不来自单个任务变贵；Base 给 2027 年推理算力加约 2%、Bull 约 15%，卡住它的是人的验收和权限，不是钱。
