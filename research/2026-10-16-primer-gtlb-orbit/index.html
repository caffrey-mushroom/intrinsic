Orbit 是 GitLab 2026 年 6 月推出的“上下文图谱”：把一家公司在 GitLab 里所有的代码、改动记录、流水线、上线记录、漏洞和负责人连成一张关系图，让 AI agent 干活前先来查。它不写代码，它告诉写代码的 agent “这里的来龙去脉是什么”。

大公司改一行代码，贵的不是敲代码，而是搞清楚改了会影响谁、上次哪里出过事、该找谁批。AI agent 写代码很快，但对这些一无所知，所以写得越多，出事越多。Orbit 卖的就是这份“公司内部的来龙去脉”，它的独家之处不在图谱技术，而在只有 GitLab 手里有流水线、上线、漏洞和负责人这些记录。方向对，但它目前只在 GitLab.com 云版测试，GitLab 一半以上收入来自的自托管客户还用不上，而且还没有任何收入数据。

1. 是什么

一句话：Orbit 把 GitLab 里所有和软件有关的记录连成一张“谁和谁有关系”的图，AI agent 可以直接问它问题，不用自己一个个文件去翻。

先说一个贯穿全篇的比喻。把 AI agent 想成一个技术很好、但第一天来公司的外包工程师。代码是图纸。图纸他看得懂，但他不知道：这张图纸上的零件还被哪些车间用着、上次谁改过它导致停产、现在谁负责、改完要过哪些检查。老员工脑子里有这些，公司档案室里也散落着这些记录。Orbit 就是把档案室整理成一张关系图，外包每次动手前先来问。

底层怎么工作

  • 收集：GitLab 本来就存着这些记录：代码、合并请求 (一次代码改动的申请和审批)、流水线和每个检查任务的结果、部署 (哪个版本上线到哪)、漏洞扫描结果、工单、团队和负责人。Orbit 把它们实时同步到一个单独的数据库里 (ClickHouse)，代码则解析出“哪个函数调用了哪个函数”，支持 Java、Python、Go 等十几种语言
  • 连线：每样东西是一个点，关系是一条线。“这个检查任务属于这条流水线，这条流水线属于这次代码改动，这次改动是这个人提的，改的这个函数被另外三个服务调用”。GitLab 自己公司的图谱有 4 万多个项目、5 亿个点、20 亿条线，45 分钟内建完，之后每有改动就实时更新
  • 查询：agent 通过 MCP (AI 工具之间的通用插头) 或命令行来问。它能看到的范围和这个人在 GitLab 里的权限完全一样，没权限看的项目，agent 也查不到

和最近的替代品差在哪。今天 agent 了解代码库，主要靠两种办法：一是自己一个个打开文件读，慢、费 token；二是“检索” (RAG)，把代码切成片段，按字面相似度找出几段塞给模型，快，但只找“长得像”的，不懂“谁依赖谁”。用外包的比喻：第一种是让他自己去档案室翻箱子，第二种是给他一个按关键词搜索的文件柜。Orbit 是直接给他一张标好关系的组织图和流程图。

拿来干什么：一个具体例子。2021 年底开源日志组件 Log4j 爆出严重漏洞，全世界的公司都在问同一个问题：我们哪些系统用了它、部署在哪、谁负责修。

  • 今天的做法：安全团队发邮件给各个团队，各自去查，汇总成表格，大公司往往要几天到几周
  • 用 Orbit：一次查询，从这个组件出发，顺着线找到所有调用它的服务、对应的流水线、部署到了哪些环境、每个服务的负责人。GitLab 的说法是漏洞出现的一小时内就能拿出修复计划 (官方口径)

现在到哪一步。2026.06.10 公开测试，只对 GitLab.com 云版的 Premium 和 Ultimate 客户开放 (官方博客)。另有一个本地版命令行工具，只看本机代码、不含流水线等记录，可离线用。代码在 GitLab 公开仓库里，用 GitLab 企业版许可证，不是开源免费。

2. 客户的底层需求

大公司改代码，难的从来不是“写”。一家大银行可能有几千个系统、几万个代码仓库，很多代码写于十几年前，写的人早已离职。工程师改一处，真正花时间的是：

  • 搞清楚改了会影响谁 (谁调用了这段代码，哪些系统依赖它)
  • 搞清楚历史 (上次谁改过、为什么改、有没有因此出过事故)
  • 找对人 (谁负责、谁有权批准)
  • 过检查 (要跑哪些测试、哪些安全扫描、审计要留什么记录)

这些信息散在 GitLab 的不同角落、工单系统和老员工脑子里。没有 AI 的时候，靠人慢慢问，速度慢但出事少。

AI agent 把这个问题放大了。agent 写代码的速度是人的很多倍，GitLab 说部分客户的代码库一年扩大到 5 倍。但 agent 对上面四件事一无所知，只能自己翻文件猜。结果是两种浪费：

  • 慢和贵：agent 翻几百个文件来理解上下文，每翻一个都要花 token
  • 出错：猜错了依赖关系，改出问题，到上线前才发现，或者上线后才发现

GitLab 拿 Claude Code 做的对比 (同样的任务、同样的模型)：用 Orbit 最多快 11 倍、少用 4.5 倍 token、幻觉少 45 倍。这是 GitLab 自测，而且对比对象是“让 agent 自己翻文件”这种最笨的办法，见第 3 节打折。

客户要的是三样东西：

  1. 准：agent 改得对，少返工、少事故
  2. 省：少花 token，少等时间
  3. 管得住：agent 只能看到它该看的，所有查询和改动有记录，审计过得去。这一条对银行和政府最重要
一句话：agent 让“写代码”变便宜了，让“搞清楚来龙去脉”变成新的瓶颈。Orbit 卖的是这个瓶颈。

谁都能做吗？图谱技术本身不稀奇：存储用的是现成的 ClickHouse 和 DuckDB，“解析代码里谁调用谁”Sourcegraph、Cursor、Augment 等都在做。能做的人很多。真正别人做不了的，是图里那些代码以外的点：流水线结果、部署记录、漏洞、审批人、负责人。这些数据只在 GitLab 里，外人拿不到完整的。GitHub 是唯一也有全套数据的公司。

一句话：11 倍、45 倍是拿最弱的对手打出来的；真实客户测出来是准确率提高约 12 个点。优势不在技术，在数据只在 GitLab 手里。

4. 一句话规则

agent 要回答的问题，答案是否需要“代码以外”的记录 (流水线结果、上线记录、漏洞、审批人、负责人)？

需要：Orbit 有别人给不了的东西。只需要看代码本身 (这个函数在哪、谁调用它)：Cursor、Sourcegraph、Augment 都能做，Orbit 没有优势。

用这条规则过一遍：“帮我写个排序函数”不需要，Orbit 没用。“这次改动会不会让别的团队的流水线挂掉”需要，Orbit 有用。“这个漏洞影响了哪些线上系统、谁负责”需要，Orbit 最有用。

5. 反过来想：它缺什么

agent 干活需要的能力普通代码索引 (Cursor 等)Orbit缺的性质说明
看懂代码结构、谁调用谁有有—大家都有
跨几千个仓库看依赖弱有—普通工具多数只看打开的那个仓库 (推断)
流水线、测试、上线记录无有天生 (对别人)数据在 GitLab 里，外人要通过 GitLab 接口拿
漏洞和负责人无有天生 (对别人)同上
按公司权限过滤弱有—权限直接沿用 GitLab，审计友好
装在客户自己机房部分有无没适配目前只在 GitLab.com 测试，自托管要客户另装 ClickHouse 等组件
GitLab 以外的数据 (Jira、GitHub 仓库、线上监控)部分有无天生Orbit 只连 GitLab 里的数据。公司代码一半在 GitHub、工单在 Jira 的话，图是残缺的
线上运行数据 (报错、性能)无无天生这是 Datadog 这类监控公司的数据
  • 没适配的只有一个：自托管。这会因为下一个版本翻掉，也是最该盯的一条，因为这是 GitLab 核心客户
  • 天生缺的是“GitLab 以外的数据”。这不会翻。客户 100% 用 GitLab 时 Orbit 最强；混用 GitHub、Jira 的客户，图只有一半
  • 推论：Orbit 让“全部放在 GitLab 上”变得更值钱，反过来也会推动客户把更多东西搬进 GitLab。这是它对 GitLab 一体化策略的真正作用

6. 场景逐个过

场景要代码以外的记录吗Orbit 适不适合今天怎么做状态
漏洞影响范围 (哪些系统、在哪上线、谁负责)要最适合发邮件、汇表格，几天官方主推，无客户数据
改动影响评估 (会不会弄坏别的团队)要适合靠经验和问人官方主推
AI 审代码 (懂整个代码库，不只是这次改动)部分要适合AI 只看本次改动，或用检索有一家客户实测 (58% → 70%)
流水线失败排查 (同一个错还会影响哪些改动)要适合值班工程师逐个看官方举例
合规检查 (哪些项目漏了必须的安全扫描)要适合平台团队写脚本查官方举例
新员工上手 (谁负责什么、系统怎么连)部分要有用看文档、问人官方举例
写一段新功能代码不要帮助小Cursor、Claude Code 自带索引—
一句话：越是“出事了要查清楚”和“改之前要评估风险”的场景越适合，越是“从零写新代码”越用不上。前者恰好是受监管大客户最在乎的。

8. 最容易被误读的几点

大家以为实际
Orbit 是 GitLab 的 AI 写代码工具它不写代码。它是让任何 agent (包括竞争对手的) 写得更准的数据层
知识图谱是很难的新技术，是壁垒技术是现成的 (ClickHouse、DuckDB)。壁垒是数据：流水线、上线、漏洞、负责人只在 GitLab 里
80% 查询来自外部 agent，说明 GitLab 自己的 AI 没人用两件事都可能对。但对 Orbit 来说是好事：它本来就是给所有 agent 用的，外部调用还要付 credits
GitLab 的核心客户已经在用没有。目前只在 GitLab.com 云版测试，自托管客户 (约 57% 收入) 还用不上
快 11 倍、幻觉少 45 倍对手是“不给任何上下文”。真实客户对比常规检索，准确率是 58% → 70%

9. 能值多少钱

Orbit 没有单独收费，钱通过两条路进来：

  1. 直接：外部 agent 调用 Orbit 消耗 credits，进 Paid CRR
  2. 间接：让客户更愿意买 Ultimate、更不愿意离开、更愿意把 GitHub 和 Jira 的东西搬进 GitLab。这部分没法单独量

直接那一块可以粗算，但三个参数都没有公开数据，下面全是假设，拿来感受量级：

每年 Orbit 直接收入 = 付费开发者数 × 用上 Orbit 的比例 × 每人每月 Orbit 相关 credits × 12
  • 付费开发者数：GitLab 不披露。按 FY27 收入约 $11.3 亿、平均每人每月约 $45 粗算 (Premium 牌价 $29，Ultimate 更贵)，约 200 万人 (估算)
  • 用上 Orbit 的比例：目前只开放给云版 Premium / Ultimate，云版约占收入三分之一
  • 每人每月花费：credits 每个 $0.01，Orbit 单次查询价格未公布

一句话：只有云版客户在用时，Orbit 直接收入约 $1,800 万，不到收入的 2%；进了自托管版、每人每月多花 $10，约 $8,400 万 (7%)；要到 $3 亿，得六成开发者每月多花 $20。直接收入能不能做大取决于自托管版和单价，两个都还没数据，所以今天它的主要价值是间接的：让客户更离不开 GitLab。
