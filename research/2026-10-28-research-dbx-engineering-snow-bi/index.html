v1.0 · 内部 · 复查 2026.12 (SNOW Q3 FY27 财报后)

Caffrey 的问题：为什么 Databricks (下称 DBX) 能赢下数据工程、AI/ML 和新工作负载，而 Snowflake (SNOW) 能守住 BI 和分析？这页从零讲两家的产品怎么用、谁在用、谁在买，再讲出身、架构、定价、治理、Iceberg 和锁定，最后给两边互相进攻的反证和数字。专家原话都是完整段落，旁边附背景。

结论

一句话：两家不是在同一块地上打，是在分两类人的预算。DBX 卖给"写代码加工数据的人"(数据工程师、数据科学家、ML 工程师)，SNOW 卖给"用数据回答业务问题的人"(分析师、BI 开发、业务部门)。新增的钱 (agent 开发、流处理、非结构化数据、模型) 天然是工程活，所以 DBX 长得快；而全市场大部分存量需求仍是报表和分析，所以 SNOW 守得住。

1. DBX 赢工程，靠的是出身和用户习惯，不是正面打赢 SNOW。它起家于 Spark，产品就是 notebook + 代码 + 集群，工程师能调每一个旋钮；非结构化数据 (图片、PDF、文本) 从第一天就是一等公民；大数据量批处理在工程师手里更便宜。Thoughtworks 的 SVP 原话："不是 Databricks 正面赢了 Snowflake，是新增工作偏向工程重的 agent 构建和流处理，这本来就是 Databricks 起家的地方。"

2. SNOW 守 BI，靠的是"简单"和"被信任的口径"。开箱即用、免运维、像个黑盒，业务用户根本不想调参数；财务、销售看的数字、权限、几百张看板都建在 SNOW 的 SQL 和整理好的表上。专家估计核心传统数仓 (仓库计算、SQL、BI、ELT) 仍占 SNOW 消费 60-65%，增速 20-25%：慢，但很稳。

3. 锁住客户的不是数据，是数据上面建的"活"。Iceberg 让数据格式开放了，两家都能读同一份数据，数据本身越来越容易搬。真正难搬的是 DBX 上的管道代码、作业和模型，以及 SNOW 上的 SQL 逻辑、看板、口径和权限。所以大客户整体互换极少 (专家常说"押一家 5-10 年")，但新增工作负载放哪家，每年都在重新选。

4. 两边都在进攻对方，数字不小。DBX 的 SQL 数仓 run-rate 已超 $15 亿、同比翻倍 (公司口径)，Genie 在抢业务用户；SNOW 的 Snowpark 约占消费 20-25%、CoCo 用到 9,100+ 账户、贡献约 12-15% 的增量消费，而 CoCo 的用户 95% 是开发者，也就是说 SNOW 这轮加速主要靠打进工程这一侧。

5. 最大的变量是 AI 编程 agent 把迁移成本打下来了。SNOW CEO 自己说"迁入变快，迁出也一样变快"。护城河正从"数据放在哪"移到"目录和治理 (Unity Catalog vs Horizon) 归谁"、"agent 调谁"。

口径提示：DBX 的 run-rate 是"当期月收入×12"，SNOW 是季度产品收入。按年化算，DBX 已比 SNOW 大 (SNOW FY27 产品收入指引 $60.7 亿，+36%)。项目记忆里写的 "SNOW ~30%" 是 FY26 的速度，FY27Q2 已到 37%。

1 从零说起：两家到底卖什么

拿一家有 2,000 家门店的连锁超市举例。它每天产生三类数据：收银机的流水、会员 App 的点击、供应商寄来的 PDF 发票。公司里有两类人在碰这些数据。

数据工程师 小王 · Databricks 的典型用户

每天凌晨 2 点，他写的程序把前一天 2,000 家店的流水、App 日志、发票 PDF 全部拉进公司的云存储，去重、对齐商品编码、把 PDF 里的金额抽出来，算出"每家店每个商品卖了多少"。然后训练一个模型，预测明天每家店要进多少盒牛奶。

他用的是 notebook (一种边写代码边看结果的网页文档) 和 Python/PySpark 代码，写好后排成每晚定时运行的作业 (Job)。他关心：数据量再大也跑得完、能自己选机器型号压成本、图片和文本也能处理、模型能直接上线。

财务分析师 小李 · Snowflake 的典型用户

每周一早上 9 点，她打开 Tableau 看板看"上周华东区乳制品毛利率"，按区域、品类点筛选。看到异常，就在网页控制台写一句 SQL：select 门店, sum(毛利) ... group by 门店，几秒出结果，再导给区域经理。

她不写 Python，也不想知道背后用了几台机器。她关心：数字和上周口径一致、她只能看到自己负责的区域、查询快、月底不出错、账单别失控。

交接点就是小王加工好的那张"销量表"。很多大公司两家都买：DBX 负责加工和建模，SNOW 负责存放整理好的表、给分析师和看板用。一位渠道专家的说法是："历史上 Databricks 常被用来在 Snowflake 里产生的受治理数据上跑 AI 和机器学习。"(Funda 渠道调研，2026-09-01)

一个好记的比喻：DBX 像中央厨房，原料、刀具、灶台都给你，厨师想做什么都行，但得有厨师；SNOW 像出餐很快的餐厅前台，菜单是定好的，按按钮就出餐，谁能点什么有规矩，不需要懂厨艺。

2 出身：一个从"计算引擎"长出来，一个从"数据仓库"长出来

为什么出身重要：DBX 的默认用户会写代码，所以它的产品允许你"把自己弄得很复杂"，换来灵活；SNOW 的默认用户只会 SQL，所以它把复杂度藏起来，换来简单。这两种取舍很难同时做到最好，这是分工能维持的根本原因。

这对用户意味着什么：经典版是工程师喜欢的。机器在自己账号里，能看、能调、能用便宜的 spot 实例，数据也一直在自己手里，所以 DBX 的单价看起来贵，但调得好的总成本低。SNOW 是业务部门喜欢的：什么都不用管，预算和权限都在一处。DBX 这两年把 SQL 仓库、notebook、作业都做成了 serverless，就是为了把 SNOW 那种"简单"也拿过来。

两家都说自己更便宜，而且都有专家撑腰。把下面几段放在一起读，规律很清楚：数据量大、批处理多、有工程师调优时 DBX 便宜；数据量小、查询简单、没有工程师时 SNOW 便宜。DBX 的成本优势要靠工程师的劳动去兑现，这本身就把它推向了工程师用户。

Ghodsi 的说法是"今天我们通常靠 TCO 赢" (Sequoia 播客，2026-09)。两边的数字都来自利益相关方，只能当方向看。

5 治理：Unity Catalog 对 Horizon

"治理"是什么：一本目录，记下公司有哪些表、文件、模型，每样东西是谁的、谁能看哪几行哪几列 (比如小李只能看华东区，身份证号要打码)、数据从哪来到哪去。以前这是合规部门的事；有了 agent 之后，它变成"机器能替谁、读什么、写什么"的闸门，所以两家都把它当成新的主战场。

Unity Catalog (DBX)Horizon (SNOW)
管什么表、文件 (非结构化)、ML 模型、特征、函数，现在加上 agent、MCP、模型网关 (Unity AI Gateway)表、视图、标签、打码和行级策略、血缘、语义视图；Iceberg 表另有 Open Catalog (Polaris 托管版)
开放程度2024 年开源；能管外部引擎读写外部引擎经 Horizon 读数据时，权限和打码策略照样生效
优势一套目录管所有资产类型 (专家多次称为 DBX 的核心护城河)业务导向的工作流更容易治理和"对审计说得清"
弱点迁移进 UC 本身有工作量专家认为 Horizon 和 Open Catalog 两套体系有割裂

6 Iceberg：数据格式开放了，锁定转移了

Iceberg 是什么：一套"怎么在云存储上摆放数据文件和目录信息"的公开规则。只要按这个规则存，任何引擎 (DBX、SNOW、Spark、Trino、BigQuery) 都能把这些文件当成同一张表来读写。Delta Lake 是 DBX 自己的同类格式。以前 SNOW 的数据存成它自己的专有格式，数据进了 SNOW 就只能用 SNOW 的算力去读，这是它过去最硬的锁定。

发生了什么：2024 年 DBX 收购 Iceberg 的创始团队 Tabular，SNOW 开源 Polaris 目录，两家都宣布支持 Iceberg。结果是：

  • 对 SNOW：一部分客户把数据放在自己的 S3 上 (SNOW 少收存储费)，只在 SNOW 上跑计算；但 SNOW 也因此能"吃"到原本放在湖里的数据，并推出 SNOW 托管的 Iceberg 存储把存储收入拿回来。专家估计 Iceberg 相关只占 SNOW 消费约 5% (2026-02)，另一位估 10-15% (2026-06)，口径很不一致。
  • 对 DBX："数据在湖里、格式开放"本来是 DBX 的卖点，现在 SNOW 也能讲，差异变小。
  • 对客户：两边能读同一份数据，不用复制，所以"二选一"变成"各放多少工作负载"。

Dairy Farm 案例正好说明开放格式是双刃剑：这家亚洲零售集团从 DBX 迁回 SNOW，第一条原因是集团要求统一用 Iceberg 而不是 Delta。

7 锁定：锁住客户的是"建在数据上的活"

把专家说法归纳一下，两边各自锁住客户的东西不一样，但共同点是：锁住客户的不是数据本身，而是建在数据上、要重写才能搬走的东西。

锁住 DBX 客户的锁住 SNOW 客户的
代码 / 逻辑几百上千个 notebook、PySpark 管道、定时作业、ML 训练和上线流程几千条 SQL、存储过程、dbt 模型
面向人的东西工程师的工作方式和技能 (Spark 调优)几百张看板、报表、语义口径 ("收入""活跃客户"怎么算)
治理Unity Catalog 里的权限、血缘、模型注册Horizon 里的标签、打码、行级权限；整理多年的一方数据
架构serverless 和托管表 (见第 3 节)数据共享：和客户、供应商不复制就能共享数据的关系网
谁怕出事平台工程团队CFO 和业务部门：报表口径一变，月报就对不上

这能解释几组看起来矛盾的证据：大客户"整体迁移"极少 (动辄数百万美元、有业务中断风险)，但小客户 (年合同 1-2 万美元) 来回切换；DBX 说去年约 200 家客户从 SNOW 迁入，但仔细读，那主要是 AI/ML 和流处理工作负载，不是整个数仓。

但 AI 正在拆这道墙

AI 编程 agent 能自动翻译 SQL 和管道代码，迁移从两年缩到一两个季度。SNOW 在用它 (SnowConvert、CoCoEvolve 能把 DBX、dbt、Airflow 的工作流搬进来)，DBX 也在用 (BladeBridge、迁移 agent)。云厂商还开出数百万美元补贴把客户拉回自家。墙变矮了，对双方都是。

8 为什么 DBX 赢工程

五条理由，按重要性排：

  1. 新增的钱本来就是工程活。2026 年的新预算是搭 agent、做流处理、处理文档和图片、训练和微调模型，这些都要写代码。DBX 不需要"赢"SNOW，只要站在原地，新钱就会流过来。
  2. 非结构化数据是一等公民。DBX 从第一天就能把 S3 里的图片、PDF、文本直接给 notebook 用，向量检索也上得快；SNOW 在 AI 之前基本只处理结构化表。
  3. 工程师能调，所以大规模便宜。经典架构让工程师选机型、用 spot 机器、控制数据位置。对工程文化强的公司，这是他们想要的。
  4. 买家是技术负责人，DBX 把自己定位成"控制面"。Unity Catalog + AI Gateway 管所有数据、模型和 agent 的权限，卖给懂 agent 细节的技术领导。
  5. 对手打不进来。微软销售为了完成配额实际卖更多 Azure Databricks；Fabric 的 POC 很少转成生产。

9 为什么 SNOW 守得住 BI

  1. 简单就是产品。业务用户不想调参数，"黑盒"对他们反而是优点：成本和权限更可控。没有数据工程师的公司 (包括很多初创) 首选 SNOW。
  2. 它已经是"真相的来源"。财务、销售的口径、权限、看板都建在 SNOW 上。面向业务的分析更容易治理、更容易"对审计说得清"，agent 时代风控和安全部门进场后，这一点更值钱。
  3. BI 仍是市场的大头。Thoughtworks SVP 的原话是"世界其他地方仍然以 BI 洞察为主，这种情况 Snowflake 赢"。专家估计 SNOW 核心传统数仓占消费 60-65%，增长 20-25%。
  4. 数据共享网络。不复制就能和客户、供应商共享数据，这是 SNOW 在面向客户业务上的独有杠杆。
  5. 其他对手更弱。Fabric 和 Synapse 在易用和集成度上比不上 SNOW；DBX 的 SQL 早年"没飞起来"(现在起来了，见第 11 节)。

还要注意一个新动作：SNOW 在用 AI 往下吃 BI 工具本身。SNOW 的 CFO 说他们公司已经取消了所有 BI 和分析软件合同，改用 CoCo + Streamlit 生成看板。这对 Tableau、Power BI 是威胁，对 SNOW 是把"BI"这块地从展示层也一起收进来。
