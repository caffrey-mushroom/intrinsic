Agent 进大企业有多难

先分清哪些事规则软件早就做完了 (比如 Amazon 退货)，再用一张"对不上的供应商发票"一步一步看 agent 要经过哪些系统、哪些部门，解释 Deloitte 说的数据 (72%)、治理 (70%)、集成 (67%) 三个卡点，多 agent 协调到底指什么，企业要做哪些事，每一层是谁在卖；最后用保险理赔、贷款审批、供应链合规三个例子对照。

一句话

模型已经够聪明了，难的是让它在一家大公司里"有资格干活"。能写成固定规则的事 (比如 Amazon 上的普通退货)，传统软件早就自动化了，不需要 AI。AI 要接手的是剩下那部分：输入是 PDF、邮件、照片，规则写不全，要跨好几个部门去查和问。偏偏这部分最依赖数据、最需要接很多系统、权限最敏感。

本文用一张"对不上的供应商发票"走一遍：它要经过 8 个系统、7 个部门。人类会计靠多年积累的默契把它们串起来，agent 没有这些默契，所以企业得把它们一条一条写出来、接起来、管起来。

"大规模、协调的多 agent 部署"就是指：一个跨部门的真实流程，由几家厂商的多个 agent 接力完成，有一个编排者负责派活和交接，有统一的身份、权限和审计，而且是在动真钱、真数据的生产环境里跑，不是演示。做到这一步的公司约 15%，而且很可能每家只跑通了少数几个流程。每个流程从试点到全面上线要 6 到 12 个月，生产成本是试点的 3 到 4 倍，钱的大头花在实施、集成和人身上。

这份调查是 Deloitte 2026 年 8 月发布的，样本是 501 位美国企业的业务和 IT 高管，都参与本公司的 AI 战略或落地。答案是高管自己报的，不是审计出来的。原始分布如下 (据 ZDNET 2026-08-24 的报道)：

和我们手里的专家数据交叉对一下，15% 大致可信，甚至偏乐观：

  • 美国一位负责财富 100 强客户的云生态专家 (2026-06)：75-80% 客户做过 POC，25-30% 有小规模生产，约 15% 有多个生产负载。
  • 微软 FDE 团队负责人 (2026-08)：POC 到单一部门试点的转化率 40-45%，POC 到全企业生产只有 4-5%。
  • ServiceNow 内部人员 (2026-09)：客户从 POC 走到生产的比例，去年 5-10%，今年 25-35%，预计明年约 60%。方向在快速变好，但起点很低。

所以 15% 应该读成："有 15% 的大公司，至少有一两个跨部门流程由多个 agent 在生产里接力跑起来了。"不是"15% 的公司已经全面 agent 化"。

先说清楚：哪些事不需要 AI

在 Amazon 上退货很丝滑，不需要 AI。原因有三个：

  • 走的是标准路径。30 天内、商品可退、账户没风险，三条规则写死就行。
  • 系统是一家建的。订单、支付、仓储、物流都是 Amazon 自己的，只有一套编号。一般企业的系统是从 SAP、Salesforce、Workday 等五六家厂商买来拼起来的。
  • 它宁可"先退钱再说"。规模大，被薅羊毛的损失比雇人审核便宜，所以很多判断直接省掉了。
标准件例外件
例子金额对得上的发票、30 天内的普通退货、标准员工入职数量少了、单价涨了、供应商用邮件解释；理赔照片模糊；贷款材料不全
输入结构化字段 (订单号、金额、日期)PDF、扫描件、邮件、照片、合同条款
判断规则写得完要"在政策范围内酌情"，要去问人
谁在做规则软件早就做完了 (ERP 自动匹配、电商退货流程)今天全靠人，常外包给印度、菲律宾的共享服务中心
AI 的位置不需要大模型第一次能做，这是 agent 要抢的活

所以更准确的说法是：规则软件已经吃掉了标准件，AI 进来抢的是例外件。例外件恰恰最依赖数据、最需要跨系统去查、权限最敏感，所以会撞上 Deloitte 说的那几道坎。下面用企业里最典型的例外件来演示。

一张对不上的发票，走一遍

设想一家财富 500 强的美国消费品公司，每个月收几万张供应商发票。大部分在第 ④ 步自动对上、自动付款了。下面这张没对上。场景是构造的，系统和部门分工是大公司的典型配置；文末专家讲的真实案例规模更大：一个供应链中心每天审约 1,300 张发票，经过 13 个角色环节。

步骤今天人是怎么做的用到的系统这个系统归谁管agent 要做到什么
① 收票读票供应商"华东包装"发来邮件，附一张扫描 PDF 发票：纸箱 10,000 个 × $4.86 = $48,600。系统 OCR 识别抬头和金额，行项目识别错了一半。Coupa / SAP Ariba 收票平台；邮箱AP 共享中心 (很多公司外包给 Genpact、埃森哲等)读懂各种格式的发票；认出是哪家供应商
② 找采购单发票上没写采购单号。会计按供应商和日期在 SAP 里搜，找到采购单：10,000 个 × $4.70 = $47,000。SAP 采购模块采购部；SAP 团队在没有单号的情况下找到对的采购单
③ 找收货单查仓库收货记录：只收到 9,700 个。SAP 收货 / 仓储系统 WMS仓库运营读收货记录；收货可能当天还没录入
④ 三单匹配SAP 自动比对发票、采购单、收货单。数量差 300 个、单价高 3.4%，超出容差，发票被冻结付款，进入例外队列。SAP 发票校验财务这一步规则软件已经做了。对得上的发票在这里就自动付款
⑤ 查合同翻合同库，在 40 页框架合同第 14 页找到调价条款：纸价指数涨超 5% 时可调价，需提前 30 天书面通知。合同库 (PDF，SharePoint 或 Icertis)法务 + 采购读懂条款，判断这次涨价是否合规
⑥ 问人发邮件问仓库：300 个是没到还是没录？问采购：有没有收到调价通知？回邮件问供应商要依据。来回 3 到 5 天。邮件 / Teams采购、仓库、供应商写邮件、看回复、追进度
⑦ 审批差额超过 $500 要采购经理和财务主管批。审批人是谁，看 Workday 的组织架构和授权矩阵。SAP 审批流或 ServiceNow；Workday采购经理、财务；HR 维护授权矩阵知道自己能放行多少钱，找到对的审批人
⑧ 付款按 9,700 个付款；单价按合同决定付 $4.86 还是 $4.70；在 SAP 里释放发票，进下周付款批次。SAP 付款 + 银行系统资金部放真钱。绝不能付两次，不能付到错误账户
⑨ 留痕每一步留记录。季末审计抽查：为什么多付 $1,552？依据哪条条款？谁批的？各系统日志内审；外部审计 (SOX)每一步可追溯

熟练会计处理这张发票，实际动手大约半小时到一小时，但因为要等别人回邮件，往往拖一周。她能做成，是因为她已经拥有这些东西：

  • 账号和权限：入职时 IT 给她开了每个系统的账号，她能放行 $10,000 以内的差异。
  • 默会知识：她知道"华东包装"在 SAP 里登记的是母公司名，知道哪个仓库录收货总是晚一天，知道纸价条款要先问采购。
  • 责任：付错了钱会被追责，所以她会自己多检查一遍。

Agent 一样都没有。它要拿到 8 个系统的访问权，就要说服 7 个部门的系统负责人。每个负责人都有自己的预算、管理员、变更审批委员会和厂商合同，KPI 里都有"别让我的系统出事"。技术问题背后是 7 个部门的组织问题。

为什么值得做：专家讲的真实案例里，每天 1,300 张发票的人工成本约 $900；用 agent 跑，1,000 张发票的 token 成本约 $31.6。省的是外包共享中心的人力，这也是 IT 服务和 BPO 最先承压的地方。

为什么数据不"统一可访问" (72%)

听起来像"数据没放在一起"。实际上数据通常都在，问题是下面这几种：

问题在发票例子里长什么样人怎么绕过去
同一个东西有好几个编号"华东包装"在 SAP 供应商主数据里是 100234 (登记的是母公司名)，在 Coupa 里是另一个号，在合同库里用的是子公司名。会计知道它们是同一家。
同一个词，不同口径采购单按"个"，发票按"箱" (50 个/箱，写的是 200 箱)。不换算的话，系统以为数量差了 49 倍。她一眼看出单位不同。
规则不在系统里调价条款在合同 PDF 第 14 页；"纸价指数"去哪查，只有采购知道。问采购。
数据不够新仓库下午才补录收货，数据仓库每晚同步一次。agent 上午读到的是"只到 9,700"，其实 300 个已经到了。她打电话问仓库。
复制一份，权限就丢了供应商合同价格是敏感信息，在原系统里只有采购能看。把合同复制进向量库给 agent 搜，如果权限没跟着走，全公司都能搜到每家供应商的价格。人在原系统里查，原系统替她管权限。

所以"统一、可访问"真正的意思是四件事同时成立：一个编号、一个口径、足够实时、权限跟着数据走。这正是数据平台和目录治理产品在卖的东西：Databricks 的 Unity Catalog、Snowflake 的 Horizon、SAP Business Data Cloud、Salesforce Data Cloud。Glean 做的也是其中一部分：把各系统的文档连同权限一起"复印"一份给 agent 搜。

美国一位大企业客户专家 (见文末) 说，POC 没进生产的主因"并非 AI 的技术能力"，而是"企业逐渐意识到自身数据质量不佳"。

集成是什么，为什么贵 (67%)

一个朴素的比喻：每个系统都是一个只开一扇小窗口的办公室，窗口里的人只说自己的方言，只认自己的表格。"集成"就是在每两个窗口之间修一条传话通道：谁有资格来递单 (登录认证)、表格怎么翻译 (字段映射)、对方没回应怎么办 (报错和重试)、一天最多递多少张 (限流)。

以第 ② 步为例，让 agent 能"在 SAP 里查采购单"，具体要做：

  1. SAP 团队把采购单查询开放成接口 (SAP 里叫 OData 或 BAPI)。这要排进他们的工作计划，可能排到下个季度。
  2. 给 agent 开一个系统账号，决定它能看哪些公司、哪些工厂、哪些字段 (单价要不要给它看？)。
  3. 做字段映射：Coupa 的供应商编号怎么对到 SAP 的，"箱"和"个"怎么换算。
  4. 在测试环境 (一份 SAP 的副本) 里测，再过 SAP 的变更委员会才能上线。
  5. 以后 SAP 每次升级或改字段，这条通道都要回归测试一遍。

这只是 9 步里的一步，整个流程要修 8 条这样的通道。大公司的 SAP 几乎都是深度定制的：一位前埃森哲资深人士说，90% 的大型客户系统高度定制，厂商的自动化工具"只能完成 10%"。所以每家公司的通道都要单独修，没法批量复制。

花多少钱、多久：

  • 美国大企业客户专家：从 POC 到生产，第一年成本"至少 3 倍，通常 3 到 4 倍"。
  • 埃森哲一位 AI 高管：客户在软件上花 $1，近期要在集成商身上花 $4-5。
  • Salesforce 新加坡一线人员讲的雅诗阁 (Ascott) 项目：Salesforce 只收 agent 费，不到 100 万新币；算上 FDE 和实施费，整单约 600 万新币。agent 本身只占约六分之一。
  • 一位服务多家大客户的 IT 服务专家给的周期：POC 约 3 个月，小规模生产 4-6 个月，大规模生产至少 6-8 个月。
  • 美国一家大型电商平台的专家："没有人去做集成、重新设计流程、做治理和衡量结果，再多花 3,000 万美元在模型上也没用。"

新变化：MCP (模型调用工具的通用接口标准) 让"修通道"有了统一插头，类似 USB-C。它降低了每条通道的成本，Salesforce 一线人员说 MuleSoft 这类传统集成工具增速因此变弱。但插头统一了，"允许 agent 通过这个插头做什么"仍要每家公司自己定义和审批，这部分省不掉。

权限、身份、审计

人是怎么被管的：会计每天早上用公司账号 (比如 Okta 单点登录) 登录一次，就能进所有系统。她的角色决定她能放行 $10,000 以内的差异，超过要经理批。她做的每一个动作，系统都记成"她做的"。

Agent 以谁的名义干活？这是第一个要回答的问题，有两种做法，都有毛病：

做法好处问题
借会计的身份 (代表某个人办事)权限天然有边界：她能做的它才能做。agent 7×24 同时处理几千张发票，日志里全记成她，出事说不清是人还是机器。
给 agent 自己的"系统账号"简单，一次配好。为了省事，系统账号常被开成管理员权限。风险最大的是假冒供应商的邮件："我们的银行账户变了，这期款请付到新账户。"人会打电话核实，agent 如果照邮件改了收款账户，钱就没了。

所以企业要做的是：给每个 agent 发一个独立身份 (行业叫"非人身份")，只给它刚好够用的权限 (比如能读合同、能写邮件，但不能改供应商银行账户)，设金额上限，令牌限时过期，超过阈值转人工审批，出事能一键停掉。这正是 Okta、Microsoft Entra、CyberArk (已属 PANW)、SailPoint 在争的新市场。

审计：美国上市公司受 SOX 约束，每一笔付款放行都要有审批证据。季末审计师抽到这张发票会问：为什么多付 $1,552？依据合同哪一条？调价通知在哪？谁批的？如果是 agent 做的，就要能拿出它当时读了哪些数据、用了哪个模型版本、依据哪条条款、谁按了确认。今天这些记录散落在 8 个系统的日志里，格式各不相同。

Deloitte 那条 70% "难以信任和治理 agent"说的就是这一块。一位 EMEA 集成商的安全负责人 (2026-10) 认为 agent 身份是好方向，但"现在还不是量的生意，因为大多数客户没有那么多 agent 在生产里"。

多 agent 协调到底指什么

为什么会有多个 agent？因为没有哪家公司会让一个外来 agent 随便写 SAP。现实是每家系统厂商都在自己系统里放一个 agent：SAP 有 Joule，Coupa 和 Ariba 有自己的，Salesforce 有 Agentforce，ServiceNow 有 Now Assist，Workday 也有。公司还会自建几个。于是一个跨部门流程就变成了几个 agent 接力。

编排者就是这场接力的调度员：它知道这张发票走到第几步、下一棒交给谁、交接时要带哪些信息、两个 agent 意见不一致听谁的、什么情况必须停下来叫人。

交接时会出的事，用发票例子说：

问题具体例子要怎么防
交接丢信息读票 agent 交出"200 箱"，匹配 agent 按"个"比对，判定数量差 49 倍，整张发票被拒。统一编号和单位 (又回到数据那一节)

出事找谁多付了钱，是模型厂商的错、SAP 的错、写编排规则的人的错，还是财务的错？见下

责任最后落在谁身上：模型厂商和软件厂商的合同都有责任上限，不会为一笔错付兜底。所以责任仍然落在业务流程的负责人 (这里是财务总监和采购总监) 身上。正因为他们要背锅，他们会坚持设金额阈值、保留人工确认、先在一个工厂或一个区域试。这些做法很合理，但也直接拖慢了"规模化"。

真实案例：一家为大型客户做交付的集成商专家讲，某石油公司供应链从发票结算、供应商资质审核这类单点 agent 做起，复制到 17 个供应链中心，最近把 26 个 agent 协同起来，用"三角模型"：一类 agent 解读需求，一类执行，一类专门做合规监控。专门加一类 agent 去盯别的 agent，这就是"协调"在实践里的样子。反面案例：某客户先做了 100 多个 agent，几个月后真正常用的只剩 4 到 5 个。

企业要做什么，谁卖什么

对我们意味着什么

  • AI 抢的是例外件，例外件今天是人在做，而且常是外包的人。发票例外、理赔初审、贷款材料审核，大量在 Genpact、埃森哲、Cognizant 的共享中心里。这和我们"IT 服务和 BPO 最先承压"的判断一致。
  • 瓶颈在部署，不在模型。一位为大客户做交付的专家说：模型能力"已经具备较高的供给能力"，"最大的问题在于客户现场的部署和交付"。所以近两年钱先流向人 (SI、FDE) 和数据整理，agent 软件费占比小 (雅诗阁约 1/6)。这和我们"PLTR 式部署层"的判断一致。
  • 规模化是按流程一个一个推的。每个流程 6-12 个月，所以"全企业 agent 化"是多年的事。这解释了为什么记录系统厂商 (CRM、NOW、SAP、WDAY) 的 AI 收入还小：它们卖的是写入关口，但每家客户一年只能开通几个流程。
  • 不可绕开的层不等于马上有钱。身份和审计每个流程都必须做，但现在 agent 数量少，还没成独立预算。数据平台和观测已经按用量收钱，所以它们先受益。这和我们之前"按门收费 vs 按量收费"的框架一致。
  • 可以跟踪的信号：Deloitte 下一轮调查里"有编排的多 agent"是否从 15% 明显上升；专家口中 POC→生产比例 (ServiceNow 内部人员预计明年约 60%)；OKTA 是否开始单独披露 agent 身份收入；NOW Action Fabric 和 CRM 按动作计价的收入；Genpact 等 BPO 的财务外包收入增速。
