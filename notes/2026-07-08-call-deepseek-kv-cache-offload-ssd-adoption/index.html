纪要总结

1. KV Cache分层Offload技术与现状

  1. Deep在推理（inference）场景下，目前KV cache的分层offload是如何实现的？特别是DDR和SSD的offload？
  • SSD Offload采用率与决策边界
  • 目前SSD offload的采用率在20%到30%之间。
  • Offload存在决策边界，由HBM占用率、访问间隔、命中率等条件决定。V4上线后，决策曲线整体右移，使SSD更早进入ROI优化区间。
  • 三层存储间的数据流动策略
  • HBM -> DDR/SSD：当HBM占用率达到90%，访问间隔超过N个token，且命中率阈值为70%时触发。
  • DDR -> SSD：当DDR占用率达到70%，复用命中率超过50%时触发。
  • HBM -> SSD (直接)：当命中率阈值高达95%时，会不经过DDR直接offload到SSD。
  • SSD的角色定位
  • SSD不用作working memory，而是用作cold storage（冷存储）。
  • V4架构下的压缩技术
  • CSA加HCA架构能将1M上下文的KV cache大幅压缩，VSS Pro压缩至4.6GB，VSS Flash压缩至3.2GB。
  • 作为对比，V3.2版本时压缩后为68.6GB，单张H100卡无法承载。V4的压缩从根本上改变了HBM的容量压力格局。
  1. 三层存储架构在延迟与带宽方面的具体对比是怎样的？
  • 热层 (HBM3e)：作为working memory，延迟在1微秒以内，带宽为3.35TB/s。
  • 暖层 (DDR5)：作为KV温层，延迟在100纳秒级别，带宽为460GB/s（约HBM的1/4）。
  • 冷层 (NVMe SSD)：作为cold storage，延迟为100微秒，带宽为7GB/s，速率相比HBM有100到1000倍的差距。
  1. 基于V4架构，这种存储层级的改变在实际性能和系统负载方面带来了哪些具体影响？
  • 回读性能对比
  • 从SSD回读4.6GB的KV cache总时间约1.3秒。
  • 从DDR回读仅需10毫秒（包含DMA传输）。
  • HBM本地访问在1微秒以内。
  • HBM压力显著降低
  • V4的压缩技术使单个H100可承载55个VSS Pro或80个VSS Flash的并发请求。
  • HBM自身就能容纳大量并发请求的完整KV cache，大幅降低了HBM压力，也使得将SSD用作working memory的紧迫性下降。

2. SSD技术演进与需求驱动

  1. 从行业演进的角度看，SSD offload技术的采用率和其在系统中的角色定位发生了怎样的变化？
  • 采用率变化
  • V3.2时代：约40%-50%的集群节点配置SSD offload。
  • V4时代：采用率降至20%-30%，且主要用于checkpoint归档和RAG冷数据，而非KV cache。
  • 驱动因素转变
  • 驱动力已从解决“KV cache容量不足”转变为满足“aging（老化数据）的常态化持久化需求”。
  • 预计年底采用率将回升至50%-60%，主要因新部署的aging集群将其作为标准配置。
  • 角色定位转变
  • 即便采用率回升，在V4节点中SSD用于KV cold层的容量分配仅占12.5%。
  • 主要容量用于RAG语料(47.5%)、checkpoint(22.5%)和aging trace日志(17.5%)。
  • SSD在KV cache体系中的角色已转变为冷数据归档和跨会话前缀共享，不再是活跃的working memory。
  1. V4的KV cache压缩优化是否意味着不再需要SSD？Agent等新需求的出现是否是驱动SSD配置率回升的主要原因？
  • KV Cache需求：是的，V4的压缩技术优化使得HBM+DDR基本能满足GPU的batch处理需求，因此不再需要SSD来承载活跃的KV cache。
  • Agent新需求驱动：是的，Agent场景的出现带来了新的增量需求，如满足Agent长对话和RAG知识库等，这些是驱动SSD配置率从20%-30%回升至40%-50%的主要原因。
  1. 除了KV cache，在Agent等场景下SSD还有哪些新增需求？其驱动因素和重要性如何？
  • RAG知识库：为使Agent具备更多上下文理解能力而配置的、针对不同垂直场景的独立知识库。Agent任务复杂，需要更多RAG知识库，驱动SSD需求。
  • Checkpoint：为满足企业或政府的合规性要求，在Agent运行的关键节点将状态写入SSD进行永久保存，以备后续审核。
  • 总结：在Agent场景下，对SSD需求增长的最大驱动力是RAG和checkpoint。
  1. 主流存储方案选型（TLC/QLC/SLC）的主要考量是什么？
  • 核心权衡：在延迟、耐久性（DWPD）和成本之间进行权衡。
  • TLC (主力方案)
  • 定位：KV冷存、AIGC和checkpoint的主力。
  • 优势：在延迟（60-80μs）、带宽（~10GB/s）、耐久性（1-3 DWPD）和成本之间取得最佳平衡。配合pSLC缓存能优化热点数据访问，完美匹配prefix cache的访问模式。
  • QLC (大容量低成本方案)
  • 定位：AIGC冷存和checkpoint归档。
  • 优势：容量大、成本低（TLC的0.5-0.7倍）。适用于大容量、低频次、顺序读取为主的场景（如RAG语料）。
  • 劣势：延迟高（100-150μs），耐久性极低（0.1-0.3 DWPD），不适合高频读取的KV场景。
  • SLC (极致低延迟方案)
  • 定位：极少量对延迟敏感的KV温层试点。
  • 优势：延迟最低（15-25μs），最接近DDR。
  • 劣势：成本极高（TLC的3-5倍），容量小，无法在万卡集群中规模化部署。

3. 未来架构路线与战略选择

  1. 未来是否会考虑采用类似NVIDIA Ruben的架构路线，即通过Bluefield SOC直接在GPU下挂载SSD？
  • 基本态度：会考虑该路线，但不会完全照搬，而是采用混合并行路线。
  • 核心原因：业务负载分层需求多样，无法统一用集群SMS（Storage Management Service）替代本地SSD。
  • 头部云客户：追求极致低延迟（<50ms TTFT），可适配Ruben路线，最大化利用HBM/DDR/CXL，削减本地SSD。
  • 中长尾客户：延迟容忍度较高（100-200ms），必须保留本地TLC SSD以保证延迟稳定性和TCO优势。
  • 政企专属云客户：有合规、离线和归档需求，强制要求大容量本地SSD进行物理隔离存储，集群共享SMS方案难以满足合规审计。
  1. 与NVIDIA基于BlueField的私有SSD架构相比，我们选择的CXL DDR路线有哪些核心优势？
  • 延迟优势：CXL访问延迟在150纳秒级别，比SCM SSD低约100倍，能更好地服务高频复用的KV场景。
  • ROI极高：CXL投入能将GPU利用率从40%提升至75%，硬件回收周期仅5.8个月，三年ROI高达500%，远超SSD升级方案（ROI 140%）。
  • 原生压缩协同：V4原生KV压缩技术大幅缩小温KV体积，使其可置于CXL内存中，极大降低对SSD的IO压力。
  • 硬件生态开放：CXL是行业通用标准，不绑定Nvidia专用硬件，支持国产供应链替代（如长鑫DDR模组），供应链更灵活。
  • 调度逻辑简单：沿用HBM->DDR->CXL的三层内存调度，无需处理复杂的跨节点闪存转发协议栈。
  • 解决带宽瓶颈：CXL新增独立内存带宽通道，能有效分流KV cache读写，缓解本地DDR带宽不足的核心瓶颈。
  • 资源全局池化：将单机DDR孤岛资源池化，大幅提升利用率。

4. Agent场景下的存储需求与配比

  1. 在Agent场景下，SSD和DDR的主要存储需求构成是怎样的？
  • DDR用途占比 (V4 for-agent集群)
  • KV Cache暖存：32.5% (最大单一用途)
  • RAG向量索引：27.5% (必须常驻DDR以保证毫秒级响应)
  • CPU working memory：22.5%
  • Framework worker及预留：17.5%
  • SSD用途占比 (V4 for-agent集群)
  • KV Cache冷存：12.5%
  • RAG知识库与向量：47.5% (主要构成)
  • Checkpoint：22.5% (主要构成)
  • Aging的trace和日志：17.5%
  • 核心变化：Agent会话使KV停留时间从秒级延长到分钟级，DDR从被动内存升级为HBM和SSD之间的主动缓存层。
  1. 从量化角度看，V4集群中HBM、DDR、SSD的容量配比是多少？未来演进趋势如何？
  • 当前配比 (HBM:DDR:SSD)：约为 1 : 2 : 60 (不含CXL)。
  • 2028年预期配比 (Agent成熟阶段)：将达到 1 : 4.3 : 80 (DDR部分包含CXL)。
  • 演进速度分析
  • DDR增速最快：容量配比翻倍（从1:2到1:4.3），主要由Agent场景下KV缓存（预计增长5-8倍）和RAG索引等需求爆发式增长驱动。
  • SSD绝对值增长显著：总容量增长1.1倍多，主要因RAG语料库规模膨胀。
  • HBM增长相对温和：受限于单卡物理封装和高昂成本。
  1. Agent场景下DRAM增长最快，其在整体配比中变化最大，这个理解是否正确？
  • 是的，这个理解完全正确。DRAM（主要指DDR及未来的CXL）是增长最迅速的部分，主要用于满足Agent场景下强劲的KV Cache和RAG索引需求。

5. 市场趋势与采购策略

  1. 如何看待当前存储产品的涨价幅度？公司的采购策略和支付意愿是怎样的？
  • 涨价幅度：今年上半年是过去40年最剧烈的涨价周期之一，DDR5累计增长超150%，企业级SSD增长110%。
  • 采购决策核心：投资回报率（ROI），即存储投入对GPU利用率的贡献度。存储被视为“算力杠杆”而非“成本中心”。
  • 支付意愿与弹性 (弹性越小，需求越刚性)
  • HBM：刚性必需品，支付弹性极小（5%-15%）。
  • DDR/CXL：强烈建议/战略性投入，能显著提升GPU利用率，支付弹性较小（DDR: 5%-15%, CXL: 15%-25%）。
  • TLC SSD：有条件接受涨价，支付意愿低于DDR/CXL，存在QLC替代方案，支付弹性较大（25%-40%）。
  • QLC SSD：成本优先，支付意愿最低，存在HDD替代方案，支付弹性最大（40%以上）。
  1. 您认为存储产品的价格未来走势如何？
  • HBM：明年上半年仍有15%-20%上涨空间，下半年走势取决于三星HBM4认证进度。
  • DDR5：明年将处于高位震荡区间，上半年高位持平，下半年可能小幅上涨5%-10%，供需缺口依然显著。
  • CXL：明年市场趋于成熟，价格将呈快速下降趋势，全年累计降幅预计30%-40%。
  • TLC/QLC SSD：明年预计进入价格回落通道，下半年由于产能集中释放，TLC预计下降5%-10%，QLC下降10%-15%。

  • 自研核心技术：
  • 四层分层存储的自动化引擎和核心调度逻辑。
  • 分层驻留规则。
  • SSD资源分配、KV区组管理、IO调度等。
  1. 在政企合规场景下，公司如何通过存储分层和软件优化来扩容SSD并控制成本？
  • 存储分层
  • TLC (75%容量)：用于KV冷缓存、高频更新数据和频繁快照。
  • pSLC缓存：承接热点前缀读取，降低延迟。
  • QLC：分配给历史支持库等低频访问的冷数据。
  • SLC/PLC：独立高速分区，服务于全局高频共享数据。
  • 软件优化
  • KV压缩前置：V4原生压缩技术，从源头减少写入量。
  • Prefix缓存全局共享：减少重复数据写入。
  • Dual Pass双IO流量隔离：缓解带宽瓶颈。
  • 生命周期分级TTL管控：减少无效SSD占用。

在 inference 集群中，KV cache 在三层存储之间的数据流动，是由动态策略引擎根据实时负载特征驱动的。具体的决策边界如下：从 HBM offload 的触发条件是 HBM 占用率达到 90%，访问间隔超过 N 个 token，且命中率阈值为 70%。从 DDR offload 到 SSD 的条件是 DDR 占用率达到 70%，复用命中率超过 50%。此外，也存在直接从 HBM offload 到 SSD 的情况，即不经过 DDR 缓存，其命中率阈值为 95%。

需要说明的是，SSD 不用作 working memory，而是用作 code storage。

我们目前的 CSA 加 HCA 架构，能将 1 兆上下文的 KV cache 压缩。其中，VPROs 压缩至 4.6 GB，Vflash 压缩至 3.2 GB。作为对比，在 V3.2 版本时，压缩后的大小为 68.6 GB。这种压缩从根本上改变了 HBM 的容量压力格局。在 V3.2 版本时，单张 H100 卡甚至无法承载一个 1 兆上下文的请求。

能否请您介绍一下三层存储架构在延迟与带宽方面的具体对比？

我们对三层存储的延迟和带宽进行了对比。热层采用HBM3e，延迟在1微秒以内，带宽为3.35TB/s，其角色是working memory。暖层采用DDR5，延迟在100纳秒级别，带宽为460GB/s，相当于HBM的1/4，作为KV温层。冷层采用NVMe SSD，延迟为100微秒，带宽为7GB/s，其速率相较于HBM有100到1000倍的差距，因此作为cold storage。

基于V4架构，这种存储层级的改变在实际性能和系统负载方面带来了哪些具体影响？

以V4的实测数据为例，从SSD回读4.6GB的KV cache总时间约为1.3秒，而从DDR回读仅需10毫秒，此时间已包含DMA传输，HBM的本地访问则在1微秒以内。V4的压缩技术对存储层级带来了显著改变，对于1M上下文的请求，VSS Pro的KV cache大小为4.6GB，VSS Flash为3.2GB。因此，单个H100可承载55个VSS Pro或80个VSS Flash的并发请求。这意味着在V4时代，HBM自身就能容纳55个并发请求的完整KV cache，从而大幅降低HBM的压力，使SSD作为working memory的紧迫性也随之下降。

从行业演进的角度看，SSD offload技术的采用率和其在系统中的角色定位发生了怎样的变化？

在实际部署中，V4集群的SSD offload采用率显著低于3.2时代。在3.2时代，约有40%到50%的集群节点配置了SSD offload路径；而在V4集群中，只有20%到30%的节点启用此功能，且主要用于checkpoint归档和RAG冷数据，而非KV cache或working memory。

从行业演进来看，SSD offload的采用率正处于上升通道，但其驱动因素已从解决KV cache容量不足转变为满足aging的常态化持久化需求。我们预计到今年年底，SSD offload的采用率将达到50%到60%，这主要是因为新部署的aging集群将其作为标准配置，且长TTL的策略得到普及。

即便在50%到60%的采用率预期下，根据万卡集群的实测数据，SSD在V4节点中用于KV cold层的容量分配仅占12.5%。其余容量中，47.5%用于RAG语料和向量索引，22.5%用于checkpoint，17.5%用于aging的trace和日志。因此，SSD在KV cache体系中的角色已转变为冷数据归档和跨会话前缀共享，而不再是活跃的working memory。

SSD需求的驱动因素，核心在于其介质选择需要在延迟、耐久性和成本之间进行权衡。目前，PCIe 5.0 TLC SSD是KV冷存、AIGC和checkpoint的主力方案；QLC仅用于AIGC冷存和checkpoint的归档；而SLC则仅在极少量对延迟敏感的场景中使用，不进行规模化部署。

这能够完美匹配prefix cache中少量热前缀和大量冷前缀的访问模式。单盘容量为1.6到3.2TB，与V4节点的SSD需求正好匹配。QLC方案我们只用于IG冷层和checkpoint的归档。IG语料占到47.5%，checkpoint占到22.5%，其特征是大容量、低频次、以顺序读取为主。QLC的高容量（每盘3.2到7.7TB）和低单位成本在此场景下具备优势。但是，我们很注意QLC的耐久性限制，checkpoint的频繁写入可能会快速消耗其TBWP配额，因此我们配合了写入缓冲层。SLC SCM方案我们仅少量使用，未规模化部署，只在一些延时非常敏感的KV温层进行试点，主要用于需要在小于35秒内访问的共享system property热前缀。容量限制在单节点0.2到0.4TB，这部分占我们SSD总量的2.5%以下。以上就是我们在存储选型方面的考量。

能否请您介绍一下CXL方案的核心优势？

CXL的核心优势首先在于延迟，可以显著优于闪存方案。CXL的访问延迟在150纳秒级别，比本地DDR高出50%，但相较于SCM SSD百微秒级别的闪存，延迟低了约100倍。因此，对于高频复用的One-KV场景，不需要牺牲用户体验来换取容量。

其次，KV缓存的投资回报率（ROI）非常高，硬件回报周期短。根据实测，CXL的投入为每机架8.5万亿，可将GPU利用率从40%提升至75%，整机吞吐量实现翻倍。回收周期为5.8个月，三年的ROI可达到500%，远高于SSD升级方案。SSD升级的回收周期为10.6个月，ROI仅为140%。

第三，V4方案采用原生的KV压缩架构。通过SA和HCA，可依据上下文将KV压缩93%，从而大幅缩小温KV的体积。绝大多数高频复用的KV可以置于CXL内存中，无需下沉至SSD，只有极低复用率的历史KV才会被存入SSD。这极大地降低了闪存IO压力并减少了延迟惩罚。相比之下，Nvidia没有原生的模型压缩，只能依靠大容量的SCM闪存承接海量的压缩KV，硬件投入非常高。

第四是硬件生态方面，我们支持国产供应链替代。CXL是行业通用标准，不绑定Nvidia专用的GPU和DPU。DDR内存可以选择长鑫等国产模组，我们预计明年国产替代率将达到20%。考虑到海外存储产品持续涨价且供应链存在风险，国产替代方案使整机硬件选型更灵活，无需强制采购Nvidia BlueField-4 DPU或Robin的全套专用芯片，从而优化供应链采购。

第五，分层调度逻辑更简单。我们沿用从HBM到本地DDR，再到CXL的三层内存调度，并复用自研的命中率预测策略。超过70%的DDR访问被下沉。此方案不需要DPU进行卸载，也无需处理RDMA跨节点闪存转发和复杂的NVMe-oF协议栈，尤其适合我们的几类客户。

在 V4 for-agent 集群中，这几种内存用途的占比是怎样的？

在 V4 集群中，对于 SSD，KV cache 冷存占比为 12.5%，每个节点的容量为 7.5TB；RAG 知识库与向量的占比为 4%。

对于 DDR，KV Cache 暖存占 32.5%，每个节点容量为 640GB；CPU working memory 占 22.5%，每个节点容量为 450GB；RAG 向量索引占 27.5%，每个节点容量为 560GB；framework worker 及 NUMA 预留占 17.5%，每个节点容量为 350GB。

在纯 chatbot 场景中，DDR 的主要角色是为 CPU 提供公共内存和为推理框架提供运行空间。此时 KV Cache 几乎全部驻留在 SSD 上，因此其在 DDR 中的占比较低。但在 agent 场景中，KV Cache 的暖存成为 DDR 最大的单一用途。

这一变化的主要原因是 Agent 会话的 KV 停留时间从秒级延长到分钟级。单次 Agent 任务流可能涉及多轮模型调用、工具执行和上下文拼接，导致 KV 张量在完成一轮注意力计算后不能立即释放，而需在 DDR 中保持温热状态以等待下一轮调用。这种工作模式的转变，使得 DDR 从被动的 CPU 附属内存升级为 HBM 和 SSD 之间的一个主动缓存层。

对于 RAG 索引，在 Agent 系统中几乎每个任务都会触发 RAG 检索，因此向量数据库的索引必须常驻 DDR 才能保持毫秒级的检索响应。如果将向量索引置于 SSD，即使采用最先进的 PCIe 5.0 设备，检索延迟也会从毫秒级劣化到几十毫秒级，这将严重影响 Agent 的端到端响应时间。

CPU working memory 主要用于 Agent 编排器运行、工具调用和上下文代码执行等计算密集型任务。framework worker 则为 vLLM 和 SGLang 等推理引擎的内部开销进行预留，为缓存对齐等操作提供必要空间。

这四种用途在物理上共用同一组 DDR 通道，因此带宽竞争不可避免。DDR5 的理论带宽为 460GB/s，而这四种用途的峰值带宽需求叠加后会远超此上限。具体而言，KV cache 暖存在换入换出时需要高吞吐的顺序带宽；RAG 向量索引需要低延迟的随机访问带宽；CPU working memory 需要持续稳定的低延迟带宽；而 framework worker 预留则需要大块连续的内存映射。这四种截然不同的访问方式在同一个物理介质上相互交织，形成了 DDR 侧的结构性带宽增强问题。

那么CXL以及其他存储类型（如SSD）的情况是怎样的？

CXL内存属于战略性投入，其付费意愿与DDR相当。它能为GPU利用率带来25%到45%的直接提升，并与DDR形成互补。我们评估其支付弹性在15%到25%之间。

对于TLC SSD，我们对涨价的接受是有条件的，其支付意愿低于DDR5和CXL。它对GPU利用率的间接辅助作用在5%到15%之间，并且可被QLC替代。因此，其支付弹性较大，我们评估在25%到40%。

QLC SSD则主要满足成本优先的需求，支付意愿是最低的。它与GPU利用率的关联度低于5%，并且可被HDD替代。相应的，其支付弹性在40%以上。

总体而言，TLC和QLC SSD的支付意愿处于最低水平，因为它们对GPU利用率的间接辅助作用有限，同时存在清晰的介质替代路线：TLC可被QLC替代，QLC又可被HDD替代。如果价格上涨过高，我们会选择采用替代方案。

在软件栈层面，我们是否采用了例如 Vast Data 等海外公司的方案，来合理调配 SSD 和 DRAM 资源，并实现 KV cache 的分层存储与 offload？

我们采用的分层技术，基本上是在使用海外的一些方案。我们采购现成方案后，会自己进行调试，将其整合并运行在我们的集群中，整体是一个混合软件栈的模式。

我们有一个四层分层存储的自动化引擎，其核心调度为自研，复用了 Dynamo 的基础能力，并制定了分层驻留规则。

L1 HBM 热层负责承载高频访问的 KV 和 MoE 激活专家权重。其驱逐策略为：当 HBM 占用达到 90%，且 KV 超过 256 到 1024 token 未被访问时，会将其标记为温数据并下放到 DDR。我们不会主动将热 KV 直接写入 SSD，以规避百微秒级的延迟惩罚。

L2 DDR 温层，包括未来的 CXL 内存池，主要承载短期复用的多轮 KV 以及 RAG 热点向量引擎索引。只有当 DDR 命中率超过 70% 时才允许数据留存，低于该阈值则直接丢弃，不进行下沉存储。

对于冷存，我们只存储高价值的前缀 KV，其准入门槛是 KV 复用命中率超过 90%。该层仅共享 System Prompt 和公用的 RAG 文档。在容量分区方面，SSD 会固定将 12.5% 的空间留给 KV 冷存，剩余的 87.5% 分配给 RAG 库、Checkpoint 和 Agent 日志，以杜绝 KV 挤占存储空间。

最后一层是持久归档层，使用独立容量的 SSD 和 HDD。它用于存储历史日志、过期的模型快照等，这些数据完全脱离推理链路，不占用在线 SSD 的 IO 带宽。

此外，我们还根据负载类型差异化分配 SSD 资源。对于要求低延迟的头部 CSP 场景，策略是严格控制 SSD 的 KV 写入量，主要使用 HBM+DDR+CXL。而对于能容忍 100 到 200 毫秒延迟的中长尾成本型 CSP，策略会启用 SSD 前缀缓存，以平衡成本和复用率。

请您介绍一下在正企合规技术方面，贵司是如何进行SSD总容量扩容与成本控制的，尤其是在存储分层和软件优化层面有哪些具体手段？

正企合规技术会大量扩容SSD总容量，并提升checkpoint和trace日志分区的占比。在存储分层调度方面，我们以此控制SSD成本。

TLC颗粒分配了 75% 的SSD容量，用于KV冷缓存、高频更新数据、IG以及频繁快照。

pSLC缓存则用于承接热点前置读取，以降低随机读取的延迟抖动。

QLC颗粒主要分配给低频访问的冷数据，例如历史支持库和老旧模型版本，并禁止存放KV缓存。

SLC和PLC则被划分为独立的高速分区，专门服务于全局高频共享数据，不占用通用SSD容量。

在软件层面，我们有四项主要的SSD资源优化手段。

第一是V4原生的KV压缩前置技术，通过CSA和HCA算法，可将 1 兆的上下文KV压缩 93.3%。

第二是Prefect缓存全局共享，以减少重复数据写入SSD。

第三是Dual Pass双IO流量隔离，用于缓解SSD的带宽瓶颈。

第四是生命周期分级TTL管控，旨在减少无效的SSD占用。

尽管海外软件栈为我们提供了底层硬件驱动、通用推理及分布式编排等技术底座，但核心的三层存储分层、SSD资源分配、KV区组管理以及IO调度等技术均为我们全部自研，因此拥有完整的自主调控权。
