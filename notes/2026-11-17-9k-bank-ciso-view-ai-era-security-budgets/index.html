银行网络安全预算、AI安全需求与供应商格局专家访谈纪要

1. 网络安全预算趋势与增长驱动

a) 过去一年及明年的安全预算增幅如何？

  • 预算按年度制定，而非单季度同比增长：
  1. 从去年第四季度开始，安全预算持续提升。
  2. 今年全年预算同比增长约25%，明年预算预计继续增长25%-30%，至少不会低于25%。
  3. 每年新增预算约为2,000万至3,000万，原访谈未明确币种。
  • 年度预算通常在年底统一规划，并平均分配至下一年度各季度，因此Q1至Q4的预算差异不大。
  • 当前正在同步审批下一季度预算和明年预算，各团队提交方案后由管理层统一审核。

b) 年度预算确定后是否还会动态调整？

  • 年度预算并非完全固定：
  1. 已批准预算可在预算池内重新调配。
  2. 若Q2或Q3出现项目资金不足，或者临时需要引入新技术、新软件，可以单独申请额外预算。
  3. 临时追加支出不包含在年度25%-30%的常规增幅中。
  • 银行倾向于在年底尽可能完整地提出下一年度可预见项目，以便从Q1直接执行，减少中途审批带来的延迟。

c) 哪些因素会导致安全预算发生较大变化？

  • 预算下降通常由经营压力驱动：
  1. 若企业收入或利润大幅下滑，可能通过裁员、减少许可证数量和削减安全投入降低成本。
  2. 该情况在咨询公司等项目制企业中较为常见，但银行收入相对稳定，发生概率较低。
  • 预算上升主要由外部威胁变化驱动：
  1. ChatGPT、Claude、Gemini等AI工具降低了攻击者发现漏洞和实施渗透的门槛。
  2. 过去攻击者获取管理员账户后，还需要较长时间了解银行架构并寻找后续路径；现在AI可以辅助判断漏洞、规划攻击路径并给出下一步操作。
  3. 黑客进入银行内部的成本和时间显著下降，推动银行增加AI安全防范投入。
  • 近期安全预算明显增长，核心并非传统系统扩容，而是应对AI增强型攻击。

2. 增量预算分配与重点投入方向

a) 明年新增项目预算主要投向哪些领域？

  • 明年项目预算的预计分配如下：
  1. 漏洞管理与暴露管理：约50%-60%
  • 主要用于引入AI驱动的漏洞扫描、攻击路径分析和自动验证产品。
  • 当前正在对多家厂商进行Proof of Value测试。
  • 产品价格较高，正式采购后通常需要签订2-3年合同。
  1. 安全运营中心SOC：约25%-30%
  • 重点推动SIEM、SOAR与AI Agent结合，建设Agentic SOC。
  • 银行在该领域相对落后，部分企业已提前半年以上开始实施。
  1. 剩余约10%-15%
  • 主要涉及治理、风险与合规服务，即GRC。
  • 身份权限管理当前增量投入有限，原因是银行已经采购Microsoft Entra，现阶段主要支付固定续费。
  • 如果市场出现成熟的Agent身份与生命周期管理产品，可能在Q2或Q3单独申请额外预算。

b) 上述比例是否包括现有许可证续费？

  • 不包括。
  • 上述预算仅指明年的新增项目成本和项目预算，即Project Cost与Project Budget。
  • 微软、Palo Alto、Entra等现有产品的License续费属于正常运营支出，未计入增量项目预算。

c) 哪些安全领域受AI驱动的增量最明显？

  • 第一梯队：
  1. 漏洞与暴露管理。
  2. Agentic SOC和安全运营自动化。
  3. Agent身份、权限及生命周期管理。
  • 相对受益有限的领域：
  1. 边缘网络与传统防火墙。
  2. 终端安全。
  • 原因是防火墙和终端传感器本身已长期执行拦截与监控，AI更多用于提高分析和误报甄别效率，而非创造全新的安全需求。

3. AI驱动的漏洞管理与自动化红队测试

a) 银行当前最关注的AI安全产品是什么？

  • 当前重点评估能够调用ChatGPT、Gemini、Claude等大模型的自动化安全测试产品。
  • 其工作方式包括：
  1. 通过API调用多个大模型，生成不同的攻击方式和攻击组合。
  2. 对银行外围和内部系统进行持续扫描。
  3. 识别单个漏洞，并判断多个漏洞是否能够组合成完整攻击路径。
  4. 模拟攻击者从外部进入内部后的横向移动和潜在破坏。
  5. 提供漏洞优先级、修复建议，并在修复完成后自动重新验证。
  • 相比仅发现单点漏洞，管理层更关注产品能否说明攻击者如何通过多个漏洞逐步进入核心系统。

b) AI安全测试与传统红队测试有何区别？

  • 本质上仍属于红队测试，但AI提高了频率、效率和验证能力。
  • 传统红队测试模式：
  1. 银行通常不自建红队，而是委托外部机构执行。
  2. 外部机构完成测试后提交报告，银行内部协调各部门修复问题。
  3. 传统测试通常每4-6个月甚至每年开展一次。
  4. 单次测试费用可能在1万至10万、20万之间，具体取决于企业规模。
  • AI自动化测试的优势：
  1. 修复完成后可以立即复测，无需等待下一次外部红队项目。
  2. 可以持续确认高风险漏洞是否真正消失。
  3. 降低对外部咨询公司的持续依赖。
  4. 将低频、项目制红队测试转变为持续性暴露验证。
  • 外部红队不会完全消失，但AI工具会承担大量日常扫描和修复验证工作。

c) 为什么传统漏洞扫描工具难以满足需求？

  • 以Qualys为例，其优势是已知漏洞数据库完善、传统扫描能力强。
  • 其局限在于：
  1. 主要通过在服务器和终端安装Agent，扫描已经公开的CVE和已知漏洞。
  2. 对尚未公布、尚未进入漏洞数据库的问题识别能力有限。
  3. 无法像大模型一样主动生成新的攻击思路并组合攻击路径。
  • 专家认为，如果Qualys不能加快与AI结合，未来增长空间可能逐步收窄。
  • 银行的核心目标不是“在AI发现漏洞前发现”，而是在黑客使用AI发现并利用漏洞之前，提前识别和修复问题。

d) 当前正在评估哪些相关供应商？

  • 受访者提到的候选名称包括Pentera、Horizon3/NodeZero及其他初创厂商；原始表述中的厂商数量与名称存在一定混用。
  • 这些厂商的共同特点是：
  1. 多为初创或非上市公司。
  2. 通过API调用大模型开展自动化攻击模拟。
  3. 以SaaS平台呈现漏洞、高危风险、攻击路径和修复建议。
  4. 支持修复后的持续复测。
  • 当前银行正在开展Proof of Value，实际比较产品效果后再决定最终采购对象。
  • 受访者认为该方向具有明确需求，银行、政府、医疗、零售等持有大量数据的行业都会逐步采购相关能力。

4. Agentic SOC与安全运营自动化

a) 为什么SOC是AI安全投入的第二大方向？

  • SOC每天需要处理大量日志、漏洞和安全告警，人工逐条分析已不可持续。
  • 传统SOC通常配置L1、L2、L3分析人员，分层处理日志、调查事件并执行响应。
  • AI Agent引入后：
  1. 基础日志拆解和初步研判可由Agent完成。
  2. 人员主要负责审核Agent结论和处理复杂事件。
  3. SOC人员能够从重复性调查转向高风险事件处置。
  • 每家公司都需要SOC，因此Agentic SOC具有普遍需求，不取决于企业是否主动接受这一趋势。

b) 为什么事件关联比单点告警更重要？

  • 蓝队每天可能收到200-300条告警，团队没有时间逐条深入调查。
  • 通过跨产品关联，这些告警可能被整合为20-30条完整事件故事：
  1. 用户先收到钓鱼邮件。
  2. 账户凭证被攻击者获取。
  3. 终端开始执行危险代码。
  4. 攻击者尝试通过邮件、SharePoint或其他渠道泄露数据。
  5. 账户进一步尝试获取管理员权限并进入数据库。
  • 将零散告警串联成完整时间线，可以显著降低工作量，并帮助分析人员快速判断事件是否真正构成威胁。

c) 哪些厂商可能受益于Agentic SOC趋势？

  • 主要参与者仍是现有大型安全平台，包括：
  1. Microsoft Sentinel。
  2. Palo Alto的SIEM与安全运营产品。
  3. CrowdStrike Falcon及Next-Generation SIEM。
  4. Splunk等日志与安全分析平台。
  • 受访者认为新进入者突破难度较高，市场大概率仍由已有大型厂商主导。
  • 各厂商的核心任务是将现有SIEM、SOAR、日志分析和响应能力升级为Agentic SOC。

d) AI Agent的异常行为如何被安全系统识别？

  • Agent进入系统后可能出现明显不符合人类习惯的操作，例如：
  1. 一秒内连续点击30-40次。
  2. 数秒内创建多个API。
  3. 在非正常时间大规模下载或访问数据。
  • 安全团队可以结合操作速度、行为模式和账户权限判断其是否为异常Agent行为。
  • 未来安全运营的重要能力之一，是区分正常员工、合法Agent、被劫持Agent和恶意自动化程序。

5. Agent身份、权限与生命周期管理

a) 企业使用Agent后，身份权限管理面临哪些新问题？

  • 目前每名员工可能拥有2-5个Agent，未来可能增加到10-20个。
  • 主要风险包括：
  1. Agent数量快速增加，缺乏统一资产清单和管理平台。
  2. Agent权限可能设置过高或与实际职责不匹配。
  3. 员工离职后，其Agent可能继续运行。
  4. 临时员工、合同工和留学生流动频繁，进一步增加Agent清理难度。
  5. Agent可能自动创建API、访问数据或长期保留系统权限。
  • 理想平台需要覆盖Agent的创建、身份登记、授权、持续监控、实时撤权和注销全生命周期。

b) 微软目前能否解决Agent管理问题？

  • 银行当前使用Microsoft Entra进行身份权限管理，但其Agent治理能力仍不成熟。
  • 微软推出了Agent 365等管理能力，但目前存在以下问题：
  1. 告警信息实用性有限。
  2. 对可疑Agent的识别存在较多误判。
  3. 无法有效统一管理员工名下的多个Agent。
  • 银行正在寻找第三方解决方案，但市场上尚未出现能够充分满足要求的成熟产品。
  • 因此，身份与Agent管理是明确的潜在需求，但短期预算释放速度取决于产品成熟度。

c) Microsoft Entra和Okta的竞争力如何？

  • 两者在传统身份权限管理领域都较为成熟，基础能力没有根本性差异。
  • Microsoft Entra的优势：
  1. 与Azure、Windows Server和微软云服务天然集成。
  2. 微软客户基础广泛，采购和销售路径更顺畅。
  3. 价格更具吸引力。
  4. 风格相对保守，但稳定性和大型企业覆盖更强。
  • Okta的优势：
  1. API和单点登录能力较强。
  2. 与第三方应用和运营商的合作范围广。
  3. 在跨平台身份连接方面起步较早。
  4. 在美国及中小企业市场可能拥有更多客户。
  • 加拿大大型企业更倾向于选择微软，主要原因是既有IT架构、采购便利性和价格，而非Okta产品能力不足。

6. 微软、Palo Alto与平台化竞争

a) 当前主要供应商支出结构如何？

  • 微软相关支出约占年度网络安全支出的40%。
  • Palo Alto相关支出约占30%。
  • 其余预算分散在CrowdStrike、Fortinet、SentinelOne、Akamai、Proofpoint等供应商。

b) 为什么微软在银行安全采购中占比较高？

  • 公司约90%的基础设施部署在Azure上，整体采用混合云架构。
  • Word、Excel、PowerPoint、Teams、Power BI等微软产品属于企业必需品，安全产品可作为附加模块打包销售。
  • 微软可能为全套安全产品提供高达80%的折扣，其他独立厂商很难复制这一价格条件。
  • 银行的采购策略通常是：
  1. 先判断微软产品能否满足基本需求。
  2. 若能够满足，则优先采用微软方案。
  3. 若产品明显不足，再采购各细分领域的专业供应商。
  • 微软产品未必在每个领域都是最优，但具备价格、集成和采购便利性优势。

c) Palo Alto的核心竞争力是什么？

  • Palo Alto的防火墙能力在北美大型企业中处于领先位置。
  • 公司正在从单一防火墙厂商向综合安全平台扩张：
  1. SIEM。
  2. SOAR。
  3. WAF。
  4. 安全运营和日志分析。
  5. 数据安全等其他模块。
  • 其策略是补齐微软已有的产品类别，通过产品组合与微软进行平台级竞争。
  • 企业未来比较的不再只是“哪家防火墙最好”，而是：
  1. 哪个平台的整体安全性更强。
  2. 哪个平台的产品组合更完整。
  3. 哪个平台的综合性价比更高。
  4. 哪个平台能减少供应商和合同管理成本。

d) 大模型厂商直接进入安全领域是否具有竞争力？

  • 银行不会快速采购大模型厂商刚推出的安全产品，原因包括：
  1. 新供应商审核和审批通常需要8-12个月甚至更久。
  2. 产品必须明显优于现有方案。
  3. 必须与银行现有系统高度兼容。
  4. 银行还会评估供应商能否长期提供多项服务，而非单一产品。
  • 如果OpenAI等厂商能将多项网络安全服务整合成完整产品组合，竞争力会明显高于仅提供单点AI安全工具。
  • 银行也会顾虑采购OpenAI安全产品后，是否必须进一步绑定OpenAI大模型及相关合同。

7. 平台整合与“最佳单品”模式的取舍

a) 部署方式是否决定安全产品选择？

  • 部署架构是重要因素，但并非唯一因素。
  • 银行采用混合云架构，且大部分基础设施位于Azure，因此微软天然占优。
  • 中小企业的选择更依赖首席安全官或安全负责人的策略：
  1. 一类企业倾向选择单一大型平台，集中采购其全部服务。
  2. 另一类企业会按安全领域选择最佳产品，形成混搭架构。

b) “最佳单品”组合的优势和问题是什么？

  • 典型组合可能包括：
  1. 终端安全选择CrowdStrike。
  2. 防火墙选择Palo Alto。
  3. 高性价比防火墙选择Fortinet。
  4. 邮件安全选择Proofpoint。
  5. 云平台选择Azure或AWS。
  • 优势是每个领域都能获得相对最佳的专业防护。
  • 问题在于不同厂商之间难以共享数据，无法形成完整攻击故事。
  • 单一平台虽然每个模块未必最强，但可以跨邮件、终端、身份和数据防泄漏进行事件关联。

c) AI攻击是否会推动安全能力进一步集中？

  • 整体趋势将更加偏向平台化和供应商整合。
  • 原因包括：
  1. AI攻击速度更快，需要跨产品实时关联。
  2. 蓝队无法逐条处理大量告警，需要平台自动生成完整事件时间线。
  3. 统一平台更便于自动响应和权限控制。
  4. 减少供应商数量可以降低续约、合同和运营管理成本。
  • 但平台整合不会无限推进。如果平台厂商某一模块质量过差，企业仍会选择专业第三方产品。

8. 各细分领域供应商份额变化

a) 防火墙领域未来如何变化？

  • 银行目前使用Palo Alto和Fortinet等多家防火墙供应商，不同国家、分行和合作业务可能采用不同产品。
  • 双层防火墙可以提高安全性，但管理层开始评估重复投入是否真正有效：
  1. 如果Fortinet拦截的威胁已全部被Palo Alto覆盖，继续支付两份费用的意义有限。
  2. 释放的预算可以转向漏洞管理、SOC等增量更高的方向。
  • 未来2-3年，防火墙投入可能收紧，并逐步向Palo Alto集中。
  • 当前WAF由Akamai提供，管理层可能逐步评估整合至Palo Alto的可行性。

b) 终端安全领域未来如何变化？

  • 当前同时使用：
  1. Microsoft Defender for Endpoint。
  2. CrowdStrike。
  3. SentinelOne。
  • 微软目前占比较高，主要因为整体产品组合和采购便利性。
  • 银行希望逐步提高CrowdStrike占比，因为其终端产品明显优于微软。
  • 明年可能不会立即大规模迁移；如果微软终端产品到后年仍未改善，可能从明年下半年开始提出正式迁移方案。

c) 数据防泄漏DLP领域会发生什么变化？

  • 银行已使用Microsoft Purview DLP约3年，但今年决定停止使用并迁移至其他产品。
  • 主要问题包括：
  1. 产品使用体验较差。
  2. 无法有效完成最基础的数据标签管理。
  3. 产品质量未持续改善，可能并非微软重点投入方向。
  • 当前候选供应商包括Proofpoint、DTEX，Palo Alto也提供DLP产品。
  • 微软云原生DLP的理论优势是数据无需跨系统迁移；但如果产品无法满足基本需求，银行仍会选择第三方方案，并承担额外集成成本。

d) 供应商数量将如何调整？

  • 银行目前拥有约40-50家安全供应商。
  • 管理层希望逐步减少至20-30家，以降低：
  1. 合同管理成本。
  2. 每季度续约压力。
  3. 产品集成复杂度。
  4. 安全运营人员的学习和维护成本。
  • 最终方向是减少供应商，但不会以牺牲核心安全能力为代价。

9. 自研与外部采购的战略取舍

a) 银行更倾向自研还是采购第三方安全产品？

  • 从战略意愿看，管理层更倾向自主开发：
  1. 希望内部AI模型具备类似ChatGPT的能力。
  2. 不希望敏感数据发送至OpenAI等外部模型厂商。
  3. 希望将更多安全资金投入内部团队和自有系统。
  • 但实际执行中仍以外部采购为主，原因包括：
  1. 自研成本高。
  2. 产品需要持续升级、打补丁和修复漏洞。
  3. 需要长期保留专门维护团队。
  4. 核心员工离职可能导致系统无法持续运行。
  • 第三方产品可以将开发、维护和漏洞修复责任转移给供应商。

b) 采购第三方产品面临哪些风险？

  • 银行系统通常通过API与第三方平台连接。
  • 如果第三方供应商遭到入侵，攻击者可能借此进入银行内部系统。
  • 因此，银行设有专门的第三方信任与监管部门：
  1. 大约每半年审核一次第三方系统。
  2. 检查其是否符合银行安全规范。
  3. 评估其漏洞管理、数据保护和攻击防范能力。
  • 长期方向仍希望提升自建比例，但在成本和组织能力约束下，第三方采购仍将是主要模式。

10. 安全采购节奏与AI风险缺口

a) 当前安全采购是超前还是落后？

  • 受访者的判断是：思想超前，但行动落后。
  • 超前之处：
  1. 银行已经识别到AI辅助攻击、Agent进入企业系统等新风险。
  2. 已经开始评估AI暴露管理和自动化攻击模拟产品。
  • 落后之处：
  1. 新产品采购和接入通常需要6-12个月。
  2. 即使年底确定供应商，最快可能要到次年6月才能正式上线。
  3. AI安全漏洞和新型攻击几乎每周都在出现，采购期间存在明显风险空窗。
  • 即使产品上线，也不能完全解决所有问题：
  1. 当前厂商可能只接入ChatGPT、Gemini和Claude。
  2. 如果出现新的主流模型，而厂商未及时接入，银行仍可能落后。
  3. 产品主要解决扫描与识别问题，无法覆盖所有AI相关风险。

b) 为什么银行的实际落地速度较慢？

  • 主要限制包括：
  1. 供应商安全审核。
  2. 法律与合规审批。
  3. 管理层逐级审批。
  4. 系统兼容性和API集成。
  5. 数据隐私和第三方风险评估。
  • 银行并非缺乏预算，而是组织流程和风险控制要求导致实施周期较长。

11. 收费模式变化

a) 按席位和按消耗量计费分别适用于什么情况？

  • 若企业席位数量很多但实际使用量不高，按流量或消耗量计费可能更划算。
  • 若只有少数员工使用，但使用频率和数据量很高，按席位计费可能更有优势。
  • 实际上收费模式主要由供应商和产品属性决定：
  1. 微软办公及部分安全产品通常按人数或席位收费。
  2. Microsoft Sentinel等SIEM产品通常按日志或数据流量收费。

b) 银行是否非常关注计费模式变化？

  • 银行对按席位还是按流量本身并不特别敏感，更关注最终合同总额和产品价值。
  • 供应商虽然可能提供不同方案，但通常会通过定价设计确保整体收入。
  • 因此，两种模式下的最终支出通常不会存在特别大的差异。

总体而言，领导层希望自主开发，并将网络安全资金投入内部团队，搭建更多自有系统。但实际上，公司更多还是采购外部产品，因为自主开发成本过高。如果某个团队突然减少了几个人，相关软件可能就无法正常运行，还需要招聘新人补位。因此，目前外部采购相对较多，但长期方向仍是希望自主搭建。

提问者：最后1个问题，基于银行的应用场景和预算规划方式，您如何看待目前收费模式从按席位逐渐转向按消耗量或流量计费？

回　答　者：实际上没有太多选择，因为收费方式通常由运营商决定。有时运营商会提供不同选择，让客户决定按席位还是按流量计费。如果席位特别多，但使用量不高，按流量计费会更划算。如果使用人数较少，例如只有3个人或4个人使用软件，但使用量很大，运营商通常会推荐按席位计费。

有些时候客户没有选择。例如，微软产品通常按人数计费；使用其SIM或Microsoft Sentinel时，则按流量计费，主要取决于进入系统的数据量。因此，计费方式通常由运营商决定。

银行并不特别关注这一点。运营商需要盈利，提供不同选择只是让客户感觉获得了更优惠的方案。实际上，无论选择按席位还是按流量计费，最终总额应该不会相差太多。
