Q:上个季度，你预计客户在 Snowflake 的支出在第三季度会同比增长 33%。实际增长率是更高还是更低，造成差异的原因是什么？

A:略高一些，大约在 34% 到 35% 左右。核心计算仍占支出的大头，包括迁移、数据工程、Apache Iceberg 和 Openflow 工作负载。AI 起到了加速剂的作用，而 CoCo（Cortex Code）和 Co-Work正在产生查询。它们目前的贡献还不算很大，但在加速增长。过去几个季度，AI 对 Snowflake 平台的相关性逐步增强，我们现在看到的信号显示它也将推动增长加速。

Q:您预计今年第四季度和明年第一季度 Snowflake 支出的增长率分别是多少？

A:我们不做高度细化的环比季度预测，但预计增长将持续并可能略有加速。主要原因是 AI 的落地在企业内部渗透得更深，推动数据和计算量持续增长。作为一个指示性估算，我会预计第四季度增长约 35%，第一季度在 35% 到 37%之间。趋势显然是正向的，但我们不预期出现笔直向上的“曲棍球棒”式或所谓的“番茄酱效应”（瑞典语中常用的说法）。该估算也排除了任何地缘政治动荡或经济崩溃的情形，假设地缘政治环境保持稳定。

Q:在 2026 年第三季度，企业客户的 Snowflake 未实现业绩义务（RPO）同比增速相比第二季度是加速还是放缓？

A:是加速的，但这并不是趋势上的重大转变。它是一个稳定的上升，而不是趋势的断裂。

Q:您如何看待美国公司向 Snowflake 迁移的速度？本季度是否有更多美国公司在将 Snowflake 作为其数据库使用，以及美国公司的 AI 在 Snowflake 上的部署何时可能显著加速？

A:大部分增长来自现有客户的更深渗透和更高支出。很多 Snowflake 客户是从小规模起步，逐步把更多计算迁移到 Snowflake，增加更多模块，并提高整体支出。这也反映了 IT 领域向更少平台整合的宏观趋势，同时像 Snowflake这样的 平台在构建更完整的生态系统。市场正朝着“整套最优”（best-of-suite）而非“各取所长”（best-of-breed）的策略演进。

在 AI 部署方面，企业已经走出过去所谓的 POC 和试点困境。大约在六个月到一年前，很多公司运行了大量试点但没有实现规模化；现在他们正在规模化。Snowflake在促成并受益于这一过程方面处于有利位置，因为它提供了底层的管道和计算能力。然而，AI 推广不是一个离散的零到一事件；它遵循渐进上升曲线。把 AI应用到每一个工作流都需要实施项目。这些实施正在变得更快、更高效，并越来越多地在企业范围内开展。因此采用率在上升，但应当控制期望：不会出现 AI 支出的大爆发，而是持续的、渐进的增长。

Q:企业在部署 AI 时面临哪些瓶颈或挑战？主要问题是否包括缺乏统一数据库、AI 权限治理，或还有其他因素？

A:存在若干瓶颈，包括您指出的主要问题。首先，尤其在欧洲，公司面临像 GDPR 和欧盟 AI法案这样的治理和立法问题。这些法规出于良好意图，对是否必要或能否增值存在不同看法，但它们要求欧洲公司在进入生产阶段前完成大量行政工作。美国公司也面临广泛的治理工作，包括数据丢失协议、数据访问规则、代理身份授权、token支出治理和代理编排。因此，治理和立法构成了一类主要的瓶颈。

另一个被低估的障碍是传统的变更管理。很多公司错误地把 AI 实施当作纯粹的 IT 或 AI 项目。实际上，AI是被引入到可能存在多年或数十年的业务流程深处，这些流程包含大量业务逻辑和默会知识。因此公司需要项目管理、变更管理以及理解相关业务流程的业务分析师。他们还需要重新设计这些流程的授权。如果保留原始设计，仅仅在上面添加AI，就像“给猪化妆”，是捕捉不到全部业务价值的。

变更管理的延伸是高层支持以及将 AI 视为自上而下的公司范围内的举措。许多早期项目是由中层管理、布道者或内部冠军支持的试点，但缺乏规模化的授权。明确的规模化授权是必要的。底层数据也至关重要：公司需要便于大规模 AI 采用的 IT和数据格局。这些准备工作必须事先完成，但存在权衡。过度准备会导致用于实际 AI 实施的时间不足，而在没有足够准备的情况下仓促实施则可能因为数据不统一或不可访问而使项目放慢或停止。

这种权衡取决于用例。有些用例依赖于格式各异、来自多源的多样化底层数据，使得数据挑战更为复杂；另一些主要依赖单一系统，代理可能已经集成在该系统中，数据几乎不是问题。因此挑战的程度有所不同，但在企业范围的推广中这肯定是存在的。

Q:本季度 CoCo（Cortex Code）在 Snowflake 客户中的采用率是多少？它本季度和上季度分别占 Snowflake 总消费的多少比例，以及在每个期间它推动了多少百分点的 Snowflake 消费？

A:CoCo（Cortex Code）是 Snowflake 的强劲增长驱动力，因为它直接拉动核心消费，同时也有间接影响。它在与 Claude Code、GitHub Copilot 等类似产品竞争时表现良好。CoCo（Cortex Code）在 Snowflake 平台内具有优势，而 Claude Code 是更横向的代码助理，可以在不同环境中运行。CoCo（Cortex Code）对客户整个 Snowflake资产和代码库具有内建感知，这是一个重大优势。就目前而言，它可以在 Snowflake 堆栈内与 Claude Code 竞争，这正是相关的语境。

数据支持这一判断。CoCo（Cortex Code）环比增长大约在 30% 到 40% 左右，且这种增长在加速。它正在新增大量净新账户，这对 Snowflake很重要，因为该模块正被现有客户添加。我预计它会相对很快成为标准配置。Snowflake 也会公布诸如客户数或用户数等指标。基于 30% 到 40%的环比增长，我估计采用率可能每季度大约提升五个百分点左右。这是在一个不断扩大的基数上实现的，相当可观。

就产品收入而言，核心 SQL 分析、数据仓库和 BI 仍然占多数。我的估计是，AI（包括 CoCo（Cortex Code）和其他 Cortex 功能）可能占直接产品收入的 7% 到 8%，且在快速上升。上一季度这一比例可能约为6%，再前一季度为 4% 到 5%。每一美元直接花在 CoCo（Cortex Code）上，可能会大约带来四倍的消费增长。它已经是一个可观的收入贡献者，尽管很多间接收入可能本来也会发生，因此精确贡献难以估算。其底层机制是CoCo（Cortex Code）提升了 Snowflake 开发者的生产力，使他们能更快地构建数据管道并加入拉动消费的功能。

Q:Cortex AI Gateway 在第三季度发布。其当前在企业中的采用率是多少？是否提升了 Snowflake 的消耗？

A:到目前为止还没有显著提升消耗，因为现在仍然太早。以消耗来评估 Gateway 也可能不是最合适的方式。从战略层面看，许多 AI 平台——包括超大云厂商、Snowflake、Databricks、Salesforce 和UiPath——都在争夺编排和治理层的控制权。Cortex AI Gateway 是 Snowflake 的应对之策。它将 Snowflake 定位为一个在 Snowflake 内部及其外部运行的 AI控制平面或代理治理层。它还允许客户路由和控制第三方代理的流量，这对于成为能够跨企业管理其他代理的编排层是必要的。

编排和治理是高度竞争的领域。每个供应商都在争取领先地位，因为普遍观点认为控制编排将随着市场成熟而带来首要位置。最终结果将取决于每个客户的底层环境。围绕 Salesforce 或 Agentforce 生态构建的客户很可能选择Agentforce 作为其编排层。深度绑定于 Microsoft 作为其超大云厂商的客户很可能使用 Microsoft 的解决方案，尽管该方案尚不十分成熟但在发展中。对于深度绑定 Snowflake 的客户，Cortex AI Gateway 是一个可信的模块，用于纳入第三方代理。

这是一个及时的模块，会有助于增长，但目前它更多是在填补能力缺口，而不是作为主要的消耗驱动因素。只有当第三方代理流量开始访问 Snowflake数据时，消耗才可能显现。三到六个月后情况应该会更明确，那时可以评估该产品是否在获得吸引力。目前，它的价值更多在于向外界传递 Snowflake 的战略方向并完善其生态。

Q:Cortex AI Gateway 对 Snowflake 有何意义，Snowflake 如何将其货币化？

A:Cortex AI Gateway 便于第三方代理访问 Snowflake 数据。通过让 Snowflake 及其数据对这些代理更可及，它将推动底层的 Snowflake 消耗。Gateway可能会带来一些直接收入，但我预计这部分贡献会很小。Snowflake 可能会对 Gateway 提供大幅折扣，因为拥有治理层在战略上很重要。因此主要的货币化机制将是增加对 Snowflake 数据的消耗。

Q:第三季度 Snowflake 与 Databricks 之间的竞争如何演变？竞争是否更加激烈，二者的能力是趋同还是分化？

A:我没有观察到第三季度有任何具体事件实质性地改变了这种竞争。两家公司之间仍然是持续性的对抗。选择几乎是二选一：客户通常使用 Databricks 或 Snowflake中的一个，同时使用两者的相对较少。一旦公司迁移到任一平台，切换成本很高，导致客户黏性很大。

两家公司都在扩展各自的生态系统以提高黏性和营收，同时弥补功能差距。因此它们的产品重叠越来越多，竞争也显而易见。然而，各自都拥有既定的客户群，这些客户不太可能迁移到另一家平台。两家公司在各自现有客户范围内还有大量的消耗增长可捕获，这将持续若干季度。因此，这场竞争并非零和博弈。

Q:Cortex AI Gateway 还提供模型路由功能。客户已经在使用这一能力了吗？它会加速还是减缓他们的整体 AI 消耗？

A:模型路由可以视为 Cortex AI Gateway 的一部分。我相信它是在第三季度较晚推出，几乎还未进入生产阶段，因此采用仍然非常有限。其目的是提高 token 效率，这一点很及时，因为公司越来越需要监控 token开支。今年早些时候，AI 采用几乎是以 token 支出为衡量，但那种支出变得难以控制。公司现在专注于衡量 token 成本、确保物有所值，并在合适的情况下使用开源或旧一代模型来替代前沿模型。

更高的 token 效率使客户能够构建更多用例，从而推动额外的 Snowflake 消耗。动态路由通过为每个用例选择最合适的底层模型并考虑模型成本差异来实现这一点。随着 token 成本下降，来自 CoCo（Cortex Code）和Co-Work 的 token 收入可能会有所下降，但更低的成本会部分抵消那部分收入减少。更高的效率还应推动更高的使用量。因此我预计净效应为正，不过这将可能在 2027 年初更为明显。

Q:除了 Snowflake 以外，云服务提供商、安全公司、Datadog 和许多其他公司也在开发模型路由、监控和编排能力。哪家提供商可能成为企业模型编排和监控的主要入口？市场可能如何发展？

A:这是一个价值百万美元的问题。这个领域竞争非常拥挤，因为 AI 涉及技术的方方面面。各类软件平台都在开发编排和治理能力，包括带有 Agentforce 的 Salesforce、Workday 和 ServiceNow。自动化平台如UiPath 和 Automation Anywhere 也在参与，超大云厂商和数据平台如 Snowflake 亦在其中。其他参与者还包括像 Palo Alto Networks这样的专业平台、本土的代理平台，甚至可能包括前沿实验室自身。众多供应商都在处理同一个问题并试图控制顶层。

很难判断谁会控制这一层，我也没有看到有胜出者在出现。市场可能也稍微超前了。编排产品的推出是有用的，因为它表明了市场的方向：公司最终将需要涉及第三方代理的跨平台编排。然而，大多数客户尚未达到那个阶段，仍处于其 AI部署旅程的早期阶段。只有时间会揭示结果。我没有明确答案，而这种不确定性本身可能也表明市场仍然开放。

Q:Snowflake 的 Apache Iceberg 能力在第三季度是否进一步改进？这对 Snowflake 的消耗有何影响？

A:这不是一个重大进展。我没有在数据中看到任何反映出影响，尽管我可能并不掌握全部情况。就我的观察而言，它在第三季度并未成为一个显著事件。

Q:转向 MongoDB，您上个季度预测第三季度的同比消耗增长为 22%。实际增长率是更高还是更低？造成差异的原因是什么？

A:大体与预测一致，增长并未发生重大变化。MongoDB Atlas 增长更快，而 MongoDB 的多年期大单有时会导致波动。实际增速可能略低一些，大约在 21%，但这种差异更多是噪音而非信号。总体情况大约是 20%的增长并保持相对稳定，MongoDB Atlas 增速更快，仍是需要关注的关键领域。

Q:您预计本年第四季度和明年第一季度 MongoDB 消耗的同比增长率是多少？

A:在平滑了曲线以考虑大单造成的波动后，尤其是日历年末和年初的 Q4 和 Q1，我预计会略微上升至 22% 或 23%。作为指示性数字，我会估计 Q4 为 22% 增长，Q1 为 23% 增长，这主要由 MongoDB Atlas的更快增长推动。

Q:企业内部基于代理的用例在增加吗？大规模的企业代理部署何时可能开始加速 MongoDB 的消耗？

Q:您预计企业内部大规模采用 agent 化何时会显现？

Q:MongoDB 9.0 引入了哪些重大更新？这些更新会在第四季度或明年显著影响消费吗？

A:MongoDB 9.0在第三季度发布，接近季度末，因此企业采纳周期太慢，其影响尚未在数据中体现。目前对消费的影响因此是不可见的。该版本包含性能改进，如更高的吞吐量、更快的读取和更快的更新。这些是积极的发展，但更像是预期内的性能提升，而非质的飞跃。

该版本还包含一个加密扩展，对受监管行业应当有用，因此可能带来额外机会。总体上，MongoDB 9.0 更偏向于渐进式演进，而非颠覆性版本。

Q:Voyage AI 产品在 8 月 13 日进入完全商用可用。它显著提高了客户消费吗？Voyage AI 可能在第三季度、第四季度和明年为 MongoDB 的增长贡献多少百分点？

A:对于 Voyage AI 来说现在还处于早期，但将其作为数据库功能的一部分而不是独立产品或采购项来集成是正确的设计。它从非常小的基数开始快速增长。我估计环比增长大约为50%，在接下来的几季内很容易维持这种增长，因为其收入基数可能仅在数千万美元的低位。

更重要的考量是客户基础如何发展。Voyage AI 是通过 MongoDB Atlas增长的，而不是作为独立产品，应被视为一个生态系统的一部分，整体大于部分之和。企业客户采纳更慢，因此其影响尚未在数据中显现。尽管如此，这是一个不错的发布，最终应会对 MongoDB Atlas 的增长有所贡献，并填补了 MongoDB之前存在的空白。

Q:MongoDB CEO 的离职对公司产生了什么影响？它是否导致客户在第三季度犹豫或推迟采购？这种影响是否可能长期存在？

Q:Snowflake 和 Databricks 正在积极将其产品与 PostgreSQL 等开源数据库集成。这会对 MongoDB 形成越来越大的竞争压力或更大的威胁吗？

A:是的，绝对会。MongoDB 面临来自两个方向的竞争。第一类是数据平台进军运营型数据库，包括 Databricks 的基于湖的产品和 Snowflake 的 PostgreSQL。两者都在进入 MongoDB的领域。第二类是云厂商的类似动作，尤其是 Google，其 Firestore 产品提供与 MongoDB 的兼容性。

这为 MongoDB 造成了艰难的竞争环境，因为云厂商、Databricks 和 Snowflake 运营更广泛的平台，能将数据库能力捆绑进迁移解决方案中。我尚未在数据中看到重大影响，但 MongoDB 有理由对此保持一定程度的担忧。

Q:MongoDB Atlas Infinite 和 Agent Engine 在 9 月 29 日进入公开预览。这两款产品可能对 MongoDB 产生何种影响？

A:先说 MongoDB Atlas Infinite，目前仍处于早期但潜力显著。它将计算与存储分离，如果我没记错，当前只在 AWS上可用。它可以减少扩容时间，这很重要，因为客户希望尽可能快地扩展计算和容量。通过应对需求峰值，它也减少了过度预配存储的需要。

MongoDB Atlas Infinite 是把双刃剑。短期看它能减少客户的空闲支出，这对 MongoDB 不利，但它也可能使 MongoDB赢得更多有突发性需求的工作负载。其弹性意味着客户不需要为了应对峰值而预留过多存储容量。因此即时的存储需求可能下降，但最终 MongoDB 可能会赢得本来会转向 PostgreSQL等替代方案的工作负载。我认为长期效应为净正面，尽管当前影响甚微，且取决于 MongoDB 是否能吸引这些额外的工作负载。

Agent Engine 代表了对 agent 基础设施的进军，这是一个高度拥挤且困难的市场。它着眼于治理、统一执行和编排，很多公司都希望参与这一领域。贴近数据是一个优势，整合状态、记忆、检索和权限能创造价值。然而，MongoDB 面临来自Microsoft Foundry、Bedrock、Agent Core、Google、Databricks 的 Agent Bricks 以及各种框架的竞争。企业更可能从其云或 AI平台提供商那里选择治理和编排能力，而非从数据库厂商处选取。

MongoDB 正在尝试超越其作为数据库供应商的角色，进一步向价值链上游发展，这是可以理解的，因为数据库本身正在商品化。Snowflake 得出类似结论并在超越计算和存储方面更为成功。Agent Engine是一次良好且自然的发布，反映了市场方向。Agent 的记忆功能可能会成功，而 agent 的运行时可能会面临困难。MongoDB 可能会从该产品产生部分收入，但我不认为它会成为默认的 agent 基础设施提供商。我的估计是 Agent Engine 在 MongoDB 整体业务中将保持边缘化。
