Snowflake AI安全治理与开放数据架构专家会议纪要

1. AI安全与治理的战略价值

a) 为什么AI安全与治理正在成为企业部署AI的关键议题？

  • Snowflake安全实践负责人Sebastian Weitzner表示，在与客户进行超过100次交流后发现，AI治理并不是阻碍产品落地的合规核查项，而是推动AI创新的催化剂。
  • 完善的治理体系能够帮助企业：
  1. 更快推进AI项目；
  2. 建立对数据和模型使用过程的信任；
  3. 降低敏感数据泄露及违规使用风险；
  4. 获得将创新构想投入生产环境所需的信心。
  • 本次会议涉及的部分功能尚未全面开放，相关能力、发布时间及产品规划可能发生变化，应视为前瞻性信息。

b) 本次会议主要讨论哪些内容？

  • 本次分享主要包括4项内容：
  1. 企业使用AI处理敏感数据时面临的挑战与机会；
  2. 面向数据本身的数据治理；
  3. 利用AI提升数据治理与安全运营效率；
  4. Snowflake新一代AI治理能力及现场演示。
  • 会议后半部分进一步讨论了开放数据架构，重点分析Apache Iceberg、Apache Polaris与Horizon Catalog如何实现跨平台互操作和统一治理。

c) 为什么“没有数据治理，就没有AI治理”？

  • AI系统能够访问和生成什么内容，根本上取决于底层数据是否被发现、分类、标记和保护。
  • 如果企业不了解自己拥有哪些数据，就无法识别敏感数据，更无法确定应适用哪些监管、法律及内部安全要求。
  • AI治理不能仅依赖提示词、模型拒答或智能体自身判断，而需要建立在确定性、可测试、可强制执行的数据治理基础之上。
  • Snowflake的核心观点是：
  1. 没有数据战略，就没有AI战略；
  2. 没有数据治理，也就没有AI治理；
  3. AI安全必须从底层数据控制延伸到运行时交互、智能体权限和审计追踪。

2. Horizon Catalog统一数据治理体系

a) Horizon Catalog在Snowflake治理体系中承担什么角色？

  • Horizon Catalog是Snowflake覆盖数据与AI资产的统一目录和治理中枢。
  • 其管理范围不仅包括Snowflake内部数据，还包括：
  1. Snowflake托管表；
  2. Apache Iceberg开放格式数据；
  3. 客户存储在自身对象存储中的数据；
  4. 外部数据和外部元数据；
  5. 来自SAP、Salesforce、Workday等企业系统的数据；
  6. 智能体、应用程序和外部计算引擎访问的数据资产。
  • 对Iceberg表，Horizon能够提供完整资产视图，并支持数据分析、访问保护、使用监控、策略执行和审计。
  • Horizon希望成为企业数据与AI资产的统一管理层，无论数据位于Snowflake、其他云平台还是本地IDC，都能纳入同一治理体系。

b) Horizon的数据治理框架包括哪些核心环节？

  • Horizon的治理体系主要围绕“发现、保护、信任”3个支柱展开。
  • 发现
  1. 识别企业拥有的数据资产；
  2. 自动发现敏感列和敏感数据类型；
  3. 展示数据是否已分类、是否已应用保护策略；
  4. 识别治理缺口。
  • 保护
  1. 根据数据标签自动应用脱敏、加密、阻断和访问控制策略；
  2. 让标签和策略随数据转换及下游衍生过程持续传递；
  3. 在Snowflake及外部引擎访问时统一执行治理策略。
  • 信任
  1. 记录人类和AI对数据的访问行为；
  2. 提供端到端数据血缘；
  3. 支持数据质量监控和根因分析；
  4. 建立完整、可审计的数据使用记录。
  • 这3个支柱并非顺序执行，而是贯穿数据全生命周期、相互联动。

c) Snowflake如何自动发现和分类敏感数据？

  • 数据分类已经成为Horizon内置的一等功能。
  • 系统可对指定数据库、Schema或数据资产运行约150个且仍在持续增加的开箱即用分类器。
  • 分类器能够自动识别：
  1. 姓名、电子邮件、电话号码；
  2. 驾驶证号码、护照号码；
  3. 出生日期、国民身份证号码；
  4. PII、PCI、GDPR相关数据；
  5. 其他受监管或可识别个人身份的信息。
  • 企业也可以创建自定义分类器，根据自身业务定义敏感信息，而不局限于通用监管标准。
  • 系统能够展示已分类数据比例、已附加策略的数据比例，并持续扫描新增或发生变化的数据。
  • Trust Center中的Classification Profile可用于建立自动扫描机制，持续执行“监测—标记—应用策略”的闭环。

d) 数据完成分类后，如何自动应用保护策略？

  • Snowflake可以将识别出的语义类别映射到企业内部数据域和标签体系。
  • 完成映射后，可以对标签配置：
  1. 动态脱敏策略；
  2. 加密策略；
  3. 阻断策略；
  4. 行列级访问策略；
  5. 面向智能体的专属策略。
  • 当数据进入平台时，只要可靠完成分类和标签绑定，后续无论是人类、应用还是智能体访问数据，系统都可以强制执行对应策略。
  • 标签会随数据转换和下游视图传递，因此治理能力不会因数据加工、复制或衍生而中断。
  • 不同敏感级别可以采用不同处理方式：
  1. PII可进行完全遮盖；
  2. 受限数据可进行强掩码；
  3. 一般敏感数据可采用哈希处理；
  4. 在不暴露原始信息的前提下，仍可支持BI统计和分析。

e) Snowflake如何简化复杂的权限管理？

  • 传统访问控制可能依赖庞大的角色、人员和权限映射表，维护成本较高，也容易因组织变化产生配置错误。
  • Snowflake正在强化基于属性的访问控制，即ABAC：
  1. 可以直接为用户或其他主体定义属性；
  2. 用户属性可由Okta、Microsoft Entra等身份提供商推送；
  3. 策略可以根据部门、岗位、地区、职级和业务用途等属性动态执行；
  4. 无须持续维护复杂的权限映射表。
  • ABAC与传统RBAC并非互斥，而是可以结合使用，从而让权限策略更加易读、稳健和易于维护。

f) Snowflake如何支持数据使用审计？

  • 对敏感数据不能只设置访问策略，还必须记录谁在什么时间、以何种身份、在何种场景下使用了数据。
  • Snowflake内置不可变审计追踪，并提供AWS原生的365天不可变审计能力。
  • Access History能够完整记录：
  1. 访问主体是人员还是AI；
  2. 访问发生的时间和位置；
  3. 使用了什么身份、角色和方式；
  4. 访问了哪些数据；
  5. 相关数据如何被下游流程使用。
  • 当监管机构或企业内部审查需要追溯某项数据是否被某个人或某个AI使用时，可以直接通过审计记录获得答案。

3. 面向AI与智能体的安全治理能力

a) Snowflake如何针对智能体访问数据实施差异化控制？

  • Snowflake引入了面向智能体的数据治理能力，使访问策略具备情境感知能力。
  • 系统不仅识别最终用户身份，还会判断当前请求是否由智能体参与执行。
  • 数据所有者可以基于数据标签配置智能体专属策略，例如：
  1. 人类在具备权限时可以查看原始数据；
  2. 智能体访问同一数据时只能看到脱敏结果；
  3. 任何被标记为PII的数据都不得提供给智能体；
  4. 即使调用智能体的用户本人具备权限，也可以禁止数据进入智能体上下文。
  • 智能体身份控制是以数据为中心的。数据所有者可以直接定义某类数据在什么情况下能够被人类、应用或智能体访问，而不依赖智能体自身是否愿意执行。

b) 什么是受限会话，它如何缩小智能体权限？

  • 受限会话可以理解为在特定情境下生效的会话级访问策略。
  • 用户或智能体连接服务后，平台可以进一步缩小其实际权限范围，包括：
  1. 限定可以访问的数据库和数据对象；
  2. 限定读写操作范围；
  3. 限定可使用的主要角色和次要角色；
  4. 禁止激活权限过高的角色；
  5. 限制智能体只能使用获得明确授权的角色。
  • 即使用户配置了大量角色，智能体在实际运行时也只能使用策略许可的角色。
  • 该机制能够避免智能体继承用户全部权限，从而降低权限扩大和横向数据访问风险。

c) 为什么确定性、强制性的控制比单纯依赖模型拒答更可靠？

  • Snowflake将核心数据保护策略定义为“确定性”和“强制性”控制。
  • 确定性
  1. 策略可以被评估、测试和验证；
  2. 不依赖大语言模型的概率判断；
  3. 相同条件下能够稳定产生相同结果。
  • 强制性
  1. 策略位于智能体边界之外；
  2. 即使智能体受到提示词注入或越狱诱导，平台策略仍会生效；
  3. 即使智能体主动请求敏感数据，底层数据层也会阻止数据返回。
  • 例如，攻击者即使要求智能体披露他人的护照号码，智能体即便尝试发出查询，数据治理策略仍会阻止该信息进入智能体上下文。

d) Snowflake如何处理提示词注入和越狱风险？

  • 除确定性的数据层控制外，Snowflake还提供运行时AI治理和Guard能力。
  • 系统会分析用户与智能体之间的交互，识别：
  1. 提示词注入；
  2. 越狱尝试；
  3. 诱导智能体绕过安全规则的指令；
  4. 可能导致敏感信息不当使用的交互。
  • 该能力包含一定概率判断，因此不能替代数据层的确定性控制，但可以作为额外防线。
  • 相关功能可以通过目录设置统一启用，并覆盖Snowflake中的AI服务、代码生成工具和智能体。

e) 如果敏感数据由用户主动输入提示词，平台如何保护？

  • 即使平台已经阻止敏感数据从数据库流向智能体，用户仍可能无意中在聊天提示中输入：
  1. 护照号码；
  2. 身份证号码；
  3. 出生日期；
  4. 客户编号；
  5. 其他敏感信息。
  • 敏感数据保护能力可以在运行时检测用户输入中的敏感内容。
  • 默认处理方式是拒绝接收相关数据，并防止其再次出现在后续结果或列表中。
  • 这一能力解决的是“用户把敏感信息输入AI”的风险，与“AI从数据库读取敏感信息”的治理形成互补。

f) Snowflake如何利用AI提升治理效率？

  • Snowflake提出“技能化数据治理”概念，即利用经过治理专家配置的AI技能协助完成安全与治理任务。
  • 当用户提出治理问题时，技能化治理能够：
  1. 使用正确的数据上下文；
  2. 调用企业内部最佳实践；
  3. 结合主题专家确认的最新规则；
  4. 帮助生成或简化分类、标签和访问策略；
  5. 降低复杂策略的编写和维护门槛。
  • Copilot可根据自然语言需求自动生成分类标签、Classification Profile和Masking Policy，用户无须手动复制、粘贴大量代码。
  • AI负责提高效率，但最终保护仍由可测试、可强制执行的平台策略完成。

g) Snowflake未来如何提供AI资产的统一治理视图？

  • Snowflake正在开发面向AI的数据治理仪表板，会议口径为计划于Q2推出，并将先开放预览。
  • 仪表板计划提供端到端视图，覆盖：
  1. 企业生态中的所有智能体；
  2. MCP服务器；
  3. AI服务和应用；
  4. 后续接入平台的其他AI资产。
  • 其目标是让企业统一掌握AI资产、数据访问关系、治理状态和潜在风险。

4. AI治理演示与统一访问控制效果

a) 语义视图如何限定智能体能够访问的数据范围？

  • 语义视图用于定义一组可供智能体使用的数据元素和业务模型。
  • 智能体只能查询语义视图范围内的数据，无法访问模型之外的数据。
  • 企业不需要为不同用户分别建立大量语义视图，而可以：
  1. 使用一个语义视图定义统一数据模型；
  2. 根据执行智能体的最终用户身份动态应用访问权限；
  3. 通过受限会话进一步缩小访问范围；
  4. 配置智能体专属的细粒度访问策略。
  • 最终访问范围由“语义模型范围、用户权限、智能体身份、会话限制和数据策略”共同决定。

b) 实时数据分类、标签和策略应用的演示结果如何？

  • 演示环境中的原始数据最初没有标签，也没有受到保护，其中包含姓名、地址等敏感信息。
  • 运行数据分类后，Snowflake自动识别相关字段，并应用语义标签。
  • 系统进一步将语义标签映射到企业内部敏感数据分类体系，并自动应用保护策略。
  • 策略生效后：
  1. 姓氏等字段被哈希处理；
  2. PII字段被遮盖；
  3. 不同敏感级别采用不同保护方式；
  4. BI人员仍可在不获取原始敏感信息的情况下进行分析。
  • 借助技能化治理，原本复杂的策略被简化为更易理解和维护的逻辑。

c) 数据血缘如何帮助识别治理缺口？

  • Horizon能够自动构建从原始数据到报表、语义模型及智能体的完整数据血缘。
  • 用户可以看到：
  1. 数据来自哪张源表；
  2. 经历了哪些转换；
  3. 被哪些语义模型使用；
  4. 被哪些智能体访问；
  5. 最终流向哪些报表或应用。
  • 如果下游数据尚未分类，但其来源与已识别的敏感数据相似，系统会主动提示该数据可能需要分类和保护。
  • 数据血缘不仅用于展示关系，还可以辅助发现未标记数据、追溯数据质量问题并定位根因。

d) 平台策略如何阻止智能体泄露客户信息？

  • 演示中，智能体被要求展示5位客户的姓名和电子邮件。
  • 当请求由没有相应权限的用户发起时：
  1. 智能体执行了查询；
  2. 智能体本身并未主动拒绝；
  3. 底层平台策略阻止了数据返回；
  4. 用户最终无法看到敏感信息。
  • 当使用具备相应权限的用户登录时，系统可以正常返回相关数据。
  • 该结果说明，是否返回数据由平台权限和数据策略决定，而不是依赖智能体自行判断。

e) 如何验证智能体无法使用高权限角色绕过控制？

  • 演示中，平台限定智能体只能使用被授权的特定角色访问数据仓库和数据库。
  • 从智能体技能中移除高权限角色后，即使管理者本人具备更高权限，智能体也无法连接目标系统或访问受限数据。
  • 重新应用策略后，智能体虽然继续按照指令尝试访问姓名、地址等数据，但整体结果控制仍阻止了数据返回。
  • 该机制证明，平台能够在智能体边界外强制控制角色、会话和结果输出。

f) 该能力如何实现对人类和AI的统一治理？

  • Snowflake将传统数据治理能力复用于AI场景，形成统一控制体系：
  1. RBAC控制基础角色权限；
  2. ABAC根据用户和环境属性动态授权；
  3. 上下文治理识别访问主体是否为智能体；
  4. 语义模型限制可查询的数据范围；
  5. 受限会话进一步缩小角色和数据权限；
  6. 标签和策略对人类、应用和AI统一生效；
  7. 审计系统统一记录人类和AI操作。
  • 企业可以在同一套数据治理框架下实现数据自动化，而不需要分别建设一套“人类治理”和一套“AI治理”体系。

5. 真正开放的数据架构与Apache Iceberg互操作性

a) 为什么只采用开放数据格式，不代表数据仓库真正开放？

  • Apache Iceberg作为开放表格式，在2024年获得企业广泛关注。
  • 但仅开放底层数据格式并不足够，企业还必须关注Catalog和访问接口是否开放。
  • 如果底层采用Iceberg，但Catalog仍然是专有且封闭的，可能产生两类问题：
  1. 其他引擎能否访问数据，仍由专有Catalog厂商决定；
  2. 企业仍然面临厂商锁定和高昂迁移成本。
  • 真正开放的数据湖需要同时具备：
  1. 开放的数据存储格式；
  2. 开放的Catalog规范；
  3. 标准化访问接口；
  4. 多引擎双向读写能力；
  5. 可迁移、可替换的计算选择权。

b) 企业过去常见的数据仓库架构存在哪些问题？

  • 完全依赖开源技术自建
  1. 初期看似成本较低；
  2. 企业级运维、治理和规模化推广非常复杂；
  3. 可能需要数十人甚至上百人的团队维护；
  4. 数据治理容易分散。
  • 采用封闭式数据仓库
  1. 使用体验较为方便；
  2. 容易形成vendor lock-in；
  3. 当技术发生重大迭代时，迁移成本和迁移周期显著增加。
  • Snowflake希望提供第三种选择：既采用开放基础架构，又通过统一Catalog提供企业级治理，不再要求企业在开放性和易用性之间二选一。

c) Snowflake如何通过Iceberg、Polaris和Horizon构建开放架构？

  • Snowflake开放架构分为3层：
  1. 底层使用Apache Iceberg等开放Storage Format；
  2. Catalog层采用开源Apache Polaris和REST Catalog标准；
  3. 治理层由Snowflake Horizon Catalog提供企业级治理。
  • Apache Polaris已经进入Apache基金会体系，并由Snowflake、SAP、谷歌、微软等厂商和社区成员共同参与。
  • Polaris未来计划支持更多开放表格式，包括Delta、Hudi等，并继续扩展联邦、审计、策略及策略交换能力。
  • 该架构能够让企业保留计算引擎选择权，必要时可以迁移或离开某个平台，避免vendor lock-in。

d) Snowflake开放架构可以接入哪些计算引擎？

  • 只要符合开放Catalog规范，Snowflake、Spark、Trino、Databricks等引擎都可以对同一份开放数据进行组合式操作。
  • Snowflake已逐步支持多个外部引擎读取和写入Polaris Catalog。
  • 企业可以根据不同工作负载的性能和成本需求选择计算引擎，而不必复制数据或被绑定在单一平台。
  • Snowflake需要依靠具体使用场景和计算性能赢得客户，而不是依靠封闭接口限制客户选择。

  4. 支持跨引擎双向读写及Schema变更；
  5. 数据孤岛和平台割裂显著减少。

6. 多引擎环境下的统一治理与策略执行

a) 为什么多引擎和多Catalog环境会加大治理难度？

  • 大型企业往往同时拥有多个Catalog，例如Unity Catalog、自建Polaris或其他目录系统。
  • 如果每个Catalog分别维护访问策略，将产生：
  1. 策略重复配置；
  2. 运维复杂度上升；
  3. 不同引擎之间策略不一致；
  4. 外部访问时敏感数据暴露风险；
  5. 人类和智能体访问行为难以统一审计。
  • 在AI时代，大量智能体会通过大语言模型访问数据。如果治理能力只能覆盖单一计算引擎，将成为企业级AI部署的重要瓶颈。

b) Horizon如何让治理策略跨引擎持续生效？

  • 标签、脱敏策略和访问控制策略会随数据及其下游衍生过程持续传递。
  • 无论数据通过Snowflake、Spark、Databricks或其他引擎读取，只要访问经过Horizon Catalog，相应策略都会被强制执行。
  • Snowflake支持：
  1. ABAC属性访问控制；
  2. RBAC角色访问控制；
  3. 动态脱敏；
  4. 行列级策略；
  5. 面向智能体的情境策略。
  • 针对外部负载，Snowflake提供面向Spark的Connector，以及面向其他场景的SQL Scan等技术能力。
  • 外部引擎获取到的是经过策略过滤和脱敏后的数据，而不是绕过治理的原始数据。

c) Copilot如何帮助创建分类和脱敏策略？

  • 演示中，用户通过自然语言要求系统查找HR Schema中所有与PII相关的列。

  • Copilot自动生成并应用策略，无须用户手动编写或粘贴代码。

d) 外部引擎读取Snowflake数据时，治理是否仍然有效？

  • 演示中，Databricks通过Catalog读取Snowflake的HR表。
  • 即使查询由Databricks发起，Snowflake定义的脱敏和访问策略仍然生效。
  • 这说明治理不是只在Snowflake查询界面中生效，而是在Catalog和数据访问层面统一执行。
  • 企业因此可以在开放多引擎架构下，同时保持一致的安全和合规标准。

e) 血缘分析和根因分析如何提升日常运维效率？

  • 传统监控通常只能告知数据质量或Pipeline出现了问题，但无法快速指出问题来源。
  • Snowflake除提供告警外，还能够：
  1. 建立端到端数据血缘；
  2. 定位问题影响了哪些下游表、视图、报表和智能体；
  3. 追溯数据质量问题的根因；
  4. 辅助运维人员快速定位源头并处理。
  • 这一能力将治理从“发现问题”提升到“追溯并解决问题”。

7. 企业构建可信AI的总体实施路径

a) 企业应如何确保数据和AI处于可信、可控体系内？

  • 企业需要持续建立以下闭环：
  1. 发现全部数据资产；
  2. 自动分类敏感数据；
  3. 为数据添加语义标签；
  4. 根据标签自动应用访问与脱敏策略；
  5. 对人类、应用和智能体统一执行策略；
  6. 限制智能体的角色、会话和语义模型范围；
  7. 检测提示词注入、越狱和敏感输入；
  8. 记录完整访问历史和数据血缘；
  9. 持续识别治理缺口并自动修复。
  • 核心原则不是默认信任AI，而是持续验证AI和人类如何使用数据。

b) 企业应如何兼顾AI创新、业务保护和开放架构？

  • 在业务层面，应把治理作为AI创新的前置基础和加速器，而不是项目落地后的附加核查项。
  • 在安全层面，应将关键控制放在智能体边界之外，避免过度依赖大模型自身的拒答能力。
  • 在数据层面，应通过统一Catalog管理内外部数据，并确保标签、策略和审计能力随数据流转。
  • 在架构层面，应同时选择开放数据格式和开放Catalog，保留计算引擎切换及迁移能力。
  • 在运营层面，应利用AI和Copilot提高分类、策略生成和安全分析效率，但最终仍由确定性平台策略强制执行。
  • Snowflake的总体目标是：让企业在不担忧数据泄露、权限扩大和平台锁定的情况下，持续构建和部署新的AI应用。
