纪要总结

1. 算力资源战略与分配

  1. TPU内外部供给是否存在资源冲突，如何影响内部业务？
  • 冲突已实际发生。公司优先保障模型训练任务和外部客户供给，因为近期签订了许多大型合同（如Meta为其员工私有化部署Cloud Code）。
  • 为应对TPU卡供应不足，内部部分业务已转向使用GPU。例如，搜索业务中部分产品在1-2个月前开始租用Oracle或CoreWeave的GPU，这是多年来首次。
  • Gemini模型因其网络连接的重要性，仍需使用TPU机柜方案（即使是v4旧版本），其性能远优于单机配置多张H100/H200的方案。
  1. Gemini模型是否也因算力不足而转向GPU？
  • 是的，部分Gemini小模型已开始在云上使用GPU。小模型转换较容易，因可在单卡运行或利用现有多种机柜方案。
  • Gemini Pro模型因改造工作量大，尚未采用GPU。

2. B端业务模式与市场策略

  1. 优先服务B端客户的策略是否明智？
  • 这是在当前计算卡普遍不足下的必然选择。
  • Cloud Code等服务的价格高昂（如英伟达每人每月1万美元），对大企业而言不可持续，因此私有化部署成为主流解决方案。
  • TPU因其高性价比，非常适合为大客户（如Meta、苹果）提供固定价格的私有化部署（provisioned instance），能有效解决企业成本痛点。
  1. C端Gemini体验卡顿是否与算力不足有关？
  • 是的。主要原因有二：一是企业端用量巨大占用了大量资源；二是目前正在为即将发布的新模型进行大规模测试。用户遇到的卡顿或智能水平下降，也可能是被纳入了某个模型的测试组。
  1. 谷歌的策略是优先 확보 B端客户粘性，而相应调整C端优先级吗？
  • 是的，该策略主要针对B端。C端用户每次对话的Token消耗量不大（约2-3k），整体算力充足。
  • B端的核心痛点在于Cloud Code等应用价格昂贵，谷歌通过提供私有化部署（provisioned instance）和固定费用模式来解决，以保障客户粘性和持续营收。
  1. 大企业选择大模型API时主要考量什么？
  • 数据位置是首要因素：在各家模型能力差异不大的前提下，客户的数据存储在哪里是决定性因素。例如，数据在AWS上的客户除非收到极具吸引力的offer，否则迁移意愿不强。
  • 价格优惠：GCP因当前算力紧张，已不像过去那样会为吸引客户迁移而提供大幅度优惠。
  • 分成模式优势：GCP按售价分成（谷歌20%，开发者80%），相比AWS基于利润的分成模式更有优势，因此在算力可用时，系统会优先将流量路由至GCP。
  • 安全性：对于私有化部署，价格和安全性是客户最重要的考量。

3. 技术能力与竞争壁垒

  1. 谷歌在Coding能力上是否落后，这个差距未来能否弥补？
  • 目前存在差距。Anthropic在该领域有约半年的先发优势。
  • 数据飞轮效应有限：在企业级Coding Agent领域，由于客户数据隐私政策，评估团队无法直接访问企业客户数据，只能进行统计层面的分析（如工作流失败率、特定技能成功率等），因此数据飞轮的效用受限。
  • 差距可以弥补：由于数据飞轮效应有限，Coding能力的差距属于模型能力范畴，通过投入时间和资源可以追赶。
  1. 未来大模型竞争的关键是什么，TPU和GPU谁更有优势？
  • 竞争核心转向Inference（推理）：当前各家模型能力和方法论趋同，竞争的关键已从模型本身转向Inference基础设施的效率、灵活性和利用率。OpenAI的API价格高昂，部分原因在于其Inference效率不高（如KV cache无法有效移出，导致batch size受限）。
  • 新范式对硬件提出新要求：当前模型范式已从纯粹的Reasoning（算力密集）转变为频繁调用外部工具，这意味着大量计算发生在TPU/GPU之外，对通讯能力要求极高。
  • TPU的优势：
  1. 连接性强：每张卡可直连4张卡，在进行张量和流水线并行时优化空间更大。
  2. 并发通讯能力：可同时处理MoE模型带来的随机、中等规模通讯，以及KV cache移出产生的大规模、高带宽通讯。
  3. 成熟的软件栈：谷歌已实现streaming方式，可高效、可靠地（事务性保障）将KV cache移入移出HBM，而英伟达尚需依赖第三方开发相应软件栈。
  4. 总结来说，硬件迭代的关键方向是什么？
  • 是的，当前最重要的两个硬件迭代方向是：
  1. 如何更好地解决MoE等带来的随机、杂乱的通讯问题。
  2. 如何实现高频、可靠（无丢包）的KV cache输入输出。
  3. 谷歌在infra和eval上有何优势？
  • 业界普遍认为，尽管谷歌产品迭代速度较慢，但在基础设施（infra）和模型评估（eval）体系上，相比竞争对手有明显优势。

4. 商业化与市场格局

  1. 云服务（Provisioning）和API销售两种模式，收入和毛利差异多大？
  • API模式毛利极高：纯API业务毛利率约为85%，是一种非常稳定且经过精密计算的盈利模式。
  • Provisioning模式毛利较低：作为一种面向大客户的“批发”模式，毛利率低于50%。尽管利润率较低，但为服务大客户必须提供。
  1. To B AI市场的最终产品形态是什么？TAM应如何估算？
  • 市场分化：
  1. Coding场景：因程序员间Token消耗量差异巨大，必然采用按Token计费模式。
  2. Office办公场景：使用模式相对固定，Token消耗量可控，将延续按用户数订阅的模式（如Office 365 Copilot），TAM可按“用户数 x 订阅费”估算。
  3. 未来B端和C端的竞争格局如何？
  • B端：
  1. 核心是产品能力和性价比：用户粘性不强，一旦能力跟上，竞争将转向性价比和平台易用性。
  2. Office场景是“围墙花园”：原生工具（如Copilot）具备私有API和深度集成优势，第三方产品难以切入。
  3. 未来壁垒在基础设施：模型本身不再是强壁垒，谁能提供更高效、更便宜、更易用的基础设施，谁就能赢得客户。
  • C端：
  1. 盈利困难：纯聊天产品难以直接盈利，未来可能通过优化广告投放（如Google Ads）等方式变现。
  2. 竞争在于独特价值和产品体验：关键在于谁能解决别人无法解决的独特问题，并提供更好的终端产品体验。

5. 谷歌具体业务展望

  1. 谷歌在产品功能创新上会落后吗？
  • 行动速度较慢：大公司流程（先写文档再执行）导致产品交付速度慢于创业公司。
  • B端有望追赶：B端市场尚不成熟，凭借硬件和基础设施优势，谷歌仍有机会通过推出有价值的新产品来追赶和稳定市场份额。C端市场因用户粘性高，追赶难度较大。
  1. 搜索广告19%的增速是否可持续？
  • 前景不明朗，但有积极因素。
  • 增长动力：整体搜索量和用户对话轮数仍在增长；通过聊天内容优化用户画像，提升了广告精准度。
  • 新增量：Chrome未来将由IMU驱动，可直接在占搜索总量20%的入口中投放广告，带来增量。
  1. C端“最后一公里”系统打通进展如何？
  • 模式重，进展慢：该方向需要与各服务商逐一谈判集成，即使是谷歌自身进展也比较缓慢。
  • 不会放弃：尽管困难，但一旦成功将构筑极高的护城河。I/O大会上会宣布一些已完成的集成项目（如Spotify等），并计划推出SDK以期加速安卓应用的自动集成。
  1. I/O大会会有哪些亮点？
  • 主要是按计划发布的内容，包括Agent、新模型和许多个性化功能。
  • 与三星合作的眼镜项目（耳机功能是亮点）计划今年开始销售。
  • 一句话修改视频剧情的功能可能延迟发布。

新版prompt提炼之后的转译

您之前提到TPU的内部需求约为每年1000万张卡，但近期谷歌云大会上表示超过一半的TPU将提供给外部客户。考虑到今年的产量预计为400万至500万张，明年约为700万张，如果大部分供给外部，Gemini的内部使用是否会受到影响，是否存在资源冲突？

这种情况确实已经发生。大约1至2个月前，搜索业务中相当一部分产品开始使用GPU，这在过去多年是从未有过的。由于谷歌自身的GPU数量有限，这些GPU主要通过Oracle或CoreWeave租用。推荐系统对算力要求不高，因此可以使用这种方案。然而，Gemini模型仍然需要TPU机柜方案，即便是TPU v4这样的旧版本，因为其网络连接至关重要。这种机柜方案的性能远优于单台主机配置4张H100或H200卡的方案。

所以，搜索业务转向使用Oracle的GPU，的确是因为TPU卡供应不足吗？

是的。目前公司的优先策略是保障训练任务，同时优先供给外部客户，因为近期签订了许多大型合同并开拓了新的合作模式。例如，公司正在为大客户尝试Cloud Code的私有化部署，其中Meta是首个大型TPU订单客户，用于为其员工部署私有Cloud Code，该合作于2至3周前宣布。当前市场需求非常旺盛，因此TPU的供给优先级完全倾向于Gemini（对内及对外）和外部企业用户。而内部的推荐、广告等业务则开始转向使用GPU。

您提到Gemini的推理需要机柜方案，请问此处的机柜方案是指TPU还是GPU？

我所说的机柜方案均指TPU。不过，据我了解，Gemini的小模型已经开始在云上使用GPU。Gemini Pro模型尚未采用GPU，因为相关改动较大。小模型通常在单卡上即可运行，或可利用谷歌现有的各类机柜方案，因此转换较为容易。

所以，部分Gemini小模型也转向使用GPU，同样是由于类似搜索业务所面临的算力卡供应不足问题？

在您看来，这种优先服务客户的策略是好的吗？

这可能是一个不得不采取的策略，因为目前计算卡本身是不足的。此外，大家使用 Cloud Code 的花费非常高。以英伟达为例，他们现在每人每月的 token credit 大概是 10k，即 10000 美元一个月，这个花费很高，其他公司的情况也类似。因此，现在大家倾向于针对大企业进行 Cloud Code 的私有化部署，因为如此高的价格是不可持续的。

而 TPU 正好是目前性价比非常好的方案。通过做 provisioning，企业能以固定的价格运行 Cloud Code。例如，Meta 大概有超过 70000 个 API key 供员工使用，苹果则有超过 200000 个。这些都是非常大的客户。所以，目前对于这类大型应用，进行私有化部署的优先级放在了企业客户这边。

我个人体验感觉 Gemini 目前使用起来特别卡顿，这是因为计算卡不足的原因吗？

是的。有些人反映的智能水平下降问题，也与此相关。一方面是因为企业端的用量比较大；另一方面，目前正在为发布新模型进行大规模测试，这将在未来几周内进行。因此，您遇到的情况也有可能是因为您被纳入了某个模型的测试组中。

所以我的理解是，目前面向 B 端客户的 API 私有化部署是一个很大的市场，因此谷歌希望优先 확보这部分客户的粘性以产生持续营收，而 C 端 Gemini 的需求则相应地调整优先级？

是的，这主要针对 B 端。C 端的情况完全不同，在 C 端，每次对话大约只需要 2k 到 3k 个 token，整体算力是充足的。问题主要出在 B 端，因为企业都希望使用 Cloud Code，但其价格非常昂贵。同时，其他一些方案，例如某些 5.4 或 5.5 版本的模型，其价格比 Cloud Code 还要贵几倍，这远超企业可接受的范围。大家都在试图解决这个成本痛点。

目前针对大公司的解决方案是提供 provisioned instance。像 Meta、苹果这类大公司就是采用这种模式。例如，一个公司有数万个席位使用 Cloud Code 或 Cloud Co-work，我们会为其提供 provisioned instance，客户只需支付一笔固定费用。然后 Google 和 Anthropic 进行分成，这种模式对双方都更有保障。

在进行 B 端私有化部署时，客户通常会考虑哪些重要因素？除了您刚才提到的价格之外，还有其他因素吗？

价格和安全性都非常重要。以 Google GDM 和 Google Lab 为例，我们使用的也是私有化部署。后来我们发现许多客户也有同样的需求，因此 GCP 有一个专门的团队通过 Cloud Code 为大客户提供私有化部署，以增强安全性。

这是部署云时的考量。如果客户选择 API，他们会考虑哪些因素？

选择 API 时，会涉及自动路由（routing）机制。Cloud Code 提供命令行选项，例如通过 `dash by the Rock` 或 `dash Vertex AI` 来指定运行位置。如果不进行指定，系统会自动进行路由。

GCP 的分成模式非常有优势，它不按利润分成，比例也较低。因此，在有可用算力的情况下，路由会优先导向 GCP。相比之下，AWS 的分成是基于利润的。所以，对于不通过命令行指定运行位置的普通中小用户，系统目前倾向于将流量路由至 GCP。

能否具体说明这两种分成模式的差异？

两者差别很大。根据我 1-2 个月前了解到的信息，虽然最新情况可能有变，但调整幅度应该不大。

GCP 的模式是按售价分成，Google 分走 20%，开发者保留 80%。这指的是 public API 的价格。对于像 Meta 这样的私有化部署，折算成 token 成本后，价格基本上能做到公用 Cloud Code API 的 1/5，这是一个多数客户可以接受的水平。

而 AWS 与 Cloud Code 则是利润对半分成。

对于大型企业客户（例如银行），在选择对接具体哪家的大模型来构建内部 API 之前，他们的主要考量是什么？

对于普通应用，各家模型在能力和工具链上的差别并不显著。因此，客户首要的考虑因素是他们现有数据的位置。例如，如果一个客户的所有数据都在 AWS 上，他们通常没有动力迁移，除非收到一个非常有吸引力的 counter offer。

不过，GCP 目前算力紧张，已经不像过去算力充足时那样，会为了吸引客户迁移而提供大幅度的价格优惠。现在基本是有多少算力就能卖出多少。

总结来说，对于纯 API 的选择，在模型能力差别不大的前提下，客户主要关注两点：一是现有数据存储在哪里，二是有没有优惠的 offer。

而在 agentic flow 方面，由于 Google 的新产品尚未发布，而 OpenAI 的价格过高且其模型并非在所有云区域都可用，客户会有其他的倾向。

分析师：展望未来，例如到今年底或明年，我们应该如何理解这个coding能力的差距？这是一个投入时间就可以弥补的差距，还是说由于数据飞飞轮效应，这个半代或1/4代的差距在长期来看可能会持续存在？

专家：首先，Anthropic在该领域比Google和OpenAI早启动约半年时间，这使他们具有先发优势。由于各方迭代速度都很快，追赶需要时间。

其次，关于数据飞轮效应，在企业级Coding Agent领域的体现与消费端产品有很大不同。在消费端产品中，数据经过敏感信息处理（例如屏蔽身份证号）后，大部分内容如聊天记录、用户反馈等对评估团队是可见的。

然而，对于Coding Agent，情况则不同。根据Google的政策，所有来自使用API Key的大型企业客户的数据都会被屏蔽。评估团队无法直接利用这些数据来推导评估用例。因此，数据飞轮的效用主要体现在统计层面。团队可以分析哪些类型的工作流更容易收到负面反馈，或者统计出每个“skill”（技能）的成功率。

硬件上现在实际上是有区别的。以前大模型的范式是做reasoning，纯拼算力，比如16个size的batch，绝大部分时间模型就是不停地自己去iterate各种thinking token、planning等，自己算，对外的交互不是非常多。所以，在reasoning model时代，大模型基本上能干90%的活，另外10%的活可能不是非常主流，那时对TPU或GPU以外的这种infra要求本身并没有这么高。

但现在不一样了，现在开源的里面，40分钟的一个flow平均得调用200多次工具。这说明现在大模型也许自身能力没提高，但它学会了如何delegate一些工作给TPU或GPU以外的core去做。所以，现在整个计算范式和以前完全不一样了，可能有一半或一半多一点的工作并不是在TPU或GPU里做，而是在其他部分完成。在这么一个范式里，如何去做优化，差别是挺大的。而且，最好是做模型的和做infra、做cloud的公司能够一起去做优化，这些是挺重要的。

当前大家普遍缺少内存，因此影响是相似的。在这种情况下，重点在于两方面，其一是通讯能力。TPU非常适合这种场景，因为它一张卡可以连接其他 4 张卡，其邻居也能连接 4 张卡。当一个任务在等待工具输入时，如果想将 KV Cache 从当前机柜复制出去，需要占用大量带宽。这与机柜内 MoE 模型的通讯存在冲突，因为 MoE 模型也需要执行大量的聚合操作，例如 all-aggregation 或局部聚合。因此，挑战在于如何在集群内同时进行大规模（几十G）的内存复制移动，以及相对中、小规模且随机的通信。

TPU 的优势在于，至少一张卡可以无阻塞地与周围 4 张卡通信。在进行张量并行和流水线并行时，其优化空间比所有节点都连接到交换机的方案要大得多。例如，TPU 可以用一条线路与周围的邻居节点传输和聚合 MoE 的一些结果，同时用其他铜缆线路来卸载当前任务的 KV Cache。这并非无法实现，但需要投入大量软件工程精力。参考 Deepseek 等相关论文，目前大家在做推理时主要优化 MoE。这是从单模型角度看的，但如果优化更高层级的流程，通讯实际上涉及两件事：一是 MoE 带来的比较杂乱的中等规模通讯，二是 KV Cache 移动产生的大量通讯。目前 OpenAI 尚未实现后者的优化。如果不能实现这一点，整个集群的利用率会低很多。

对于这些比较随机杂乱的通讯，TPU 的优势是什么？

TPU 的优势在于其每张卡的连接数量非常多。

我看到 v8 的新架构 Bordfly，它将跳数从 16 跳减少到 7 跳。虽然每张卡连接的数量有优势，但其架构方向似乎更侧重于减少最远两张卡之间的跳数，这感觉有点像英伟达的胖树架构。

是的，可能有相似之处。它主要解决的问题是数据传输，而数据传输实际上分为两种。第一种是 MoE 模型推理时，需要将一些激活值（activation）传输出去。这部分传输的数据量不一定特别大，但比较随机，无法预知需要在何处进行聚合。在这种情况下，连接路数越多越好，而带宽不一定需要非常高。第二种传输就是

新的参数之一是KV cache需要做卸载。这种方式是以前没有的，因为在vLLM等采用continuous batching的模式中，一个batch若有 16 个任务，每个任务会一直推理到结束，其KV cache会始终保留在内存中，不存在中途卸载的问题。但在当前硬件环境下，当模型调用一个工具时，该工具的返回时间非常不确定。例如，一个系统集成测试可能需要运行 2 小时才能返回结果。因此，让几十G的HBM内存在这 2 小时内一直等待是不可行的。这就需要将这几十G的内存暂时移出，存到pod（无论是NV还是TPU的pod）之外。这种对几十G内存的频繁输入输出，对整个网络架构构成了非常高的考验。

所以这是否意味着对TPU这类架构更为有利？

是的，从目前来看，TPU在这方面非常成熟，已经针对两种不同的通讯模式进行了优化。相比之下，据我了解，NVIDIA自身并未提供相应的软件栈，在通讯这部分需要依赖OPI或其他方来编写整个软件栈，因此进展没有那么快。

从技术上理解，TPU能够实现对大量内存数据的频繁输入输出，其核心机制是什么？是通过软件进行提前调配吗？

是的。我们实现了streaming的方式，系统大致知道需要加载多少KV cache来满足计算需求。当KV cache暂时不需要时，系统就能将其offload出来。例如，如果当前芯片卡的一条通路正在用于MoE计算，其余三条通路就可以被同时用来传出KV cache。

这个过程是随机的，还是说仅需要通过软件调配实现频繁的输入输出即可？

这具有一定的随机性。首先，大模型在何时决定调用工具是不确定的，这带来了随机性。其次，网络传输也存在随机性。例如，当batch size为 16 时，可能同时有几个任务在向外传输数据，另一些在向内传输。如果网络冗余度不够高，KV cache的传输就可能受阻。此外，数据传出是一个事务性（transactional）过程，不能丢失。如果KV cache在传输中途部分丢失，整个事务就失败了。若没有这种事务保障，一个执行了 100 步的agent任务所积累的KV cache可能会全部丢失，导致任务必须从头开始。目前许多优化算法在这种情况下确实会选择从头再来。

所以总结下来，当前最重要的两个硬件迭代方向，一是如何更好地解决随机通讯问题，二是如何实现高频且无丢包的KV cache输入输出。是这样吗？

是的。

您认为B端客户在不同大模型之间的迁移壁垒高吗？未来的核心壁垒会是什么？

粘性并没有那么高。竞争对手可以提供比你便宜 1/5 到 1/10 的价格，附带很多优惠条件，并帮助客户完成迁移，而整体性能也相差不大。除非客户的所有数据都深度绑定在某个平台上，否则迁移壁垒并不高。对于本身就是多云部署的B端客户而言，切换相对容易。因此，模型本身已不再是特别大的壁垒，未来基础设施层面的壁垒会更关键。

对于一个具体场景，比如我个人使用某个模型构建了一套自动化工作流，包含爬取论文、生成报告的脚本，如果让我迁移到另一个模型，会感觉很麻烦。在您看来，这种B端场景下的迁移是否也没有那么困难？

个人用户属于2C场景，情况比较复杂。但在2B场景，例如苹果或Meta这样的大公司，通常会签订一个整体的大合同，而不会让员工自由选择并使用所有模型。因此，这更多是一个B2B层面的决策。

未来大模型公司和云厂商之间，您认为谁的议价权会更强？

如果开源和闭源模型的性能趋于同质化，那么议价能力将更多地体现在基础设施层面，即云服务和硬件。以中国为例，虽然追赶速度很快，但目前还没有能与Claude或Codex水平相当的模型。不过凭借强大的工程能力，可能在 6 个月内就能推出性能相近的版本。届时，议价权会向基础设施方倾斜。

您提到的基础设施层，是指Nvidia GPU、TPU这类硬件吗？

是的。这包括能否优先向客户提供最新的硬件，例如有了TPU8，能否优先提供给你，这将构成非常大的优势。

那么像AWS这样的云厂商，他们的议价权是否不会很高？

目前他们的议价权非常高，因为市场普遍缺少芯片，基本上不存在市场细分，有多少算力就能卖出多少。即便是没有高速互联的老旧GPU，也可以用于推荐系统等场景，从而将更先进的算力置换给其他高价值客户。

所以他们目前的议价能力主要来源于他们获取芯片的能力？

是的。现在所有芯片都能被利用起来。我认识的许多人专门从事性能优化工作，并非因为某种方案特别好用，而是因为那是他们唯一能获得的算力，其他公司的供应都非常有限。

未来能够进行训练。

2B市场的情况可能类似于谷歌过去追赶竞争对手的经历，可能会有相当长一段时间看似追不上，但最终凭借硬件等优势还是能够稳定下来。追赶的难度不好说。目前在C端市场追赶非常困难，但B端市场不同。因为B端市场本身还不够成熟，只要能推出对用户有价值的新产品，抢占客户相对比C端要容易得多。
