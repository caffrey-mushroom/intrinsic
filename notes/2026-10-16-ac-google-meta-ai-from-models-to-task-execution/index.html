本文整理了近期分析师围绕谷歌与 Meta 的调研和思考，主要涵盖模型发展趋势与竞争格局、模型与 Harness 的协同演进、模型与产品的结合，以及 C 端产品渗透、云业务和企业 Agent的落地进展。根据公开资料整理，可能存在不全面的情形，请自担风险。

总结：

1 模型能力仍有较大的提升空间

大模型仍在继续演进，能力提升正在向长程任务、图像视频、3D、专业数据和 AI for Science 等领域扩展。成熟任务中的差距缩小，不代表整体能力已经接近上限。

长程任务的成功率仍是重要瓶颈。

Benchmark逐渐失效，后续判断不能只看 benchmark，实际付费更能反映能力是否转化为用户价值。

2 能力上限与性价比会共同演进

模型一方面会继续扩大规模，探索更高的能力上限；另一方面也会针对实际任务选择合适的尺寸，兼顾能力、速度和成本。

更大的模型继续探索能力边界，较小模型则通过训练和工程优化，以更低成本承接已有能力。模型不仅只会只追求更大，也会在合适的参数规模内持续提高效率。

Agent 尤其需要兼顾成本、速度和成功率。一次任务可能涉及多轮推理、工具调用和重试，每百万 token 的价格只能解释部分成本，单位成功任务成本更接近实际竞争力。

3 模型需要与产品和场景共同优化

通用智能提升不会自动带来好的产品。个人 Agent 需要记忆、主动性、多模态和持续执行能力，Meta 对 memory 和 focus 的投入，体现了产品目标对模型训练的影响。

模型为产品服务，产品为战略服务。先明确需求，再调整数据、训练和评测，才能形成更清楚的差异化。模型与 Harness 也需要共同演进，最终效果取决于能力、工具和执行环境能否配合。

4 应用端逐渐崛起，Agent 渗透正在推进，生态会影响竞争格局

B 端办公、内部问答等场景落地较快，复杂定制工作流仍有成本和交付难题。C 端则可能从用户自己搜索、浏览和操作，转向委托 Agent 完成任务，进而改变产品交互和部分搜索入口。

市场更可能多家并存。谷歌有办公和生活服务，Meta 有社交内容、用户关系和商家网络，大厂更容易连接已有场景；创业公司仍有产品创新和细分机会。随着算力缓解，预计谷歌也会更积极推进 C 端 Agent。

5 方向偏乐观，时机和回报仍需验证

人天然追求更省事。如果高频场景足够可靠，叠加成本下降和平台分发，C 端 Agent 可能快速普及。所以时间节点非常重要。提前投入可能承担试错和闲置成本，等待验证又可能错过窗口。后续应重点观察任务完成率、人工介入程度、主动建议接受率、留存和付费，以及每项成功任务的成本，用这些指标判断普及速度和商业价值。

一、模型进展

Argon

Argon 说明谷歌仍处于模型第一梯队，但尚未形成全面领先。其与头部模型的差距，更多体现在任务完成速度和输出可读性，而非答案正确性。SaaS 操作是较明确的优势，但优势主要来自工作流数据，长期壁垒仍需观察。模型能力仍在进步，只是编程场景的差异逐渐缩小，竞争重点更多转向效率、专业领域能力，以及模型如何带动企业业务。

  1. AA排序：Opus 5.5 Max ＞ Argon ≈ Fable 5.1 Max，Argon 整体上和 Fable 5.1 Max 接近，但与 Opus 5.5 Max 还有差距。Elo 和 Artificial

Analysis（AA）评分都低一些，实际体验的差别不一定在答案对错，更多是 Opus 输出更快、内容更好读、条理更清楚。目前公开模型中，Opus 5.5 仍处于领先位置，后续 Mythos 2 的能力可能再高一点。

  1. 确实存在针对榜单优化，除榜单外，每天也做匿名A/B测试

Argon 最初的目标是超过 Fable 5.1 Max。针对榜单优化前，它的能力介于 Opus 5 和 Fable 5.1 Max 之间；优化后，Elo 已经能超过 Fable 5.1 Max，AA评分仍略低，整体比较接近。团队每天做上万次匿名 A/B 测试，通过用户偏好形成评分，也会指定模型进行对比。

  1. 现在部分 benchmark 已经不太能反映真实体验。一方面，大家都在针对榜单做优化；另一方面，一些评测限制任务完成时间，对需要长时间处理复杂问题的模型不够友好。因此，分数高不一定意味着实际用起来更好。
  2. 速度是用户选择模型的重要因素。目前的速度排序是 Opus 5.5 Max ＞ Argon ＞ Fable 5.1 Max。Fable 5.1

的参数规模据称达到9T，模型大小和执行任务的方式都会影响速度。即使能力更强，太慢、太贵也会影响用户选择。

  1. 模型进步还没有停，只是差距出现的地方在变化。编程等领域的头部模型越来越接近，但金融、法律、3D、AI for Science 等方向仍在拉开差距。Argon 在操作 SaaS

软件上得分稍高，但还没有哪项优势明显到其他模型难以追赶。头部几家之间越来越接近，与其他实验室的差距却可能继续扩大。后续可能金融、法律等领域差距也会缩小。

Carbon：能力或优于 Organ，重点提高速度、减少任务消耗

  1. 与 Organ 来自同一批持续训练，优化重点不同。

Organ 和 Carbon 可以理解为同一训练过程中的不同 checkpoint。Organ 是中途拿出来测试的版本，Carbon 则继续训练了一个多月，并更重视效率；两者底层的预训练流水线仍在运行。

  1. 速度约 Organ 的三到五倍，主要靠减少多余步骤。

Carbon 加入了更多高效完成任务的训练轨迹，包括使用 Organ 时发现的过度思考案例，以及更直接的解决方式。目标是让模型知道哪些步骤有必要、哪些可以省略，而不是一味增加思考和验证。

  1. 对应任务花费可能明显下降

效率提升后，Carbon 完成同样任务的 token cost 约为 Organ 的三分之一乃至更低。定价尚未确定，即使每 token 单价不变，用户也可能因为执行步骤减少而花得更少。

  1. 匿名用户偏好测试据称已接近 Claude 5.5，综合跑分仍未超过。

Carbon 的跑分略高于 Organ、超过 Claude 5.1，但尚未超过 Claude 5.5；由于速度和可读性改善，匿名 Arena 的 Elo 已与 Claude 5.5 基本持平，目前暂未观察到明显牺牲边缘问题处理能力的情况。

  1. 生图能力也有提升，可能更适合直接完成办公任务（针对场景进行的优化）。

Carbon 的生图能力已接近 Banana 2.1 的 SOTA 版本，它可以在制作 PPT 或 Google Doc 时直接配图。若实际效果成立，用户拿到的会更接近一份完整成品，而不只是文字回答。

flash系列

Flash 的价值仍然是速度快、日常任务基本够用，Flash 对免费用户来说也不便宜，算力紧张时仍会被限制。

  1. 模型能力的演进大致有两个方向。

第一是继续提升 SOTA 能力，通过增加参数、数据和训练计算，继续推动 Scaling Law，解决更加复杂和开放的问题。

第二是提高模型的性价比。通过更高效的架构、数据和训练方法，让较小的激活参数量获得较强的能力，再通过更低的推理计算量，把这种能力转化为更低的价格和更高的吞吐。

当前大模型训练仍然存在较大的效率提升空间。比如一个学生需要做十道题才能学会一个知识点，更好的训练方法就像一位更好的老师，让学生做更少的题也能掌握同样的知识，甚至学得更深。对应到模型上，就是用更优的架构、数据和训练方式，提高每一份参数和数据的学习效率。

谷歌认为现有的Flash优势核心来自架构、以及AI改进模型更容易先在小模型上验证。

我们之前讨论的一个重点是AI提升模型研发效率。中小模型的训练成本更低、周期更短，可以同时测试大量优化器、数据配方和训练参数。大模型的单次实验更贵，反馈周期更长，一项方法在训练早期有效，也可能在长期训练后失效。因此，AI自动搜索出来的新方法通常要先在小模型上初筛，再逐步放大验证。

RSI这里是指自迭代优化器，并称其改变了传统的参数优化方式，最早在 Flash 3.8 的中间训练或后训练中尝试，之后用于 Organ 和 Carbon的预训练。大模型使用自动优化器仍有失败风险。优化器基于一批批数据作出调整，可能判断错误，也需要能够自行修正。参数量越大，调整错误后恢复的难度可能越高。团队仍然要不断取 checkpoint测试、淘汰失败版本，因此自动优化不等于不再需要大量实验。

  1. Flash 训练效率比较高，Flash 每一到一个半月的 AA 分数仍能提高约两到三分，提升速度比 SOTA 模型更快。不过新 benchmark 加入了更多高难度问题，会拉大 Flash

与大模型的分差，但这些问题未必经常出现在实际工作中，反过来，超大模型也可能因为无法在时限内完成而失分。榜单上的差距不能直接等同于日常使用差距。

  1. 部分用户从 Argon 转回

Flash，说明日常任务对能力的需求有上限。会议总结、文档修改、普通问答等任务，只要结果足够好，用户就会更在意速度。最强模型可能只在少数复杂问题上被调用。模型发展到现在，性价比的重要性正在上升。现有模型已经能够解决很多基础场景，但调用成本依然较高。谁能够更稳定、更便宜地解决这些问题，谁就更有机会承接大规模的企业需求。

  1. 因参数较小，所以天花板问题就比较重要，Flash 还没有明显遇到能力天花板，但需要不断调整训练目标。比如不断加强某个专业领域训练；如果始终沿着同一个目标训练，效果会逐渐收敛。
  2. Flash 约为 200B 参数，Lite／Light 只有几 B，成本差异很大。谷歌正在将部分免费用户从 Flash 引向更小的模型，为新模型及其他业务留出资源

二、算力分配（无公开数据，以下仅为毛估估，感知大致两集就好）

谷歌总算力不少，但搜索、广告、外租、消费者产品和训练都要用，真正能调给新模型的资源并不多。anthropic的训练卡大约是google的2-3倍。目前卡的资源还是很稀缺的。

  1. 毛估估下，谷歌共有 700 多万张各类 TPU，其中约 300 万至 350 万张租给 Anthropic，约 200 万张用于搜索、广告和推荐。剩余高端 TPU 中，约 100 万张支持消费者服务，DeepMind 约有

70 万张的算力池。还有约几十万张支持云的推理。从现在看，算力依旧紧缺。因卡不够，限制C端使用。

  1. 谷歌 GPU 总量约 100 万出头，大部分被大客户使用，剩余能用于内部推理。且用 GPU 支持推理还会影响利润率。
  2. 明年预期出货800-900万，缺卡情况可能得到缓解。
  3. anthropic的训练卡大约是google的2-3倍，因此能并行训练更多版本、承担更多失败尝试。
  4. Google 的 Spark 据称内部优先级很高，但受限于算力，尚未充分推出。随着未来算力释放，可能会给C端做更多供给，现在还是B端优于C端。

三、云与企业 Agent

云业务仍主要靠算力租赁，企业 Agent 增长快，但基数小。B端agent的场景落地较快。

  1. 收入结构：租赁仍是大头，企业 Agent 渗透较快

目前云业务收入仍主要来自算力租赁。企业 Agent 刚开始普及，基数小，增长率可能达到数倍，但绝对规模还不能与租赁相比。

  1. Enterprise Agent：在系统和权限比较统一的环境中，更容易落地

Enterprise Agent 的一个重要能力是自己找上下文。比如授权google workflow，在用户授权范围内，它可以找出 Chat 中尚未回复的讨论串，再自行查找CRM、文档和会议纪要，提出回复建议，用户不需要逐条复制材料。主动发起可以更好。

谷歌的优势不只在模型，也在已有的办公生态。比如每个google doc都有一个隐藏的MD文件，agent可以直接接入，并提供内部接口、索引，这是便于 Agent 读取的文档格式。模型因此更容易找到信息，也更容易把任务执行下去。

外部公司即使用能力相近的模型，也未必能直接复现这套体验，需要补齐系统接入、文档处理和执行流程。目前更准确的理解是接入和适配成本较高，而不是其他模型完全无法使用谷歌生态。

  1. 定制 Agent：需求不少，但成本和维护还不容易控制

谷歌正在增加部署和实施人员，帮助企业把模型接入实际业务，说明定制需求不少，也说明这些项目目前还不能完全标准化交付。

固定费用的产品更容易卖，客户知道每个月要花多少钱。但定制 workflow 如果按 token 收费，成本就很难提前估计。看起来相似的任务，模型可能走不同的执行路径，token 消耗有时相差十倍。即使抽样一批任务，也未必能准确预测未来费用。

企业上线后，更换模型也不容易。原有工作流已经围绕特定模型完成集成、测试和验收，换模型可能需要重新适配工具、调整执行流程，再做一次测试和验收。因此，B 端客户的粘性很大程度上来自整套工作流，后续维护成本也不能忽略。

  1. 谷歌云增速

整体来看，谷歌云的增长仍然非常快。公司正在将部分原有软件团队转向客户部署和实施，以及扩充FDE人才，以满足客户需求。目前收入增长仍主要靠算力租赁，企业 Agent则是增速更快、但基数较小的一部分。短期的主要限制仍是算力供给和交付能力，而不是需求不足。

核心判断 google：

1.      模型还会继续变大，但实际使用会向合适的尺寸分化。 前沿模型继续追求能力上限，日常任务则要兼顾速度和成本。1—2T 参数可能是一个比较平衡的区间，既能处理更多 corner case，也不至于太慢、太贵。未来不同任务会使用不同规模的模型，不会所有场景都用最大的。

2.      模型效率还有很大的提升空间。 Carbon 在继续训练一个多月后，主要通过优化任务轨迹、减少不必要的步骤，就明显改善了速度和消耗。这说明当前大模型的效率还比较低，不完全是参数规模决定的，也与训练目标和做事方式有关。当然，关键不是多训练一个月，而是这一个月针对什么进行优化。

3.      “模型即产品”，模型需要围绕实际使用场景来优化。 用户选择模型，不只看智能，也看速度、成本和细节体验。回答是否好读、图表是否好用、能否直接完成一份文档，都会影响选择。比如 Carbon 在 Google Docs 中可以直接配图，就比只输出文字更接近用户需要的结果。智能差距缩小时，这些体验差异会更重要。

4.      前沿模型的进步还是很快的，只是差距出现的地方在变化。 Coding 等成熟领域的头部模型越来越接近，竞争更多转向速度、可读性和成本；3D、AI for Science 等复杂场景仍可能拉开差距。通用任务的体验趋同，不代表前沿能力已经没有提升空间。

5.      谷歌目前的模型路线仍有些被竞争对手牵着走。 感觉一直在补齐短板和打榜，差异化还没有完全想清楚。

6.      算力补齐后，谷歌 C 端 Agent 的推出和放量可能会加快。 目前不少产品已经在准备，算力是一个直接限制。供给改善后，谷歌应该会更快把产品推向用户。但能否持续使用，仍取决于产品是否解决了高频需求，以及单用户成本能否控制住。

7.      谷歌做 Agent 的优势也挺明显，在于已有的服务生态。 如果能够通过 API 打通邮箱、云盘、日历、地图及支付等服务，很多任务应该会比模拟浏览器操作更快、更稳定。谷歌有机会把这些服务直接连接成完整流程。

8.      谷歌目前更多是在打安全牌。 一边把 TPU 租给 Anthropic，承接其他模型公司的算力需求；一边发展自己的模型和云业务。这样即使自家模型没有持续领先，也能从行业增长中获得收入。不过，外租与自用也在争夺资源，这种选择会影响自身模型和产品的推进速度。

9.      谷歌云的增速仍然很快，B 端 Agent 也更容易做出场景闭环。

--- meta

muse模型：Muse Wonder & Muse Wonder Full（Muse Wonder Full将开放给Muse Code的订阅用户）

一、模型的基本信息

  1. Wonder基本上跻身第一梯队模型，重点是个人和专业 Agent；Wonder Full 是更高端版本。访谈中强调的能力包括记忆、持续执行、多模态、编程，以及法律、财务等专业任务。
  2. Wonder 总参数约 450B、每 token 激活约 40B；更高端的 Wonderful 总参数约 900B、激活约 80B，两者均支持 100 万 token 上下文（非公开信息数据，仅供参考）。
  3. 产品采用多模型分工。分类、信息提取等简单任务使用小模型；研究、文档分析和商品比较使用 Wonder；Wonder Full 用于复杂编程、持续数小时的任务。
  4. Spark 承担大量免费使用，Wonder 因成本更高，初期主要面向订阅用户，并通过 API、OpenRouter 和 Muse Code 提供。管理层希望后续能把接近 Wonder 的能力放进 Spark

规格中，再扩大覆盖范围。因此，前沿模型继续变强与服务模型持续变便宜，是同时推进的。

二、模型即产品：记忆、专注、多模态和分寸感

  1. Active momery 主动记忆：跨天、跨周、跨月使用用户信息。

它不只是保存聊天记录，而是选择值得长期保留的信息，区分事实、偏好和历史任务，并在未来检索、更新。例如，记住六个月前的酒店预算、用户拒绝过哪些位置的酒店，或每周报告的固定格式，减少反复交代。

主动记忆：让 Agent 跨次交互记住并复用信息。不只是传统 RAG，而是决定记什么、何时提取、记忆是否仍然有效。包括六个环节：

a.      记忆选择：训练模型判断信息的重要性、持久性和未来用途，例如记住偏好的航空公司，而非每次查过的航班。

b.     结构化记忆：保存事实、偏好、关系和时间戳，例如用户偏好直飞。

c.      情景记忆：保存历史任务及结果摘要，例如用户因位置问题否决过三家酒店。

d.     记忆检索：结合语义搜索、结构化搜索和重排序，在新任务中取回相关偏好。

e.      记忆更新：识别变化、冲突和过期信息，例如搬家后更新居住城市。

f.       记忆感知强化学习：奖励正确使用相关记忆，惩罚误用，减少重复询问

例如场景包括：在规划新旅行时记住六个月前的酒店预算；挑选新品时沿用“180 美元以下的 Nike 跑鞋”偏好；编制周报时记住格式和固定 KPI。

  1. 主动专注：解决长任务中忘记目标、重复失败操作、遇到困难就停止的问题

它实际上是指模型在执行任务时能够贯彻始终的能力。特别是当我们看到Muse用户以及Muse Code用户提出复杂度越来越高、越来越模糊和庞大的任务时，我们希望模型能够非常有效地执行这些任务

训练对象是完整任务轨迹，而非独立问答。流程是从目标出发规划和拆解任务，调用工具及子 Agent，评估结果，再决定恢复、重新规划或继续。

包括六个环节：

a.      长周期强化学习：使用 20 至 200 步任务训练持续跟踪目标的能力。

b.     过程监督：奖励正确中间决策，减少错误层层累积。

c.      工具训练：浏览器、Python、API、文件操作等。

d.     失败恢复：训练中加入中断的工作流和意外工具返回，学习尝试替代方案。

e.      持久任务状态：保存计划、进度和 checkpoint，支持中断后继续。

f.       结果验证：对照任务成功标准检查产出，减少错误宣称已经完成。

例如，编程 Agent 遇到多项测试失败后，分类原因、修改代码、重新测试，直到达到验收要求。

典型场景包括：软件开发 30 至 180 分钟；阅读 50 至 100 个来源的复杂研究 20 至 90 分钟；旅行协调 10 至 45 分钟；数据清洗与制图 15 至 60 分钟；发票处理和审批等业务自动化 20 至 120 分钟。

  1. 其他重要能力
  • 多模态感知：图像、视频、音频、视觉理解是个人智能体的关键。

扎克伯格用 Muse 分析格斗训练视频，模型自行提取关键帧，并在休息时间内给出反馈。这个任务需要视觉理解、专业知识、编程和速度共同配合。

  • 编码能力：在 SWE-bench、SWE Marathon、TerminalBench 4 等达到前沿/SOTA 水平。
  • 专业领域能力：法律、财务、健康、税务、购物、个人建议等，像用户身边的专家团队。
  1. 分寸感和交互细节，也需要在模型中优化

比如，模型知道用户的健康情况，订餐时应据此筛选，但不应把私人信息全部告诉餐厅。语音交互中，停顿是否意味着说完、插话是不是新问题，也会影响体验。它们看起来是产品细节，最后往往都对应训练数据、奖励和评测的调整。

思考如何随着时间的推移不断改进模型，从而构建越来越好的产品。就像马克刚才提到的许多案例，这些实际上都在一个电子表格中进行了非常严谨的详细记录，涵盖了我们认为对最终用户真正重要的所有微小能力和产品细节。也许每一项细节对用户而言只占2%的体验权重，但聚沙成塔，正是这种对细节的极致痴迷，最终造就出令人感到不可思议的模型。——meta管理层播客

Muse Agent：从回答问题到代用户完成任务

  1. 定位与形态

Muse 的定位是个人执行型 Agent。用户交给它的是一个任务，希望最终拿到结果，而不是再根据回答自己操作一遍。

产品由模型、harness、虚拟机或容器等组成。虚拟机提供独立工作空间，让 Agent 操作网站、运行代码、处理文件，并在中断后继续任务。它是执行环境，用户看到的产品仍是任务入口和结果。

隔离环境有助于减少对用户本地操作的干扰，以及确保安全和隐私仍。竞争关键不只是有一台虚拟机，而是谁能以更低成本、更少监督、更可靠地完成同一任务。

浏览器是过渡性的通用接入方式，API 更适合高频执行。浏览器可以使用尚未开放接口的网站，但容易受到界面变化、登录认证和加载速度影响。库存、报价、预订和支付等流程，长期更适合直接接入 API，或由个人 Agent 与商家 Agent 交互。

  1. 应用场景与使用情况

长期目标是记住用户偏好、保持经过授权的工具连接，并持续处理重复工作。例如，每周整理报告、跟踪价格、处理文件，而不是每次都重新解释需求。

单看搜索、总结、制表，Muse 与其他产品的功能重合较多。

占任务 30% 的信息搜集和网络搜索，其中约 82% 至 85% 也可以尝试用现有搜索引擎完成。关键差别不在找到信息，而在整合信息后采取行动。Google Search、ChatGPT、Muse 都善于查找网站和事实；Muse的优势在于后台重复执行任务，传统搜索在这方面有限，其他 AI 产品也只有部分版本提供类似功能。Muse 还能填表和操作网站，Google Search本身不提供这种能力，其他产品则在部分模式中支持。它希望做好的，是从查找信息到执行操作的完整过程。

例如，用户要求读取 50 张发票、提取供应商和金额、核对参考信息、更新费用表，再邮件发送摘要给财务。其他产品能生成表格或尝试部分自动化，Muse 的目标是串联文件、浏览器、表格和邮件，减少用户手动切换。

用户节省的是下载、处理和分发整套流程的时间。Muse 还能根据保存的指令每周重复执行，交付更新好的表格或提交的报告，而不只是分析意见。

核心是不一定是最强模型，而是优先做到任务更可靠、用户介入更少、成本更

  1. meta的优势：模型、产品和生态协同

a.      用户入口： Facebook、Instagram、WhatsApp 提供现成的分发渠道，Muse 可以直接进入用户看内容、购物和交流的场景。

b.     个人上下文： 利用用户授权的偏好、历史交互和关系信息，结合主动记忆，减少重复提问，提高个性化程度。

c.      商家链接： 广告、商品目录和商业平台积累了大量商家关系，后续可以接入库存、报价和交易，逐步从浏览网站转向与商家 Agent 直接交互。

d.     内容生态： 公开帖子、创作者内容、商品和活动信息，为搜索、推荐和购物提供依据，也能与 WhatsApp 等执行渠道连接。

e.      模型与产品协同： 根据真实任务，持续优化记忆、主动性、多模态和执行能力，让模型更适合产品场景。

1/3的任务涉及 Meta 的数据或产品操作，2/3仍依赖AI产品和外部工具。

核心判断

1.      模型为产品服务，产品为战略服务，围绕场景优化才能形成差异化。 Meta 的目标是个人 Agent，因此除了补足通用能力，更重视 memory、focus、多模态和专业能力。“模型即产品”，用户感受到的记忆、主动性、可靠性和分寸感，很多都需要落实到模型训练中。现阶段模型仍然很重要，需要与产品、工具和执行环境一起优化，而不只是追求综合榜单领先。

2.      C 端产品还有很大的演化空间，可以让用户更省事。 现在的交互方式并不极致，很多产品仍要求用户自己找信息、切换应用、决策和重复操作。Agent 如果能记住需求、主动跟进并执行，会改变这些使用方式。Active Memory、Active Focus 和主动任务都是好的尝试。

3.      搜索的竞争对手不只有 Chat，Agent 会进一步影响搜索入口。 大量搜索的最终目的都是行动，例如购物、订票和规划行程。如果 Agent 能把事情做完，用户就不必逐步搜索、浏览和操作。影响多大，要看它能接走多少高价值任务，以及用户是否愿意持续把这些任务交给它。

4.      大厂在通用个人 Agent 上更有优势，但各家的优势不同。 谷歌有邮箱、云盘、日历和地图，Meta 有社交内容、用户关系和商家网络。创业公司仍可能靠产品和特定场景做出来，但要完成更多任务，通常需要连接更多生态。随着算力缓解，预计谷歌也会更积极推进 C 端 Agent，未来可能是几家player，而不是只有一个通用入口。

5.      模型像是大公司的安全垫，但这张入场券很贵。 掌握模型，可以减少对外部供应商的依赖，也能按自己的产品方向提升能力。但追赶前沿、反复试错和提前储备算力，都需要承担很大成本。部分投入可能最终没有产出，这是探索中难以避免的代价。

6.      Meta 的战略意图很清楚，扎克伯格也确实是 all in，但回报路径还没有完全看清楚。收入来源服务于个人 Agent、广告推荐、模型ARR，也可能通过对外提供算力获得收入，但meta没有成熟的B端业务，可能其回本周期是更加慢的。不过似乎meta也不是很在意，“失败不重要，重要的是赢的时候赢多大”。

7.      成本的下降非常重要， 每MAU成本11.5美金，instinct 1.5美金 token cost / DAU，meta广告变现每用户0.2美金 DAU 每日。

8.      最难判断的是时机，提前投入与等待验证都有代价。乐观情况下，成本下降、成功率和留存提高，使用量增加，商业化逐步跟上；中性情况下，技术在进步，但产品需求集中在少数场景，回报兑现较慢；悲观情况下，成本虽下降，用户仍不愿持续交付任务，试用没有变成留存。对 C 端 Agent 的方向偏乐观，但普及和回报周期不确定。 更省事的交互方式有真实需求，随着成本下降、记忆和执行能力改善，用户会逐步把更多任务交给 Agent。但早期需求可能集中在少数场景，需要多轮产品迭代，不一定像 ChatGPT 一样迅速普及。
