Q:在 2026 财年第三季度，客户在 Snowflake 上的总体支出增长率是多少？相比此前几个季度是加快了还是放缓了？哪些因素可以解释这一趋势？

A:增长比上一季度更快。该季度于 10 月 31 日结束，官方业绩将于 12 月 2 日公布。根据 Snowflake 的公开指引，收入预计环比增长 6% 至 7%，全年指引大约为 60 亿美元。第一季度收入约为 13.9亿美元，第二季度为 15.5 亿美元，第三季度的暂定估计大约为 16.0 亿至 16.1 亿美元。

加速主要来自于 AI 和可观测性这两大支柱。客户对 Snowflake AI 服务的采用有所增加，包括 Cortex Code、Cortex AI Gateway 以及用于 ETL 和数据仓库的其他计算服务。Snowflake还赢得了若干新客户并扩大了用例的采用，这应当在下季度支持更高的收入。全年指引大约为 60 亿美元，迄今为止的同比增长大约在 37% 至 38% 之间，预计这一趋势将持续。

Q:从您的角度看，您预计第四季度 Snowflake 支出同比增长是多少？第四季度通常是许多企业签署软件合同时的重要季度。

A:结果在一定程度上取决于客户的财年：有些公司的财年是 1 月到 12 月，而有些是 4 月到 3 月。传统上，第四季度是 Snowflake 的最大季度，通常贡献全年收入的大约 35% 至40%。许多续约、现有客户的扩展以及长期交易会在第四季度达成，因此该季度应会推动消费和已预定收入的增长。

迄今为止已实现的大约为 30 亿美元，目标是再实现 30 亿至 32 亿美元，其中大约 18 亿至 19 亿美元将来自第四季度。第一季度大约为 13 亿至 14 亿美元，第二季度约为 15亿美元；其余将主要来自第三季度和第四季度。提到的一个近似数字是 6%，但官方数字将于 12 月 2 日公布。公司目前处于静默期，因此不能进一步讨论估算或贡献数字。

Q:第三季度的总体 RPO 情况如何？RPO 增速是否实现了环比加速？

A:当前未实现的 RPO 大约为 90 亿美元。Snowflake 已向市场指引，约有 45% 的这笔金额将在当前财年内被转化，这意味着预期还会有大约 40 亿至 45 亿美元的消费。目标是超出该水平，但公司目前的市场指引仍大致为 9.05亿美元未实现 RPO 中的约 45%。

Q:第三季度 Cortex Code 的使用情况如何？在第二季度，大约有 9,100 个账号使用了 Cortex Code，比上一季度增加了约 2,000 个账号。目前有多少账号在使用 Cortex Code，环比增长是多少？

A:与第二季度相比，Cortex Code 新增大约 2,000 个账号，第三季度约有 9,000 个客户使用了它。在大约 70,000 个客户的基数中，估计又新增了约 2,000 个客户。已经发布了若干新功能，包括 Cortex AI Gateway、路由和自动路由能力。数千名客户在上一季度采用或尝试了 Cortex。

另一个重要的采用指标是 Snowflake 的消费。在过去一年，包括前两个季度内，用例采用或用例上线增加了89%。上线是衡量采用和成功的有意义指标，因为许多客户首先会做试点和概念验证（POC）。平台采用是使用的最终证明。用例采用也被描述为同比增长了近 80%，尽管单个用例可能涉及多个组件。

Q:第三季度 Cortex Code 的总消费是多少？它占 Snowflake 整体使用或消费的比例是多少？Snowflake 的增长中有多少是由 Cortex Code 推动的？

A:如果客户内部即便只有一名用户尝试了 Cortex Code，该客户就会被计为已采用，因此客户数量并不能真实反映收入。在大型客户中，可能仅凭一人使用 Cortex Code 或 Snowflake 的其他 AI能力就构成了采用。尽管客户数量在增加且 AI 采用与收入呈直接相关，但使用量集中在前 20% 至 30% 的客户中。因此按客户数量来看采用可能很广泛，但分布并不均匀。

在过去两个季度中，超过 50% 的增量收入来自 AI 及 AI 服务，而不仅仅是 Cortex Code。AI 支柱有三个主要子类别：AI functions、Cortex Code 和协同工作（co-work）。最近几个季度大约有 50%的增长来自这三类捆绑或能力。

Snowflake 在公布结果前不会特别披露增量客户数。上个季度估计的新增客户数在 1,000 到 1,500 之间。通过第二季度已有超过 9,000 个客户使用了该能力，估计在第三季度又有额外约 1,000 到 1,500个客户首次尝试或采用了 Cortex Code。

Q:Snowflake 有一个名为 Cortex AI Gateway 的新功能尚未完全发布。预计何时能全面可用？企业是否已在测试？他们提供了哪些反馈？

A:Cortex AI Gateway 已以公测形式上线，并于 9 月在 AWS 上实现了可用。可用性正逐步在 Azure 和 Google Cloud 之间扩展，并应在未来 4 至 6个月内随着该服务在更多数据中心被激活而进一步扩展。已有超过 300 家客户在使用，反馈非常积极。

此前，客户在任何推理工作负载中常常使用最昂贵的模型，无论是 Anthropic 还是 OpenAI 模型。Cortex AI Gateway 可以自动将传入请求——例如代码或推理查询、工作流、ETL 任务或 Snowflake SQL查询——路由到 Snowflake 生态系统内的适当 LLM。这大幅降低了客户成本和每个任务的成本。

Cortex AI Gateway 还提供治理、成本跟踪和成本管理。客户可以按用户、团队、账户或订阅设置预算，从而控制成本并确保为每个用例或查询使用适当的 LLM。此前无法自动将查询路由到最适合的 LLM。该服务于 9 月在 AWS首次可用，正逐步在全球的 Azure 与 GCP 上展开。目前在美洲和欧洲可用，亚太地区也在逐步上线。

Q:Snowflake 如何向企业客户收取 Cortex AI Gateway 的费用？该服务可能为 Snowflake 带来多少增量收入？

A:计费模型尚未完全明确。Cortex AI Gateway 目前是免费的，没有单独收费。客户可以在 Cortex Code 桌面或服务中选择 Auto 模式，或为不同用例配置不同模型——例如一个用于代码生成，一个用于推理，另一个用于MCP。他们可以优先使用特定模型，或使用 Auto 模式自动分配任务。Snowflake 推荐 Auto 模式，在该模式下，SLM 会解析传入查询并选择适当的下游 LLM，类似于混合专家（mixture-of-experts）架构。

Cortex AI Gateway 本身不收费，但成本取决于所使用的 LLM。每个 LLM 按百万 token 和按区域定价。Snowflake 的定价文档列出了不同模型的不同费率，包括开源或开权重模型、Llama、Anthropic等。客户会根据性能、准确性、每个任务成本和可用预算来选择模型。

Q:在企业采用 Cortex AI Gateway 之前，一线模型（如 OpenAI 和 Anthropic）、二线模型（如 Gemini）以及开源语言模型之间的 token 消耗比例如何？在采用之后，这一比例会如何变化？

A:我认为 token 消耗成本将下降 30% 到 40%。客户目前在很大程度上依赖 Anthropic 的 Sonar 等模型，而 Snowflake 也提供 GLM 5.3、Kimi 和 Moonshot 等模型。许多客户正在从昂贵的Anthropic 和 OpenAI 模型转向诸如 Kimi 和 Moonshot 等替代方案，这些方案在保持准确性的同时可以更具经济性。

客户也在为自己的领域构建经过微调的小型语言模型，从而大幅降低完成同一任务的 token 成本。他们已从单纯衡量消耗的 token 数量转向衡量每项任务的成本，因为仅以 token 体量作为度量已不再充分。许多客户在 Snowflake内构建了微调的自定义开源权重模型，与 OpenAI 或 Anthropic 模型相比，大约可以节省 30% 到 40% 的成本。

客户对 LLM、微调以及部署自有模型变得更加熟悉。许多客户在私有环境中部署 LLM，以保证其数据保持私密且不被发送至外部模型用于训练。安全是一个主要关注点。总体 token 使用量在采用 Cortex AI Gateway 后可能会下降约30% 到 40%，但该服务尚未在每个区域可用，可能还需要三到四个月才能覆盖所有云区域。

客户当前或许可以在另一个区域使用 Cortex AI Gateway，但他们通常希望该服务位于其云数据所在的同一区域。数据主权要求使他们不愿意将数据发送到另一个云区域再返回。因此，许多客户在等待其所在区域可用时，通过 POC和非生产用例测试该服务。

Q:如果 AI 将每项任务的成本降低 30% 到 40%，客户会不会因此在更多任务上使用 AI，导致总体 AI 消耗和支出增加？

A:会的。客户在单项任务上节省了成本，但随着他们对 Snowflake 上可用模型日益熟悉，会采用更多用例。总体消耗在增加而每项任务成本在下降，因此总收入应当会上升而非下降。Snowflake的主要优势在于数据和上下文已经位于平台上，允许客户将数据保留在平台内并把 LLM 带到数据所在处。

这是 Snowflake AI 能力的主要价值主张：数据不会离开 Snowflake，而相关的 AI 能力被带到数据平台层。随着用例成本下降，客户会在 Snowflake 内引入更多用例、工作流、AI 能力和 MCP 集成。并购也使Snowflake 能够支持更多用例、应用和动作，同时作为一个中心化的数据与分析平台。

此前 Snowflake 主要用于处理已在平台内部的数据，但收购一家 MCP 连接器公司后增加了 90 多个连接器。现在 Snowflake 可以与 SAP、Salesforce、Workday 及多种 SaaS服务通信。客户可以在一个通用环境中构建触发 CRM、ERP、SaaS 服务和其他应用中的动作或更新的工作流，而不必为每个系统维护独立的代理、聊天机器人或工具。

Snowflake 还可以从电子邮件、SharePoint 及多个其他来源摄取数据，以提供统一的数据集成面。这些活动需要 token 和 LLM，从而使 Snowflake 成为此类用例的中心平台。

Q:你能量化这种关系吗？如果每项任务的成本下降 30% 到 40%，分配给 Snowflake 的任务数量和 Snowflake 的总体消耗会分别增加多少？

A:许多这些能力仅在两到三个月前出现，尚未在每个区域普遍可用。它们正在逐步推出，客户仍处于试用和采用阶段。下个季度或大约三个月后，随着更多证据显示可扩展性且这些能力在更多 Snowflake 区域上线，我们应能看到更清晰的情况。

Q:你能提供一个具体客户的例子，说明在每项任务成本下降后总任务数量和总消耗如何增加吗？

A:一位使用 Snowflake Streams 的客户通过 Cortex Code 和相关 AI 能力实现了可观的节省。一个 DPD 管道将所需的总计算量减少了近 25%。在 Snowflake 内重建该管道并结合增强的 AI 能力和Cortex 协作，使该特定流程的 Snowflake 计算消耗约减少了 25%，节省了几十万美元。

这些是与多个客户进行的点对点 POC。该示例涉及一家制造业客户，但客户名称和其他识别信息无法披露。

Q:你提到该特定流程的成本下降了 25%。尽管每项任务成本更低，该客户的总消耗增加了多少？

A:该特定用例的消耗增加了大约 12%。不过，这仅是评估的第二个月，该项目仍处于测试阶段。预计在未来六个月内消耗会继续增加。需要五到六个月的数据才能在多个客户间建立平均趋势。因此现在下结论还为时过早，但目前的临时增长约为 12% 到12.5%。

Q:根据你的观察，不同行业的客户在第三季度、第四季度及进入明年在部署 AI 能力方面取得了哪些进展？你预计何时总体 AI token 消耗和模型部署会加速？

A:一个新功能通常需要三到六个月才能在所有地点可用，大约六到八个月才能实现广泛的客户采用。在大型银行、制造商或跨国公司，网络安全和内部审批、测试以及 POC工作本身可能就需要三到六个月。因此通常在发布后六到九个月才能看到完整的生产价值并获得可靠的指标。对于大规模的 Snowflake 功能，关于使用、消耗和结果的完整信息通常在通用可用后六到八个月才会显现。

超过 50% 的客户已经在使用 AI，并且每个月都有超过 1,000 家客户首次开始使用 Snowflake 的 AI 能力。三四年前，客户采用 Snowflake 主要是因为它作为数据平台的可扩展性。今天，Snowflake将自己定位为以 AI 为先的公司，将 AI 作为核心用例，其 AI 能力正在吸引更多客户使用该平台。

许多客户已用 Snowflake Cortex Code 桌面替代了其他编码桌面或 OpenAI 的编码工具。Cortex Code 为多种 LLM 提供单一界面，而一些替代桌面仅提供 Anthropic 和 OpenAI 模型。现有Snowflake 客户可以将 Cortex Code 许可证分配给用户，用户可从 Snowflake 目录中的 20 多种模型中选择，包括 Mistral、Mixtral、GLM 和 Kimi。这至少促成了 AI token 使用量增加20%。

用例从生成演示文稿和文件到在制造、金融、银行、销售、零售等行业进行研究不等。这大幅增加了 Snowflake AI 消耗的 credits。Snowflake 在几个月前推出了 co-work 和 Cortex Code，约一个月前推出了Cortex AI Gateway。未来三个月计划推出许多额外功能，预计在接下来的六到八个月内将有至少 50 项新的 AI 能力。Snowflake事件上公布的功能通常先进入私有预览，大约需要三个月进入公开预览，并根据具体功能约需六到八个月达到普遍可用。

AI 现在已成为 Snowflake 活动的核心，包括编写查询、构建数据管道、监控、平台管理、制作演示文稿和开发仪表盘。客户在广泛的 Snowflake 工作流中使用 AI。过去一到两个季度里，约有 25% 到 30% 的收入增长仅来自AI。

Q:放眼 Snowflake 之外，美国企业在 AI 部署和使用方面处于什么阶段？你预计 token 消耗和整体 AI 使用何时会出现下一次大的加速？

A:在过去六个月里，许多公司的 AI token 使用量大幅增加，部分用户消耗了数十亿 token。客户现在已进入优化阶段。最初的六个月里，对 OpenAI、Anthropic 和 LLM 的热情促使客户在 token上花费数十万美元而未见太多投资回报。一些客户在六个月内几乎将其 IT 预算的 30% 到 40% 用于 AI token。

因此，客户正从昂贵的 OpenAI 和 Anthropic 模型转向本地化、定制化和开源权重模型，例如 DeepSeek。一些客户将 DeepInfra 等 API 引入 Snowflake；此类平台可将 token 成本降低近 75% 到80%。客户的应用也超越文本，扩展到图像生成、视频制作、音频转录、语音转文本、文本转语音、文档处理以及本地语言的呼叫中心转写。预计这种多模态使用将推动下一波自动化浪潮。

另一个新兴用例是让业务用户直接与数据交互并提出问题，而无需依赖 Power BI 或 Tableau 等工具。Snowflake、Databricks、SAP、Microsoft Copilot等正在使客户能够直接查询其数据。在用户层面，AI 已经被应用于调研、演示、文档和市场研究。下一阶段将涉及构建 agentic 工作流。

随着初始免费期结束，客户正在审查成本、优化使用并施加更严格的预算和控制。安全性也变得更加重要。随着客户在 agentic 框架的使用上日益成熟，他们越来越关心代理的行为、权限范围以及对数据的访问，尤其是在出现关于 AI系统被黑客攻击和数据被提取的报道之后。因此，市场目前处于优化阶段。

Q:像 Datadog 和 OpenRouter 这样的公司也提供模型路由、监控和优化。Snowflake 的比较优势是什么，Snowflake 是否有可能成为模型路由的主要网关？

A:Snowflake 相对于 OpenRouter 和其他厂商的主要差异在于它掌握客户上下文。在大型制造企业，交易、客户和财务数据可能都存放在 Snowflake 中。如果用户询问某一特定产品的顶级客户，Snowflake知道哪些表包含相关信息，理解元数据和治理，并知道应使用哪些列和 SQL 查询。相比之下，OpenRouter 主要是一个路由机制，用于为任务选择 LLM。

在 Snowflake 中执行的查询消耗的 token 大约比使用外部路由机制的查询少约 2 到 2.5 倍，因为外部路由器缺乏上下文。它不知道哪个表包含相关数据或应该编写哪个查询。Snowflake已经包含语义模型和上下文信息。OpenRouter 对于编写代码或制作演示等通用任务很有用，但在编写 SQL、应用治理和基于角色的访问控制以及以可信格式检索相关数据等具有上下文的任务上，Snowflake 更具差异化优势。

企业用户需要带有引证和落地依据的可靠答案。Snowflake 可以为查询提供引用、参考和落地依据，以及完整的记录、审计跟踪和审计历史。大型公司需要详尽的合规性、可追溯性、血缘、治理和访问控制。这些能力（包括 Snowflake Horizon）在 Snowflake 内可用，但通过通用路由器无法实现。因此，落地依据、语义建模和客户上下文是核心差异点。

Q:Cortex Code 可以缩短企业向 Snowflake 迁移的周期。你是否预计更多企业客户会在本季度或下季度使用 Cortex Code 进行迁移并更快迁入 Snowflake？

A:AIM 是 Snowflake 的 AI 迁移工具，构建于 Cortex Code 之上。基于 Cortex Code 的 Cortex Code 和 AIM 工具显著缩短了从大型机、Microsoft Fabric、BigQuery、Oracle、SQL Server 等平台迁移到 Snowflake 的时间周期。AIM 将迁移生命周期缩短了大约 40% 到 50%。

AIM 自动化了大约 70% 到 80% 的代码转换，减少了将数千行代码、存储过程和对象迁移到 Snowflake 所需的工作量。客户要求使用AIM，因为他们不希望迁移耗时达八到九个月。Snowflake、Databricks、Microsoft 及其他厂商都使用 AI 迁移工具，这已成为常态。Snowflake 的合作伙伴、专业服务团队和 FDE 团队也使用 AIM以实现更快、更准确的迁移。

Q:Databricks，作为 Snowflake 的主要竞争对手，也在快速增长。Snowflake 与 Databricks 的差距是在扩大还是缩小，你预计竞争格局将如何发展？

A:Databricks 和 Snowflake 是数据平台市场的两大主要厂商，尽管 BigQuery、Microsoft Fabric、Redshift 等也参与其中。Databricks 仍为私人公司，因此其公布的收入和增长数据无法像Snowflake 的公开披露那样被独立检验。在 Databricks 发布公开财报之前，其所报告的 50%、60% 或 70% 的增长率无法以相同的基准进行验证。

就能力而言，Snowflake 和 Databricks 扮演不同的角色，许多客户在同一环境中将它们作为互补平台使用。Snowflake 常作为 gold 层，而 Databricks 支持 silver 和 bronze层。Snowflake 作为 BI 和数据仓库层，而 Databricks 作为工程层。因此，在许多环境中这两个平台是协同工作的。

这些平台也提供可比的能力。Databricks 有 Genie 和 Unity Catalog，而 Snowflake 有对应的 Cortex和目录能力，导致在许多功能上存在一对一的特性对等。比较增长的主要困难在于私人公司的报告数据在其未上市之前无法用相同方式验证。

Q:Snowflake 在九月发布了用于协同工作的任务自动化能力和 Semantic Studio 工具。这两项功能将对 Snowflake 整体产生什么影响？

A:客户在六到八个月前就已请求 Semantic Studio。企业客户通常处理数十万张复杂表，包含大量联接和关系。在构建销售、营销或 BI 代理时，他们需要领域专家来选择正确的表和数据，因为像 sales 或 profit这样的常见列名可能出现在许多不同的表中。

Semantic Studio 使没有技术专长的业务用户能够利用其领域知识构建端到端的语义模型。它提供图形化的拖放界面。通过简单的自然语言提示和 Cortex Code，客户可以创建带版本控制的语义视图。之前需要几天才能完成的 YAML文件或语义模型现在可在不到一小时内完成。

非技术用户、业务用户和数据分析师可以构建语义模型并通过 Snowflake Intelligence将其暴露出来。目标是减少分析师的工作量，并使代理能够以有依据并带引用的方式一致地回答业务问题。该功能在访谈时仅上线约一个月，因此在再过三个月后，采用率、使用情况和反馈应会更加清晰。总体而言，它减少了分析师的工作量并提供了用于构建语义工作流的UI。

Q:Q3 对 Apache Iceberg 能力是否有重大改进，是否有更多客户使用 Apache Iceberg 来加速迁移到 Snowflake？

A:Apache Iceberg 主要是一种开表格式。一些客户将数据从 Snowflake 迁移到 Apache Iceberg，因为他们希望采用开格式、避免被厂商锁定，并希望在开表数据之上使用任意引擎。性能有所提升，已发布对 Apache Iceberg 3.0 的支持，并且对 Apache Iceberg 数据与目录的双向读写能力得到了改善。Snowflake 现在支持与目录关联的数据库、Apache Iceberg 表的双向读写，以及由 Snowflake 管理的Apache Iceberg 表。

随着 Apache Iceberg 的成熟和性能提升，至少有另外 30 到 40 家大型客户正在测试将其作为原生表格式，同时使用 Snowflake 作为查询引擎来读取、写入和转换数据。Snowflake 也支持 Delta 表。来自Databricks 或 ADLS 的 Delta 格式数据的客户可以以零或最小代码更改使用这些数据，而无需先将其转换为 Apache Iceberg。

这扩大了 Snowflake 的采用范围，并展示了其对开放标准和开源格式的支持。许多初创企业和其他公司广泛使用 Apache Iceberg，因为大量数据以 Parquet、JSON、ORC、IoT和流式格式到达。这类数据通常存储在对象存储中，因为成本更低且更易访问。因此对 Apache Iceberg 的支持使 Snowflake 能够覆盖比以往更多的用例。

Q:客户在 Snowflake 上的消费是否持续环比加速？Snowflake 的增长明年是否可能达到或超过 40%？
