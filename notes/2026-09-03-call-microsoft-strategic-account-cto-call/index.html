1. 客户背景与微软合作关系

a) 专家的职责范围和主要服务对象是什么？

  • 专家在微软担任面向战略客户的首席技术官，负责连接微软与客户的业务、产品及技术团队
  • 目前主要服务1家大型私人控股跨国综合企业集团；若为上市公司，专家估计其市值可能达到5,000亿美元以上
  • 专家参与AI项目的完整生命周期：
  1. 与客户各业务部门共同设计AI项目
  2. 基于Microsoft Cloud构建应用
  3. 整合智能体、语义AI及Azure服务
  4. 协调系统集成团队完成实施
  5. 推动产品商业化和市场发布
  • 客户自主开发应用的情况较少，多数项目由微软及系统集成团队共同完成
  • 专家的主要合作对象并非传统IT部门，而是业务线、产品部门及首席产品官等负责人

b) 客户重点应用AI的业务领域有哪些？

  • 汽车业务：
  1. 为全球汽车开发更加智能的座舱
  2. 客户向包括VinFast在内的汽车企业供应大量模块
  • 制造业务：
  1. 重点建设数字孪生
  2. 利用AI缩短产品和项目开发周期
  • 自动化与控制系统：
  1. 构建更智能的设备
  2. 降低建筑物能源消耗
  • 软件开发业务：
  1. 构建SaaS解决方案
  2. 向客户自身的竞争对手销售软件产品
  • 其他业务还包括楼宇自动化、计算机模块制造等

c) 客户是否只使用微软产品，每年在微软的支出是多少？

  • 客户并非只使用微软产品，同时与Amazon和Google合作，但合作规模显著低于微软
  • 微软是客户首选的超大规模云服务商，并广泛覆盖其知识工作者技术栈
  • 客户每年在微软的投入：
  1. 超过1亿美元
  2. 低于7亿美元
  3. 当前仍在快速增长
  • 大型企业通常采用多云策略，完全依赖单一厂商的情况更多见于中端市场

d) 微软与该客户的合作关系为何重新加速？

  • 2025年7月1日之前，微软与客户的合作关系一度停滞
  • 双方CEO均认为现有合作深度不足，微软和客户都错失了大量商业及产品机会
  • 微软随后配置了专项团队：
  1. 专家负责技术合作关系
  2. 另1名同事负责整体业务合作关系
  3. 另配1名云解决方案架构师，负责具体应用落地
  • 合作恢复后，已经从基本没有进展发展到：
  1. 约11至12个应用正在开发
  2. 多个应用即将推出
  3. 客户管理层希望进一步加快和扩大部署
  • 当前主要制约并非需求不足，而是微软及合作团队的交付能力有限

2. AI支出增长与大型项目展望

a) 客户2026年AI相关支出预计增长多少？

  • 专家预计，客户2026日历年的AI相关支出同比增长约25%至30%
  • 这一增幅主要受微软当前交付能力限制，若交付资源更加充足，实际增幅可能显著高于该水平
  • 增长主要来自两部分：
  1. 法务、人力资源、合规、国际货币计算等内部应用
  2. 与微软共同开发并向外部客户销售的AI产品

b) 大型对外AI项目的收入和支出规模如何？

  • 客户正在推进1个已经公开披露、但专家不便透露具体内容的大型AI项目
  • 项目支出预期：
  1. 未来5年达到数亿美元
  2. 上限可能接近5亿美元
  • 项目前期将缓慢启动，预计到2026年年底可能形成约500万美元销售额
  • 客户计划在消费电子展上与微软共同全面展示该项目
  • 专家预计，项目公开展示后需求将快速增长，2027年年底可能迎来显著放量

c) 客户内部AI采用是否已经全面普及？

  • 大多数事业部应用效果良好，但仍有部分事业部尚未充分采用AI
  • 主要原因包括：
  1. 对AI缺乏基本认知
  2. 对技术风险存在畏惧
  3. 不同事业部之间缺乏信息共享
  • 专家计划在欧洲开展AI基础研讨会，重点说明：
  1. AI能够带来的生产力提升
  2. 成本降低机会
  3. 因过度担忧AI而错失的业务价值
  • 预计研讨会后，客户内部AI应用范围将进一步扩大

3. IT服务台智能体的运行模式与价值

a) 客户的IT服务台如何实现智能体化？

  • 客户的IT服务台已基本实现智能体化，并采用“智能体对智能体”的协作模式
  • 微软围绕Office重新构建了连接ServiceNow的用户入口
  • 员工可以直接在以下应用中请求IT支持：
  1. Teams
  2. Outlook
  3. Word
  • Teams是最理想的入口，用户只需点击“我需要帮助”即可与智能体交互
  • 底层仍可继续使用ServiceNow等系统，但用户无需离开Microsoft 365环境

b) 与传统IT服务台相比，智能体模式有哪些变化？

  • 传统流程通常包括：
  1. 员工致电或发送邮件提交问题
  2. 等待技术人员响应
  3. 技术人员搜索文档并判断解决方案
  4. 回复用户或升级问题
  • 传统模式的响应时间可能达到24小时，每项请求均需人工介入
  • 智能体模式可以即时处理：
  1. 密码重置及账户问题
  2. VPN故障
  3. 软件安装
  4. 网络连接问题
  5. 设备配置
  6. Outlook及系统更新问题
  7. 工单状态查询
  • 此类基础问题约占帮助台工单的95%，具备较高的自动化潜力

c) 智能体具体能够完成哪些支持工作？

  • 搜索企业知识库、数据库及相关政策
  • 根据用户输入进行故障排查
  • 推荐解决方案并向用户演示操作步骤
  • 自动创建工单，并利用既有对话信息预填工单
  • 主动收集问题背景和设备信息
  • 仅在确有必要时将问题转交人工
  • 对于CSV数据错位等“判断复杂但修复简单”的问题，智能体能够快速定位并指导用户解决，避免耗费数小时排查

d) 哪些问题必须转交人工处理？

  • 严重安全事件及黑客攻击必须由人工处理
  • AI不被允许自行诊断或修复黑客攻击，主要原因是：
  1. 智能体本身可能受到攻击
  2. AI生成的诊断和修复方案可能被攻击者获取
  3. 攻击者可能借此绕过企业的修复措施
  • 对于高风险场景，必须保留人工审核和安全隔离机制

e) 智能体是否会取代支持工程师？

  • 微软向客户明确表示，部署智能体的目标不是取代支持工程师
  • 目标是让智能体承担约60%至80%的重复性请求
  • 支持工程师可以转而处理：
  1. 复杂工程问题
  2. 制造系统问题
  3. 重大客户问题
  4. 安全及高风险事件
  • 该模式有助于减少工程师因密码重置等低价值任务产生的压力和职业倦怠

4. ServiceNow、Salesforce与微软的竞合关系

a) 为什么微软能够在ServiceNow之上构建智能体入口？

  • ServiceNow具备自身AI能力，但无法端到端掌握知识工作者的完整技术栈
  • 用户解决问题时，智能体可能需要访问：
  1. Word文档
  2. Outlook邮件
  3. Teams会议与聊天记录
  4. 企业门户
  5. Fabric、SQL、Cosmos DB等数据工具
  • 微软掌握Microsoft 365及知识工作者的主要工作入口，因此能够跨应用检索上下文并给出答案
  • ServiceNow和Salesforce的不足在于，它们难以直接覆盖用户日常工作的顶层应用环境

b) ServiceNow是否会因微软进入其入口层而受损？

  • ServiceNow对此并不满意，但微软并非推动客户弃用ServiceNow
  • 微软是在ServiceNow之上构建更便捷的用户入口，底层工作流仍由ServiceNow承载
  • 如果客户弃用ServiceNow，微软需要重新开发：
  1. 完整接口
  2. 工作流系统
  3. 用户体验
  • 重新构建将耗费大量资金和时间，因此微软的方案反而提升了客户对ServiceNow的使用深度和替换成本
  • 双方呈现“既竞争又合作”的关系

c) 跨云和跨软件集成是否会成为常态？

  • 微软与AWS已宣布开展跨云数据共享合作，为终端客户提供便利
  • 即使大型云厂商之间存在激烈竞争，也需要通过合作满足企业的多云环境需求
  • 大型企业不会轻易放弃现有核心系统，因此智能体通常需要兼容并连接ServiceNow、Salesforce、SAP等既有平台

5. 从IT服务台向法务、人力资源等部门扩展

a) IT服务台智能体是否已经接近增长饱和？

  • 中央IT部门的实施已经较为成熟，但客户整体智能体市场远未饱和
  • 下一阶段将把成熟经验复制到：
  1. 法务
  2. 人力资源
  3. 合规
  4. 市场营销
  5. 其他业务条线
  • IT服务台的优质体验已经成为内部示范案例，其他部门会主动要求获得类似能力

b) 为什么部门级智能体不能简单复制IT方案？

  • 不同部门的知识体系、人员技能和业务流程差异显著
  • 以法务部门为例：
  1. 中国合同与美国合同要求不同
  2. 不同国家的合同法、监管和数据要求不同
  3. 客户业务覆盖全球大多数地区
  4. 智能体需要理解各国业务规则并匹配不同类型的法务人员
  • 当前法务和人力资源部门已经拥有机器人，但尚未形成完整的用户体验和顺畅的人工衔接机制
  • 部分流程仍依赖邮件，并存在约24小时延迟，因此仍有较大的改造空间

c) 为什么部门级智能体建设时间较长？

  • 部门知识库和工作流更加复杂
  • 需要单独构建角色、权限和人工升级机制
  • 需要处理不同国家和地区的法规差异
  • 必须确保智能体在专业、高风险场景中的准确性与可审计性
  • 客户各业务条线目前仅处于初步部署阶段，距离完整覆盖仍有较大空间

6. 智能体投资回报率与价值衡量

a) 客户如何衡量智能体的投资回报率？

  • 客户同时采用软性和硬性指标进行衡量
  • 软性指标包括：
  1. 用户体验改善
  2. 员工满意度提升
  3. 响应时间缩短
  4. 重复性工作减少
  • 硬性指标包括：
  1. 单个问题处理时间
  2. 单位时间内可处理案例数量
  3. 人力释放规模
  4. 追加销售能力
  5. 项目启动时间
  6. 直接成本节约

b) 缩短少量处理时间为何能创造巨大价值？

  • 大型企业会将单次客户问题处理时间缩短12秒作为长期运营指标
  • 虽然单次节省时间很短，但在海量客户交互下可以产生数千万美元的：
  1. 成本节约
  2. 生产力提升
  3. 增量销售机会
  • 前期表现为效率等软性收益，后期会转化为实际财务收益

c) 制造业如何衡量AI项目的回报？

  • 制造业客户会重点衡量项目开发和启动时间的缩短
  • 项目启动前需要完成：
  1. 合同谈判
  2. 不可抗力条款确认
  3. 建设地点选择
  4. 产品销售国家确认
  5. 生产国家确认
  6. 云服务运行国家及数据中心选择
  • AI能够根据预设参数快速推荐合适的部署方案
  • 例如，系统可以根据产品销售国家、生产地点和数据要求，自动判断最适合使用的数据中心，并调用已经通过法务、合规及CTO审核的标准方案

d) 智能体实施过程中最困难的部分是什么？

  • 最大难点始终是项目启动阶段，核心问题包括：
  1. 将正确的信息输入系统
  2. 接入高质量数据源
  3. 完成模型训练和验证
  4. 识别幻觉、迎合性回答及错误输出
  • 如果数据质量较好，模型训练本身并不一定耗时很长
  • 在系统投入生产前，需要由经过培训的人员或高级技术负责人发现并纠正错误

7. 开源模型与闭源模型的选择

a) 欧洲客户如何看待开源模型？

  • 客户整体不倾向于在生产环境使用开源模型，主要顾虑包括：
  1. 数据隐私
  2. 数据主权
  3. 知识产权泄露
  4. 安全边界不清晰
  • 客户的内部规定是禁止在生产环境中使用开源模型
  • 但允许在沙盒或概念验证环境中测试，以评估性能、成本和安全性

b) 开源模型为什么仍具有较强吸引力？

  • Qwen等开源模型表现出较强能力
  • 开源模型的主要优势包括：
  1. 成本较低
  2. 性能良好
  3. 部署方式灵活
  4. 数据和运行环境可由客户控制
  • 专家已经看到使用Qwen进行的概念验证项目，试点效果较好
  • 客户正在研究能否与微软、AWS等合作，为开源模型建立安全防护边界

c) 模型市场将如何演变？

  • 当前主流模型包括Claude、ChatGPT、Gemini、Grok及多个开源模型
  • Anthropic和OpenAI也在尝试推出成本更低、更接近开放权重或“共享源代码”的模型
  • 专家认为，6个月后的语言模型市场可能与当前存在较大差异
  • 企业最终可能采取混合模型策略，根据：
  1. 任务质量要求
  2. 延迟
  3. 成本
  4. 数据主权
  5. 安全等级

动态选择模型

8. 开源模型环境下微软的商业模式

a) 如果客户采用低成本开源模型，微软如何获得收入？

  • 微软的收入模式将从单纯按Token收费，转向以基础设施和完整技术栈为核心
  • 微软可以提供：
  1. Azure算力和基础设施
  2. 数据层、数据湖及数据资产
  3. 数据库与既有数据资产集成
  4. 智能体开发和部署环境
  5. 权限、安全及治理能力
  6. 类似Office的统一用户界面
  • 即使底层采用开源模型，客户仍需要购买大量云计算、数据、存储和应用服务

b) 微软为什么开始重视开放权重模型？

  • 开放权重模型适用于：
  1. 成本控制
  2. 数据主权
  3. 模型可移植性
  4. 客户自主控制环境
  5. 定制化智能体部署
  • 相关经济模式将从基于使用量的Token收费，转向基于基础设施的收费
  • 微软可以通过控制数据、部署和定制层，维持较高的商业价值

c) Microsoft 365如何从智能体增长中获益？

  • 微软会将智能体能力嵌入Office式用户界面，提升Microsoft 365的用户黏性
  • 相关AI能力可以按用户额外收费，专家提到约每位用户每月30美元
  • 微软不仅获得云和数据收入，也可以提升Office订阅收入及客户留存率

9. FDE模式与智能体项目实施

a) 为什么FDE模式受到微软、OpenAI和Anthropic重视？

  • 智能体项目需要深入接触客户数据、流程和信息访问机制
  • 控制智能体设计及数据访问方式的一方，将掌握较强的客户关系和平台话语权
  • 复杂项目无法仅由客户或供应商单独完成，需要双方共同建设
  • FDE模式通常包括：
  1. 派出具备高层CTO能力的人员
  2. 与客户共同制定战略
  3. 深入客户现场理解业务
  4. 引入系统集成团队完成执行

b) Palantir对FDE模式有何影响？

  • 专家认为，Palantir比其他公司更早完善了FDE模式
  • Palantir通过FDE获得了数亿美元收入，证明了该模式的商业价值
  • 微软已投资约20亿美元，并为Frontier组织配置约6,000名员工
  • 微软正在把FDE定位为大型复杂项目的必要配置
  • 专家参与的大型项目已经建议并获得客户同意采用FDE模式，原因是项目复杂且不能失败

10. 智能体时代的主要软件受益者

a) 哪些类型的软件公司最能从大语言模型中受益？

  • 几乎所有软件公司都能够受益，但最直接受益的是拥有以下资产的公司：
  1. 大量文本和知识库
  2. 成熟工作流
  3. 决策流程
  4. 客户交互数据
  5. 庞大用户基础
  • 主要平台型受益者包括：
  1. Microsoft
  2. Salesforce
  3. SAP
  4. ServiceNow
  5. Oracle
  6. Workday
  • 对应应用包括：
  1. ServiceNow智能体处理IT工单
  2. SAP智能体管理采购
  3. Salesforce智能体筛选销售线索
  4. Microsoft Copilot跨Microsoft 365执行任务
  • 软件厂商可获得更高订阅收入、更低支持成本和更强客户黏性

b) 客户支持软件领域有哪些主要受益者？

  • 主要参与者包括：
  1. Zendesk
  2. Freshworks
  3. Intercom

12. 数据质量与数据基础设施机会

a) 为什么数据质量仍是智能体落地的核心难题？

  • 智能体有效运行需要高质量、可访问、可解释的数据
  • 企业普遍不存在完全干净的数据，差异只在于数据质量问题的严重程度
  • 数据问题会导致：
  1. 模型幻觉
  2. 迎合性回答
  3. 错误决策
  4. 无法稳定进入生产环境
  • 企业通常不会等待所有数据彻底清理完成，而是采取迭代部署及严格质量控制

b) 哪些数据平台可能从中受益？

  • MongoDB：
  1. 擅长同时处理结构化和非结构化数据
  2. 能够帮助企业整理智能体所需的数据资产
  • Databricks：
  1. 能够进行全面数据清理
  2. 成本较高、实施周期较长
  3. 但清理完成后可显著提升企业AI能力
  • Microsoft Cosmos DB：
  1. 可承担部分数据整合工作
  2. 与Azure和微软技术栈整合较好
  • 随着智能体普及，企业数据资产的重要性还将持续提升

13. 算力需求、供给约束与基础设施展望

a) 如果算力供给增加2至3倍，市场是否有足够需求消化？

  • 专家判断，市场完全具备相应需求
  • 企业客户对算力的需求长期旺盛，当前始终无法获得足够容量
  • 即使算力供给达到现有水平的2至3倍，仍有大量积压需求等待释放
  • 目前积压需求预计需要约3年才能消化

b) 微软能否跟上算力需求增长？

  • 专家判断，微软及行业整体短期内无法完全跟上需求增长
  • 供给约束包括：
  1. 数据中心建设周期
  2. 电力供应
  3. 地方政策和审批
  4. 服务器机架及连接设施
  5. 光纤和制冷基础设施
  • 市场对微软未来现金流的预期，部分建立在AI和云算力需求持续超过供给之上

c) 除GPU外，CPU需求是否同样重要？

  • 大量内容、零售及企业应用依赖CPU，而非全部依赖GPU
  • 消费者对YouTube、Instagram、TikTok、Snapchat、Facebook及体育内容的需求持续增长
  • 企业必须跟上消费者对即时体验的预期
  • 例如，消费者如果可以在社交平台上6秒完成下单，也会要求零售企业提供类似体验
  • 这些实时交易、内容分发和传统工作负载将持续推动CPU和通用云基础设施需求

d) 基础设施需求未来将如何变化？

  • 短期内，GPU、Token、算力和电力价格可能继续上涨
  • 随着供给逐步增加，预计2至3年后价格开始回落
  • 戴尔、惠普、康宁及机架、网络、光纤等基础设施公司将共同受益
  • 若未来量子计算真正商业化，数据中心、电缆、制冷、隔音和光纤等基础设施需求可能出现数量级增长
  • 专家对太空及水下数据中心持怀疑态度，更看好在能源充足、能够自给供电的内陆地区建设数据中心

14. 智能体规模化落地的主要障碍

a) 当前最大的阻碍是否仍是ROI、治理和模型能力？

  • 数据、治理、ROI和模型能力仍然重要，但专家认为，企业采用的核心阻碍正逐渐转向安全
  • 企业不希望自行承担全部内容监控和模型治理责任
  • 企业希望模型厂商在交付前内置明确的安全防护和内容限制机制

b) 企业对AI安全有哪些具体要求？

  • 不允许员工利用AI生成或访问不适当内容
  • 对高风险内容进行：
  1. 直接屏蔽
  2. 风险提示
  3. 使用时长限制
  4. 额外确认或权限控制
  • 模型供应商应明确说明产品已内置哪些保护措施
  • 安全机制不仅不会损害企业收入，反而有助于扩大企业采购和部署

c) 专家如何评价主流模型厂商的安全能力？

  • 专家认为OpenAI、Anthropic及其他模型厂商已经具备部分安全机制，但仍未达到大型企业要求
  • Claude在敏感历史图片、自杀风险等场景会主动询问用途或提供安全提示，说明现有机制已取得一定进展
  • Grok在部分安全方面表现较好，但仍需进一步收紧
  • 专家认为，部分模型厂商为追求增长和资本市场目标，可能在安全问题上作出过多让步
  • 长期来看，强化安全能力将提升而非削弱商业化空间

15. 长时运行智能体与Token趋势

a) 长时运行智能体是否已成为实际部署趋势？

  • 长时运行智能体已经成为趋势
  • 随着任务复杂度提高，智能体运行时间已经从约3分钟延长至5分钟、10分钟、13分钟甚至20分钟
  • 任务将呈现两极化：
  1. 简单任务所需时间和Token持续下降
  2. 复杂任务所需时间和Token持续增加

b) 企业是否对长时间、高Token消耗感到不满？

  • 当前客户并未明显反对复杂任务增加Token使用量
  • 微软会根据用途设置Token配额：
  1. 正式项目可关联项目并按需使用
  2. 个人研究和自我学习会受到更严格限制
  • 企业更关注任务能否创造实际价值，而非单纯关注运行时间

c) Token价格和使用量将如何变化？

  • 专家预计Token使用量将持续上升
  • 未来2至3年：
  1. 算力、GPU、Token和电力价格可能继续上涨
  2. 之后随着供给赶上需求，价格将逐步回落
  • 单位Token价格下降并不意味着市场收入下降，因为更复杂的任务和更大规模部署将推动总使用量增长

16. 智能体对微软及整个软件生态的收入拉动

a) 智能体是否只会带动算力和存储收入？

  8. 用户界面和协作工具

b) 微软如何从跨厂商生态中获得收益？

  • 即使后端使用ServiceNow、SAP或MongoDB，最终结果仍需要以用户能够理解和操作的形式呈现
  • 微软通过Microsoft 365、Teams、Office及Copilot承担统一交互入口
  • 微软擅长将算力、数据、模型、智能体和用户界面成本进行打包
  • 对最终客户而言体验较为无缝，但微软能够从技术栈的多个环节获得收入
  • 智能体普及将提高Microsoft 365黏性，同时带动Azure及传统软件收入增长
