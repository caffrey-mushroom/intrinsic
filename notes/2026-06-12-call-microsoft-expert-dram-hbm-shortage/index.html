纪要总结

  1. 内存市场动态 (DRAM & HBM)
  2. 英伟达削减Vera Rubin机架内存配置的原因及其市场影响？
  • 核心问题：内存市场面临物理性约束，DRAM供应商的产能扩张速度远跟不上需求增长，导致物理性供应短缺。
  • 市场补偿方式：若英伟达减少每个机架的本地系统内存，超大规模数据中心会通过增加主机DRAM、利用CXL进行内存扩展及部署解耦式内存池等方式来弥补。
  • 根本矛盾：芯片对HBM的需求未变，而用于补偿的DRAM池本身也面临同样的供应限制，市场上内存总量根本不足以支持所需规模的工作负载。
  • 最终影响：此问题没有完美的解决方案，供应短缺的成本最终会传导至终端客户的定价模型中。
  1. DRAM需求是否有弹性？其价格上限是如何形成的？
  • 需求弹性：DRAM的需求比想象中更有弹性。当DRAM成本在总资本支出中占比过高时，会影响可构建的总算力容量。
  • 价格上限形成机制：价格上限由市场对Token的支付意愿反推形成。即市场愿意为Token支付的价格上限，决定了服务商能为生产这些Token的DRAM所支付的最高价格。
  • 市场信号：目前DRAM价格仍在上涨，但需求的增长速度正在放缓。企业对新发布的高价模型（如每百万输出token 50美元）的接纳变得更加谨慎，开源模型的激增也是一个信号。
  1. AI服务定价模型与客户反应
  2. AI服务的定价模型正在发生什么变化？
  • 核心趋势：行业正从固定订阅费模式大规模转向基于使用量（usage-based）的付费模式。
  • 驱动原因：AI工作流的运行需要巨大的资本支出（capex）和运营支出（opex），服务商无法长期亏本运营，必须将成本转嫁给客户。
  • 典型案例：GitHub Copilot、Claude Code等产品，因实际使用量远超订阅价值，已从固定订阅/许可证模式转为按使用量付费。
  • 主要转变领域：SaaS AI产品（如Salesforce Agent、Microsoft Co-pilot）是当前转变的主要领域。而API驱动的服务（如联络中心应用）早已是按使用量付费。
  1. 客户对定价模型变化的反应如何？这将如何影响未来的AI支出？
  • 客户反应：普遍相当负面。负面情绪并非源于对涨价本身的不理解，而是因为企业客户尚未为全面转向按使用量付费后所需的内部成本控制讨论和机制（类似FinOps的架构）做好准备。
  • 企业应对策略：大型客户将建立类似FinOps的架构来严格控制Token使用，专注于基于用例的消费模式，未来可能为每位员工设置固定的Token上限。
  • 对支出的影响：AI支出的增长速度将不会达到原先的预期水平。在建立起有效的成本控制机制前，一些客户可能会直接停止或放缓支出。
  1. NAND存储市场与AI驱动力
  2. 为什么在AI时代NAND会突然出现严重短缺？
  • 多重应用场景：NAND在AI堆栈中扮演多种关键角色。
  • 训练环节：作为“热数据层”（SSD），存储即将传入GPU的训练数据。
  • 推理环节：
  1. 存储海量上下文：企业级应用（如RAG架构）在每个提示（prompt）中都会为模型提供海量的上下文信息（如文档、数据库记录），输入的上下文数据量（存放在NAND）远大于输出的Token量（约10:1）。
  2. 支持智能体（Agents）：长时间运行的智能体需要存储大量的上下文、思考过程和与工具的交互记录。这些数据需要以热数据形式存储在NAND（SSD）中，以便随时快速访问。
  3. 存储输入输出：企业需要存储所有传入的提示和模型生成的内容，以便追溯和管理。
  4. 对SSD的采购量增长预期如何？
  • 行业增长趋势：预计未来几年将持续增长，2027年甚至可能加速。
  • 主要不确定性：增长速度的核心不确定性在于，价格持续上涨和定价模型转变后，客户的最终支付意愿和能力上限在何处。目前尚不清楚市场能承受多高的价格。
  1. 光模块与CPO技术展望
  2. 光模块市场的支出增长预期如何？
  • 2026年增长率：预计在55%至80%之间。
  • 2027年增长率：预计在30%至40%之间，但仍可能继续加速，具体取决于需求变化。
  1. DCI（数据中心互联）或横向扩展（scale-across）用例的占比和增长动力是什么？
  • 当前占比：2026年占比极小，约在1%至5%。
  • 未来增长：预计到2027年，占比将显著提升至约10%（例如，在千亿市场中占百亿）。
  • 增长动力：随着训练集群规模扩大，单一数据中心在电力、散热和土地资源方面达到物理极限。必须将负载分散到不同建筑，并通过极高速的光互连技术（即横向扩展）将它们连接起来，协同工作。
  1. CPO（共封装光学）技术的采用前景和渗透率如何？
  • 技术必然性：随着GPU间带宽需求提升至1.6T及3.2T，CPO成为必然选择。主要因为铜缆传输距离限制、可插拔光模块的高功耗以及交换机前面板物理空间不足等问题。
  • 支出占比：在光学总支出中，CPO的占比预计在2026年底达到7%-10%，2027年底上升至15%-16%。
  • AI交换机渗透率：在用于训练集群的AI交换机中，基于CPO技术的交换机渗透率预计在2026年底达到15%-20%，2027年底达到40%-45%。
  • 良率问题影响：良率问题确实存在，比几个月前预想的要突出，在一定程度上减缓了其发展进程，但由于行业没有其他技术方案可选，CPO是必然趋势，因此整体影响不大。
  1. 下一代数据中心架构演进
  2. 从Blackwell到下一代技术（如Rubens/Vera），数据中心架构将有哪些显著变化？
  • 功耗与散热：将发生巨大变革。关键变化是向800伏直流供电架构的转变，以降低功率损耗。同时，散热技术将更多采用芯片级直接液冷。
  • 内存与存储：战略地位将日益凸显。更大的模型、更长的上下文和更高的推理并发性，都对内存和NAND存储提出了更高要求。
  • 光学技术：将成为关键。为满足Ruben架构极高的带宽需求，至少需要1.6T的光链路，交换机层面必须采用CPO。未来CPO甚至可能应用于GPU间的纵向扩展（scale-up）连接。
  • CPU：战略地位将日益重要。随着多智能体（multi-agent）等工作流的兴起，CPU性能成为瓶颈。CPU与GPU的配比将显著提高，可能从目前的1:2（0.5）向1:1甚至更高发展，以减少GPU在等待CPU执行任务时的微小阻塞，提升整体效率。
  1. 为什么CPU与GPU的配比会提高？
  • 智能体工作流的瓶颈：智能体（Agent）的本质是使用工具的大语言模型，而每个工具（如调用SQL脚本、提取数据）都是一个CPU进程。长时间运行的Agent会调用数百种工具，产生大量CPU进程，从而造成CPU瓶颈。
  • 优化目标：提高CPU配比的核心目标是减少GPU在等待CPU完成任务（如脚本执行、数据推送）时的“微小阻塞”（如20毫秒的等待），从而让GPU能更接近其性能极限，提升单任务处理效率。
  1. 重点供应商分析
  2. 如何评价AAOI作为光模块供应商的可靠性及其激光器自供能力？
  • 市场定位：一家不错的生产商，在800G光模块领域表现出色，但并非超高端供应商。其自研激光器在功率上略低于行业顶尖厂商（Coherent、Lumentum）。
  • 核心策略：通过对激光器等关键部件的垂直整合，建立其供应链弹性和成本控制的品牌故事，致力于成为一个可靠的战略性供应商，而非追求市场份额第一。
  • 近期可靠性：短期内表现可靠，近期交付和实验室测试结果均显示了其可靠性。
  1. 对Maxlinear在1.6T DSP市场的看法是否有变？
  • 观点维持不变：依然认为Maxlinear有能力在1.6T DSP市场成为一个“有意义的供应商”，即一个可靠、专业的参与者，但不一定是市场份额第一的主要供应商。

新版prompt提炼之后的转译

我们从 DRAM 谈起。近期有消息称，英伟达为了出货更多芯片，已将其 Vera Rubin 机架的内存配置削减了一半。您如何看待这一动态？贵公司是否计划通过独立的主机 DRAM 或 CXL 内存池来弥补这一削减？

目前内存市场的核心问题是物理性约束。DRAM 及内存供应商的产能扩张速度远跟不上市场需求的增长，这导致了物理性的供应短缺。一旦面临这种短缺，可行的调整方案就非常有限。

如果英伟达减少每个机架的本地系统内存，超大规模数据中心确实会通过增加 DRAM、利用 CXL 进行内存扩展以及部署解耦式内存池等方式来补偿。

但需要明确的是，芯片本身对 HBM 的需求并未改变，我们必须通过这些 DRAM 池来弥补被削减的本地系统内存。然而，这些 DRAM 池本身也面临着非常相似的供应限制。问题在于，市场上内存的总量根本不足以支持所需规模的工作负载。

坦率地说，这个问题没有完美的解决方案，这种供应短缺最终会传导至面向终端客户的定价模型中。

考虑到所有的价格上涨，服务商自身无法完全消化这些成本，最终将不得不提高终端客户的价格。您预计当这种情况发生时，客户的反应会是怎样的？他们会比较容易接受吗？

我确实参与了相关讨论，这是我职责的一部分。在此我不会具体谈论微软，而是从超大规模云服务商和模型提供商的普遍情况来分析，因为一旦涉及具体定价则属于机密信息。

整个行业的发展趋势是明确的。从 GitHub Copilot 和 Anthropic 公布的基于使用量的定价模式可以看出，这些工作流的运行需要大量的资本支出（capex）和运营支出（opex）。服务商不可能永远亏本运营。随着领域内成本的不断上涨，增加算力容量的费用也越来越高，因此他们最终必须将这些成本转嫁给客户。

我们观察到，价格上涨的实际体现方式是，许多提供商并未改变其固定的订阅费用，而是在此基础上增加了基于使用量的计费。

我们以及行业内的许多公司都与客户就此进行了沟通，客户的反应相当负面。这种负面反应并非源于对公司决策本身的愤怒，因为客户理解这些工具的使用量不可能永远增长而没有任何费用回收机制。关键的变化在于，客户群体普遍认为，当计费模式全面转向按使用量付费时，他们尚未为需要进行的内部讨论和需要实施的成本控制做好充分准备。

当一切都转为按使用量计费时，企业必须认真讨论：为每位员工提供个人生产力 AI 工具的投资是否值得？例如，如果每位员工消耗价值 1,000 美元的 token，这笔投资是否划算，是否为组织创造了相应的价值？这是一个非常合理的讨论，但客户感觉尚未准备好进行这样的对话。

大型客户中将会出现类似FinOps的架构，以严格控制其token应用的使用方向。他们会专注于基于用例的消费模式。未来可能会转向为每位员工设置固定的token上限，迫使他们审慎考虑如何使用这些配额。我预计当所有服务都转向基于用量的模型时，这将是行业的发展方向。

但客户不已经是按使用量付费了吗？比如主要通过API的方式。

并非如此。通过API调用的服务确实是按使用量付费，但在非使用量付费的领域也发生了很多变化。

以Claude Code为例，它最初是一项付费订阅服务，用户的使用量不影响价格。但由于用户实际使用量远超订阅价值，尤其是在编码这一全球最大的用例之一上，他们不得不将其转为按使用量付费的模式。长时间运行的代理（agent）和基于代理的推理模型，使得维持订阅模式变得不可行。

目前，大多数商业用例，特别是那些已经SaaS化或围绕其构建了产品的服务，并非按使用量付费。例如，Microsoft Co-pilot就不是按使用量付费。另一个例子是GitHub Co-pilot，这是一个庞大的编码平台，最初采用的是基于许可证的模式。由于使用量巨大，微软也不得不将其转变为按使用量付费的产品。

因此，这个领域正在发生巨大变化，所有服务都趋向于采用按使用量付费的模式，至少对于SaaS产品是如此。API驱动的服务将始终按使用量付费，但它们不一定是传播最快的服务。目前，如果一个企业有像联络中心这样的应用，这是一个典型的API驱动用例，他们会监控成本和价值，这些服务早已是按使用量付费，并被固定在投资回报率（ROI）模型中。但现在的大趋势是SaaS AI，即Salesforce提供Salesforce Agent，微软在其开发工具中提供Co-pilot，以及GitHub Co-pilot或Claude Code这类产品。这种将SaaS分发与AI使用相结合的模式正在改变。

好的。那么当定价模型最终改变后，您认为客户的支出增速会因此明显放缓吗？因为在此之前，他们可能只是将服务开放给所有员工，并没有设置使用上限。

我认为支出增长将不会达到原先预期的水平。不同客户的反应会有所不同。一些客户在建立起成本控制机制前，可能会直接停止支出。

我们来谈谈 DRAM。目前市场普遍短缺，您如何看待其价格上限？是否存在一个价格点，使得采购在经济上不再可行，或者说采购是不可或缺的？我们应该如何看待 DRAM 的整体需求？

DRAM 的需求比想象中更有弹性。当 DRAM 成本在资本支出中占比过高时，情况就会发生变化。具体来说，您能够构建的总容量取决于 DRAM 的总成本。例如，假设您有 100 GB 的 DRAM，这可以支持每天 20 亿个 token 的使用量。最终，您需要为这些 token 定价并对外销售。

市场对这些 token 的支付意愿存在一个上限，一旦价格超过这个上限，市场便会停止购买。因此，当您触及市场愿意支付的 token 价格天花板时，就可以反推出您能为生产这些 token 的 DRAM 支付的最高价格。这就是价格上限的形成方式。

目前我们尚不清楚市场的支付极限在哪里，但已经出现了一些信号。例如，开源模型的激增，以及像 Open Router 这样旨在将请求路由到最佳模型的项目。此外，现在当新模型发布时，比如几天前发布的 cloud fable，我们不再看到企业会立即大规模采用。企业对这些模型的使用变得非常谨慎，因为其定价可能高达每百万输出 token 50 美元，这是一个极高的价格。

因此，随着定价持续推高，需求信号开始减弱。就我们目前所见，DRAM 价格仍在上涨，需求也依然存在，但需求的增长速度正在放缓。市场不会再像以前那样立即接纳每一个新发布的模型。

目前，一些大型云服务商（hyperscalers）正在公开讨论长期供应协议（LTA），据报道他们正在签署这些协议以锁定NAND产能，有些协议甚至持续到2030年或更久。您如何看待这一现象？我的理解是，KV缓存主要存储在DRAM中，那么为什么NAND会突然出现如此严重的短缺？

NAND在数据中心中扮演着多种角色。首先，从最小的应用场景来看，NAND在AI堆栈中用于训练环节。虽然训练主要依赖硬盘驱动器（HDD），但其中存在一个“热数据层”，即准备立即或即将传入GPU的数据。这部分数据实际存储在SSD上。因此，训练规模的增长对NAND有一定影响，其需求不仅限于推理类工作负载。

其次，在推理过程中，虽然DRAM和KV缓存确实用于生成token，但关键问题是这些token是基于什么内容生成的。在任何企业级应用场景中，用户并非仅仅与模型本身进行交互或利用其固有知识，而是在每个提示（prompt）中为模型提供海量的上下文信息。

例如，在基于RAG（检索增强生成）的架构中，上下文可能包括3份相关文档。或者，模型需要从现有企业数据库中提取最新的7个数据点，并基于这些数据点来回答查询。模型的token性能类似于过去的CPU，负责执行“思考”任务，但它必须有思考的对象。所有企业级应用场景都有海量数据被输入到模型中。

以编码为例，整个代码库就是模型进行思考所依赖的数据存储。同样，RAG架构也是在现有文件库的基础上进行思考。企业需要存储所有输入和输出信息，包括传入的提示和模型生成的内容。例如，当用户与GitHub Copilot进行长达40小时的交互时，系统必须能够存储代码库在此过程中的每一次变更，以便用户随时要求恢复到最初的对话状态。可以想象，在超大规模下，所有这些数据都需要被快速访问。

这就是NAND需求激增的原因。它作为底层的数据存储，支持高频或低频的随机访问，并承载着嵌入（embedding）和向量数据库等关键组件。

有一种关于NAND的论点是，在AI智能体（agents）的应用中会产生大量的上下文和思考过程（thinking tokens），这个过程有时会持续30分钟甚至更长时间。所有这些上下文都需要被存储，但由于任务完成时间很长，不一定需要存储在DRAM中。因此，在智能体处理过程中生成的数据越来越多地被存储在SSD中。这种说法是否属实？这是一个相关的应用场景吗？

是的，这确实是一个相关的应用场景，但这只是其中较小的一部分。首先，这类数据从未存储在DRAM中，因为其产生的数据量非常庞大，DRAM不适合用于这种存储。DRAM用于执行计算任务，而不是存储任务结果。

数据生成本身是一个驱动因素，但更关键的是输入的上下文。如果生成的数据量是 1，那么输入的上下文数据量就是 10。输入的数据量是输出数据量的 10x，因为智能体需要获取足够丰富的上下文才能智能地完成工作。

以呼叫中心客服为例：如果客服没有来电客户的最新信息、历史数据以及最近的 10 次查询记录，他就无法提供有效的服务。在这个场景中，输入的上下文数据量远超输出内容。所有这些上下文都存储在NAND中。对于单个应用场景，可能需要将TB级别的数据存储在NAND中，因为智能体可能需要随时调取客户编号 423 的信息，或是 2000 号段的客户资料。所有这些数据都必须以热数据的形式存储，以便智能体随时访问。

关于CPU的情况如何？

是的，CPU的战略地位也将日益重要。我们将看到CPU与GPU的配比发生显著变化，同时CPU性能会成为整个流程中越来越大的瓶颈。

在多智能体（multi-agent）等场景中，CPU的性能至关重要，CPU与GPU的配比最终可能会趋向1:1，甚至可能超过1:1。这是因为，尽管生成Token很重要，但Token的排序、底层脚本（如PowerShell）的运行等任务与商业变现直接相关。如果系统因为等待脚本运行响应而出现延迟，就无法即时生成更多Token，从而导致系统积压，降低了商业化效率和有效工作产出。由于智能体工作流（agentic workflows）等场景都需要CPU的参与，预计CPU与GPU的配比会随着时间推移而提高。

这些CPU与GPU的配比是如何确定的？我记得年初时这个比例大约是0.5。

我们观察到CPU与GPU的配比有从1:1向更高比例发展的趋势。这背后的逻辑是否主要是为了提升GPU的利用率？具体来说，是不是因为CPU性能不足导致GPU无法全时运行，而GPU成本高昂，任何闲置都意味着资源浪费，因此需要为GPU配置更多的CPU资源？

这个逻辑在一定程度上是正确的，但实际情况更为复杂。GPU通常不会完全闲置等待单个任务，它可以在等待CPU输出时切换到其他任务或代理。因此，关键指标并非宏观的利用率，而是每个具体任务的“等待时间”以及CPU层面的瓶颈。

优化CPU与GPU配比的目的是通过分析工作流数据，例如GPU的等待时长、各进程耗时百分比以及CPU的上下文切换频率，来减少这些瓶颈。CPU的上下文切换本身会消耗时间，因为它并非完全并行的处理器，频繁切换任务会延长处理周期。

因此，核心目标是更好地匹配CPU和GPU的能力，以缩短单任务的等待时间。这包括减少CPU向GPU推送数据或完成脚本执行时的延迟。我们关注的是微小的阻塞，而非长期的闲置。例如，当CPU正忙于运行一个脚本时，需要送入模型的数据可能要等待 20 毫秒，这些微小的阻塞累积起来，会导致GPU无法达到其绝对性能极限。

那么在实际应用中，性能提升的效果如何？例如，如果将配置从 1 个CPU对应 2 个GPU调整为 1 个CPU对应 1 个GPU，在时间加权性能上能看到多大程度的改善？

性能提升的幅度与资源投入大致呈线性关系，有时甚至能实现超线性增长。通过减少上下文切换和微小阻塞，即使只是将处理线程数量增加一倍，也可能因为上下文切换频率降低而带来超过一倍的性能提升，具体体现在特定GPU组合内可完成的任务数量上。这种关联是直接的，当然，最终的性能上限仍受限于GPU本身的瓶颈。

对于需要一小时才能完成的 Agent 任务，这种上下文切换（context switching）问题是否会变得更加严重？

是的。对于长时间运行的 Agent，上下文切换问题尤其严重。Agent 本质上是一个能够使用工具的大语言模型。每个工具都是一个 CPU 进程，例如调用 SQL 脚本、从数据库提取数据或从上下文中获取信息，这些都是基于 CPU 的进程。因此，Agent 的性质决定了它比简单的文本输入输出需要更多的 CPU 资源，从而造成了 CPU 瓶颈。

长时间运行的 Agent 情况更糟，因为它们会使用多种工具，等待不同任务完成，然后按顺序输入下一个任务。这类大型任务实际上不是一次大语言模型调用，而是数百次调用，过程中可能使用数百种不同的工具，而每次工具的使用都是一个独立的 CPU 进程，这进一步加剧了 CPU 瓶颈。
