核心摘要

  1. 专家认为GCP并不想做开源模型托管，人才被调去做Gemini，用户体验从不优先；AWS是三大云中唯一有竞争力的，微软难以深入基础设施层。
  2. 目前只有微软把Fireworks能力嵌入自身平台，GitHub和Copilot部分模型直接跑在Fireworks上；Google因不愿使用Fireworks品牌而未能合作，亚马逊偏好单干。
  3. OpenAI已停掉纯自助的self-serve训练服务，企业做深度定制需交出数据和harness，因此更倾向选开源模型自建，而非OpenAI/Anthropic。
  4. CoreWeave推出Forge推理平台不足为虑，多数neocloud只是套用开源SGLang/vLLM，真正能做好吞吐和延迟优化的只有Fireworks和Baseten。
  5. 后训练方案到2026年已趋同为类似Thinking Machines的训练API，企业工程师更愿意写代码而非一键式产品。
  6. Palo Alto收购Applied Compute对其安全模型帮助有限，核心在数据而非基础设施；PANW推理仍会走Fireworks，GB300上开源模型可达1800-2000 token/秒。
  7. Fireworks第二次被黑源于新加坡开发机被代码注入，攻击者窃取数据集和API key并转卖，公司需花1-2个月全面加固安全。
  8. 此次泄露导致几个知名但AI化程度不高的客户关停服务，专家认为迁移到其他平台风险相同。

摘要

/ 北美云厂在后训练和推理服务上的能力对比。/ 企业AI落地挑战，大厂短期二次被黑的影响。

【以下为专家观点汇总，具体细节仅供参考。】

怎么对比三大云厂商目前在企业垂类模型训练和落地的能力以及增长前景？

不是我说GCP不能打，而是GCP根本就不想打。比如你去和GCP合作，他们会说支持这些SOTA模型，但实际上Google是在把人往外撤。很多有能力的人都被调去做Gemini了。所以长期来看，Google未必想继续维护这些开源模型，对他们来说R OI太低。如果能把Gemini做好，收入是有保障的，但支持一堆开源模型，回报能有多少？即使在平台上支持了开源模型，用户还是会流失。过去四五年，GCP从来不以用户体验为优先，所以用户大概率会流失。比如企业最初为了合规在GCP训练模型，后期只要法务、合规部门和Fireworks达成合作，审查通过后，用户就会立刻切换，而且还更便宜。所以Google其实没有什么动力。AWS可能是这三家里唯一有竞争力的。整体来看，它的服务尤其是在基础设施增值服务上，体验比较差，速度慢。微软整体是一个比较弱的公司，要让它深入到基础设施层面，做模型核心训练和大规模GPU并行，对微软来说太难了。

还有哪些云厂商或者AI Lab是直接把Fireworks的能力嵌进去的？

没有，目前只有微软，其他Fireworks不合作。其实大家要么合作，要么竞争。Google之前找Fireworks谈过合作，愿意给Fireworks分成，比如Fireworks的需求放到GCP上跑，GCP除了提供硬件资源，还会分成。但问题是他们不愿意用Fireworks的logo，这对他们来说很尴尬，因为一直强调自己是AI First公司，结果开源模型用的是Fireworks方案，所以Fireworks就不和他们合作了。微软愿意这么做，愿意提供部分硬件，也愿意公开宣布合作，甚至微软自己的GitHub和Copilot的一些模型也直接跑在Fireworks的平台上，所以合作更紧密。亚马逊基本不和任何人合作，他们喜欢自己单干。

是否听说近期OpenAI/Anthropic的垂类模型训练业务和FDE团队进展？

他们没有披露太多，现在他们企业客户规模也大了，一般来说，如果用户决定把数据交出去做自己的模型，大概率不会和OpenAI合作。你看OpenAI官网，已经把纯自助的self-serve training服务停掉了。这和Fireworks遇到的情况很像，现在想把训练服务做成傻瓜式、一键触达的，适用范围非常有限，只能满足一些非常简单的客服场景。更深入的，比如需要和客户深度合作的，就做不了，双方团队必须配合。

你比如说，如果像 Harvey今天让我训练他的模型，他得首先把 harness 给我。Fireworks做大规模的强化学习，这种多步的 rollout，具体要调哪个工具、反馈是什么，这些都必须模型和 harness结合起来一起做。所以对于很多公司来说，一旦进入深度定制，他们既要把数据给出去，又要把 harness 给出去，这对他们来说是非常有顾虑的，因为 OpenAI 转手就可以把他们的工作做了。

基本上，如果公司想明白了，不再用他们的模型，也不愿意为溢价买单，想自己深入做，那就会直接选择开源模型，而不会选他们的模型。他们的模型或者 FDE 主要的切入点还是在于帮助科技公司之外的企业做落地。比如大量对接 agent、co-work这类场景，他们公司内部的工作流有各种工具，怎么把权限打通，这是他们关注的重点。实际上，真正做定制化训练的企业并不多。

怎么看最近CoreWeave上线了自己的Forge推理平台？意味着Fireworks也不会和他们合作了？

Fireworks其实一开始和他们合作得不多，2023年到2025年期间短暂合作过一点。但我觉得没什么可担心的，因为很多 neocloud都在做这些事情，比如 GMI Cloud、LAMBDA Labs这些小型云厂商也都在做，但本质上能做好的非常少。大家基本上是把开源的 SGLang 或者 vlm拿过来跑一下，就生成了自己的服务，仅此而已。真正能把整套服务做得足够可靠，把用户的吞吐、延迟等指标优化到理想水平的公司其实很少。可能除了Fireworks，也就是 Baseten 还有点竞争力，其他的Fireworks基本没怎么关注。

怎么看Applied Compute在后训练和推理优化上的能力？

我理解 Applied Compute 现在采取的完全是纯 FDE 的切入方式。比如一些企业有各种需求，但 Fireworks 的逻辑是先尽可能把推理的 kernel通用化。对于用户潜在的需求，有的关心延迟，有的关心吞吐，Fireworks先做成通用产品。比如像 thinking machine labs 一样，Fireworks也有自己的 training API。真正有客户需求时，Fireworks就单纯看他的 use case，现有的训练基础设施没必要重新开发。但 Applied Compute 的逻辑就是纯FDE，和企业深度绑定，像打长工一样，直接去客户厂里，把模型一个个手动训练和跑，类似 researcher as a service 的逻辑，所以他们没有公开的服务。

Applied Compute更核心的 offering 是后训练，现在招人是不是主要招 FDE？

他们现在想系统性地做后训练。我觉得后训练这项工作长期来看会特别趋同。2425年时大家的方案还百花齐放，各不一样。到26年，基本上大家的方案都统一了，都是类似 thinking machine labs 这种训练API。25年大家还想着怎么把训练做得越简单越好。但你会发现，强化学习算法从一开始就有很多天生缺陷。不管怎么配置 reward，对于数据集分布和 reward 设置其实都需要人去看。比如任务设置太简单，像 grpo这种算法其实学不到什么；如果太难，所有模型打分都是0分，也学不到东西。所以对数据 setup 和算法稳定性都是考验。

Fireworks当时把这套东西做得很简单，还做了个很 fancy 的网页，告诉用户怎么自己看训练的 loss curve，结果发现根本没用，用户既不想看也看不懂。最后结论就是“你帮我看”。所以Fireworks发现自己搞了套 fancy的东西，最后只有自己用，客户根本不关心。最后Fireworks也选择了像 thinking machine labs 这样的方式。

最早Fireworks还质疑过他们，觉得搞个 API 还要自己写代码，谁会用？其实只有高效的 researcher 或 PhD 会用。但除了刚才说的原因，还有一个原因很多企业没想到，就是他们喜欢写代码。你卖的是 to B服务，使用产品的人其实是客户公司的工程师。如果产品做得太简单，比如只要点两个按钮就能完成，他们反而会觉得产品不够高端，会提出各种奇怪的要求，比如透明度不够、需要定制化等。实际上他们追求的是还有活可以做。如果你把基建搭好，比如让1000个GPU 并行跑，但模型训练过程中的 loss、reward 这些还要他们用代码实现，他们反而觉得你是来帮忙的，不是来抢饭碗。所以有很多这样的细节迭代在里面。今天来看，大家又都回到了纯写代码做训练的路径上。Fireworks帮助你把 GPU可靠性问题解决了，包括怎么在 moe 前向后向传递梯度和权重，这些Fireworks来解决。

怎么看Palo Alto Networks收购Applied Compute对PANW做安全模型的实质性推动？或者能在其他网络场景下有帮助吗？

个人预计非常有限。现阶段做模型，本质上最关键的是数据。如何筛选高质量的数据，以及如何从比如 multi turn agent trajectory 里筛选可用的训练信号，然后再进行蒸馏，或者生成更多的 hint，现在像 on-policy self distillation 这些方法，基本都是这个思路。最近 Applied Compute 推出的 continue learning 产品，其实也是按照这个思路做的。实际上，核心工作还是在数据层面。infrastructure方面，比如 palo alto networks 本身用的就是Fireworks的训练平台，这部分其实他们可以不用太在意。

Palo Alto和 Fireworks 的合作涉及哪些方面，规模？以后还会继续用 Fireworks？

推理肯定还是走 Fireworks，训练可能他们想自己做，因为推理层面无法绕过底层 GPU 的 infrastructure。当然。最近Fireworks把一些开源模型跑到了 GB300 以上，基本可以达到 1800 到 2000 个token 每秒，比如 Kimi 现在的模型也能做到至少 1500 个 token。对于他们的安全 use case 来说，这其实很关键。原本Fireworks希望模型能跑到接近 2000 token 每秒，这样大部分客户，尤其是写code的用户，体验会非常好，很多生成任务一秒就能完成。但实际上最早来找Fireworks的也是他们。Fireworks和他们的关系很特殊，一方面卖给他们推理服务，另一方面又采购他们的安全产品。最近Fireworks在安全方面也遇到了一些挑战。比如现在researcher 访问用户数据做训练，整个过程都需要 two factor authentication、人脸识别等多重验证。以前很多跨服务的云上 service account，黑客其实很容易获取。现在Fireworks作为infra 公司，本身没有获取用户数据的动机，任何用户来找Fireworks，Fireworks都去对方的数据环境访问，并且访问也需要人脸识别，完全是人工操作。我宁可不在用户数据上获取任何 insight，也不愿再冒这个风险。

Fireworks最近第二次被黑了的严重程度？在采取什么补救措施？

这次被黑确实没办法。原来被黑时，比如企业自己做大量 by coding，代码和各种内容只要权限上有疏漏，基本上全公司的人都会受影响。攻击者只要能进入系统，基本上就能获取所有人的服务和权限。第一次被黑后，Fireworks将内部大部分人的github 账号全部更换，各种 key 全部撤销并重新生成，基本上就挡住了。

第二波攻击就更难防了。Fireworks自己开发的机器在新加坡的几个 dev machine 上，攻击者用了代码注入的方法，很可能也是 AI 实现的。他们在加载模型权重时执行了恶意代码，hugging face其实也有类似功能。攻击者在执行代码时植入木马，把自己的 bot 插件挂到 GPU 集群上。从那以后，只要Fireworks通过那台机器访问内部服务，攻击者也能获取相关信息。

他们主要做两件事，一是窃取用户数据。比如程序员写代码时，难免会输出一些文件路径，如果是 gcs 路径，攻击者就会去扫描，发现是数据集就会窃取数据集。如果是 api key，就会把 api key拿走。Fireworks这边很多工程师也有自己的 bot、codex、anthropic，攻击者拿到这些 api key 后会转卖。比如像 Fireworks 这样的公司，每家公司搞50个 key，10家公司就有500个key，理论上就能形成一个算力池，然后在其他平台上把服务卖出去，用户付费使用。这是一种常见的手法。数据被窃取后也会被转卖。

实际上Fireworks一开始的风险意识确实不够。当然，防护的代价也很大，相当于要把整个基础设施彻底排查一遍，包括云端运行的 gateway 等，服务与服务之间现在都是微服务架构，也需要各种认证。除了防范 api key被盗，还要限制服务之间的 ip 白名单，这些都是额外的负担。整个公司可能一到两个月都要专注于安全工作。这次的疏漏，基本上就导致了第二次重大损失。

这次被黑好像涉及到一些模型weights和数据集，有没有观察到一些大客户因为最近的安全事件担心数据隐私问题迁移到其他厂商？

实际上迁移到其他厂商也没用，其他厂商只可能比Fireworks更差。Fireworks作为最大的平台，是第一个被攻击的。但你迁到 base，base也有同样的问题。我不认为其他厂商会更安全。这次数据泄露确实导致有几个客户离开了，但这些客户虽然名气大，整体服务的 AI 化做得并不好。

迁移走的客户会迁到哪里？

他们只是把服务关了，目前还没有确定迁移到哪家。实际上我认为无论迁到哪个平台，风险都是一样的，没有区别。
