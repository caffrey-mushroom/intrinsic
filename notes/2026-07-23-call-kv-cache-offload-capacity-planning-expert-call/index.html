专家访谈会议纪要

1. AI推理集群的容量规划与全球部署

a) 大规模AI服务应如何规划Pod及KV Cache容量？

  • AI服务请求通常具有高并发特征。以云服务及企业许可证客户为例，可能同时有1,000、10,000乃至100万名用户访问。
  • 容量规划需要从用户规模反向推算：
  1. 先确定每个Pod需要承载的并发用户数。
  2. 再根据并发规模、上下文长度及缓存保留时间测算KV Cache容量。
  3. 单个Pod可能需要配置10—100PB容量。
  4. 最终将相应配置复制到美国东海岸、西海岸、亚洲和欧洲等数据中心。
  • 请求应从初始阶段进行智能编排和就近路由。例如，中国或日本用户应由亚洲数据中心处理，而非发送至美国。
  • 全球调度的核心优化目标包括：
  1. 降低首个Token响应时间。
  2. 提升Token处理效率。
  3. 减少跨区域网络传输。
  4. 提高各Pod的缓存命中率和资源利用率。

b) HBM供应受限时，闪存能够发挥什么作用？

  • 每个Pod需要同时配置HBM、DRAM和闪存，其中闪存通常是容量最大的资源池。
  • HBM供应受限，无法完全依靠增加HBM满足用户及Token增长，闪存是现阶段最现实的容量扩展方案。
  • 在现有计算硬件不变的情况下，通过增加闪存承载KV Cache，可支持约10倍的用户规模。
  • 如果不使用闪存卸载，现有基础设施可能只能支持原有方案约1/10的用户数量。
  • 闪存的核心价值不是替代GPU计算，而是提升已部署GPU机架的服务能力、Token产出能力和收入能力。

2. HBM、DRAM与闪存的分层架构

a) AI存储体系应如何划分层级？

  • AI推理存储体系可划分为热层、温层和冷层：
  1. 热层：以HBM3E、HBM4及部分DRAM为主，承载最活跃、对延迟最敏感的数据。
  2. 温层：以本地或网络化NVMe SSD为主，承载KV Cache、长期上下文和高命中率数据。
  3. 冷层：以全闪存对象存储为主，承载共享数据湖及对延迟要求较低的数据。
  • 第1层通常由HBM与DRAM共同组成。单个Pod的HBM容量通常只有1—2TB，而DRAM可以达到数十TB。
  • 对Anthropic、OpenAI等大规模AI服务商而言，模型、权重、上下文及用户状态无法全部装入HBM和DRAM，因此必须从本地或网络化NVMe闪存中调取数据。

b) 各存储层级的延迟边界如何划分？

  • 原始访谈给出的延迟划分为：
  1. 低于1微秒：主要由HBM承担。
  2. 10—200微秒：适合采用第2层闪存。
  3. 200微秒—10毫秒：可进入对象存储层。
  • 软件需要根据工作负载类型、缓存命中率、上下文大小及服务等级协议，动态决定数据在HBM、DRAM和闪存之间的放置与迁移。

c) 推理不同阶段应分别使用什么介质？

  • 活跃Token生成，即解码阶段，以及当前活跃KV Cache，主要放在HBM中。
  • 需要保留数分钟至数小时的多轮会话上下文，通常放入基于闪存的KV Cache。
  • 对象存储主要采用全闪存架构，用于共享数据湖及延迟要求相对较低的场景。
  • HBM负责最高性能的即时计算，DRAM负责补充HBM容量和部分批处理，闪存负责大规模、持久化、可共享的上下文存储。

3. DRAM与SSD的适用边界

a) 为什么SSD在部分KV Cache场景中可能优于DRAM？

  • 从单颗芯片的访问延迟看，DRAM快于闪存；但从完整推理流程看，结果可能相反。
  • 当上下文无法完整装入DRAM时，系统需要频繁驱逐数据，并在后续请求中重新执行Prefill或重建上下文。
  • 频繁重建上下文会消耗大量GPU计算资源、时间和成本，其性能损失可能高于通过高速网络读取共享闪存KV Cache的开销。
  • 因此，对长上下文、高并发和高缓存命中率场景而言，SSD能够避免重复计算，从系统层面获得比DRAM更好的响应效率。
  • 如果对所有机架和Pod进行统一编排，共享闪存能够支撑百万级用户，并提高整体缓存命中率。

b) 哪些工作负载更适合HBM和DRAM？

  • 图像、Logo、视频等内容生成通常具有以下特点：
  1. 请求高度个性化。
  2. 重复内容较少。
  3. 单次生成后缓存复用价值有限。
  • 此类工作负载更适合路由至HBM和DRAM，完成生成后迅速逐出相关数据，再处理下一项任务。
  • Sora等图像或视频生成平台更依赖HBM，其大规模长期KV Cache需求相对有限。

c) 哪些工作负载更适合闪存？

  • 大语言模型、聊天机器人、代码生成、自动化、文档分析、翻译和预测类工作负载，更适合将上下文及KV Cache卸载至闪存。
  • 此类工作负载通常具有：
  1. 上下文较长。
  2. 多用户共享相同基础数据。
  3. 对相同上下文反复调用。
  4. 缓存命中率较高。
  • 结论上，DRAM主要用于支持GPU批处理规模并补充HBM不足；经过软硬件优化后，大规模KV Cache最终将更多卸载至闪存。

d) CXL扩展DRAM是否会替代闪存方案？

  • CXL仍处于较早发展阶段，Amazon和Google目前尚未在相关生产环境中大规模使用。
  • CXL未来可能成为扩展DRAM容量的手段，但当前AI工作负载并不完全适合依赖DRAM承载全部上下文。
  • 只有在HBM容量不足且工作负载适合时，系统才会使用DRAM补充。
  • 长上下文、高复用率和跨节点共享场景仍更适合闪存KV Cache。

4. KV Cache卸载的行业渗透与技术生态

a) KV Cache卸载目前处于什么发展阶段？

  • KV Cache卸载大约在过去1年内已变得较容易实施。
  • 美国在该领域领先亚洲和欧洲：
  1. 美国接入率已处于约80%区间。
  2. 欧洲和亚洲目前约为20%。
  3. 部分亚洲市场仍处于个位数渗透率。
  • 美国部分客户的KV Cache初始容量约为100TB，随着许可证及用户规模增长，一年内可能提升至500TB，部分订单预计最终增长至初始规模的约10倍。
  • 市场需求既来自已部署系统扩容，也来自新建数据中心预配置大规模闪存。

b) 亚洲市场的进展如何？

  • 亚洲本土企业对KV Cache卸载的认知仍相对不足，但市场已经开始起步。
  • 进入亚洲市场的美国超大规模云服务商通常已经了解并采用相关方案。
  • 亚洲本土Neo Cloud公司也开始建设KV Cache集群。
  • 印度部分企业已在KV Cache卸载方面投入较多资金。
  • 专家已开始获得亚洲地区KV Cache Pod建设订单，预计区域渗透率将继续提升。

c) Nvidia目前如何推进KV Cache闪存架构？

  • Grace Blackwell 200配置了本地NVMe，并通过BlueField 3连接多个NVMe和NIC。
  • 现有本地NVMe主要用作暂存空间，适合存储临时文件或部分训练检查点，无法充分满足企业级KV Cache卸载需求。
  • Nvidia正转向BlueField 4和CMX机架，并计划配置高性能、高成本闪存，再将CMX与计算机架连接。
  • CMX预计成为Nvidia下一阶段KV Cache卸载或高速训练存储方案之一，计划于下一年度推出，当前设计仍在完善。
  • Weka等合作伙伴正参与相关软件定义存储方案，未来可能形成面向Nvidia CMX的专用版本。

d) 不同芯片及云平台是否都会采用闪存KV Cache？

  • KV Cache卸载并非只有一种实现方式：
  1. Amazon可使用自有硬件、Nitro及闪存。
  2. Google和Azure可使用常规软件定义KV Cache架构。
  3. AMD正围绕Helios机架探索配套存储机架。
  4. Nvidia正在推进BlueField 4与CMX。
  • 无论底层采用Nvidia、AMD还是定制ASIC，最终都需要建设KV Cache卸载网络。
  • 专家判断，其核心存储介质将持续是闪存，且容量会随用户、Token和上下文长度增长而不断增加。

5. KV Cache的服务化与客户分层

a) AI服务商如何根据客户类型分配KV Cache？

  • Anthropic等AI服务商会按照客户价值和许可证类型划分不同服务层级。
  • Tier 1战略企业客户通常具有：
  1. 企业许可证。
  2. 至少1,000名员工。
  3. 更高的月度付费金额。
  • 此类客户会被分配更大规模的KV Cache和配置更高的Pod，以保证更快的响应速度和更稳定的服务等级。
  • 高校、学生、个人或小团队客户获得的KV Cache规模较小。
  • 中型企业通常被路由至其他Pod，等待时间及首个Token响应可能略长。

b) 为什么KV Cache已经成为一项战略性服务？

  • 原因主要包括：
  1. HBM供应短缺，需要更灵活地组合使用DRAM和闪存。
  2. 企业客户贡献更高收入，对服务速度和稳定性要求更高。
  3. 如果响应速度下降或首个Token等待时间持续增加，AI服务商可能失去高价值客户。
  4. 不同规模的KV Cache能够直接形成不同等级的服务体验。
  • KV Cache已不再只是底层技术资源，而是服务等级、客户留存和商业定价的重要组成部分。
  • AI服务商可以通过不同缓存规模、缓存时长和Pod配置，为不同付费层级提供差异化服务。

6. Agent工作负载对KV Cache的推动

a) Agent AI为何会改变传统推理基础设施？

  • 传统推理调用持续时间较短：用户提出问题、模型回答后，会话进入休眠。
  • Agent AI具有自主、非线性和循环运行特征：
  1. 一个用户提示可能触发一个管理Agent。
  2. 管理Agent可能协调另外多个子Agent。
  3. 子Agent会调用API、阅读论文和PDF、编写工具并分析其他Agent输出。
  4. 工作流可能持续数小时，甚至全天候运行。
  • 因此，推理基础设施从计算密集型读取操作，转变为持续、突发且内存密集的读写操作。
  • 内存数据需要长时间往返传输，闪存因而成为Agent工作负载的关键基础设施。

b) 为什么Agent工作负载会显著增加缓存命中需求？

  • 多个Agent处理同一项目时，通常会共享：
  1. 核心指令。
  2. 工具模式。
  3. 企业数据集。
  4. 前序Agent生成的上下文。
  • 如果每个Agent在多步循环中不断重新加载或重新计算相同上下文，会迅速占满GPU内存并带来严重延迟。
  • 相较于反复执行Prefill，将上下文保存在KV Cache中具有更高投资回报率：
  1. 避免重复计算。
  2. 降低GPU成本。
  3. 缩短响应时间。
  4. 提升Token产出效率。

c) 多节点调度为什么需要共享KV Cache？

  • 分布式推理通常通过负载均衡器执行：
  1. Agent工作流的步骤1可能在节点A执行。
  2. 步骤2可能被调度至节点B。
  3. 如果节点B没有节点A的历史KV Cache，就必须跨网络拉取数GB数据或重新计算全部历史记录。
  • 重新计算成本高、速度慢，跨节点传输也会形成突发性I/O压力。
  • 解决方案是建立全局上下文数据结构和多节点共享KV Cache：
  1. 节点A完成任务后，通过高速RDMA将KV Cache同步写入共享闪存层。
  2. 节点B启动后，以接近线路速率获取相同预计算缓存块。
  3. 该架构可实现约90%的缓存命中率。

d) 全局KV Cache应如何进行生命周期管理？

  • 未来KV Cache不能只依赖基本的最近最少使用淘汰策略，而应具备生命周期感知能力。
  • 编排器需要监听Agent工作流终止信号：
  1. 私有任务完成后，将相关缓存标记为已完成和停用。
  2. 对不再使用的数据进行主动清除。
  3. 对共享工具、公共指令和高频企业数据进行长期固定。
  • 目标是形成既能主动清理低价值缓存、又能长期保留高价值公共上下文的全局缓存体系。

e) 预测性预取如何提升Agent执行效率？

  • Agent工作流通常基于执行图运行，系统可以根据历史概率预测后续会调用哪个Agent。
  • 当GPU仍在处理Agent A时，存储系统可以异步提取Agent B所需的上下文。
  • 在Agent A输出最终Token前，Agent B的数据已经从冷存储迁移至热层HBM。
  • 预测性预取能够：
  1. 缓解KV Cache反压。
  2. 减少Agent切换等待时间。
  3. 提升GPU利用率。
  4. 降低跨节点重复计算。
  • 该能力将成为现代Agent编排器和Agent路由器的重要组成部分。

7. KV Cache的重点应用场景

a) 代码服务为什么会产生大量KV Cache需求？

  • 企业软件可能包含100万行代码，不适合在每次请求时重新加载、分析和创建上下文。
  • 将整个代码库保存在闪存中，可以支持不同用户围绕同一代码库提出不同问题。
  • 例如：
  1. 用户1询问如何创建日志程序。
  2. 用户2询问如何改进图形用户界面。
  3. 用户3分析数据库相关模块。
  • 所有用户使用同一代码库，但关注不同部分，因此具有很高的缓存复用率。
  • 代码服务是KV Cache的重要场景，但并非唯一场景。

b) 法律、保险和合同处理行业如何使用KV Cache？

  • 律师事务所处理案件时，多名律师会共同使用案件材料、证据和法律文件。
  • 将相关资料保存在KV Cache中，可以避免不同律师或不同Agent反复重建相同上下文。
  • 保险公司、产权公司、物业管理机构、翻译公司和合同处理机构同样属于文档驱动型企业，具有较高缓存命中率。
  • 合同在处理、审核和签署期间可以持续保存在KV Cache中，提升流程效率。

c) 金融服务和资本市场有哪些应用？

  • 彭博、路孚特等数据流每天产生大量市场和交易数据。
  • 市场收盘后，数据仍需被对冲基金、投资银行和量化工程师反复调用，用于预测股票、数字货币和外汇市场走势。
  • 将市场数据保存在缓存中，可避免每天重新构建数据上下文。
  • 研究团队也可以将访谈笔记、研究文档和投资分析材料放入共享缓存，供多个成员和Agent重复使用。

d) 生命科学和药物研发有哪些应用？

  • 药物研发涉及试验数据、患者数据、化合物资料及多名工程师或研究人员协作。
  • 将相关信息放入KV Cache，可以提高实验分析和药物研发效率。
  • 基因组学、生命科学和制药企业均属于潜在的高价值KV Cache应用行业。

e) 哪些场景不需要大规模KV Cache？

  • 高度个性化且复用率低的图像、Logo和视频生成场景，通常不需要特别大的长期KV Cache池。
  • 此类业务更依赖HBM进行即时生成，任务结束后即可逐出相关缓存。
  • 判断KV Cache价值的核心，不是行业名称，而是上下文是否需要长期保留、跨用户共享和反复命中。

8. 存储供需、增长曲线与行业趋势

a) 当前哪些存储资源真正短缺？

  • 当前最严重的供应问题是HBM，专家预计HBM短缺可能持续约2年。
  • DRAM、CPU和闪存目前仍可获得，尚未观察到同等程度的供给问题。
  • 部分供应商的交付周期较长，可能拖延销售和项目建设周期，因此需要扩大供应商范围，实现供应链多元化。

b) 未来闪存需求将如何增长？

  • 数据中心NAND需求正在从线性增长转向指数级增长。
  • 过去，NAND需求主要随文件和数据库数据量同步增长；AI推理、KV Cache和Agent工作负载正在显著抬升增长曲线。
  • 主要推动因素包括：
  1. 长上下文持续增长。
  2. 同时在线用户增加。
  3. 模型和权重规模扩大。
  4. Agent工作流延长并循环运行。
  5. 跨节点共享缓存需求增长。
  6. 数据中心逐步从HDD转向高密度SSD。
  • 即使GPU算力增速趋于稳定，KV Cache保存时间和容量仍会继续增长，因此闪存需求有望保持高增。

c) QLC企业级SSD的需求趋势如何？

  • Tier 1服务商开始替代或逐步减少传统硬盘使用，转向高密度QLC SSD。
  • Google和Azure在QLC部署方面较为积极。
  • Amazon由于拥有Nitro卡，可以通过Nitro加速硬盘，架构路径有所不同，因此对QLC的依赖相对存在差异。
  • 原始会议口径显示，企业级SSD收入已出现约86%的显著增长，反映数据中心存储需求快速提升。
  • 市场资源和产业投入正从移动设备、PC等消费电子领域，转向高容量数据中心存储基础设施。

9. 闪存价格、采购策略与产业链影响

a) 闪存涨价是否会阻碍客户采购？

  • 对大型超大规模云服务商而言，价格不是主要障碍：
  1. 通常会与Micron等供应商签订长期协议。
  2. 长期协议可限制价格波动。
  3. 大批量采购能够获得折扣。
  4. 大客户通常可优先获得库存。
  • KV Cache能够减少重复Prefill和GPU计算，投资回报率较高，因此即使闪存价格上涨，大型客户仍有较强采购意愿。

b) 闪存价格上涨对不同类型公司有何差异？

  • 软件定义存储企业：
  1. 客户自行采购闪存硬件。
  2. 软件企业不直接承担主要硬件成本。
  3. 高软件毛利率能够抵御闪存价格波动。
  4. 专家所在业务的软件毛利率仍在70%以上。
  • 硬件及一体机企业：
  1. 需要直接承担闪存和内存成本上涨。
  2. 如果没有长期采购协议，成本上升会明显压缩毛利率。
  3. 例如原制造成本约2万美元的一体机，成本可能上升至3万—3.5万美元。
  • 闪存涨价的影响取决于企业处于软件、硬件还是云服务环节，其中硬件厂商承受的压力最大。

  • 长上下文及Agent AI将推动企业级SSD、QLC、高性能NVMe、RDMA网络和软件定义存储需求。
  • 超大规模云厂商、Neo Cloud、AI实验室及自建集群企业将持续扩大KV Cache容量。

  • 长期来看，AI基础设施的竞争重点将从单纯增加GPU算力，扩展至计算、网络、内存和存储的系统级协同。
