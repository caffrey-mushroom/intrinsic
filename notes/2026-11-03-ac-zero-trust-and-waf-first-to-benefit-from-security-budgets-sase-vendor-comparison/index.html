【以下为专家观点汇总，具体细节仅供参考。】

PHP漏洞目前波及的范围？近期是否看到较严重的渗透事故？

首先，P2P2Shell这个漏洞影响非常广泛，几乎全球范围内都知晓这件事。主要原因在于权威媒体和国家机构的介入，这与以往只在特定社区、项目或公司内部流传的零日漏洞不同。PHP这种模式的网站覆盖面极广，有统计数据称其占比超过70%。很多安全路径的结构本身就是PHP，比如Palo Alto或Fortinet等硬件设备的防火墙和管理接口，可能都是基于PHP开发的。这种攻击并不局限于某一台服务器，而是覆盖整个链路，中间的安全防火墙本身也可能成为攻击目标，这是最危险的地方之一。

这个漏洞的暴露方式也很特殊，不像某些漏洞需要泄露信息或人员参与才能完成攻击。它属于直接提前暴露的漏洞，只要页面是PHP，甚至不需要登录或找到可登录接口，就可以被利用。由于覆盖面超过70%，影响非常大。一旦漏洞被公开，权威机构就会迅速介入，比如欧洲、日本、中国的相关单位会直接通知，要求所有PHP网站下线，直到修复后再上线。有权威机构参与，响应速度远快于以往单个社区的处理方式。

据观察目前并没有严重的利用案例，没有出现PHP2Shell导致重要网站或政府机构被攻破、敏感信息泄露的情况。包括黑客组织和勒索团伙，也没有通过该漏洞造成重大事件。响应速度快的情况下，漏洞没有被大范围利用，但攻击行为确实大范围存在。即便在漏洞发布前，Cloudflare内部也提前不到24小时观测到攻击流量上升，我个人网站也出现类似情况。当时还疑惑为何突然有攻击，后来才知道是PHP2Shell漏洞被曝光，大家开始扫描相关目标。

但目前来看，真正造成重大影响的案例还没有出现。很多受影响较大的单位都很配合，直接下线服务。如果漏洞只影响小部分人，反而更危险，因为大家难以及时知晓漏洞存在及其业务影响能力。如果同行都在线，企业也不愿下线，担心业务损失，比如去哪儿旅行、携程、飞猪等都是PHP网站，若同行不下线，老板也不会让自己下线。但这次权威机构直接要求停服，大家都采取了紧急措施，商业成本均摊，防御及时，没有造成大范围成功入侵的影响。

是否预期PHP漏洞的问题在短期质推动Cloudflare的获客和现有客户安全预算的增加？哪个安全细分会最先最多受益？

大家对安全预算的紧迫感会提升，但很难直接与获客提升挂钩。以这次安全事件为例，它属于严重的大型事件，没有安全公司会把这种事件当作卖点，因为它已经成为公序良俗的一部分。即使你不购买Cloudflare的产品，也会受到保护，这其实已经超出了常规。Cloudflare提前将安全策略部署在全网的WAF上，无论是免费用户还是企业级用户，都有相应的拦截措施，而且这些措施早于漏洞公布时间就已上线，内部安全团队有能力提前掌握漏洞信息。也就是说，即使你不付费，也能获得保护。大家可能会有后怕，觉得如果没有用Cloudflare，影响可能会更大。这会增强Cloudflare在安全领域的获客能力，把社区入口和中长尾入口把控得更严，大家更倾向于使用高分免费服务，从而扩大存量客户池。这是一定的，但我不认为这会直接带来收入，因为这不是高级安全功能，而是更基础、更具社会道义的功能，只要使用就有，不会因此产生额外付费。即便获得了用户池，要真正转化为企业级用户，中间还有很长的路，可能需要一两个季度。大家对安全能力的需求会更紧迫。

当前安全攻击的风潮也在变化，比如最近Cloudflare发布的新报告，涉及DDoS等问题。过去有几个大型犯罪组织，僵尸网络被打掉后，大规模攻击大幅减少，但攻击频次却涨幅超过200%。由于AI和安全工具普及门槛降低，绝大多数人都可以发起一定量的攻击。小型攻击对安全预算的要求更高，小型攻击不挑目标，谁都可能成为目标，安全产品需求的紧迫性大幅提升。这次事件也是一个影响，后续安全暴露风险会越来越多，安全预算一定会上涨，但具体涨到Cloudflare这个层级还是其他地方，我不好判断。

这种紧迫感会率先体现在防火墙支出、相关软件订阅、WAF、SASE/零信任等哪个方向？

我比较看好两个方向。第一是WAF，这很直观，现在暴露面增多，之前没有WAF或WAF较弱的企业一定会升级这部分，但附加价值不是很高。伴随的还有Bot Management、自动化防御、API防护、Shadow API检测、报告、SOC安全平台等，把所有功能整合分析。这是最基础的，缺乏就必须投入。

第二个新赛道是AI agent，主要带来身份管理。我最近写过博客，安全公司并购时，买的都是观测入口和身份入口，更偏向零信任概念。我一直看好零信任，SASE在AI时代最有价值扩展，把管理模式从人转到AI agent，逻辑是通的，可以复用很多东西，agent权限管理、行为判定都能通过这套系统实现。AI时代，SASE受影响最大。行业里像Palo Alto等公司，之前做SOC不太好，主要做硬安全WAF，但现在收购CyberArk等身份认证公司，做行为管理，大家都看好这条线。原生做SASE的如Zscaler、Cloudflare等公司在赛道上有优势，因为这需要技术积累和行业声望，不是普通安全公司能轻易切入。像CSD、SGW、SSE等功能都需要长期市场积累，从品牌到实际应用都需要时间。很多公司通过收购完成品牌升级，自研难度较高，已经站在赛道上的公司会受益。

Cloudflare One作为 SASE 主要方案，近期是否有重要的获客或实质业务进展？outperform其他方案？

Cloudflare One是Cloudflare主推的SASE产品，是整体解决方案，不仅包含身份安全，还包括基础网络安全，比如Magic WAN和Cloudflare自有的SD-WAN产品。维基百科等大企业、各地运营商都在用这种产品，主要服务对象还是大型企业。后续可能会有类似FDE或安全监控团队，专门做大客户支持，提升大客户粘性。

如何对比 Cloudflare One与 Zscaler、Netskope 方案的竞争优劣势？目标客户群体有何不同？

Cloudflare内部目前主要和Zscaler做比较。首先，Cloudflare有一定优势。考弗莱的一个优势是单一数据面，更符合现在安全平台的趋势，比如安全SOC。所有CDN、WAF、DDoS等基础网络都在同一平台上，再加上Zero Trust边缘身份安全，以及边缘计算、边缘推理和agent安全，都可以统一基建。这本身有门槛和护城河。如果在AI agent时代，把零信任扩展到AI边界，Cloudflare作为agent的边缘网络基础设施，可以提供agent运行所需的一切，甚至包括大模型。只需在Cloudflare上运行7×24小时，无论是做Code Review、客服还是内部办公，用Cloudflare OS搭建内部AI系统，都可以原生联动Zero Trust。比如用Cloudflare OS办公，它就是一个AI在线agent平台，可以做自动化任务，连接各种大模型和内部系统，比如Wiki等，帮助管理项目。判断用户身份和权限直接通过Zero Trust实现。运行在Cloudflare OS上，Zero Trust也在同一平台，权限配置只需写入用户组即可完成。如果用Zscaler或Netskope做办公类AI agent，就比较麻烦，需要外接很多组件，流量走向、调用、验证都要自己开发，无法实现agent原生支持。

他们也有优点，比如云原生。Netskope不是，Zscaler是。云原生在多云、混合云或数字化转型场景下部署比传统企业上云更有优势，未来扩展性和稳定性也更好。另外，企业如果有Cloudflare，拥有CDN级别节点，可以做量子安全、节点抗D DoS等。作为安全产品，自己也是靶子。用Zscaler或Netskope，他们自身也很安全，有团队全天候监控，不会被打掉。大企业在零信任方面还是需要渠道支持。国内很多卖CDN、卖WAF的公司，比如神州数码等，都是渠道商，他们手里有大量散客和大客户，大家都卖solution，因为原厂没有提供完整的解决方案，从设计、交付到后续观测都缺失。于是客户会找运营商渠道，比如神州数码，他们能提供各种支持，把所有环节都处理好，但最终交付的不是他们自己的产品，而是整合了Akamai、Cloud flare等，做成完整的解决方案。渠道在传统企业和大企业中非常重要，很多大企业不会直接和Cloudflare厂家签约购买产品，也需要渠道支持，所以会通过渠道采购。

Cloudflare的CMD服务需求是否看到显著增长？多少客户会绑定？

因为Cloudflare不是做安全SOC的，对大客户缺少这类服务。以前Cloudflare做过PS类似的服务，Cloudflare也需要做这些，主要是为了企业级客户，尤其是头部客户。目前它和AWS有点像，也有对应的团队，但真正意义上的SOC和CMD服务案例我还没见到。可能客户都自己解决了，不会经过Cloudflare，所以Cloudflare也观察不到相关场景，但我认为这类服务是必须要做的。服务大客户需要7×24小时监控、定期报告，出问题后要快速响应。以前服务甲方时，出了问题甲方会问，Cloudflare就要检查、解决并快速响应，之后给报告，甲方满意事情就结束了。这类服务单价很高，对服务质量和跟进速度要求也很高。

通常会在美国两个时区、亚洲一到两个时区（如印度、新加坡或中国），再加上欧洲一个时区，部署团队实现7×24小时交班。每个团队都要服务全部客户，不会只服务某一个客户。所有客户只要有问题就能快速联系到人，响应时间合同里会有规定，比如小于一个小时、几个小时或30分钟，必须响应处理问题，这是额外的SLA。可以理解为单独售卖技术支持，叫“专家服务”。如果这个模式跑通了，未来可以用agent自动化处理。以前做PS或值班服务时，一个时区要十几二十个工程师，每人每天三到四个case，工作量很大。现在有agent的话，一个地方派一到两个人，加上几十个agent，就能覆盖上市公司的安全产品需求，不需要那么多人。agent做得好可以实现7×24小时自动响应，人工只需做supervisor，负责监控和人工审批分析。我认为这是很好的发展方向，把安全服务做成一环也可以。

Cloudflare的AI Code Review工具成熟度？与GitHub Copilot Code Review相比的差异？市场潜力？

Cloudflare的AI code review工具本质上不是一个产品，而是一个工程成熟度很高的内部生产力工具。它非常成熟，适合内部使用，但并非一个可以直接对外销售或作为SaaS服务的产品。该工具高度自定义，Cloudflare对外只开源了部分架构设计，像基于open code的bank项目，最初是内部使用，现在的具体情况我也不太清楚，整体已经变得很复杂。

这个工具主要利用open code做reviewer，分为安全、性能、质量、合规、发布等多个类别，并通过协调器运行，结合各种AI模型和大量缓存以降低成本。它并不是用来替代人工review，而是辅助review过程。市场上像copilot这样的产品已经非常成熟，大家都在用它做code review，功能类似，差异不大。

Cloudflare的工具更适合企业级客户，尤其是需要多智能体协作、组织级code review和合规要求的场景。例如，review必须打标记，agent md文件和readme文件要明确哪些内容是AI开发的，注释要达到公司内部规定的标准，否则code review会被阻断。这些功能对于企业应用很重要，但对个人开发者或小型创业公司来说显得冗余，copilot这种轻量级工具已经足够满足中长尾客户的需求。

对于像fortune 500这种跨国、多部门协作且对生产环境和业务质量要求极高的企业，更适合采用Cloudflare内部的AI code review架构。但它并不是一个商业化产品，不会用于收益化，更多是作为架构和社区化的参考，可能开源部分内容供大家借鉴。要将其做成对外服务的产品并不在其赛道上，Cloudflare提供的agent runtime SDK等工具只是展示如何搭建code review系统，最终如何使用由各企业自行决定。

目前code review工具基本已被copilot免费化，很难有公司通过此类工具盈利。按席位或代码行收费都不合理，最多按token收费，即根据review消耗的token数量计费。实质上还是在销售算力资源，而不是code review产品本身。Cloudflare的战略价值较高，但独立来看不会成为一个盈利产品。

现在内部做code review时，分别有多少比例使用Claude、Kimi和其他模型？趋势如何？

开源模型发展非常快，像GLM-5.3 Flash、DeepSeek V4.1 flash等新模型已经强到让人不想用Claude，性价比极高。对于Cloudflare来说，趋势一定是采用开源模型进行自部署。例如DeepSeek，Cloudflare可以自部署，无需向外部支付费用。使用Claude模型时，代码必须上传到其仓库，即LLM上。即使签了合同，Cloudflare也要求zero data retention，所有大厂在Cloudflare都执行零数据留存政策，可以在AI Gateway中开启，确保大模型厂商不会用你的数据做训练。

Clairic模型对token 节省能达到50%，生产环境中是否如此？对前沿模型调用的替代效果？

这个产品还是挺有意思的。如果是在 GPT刚推出时出现，我会很感兴趣。现在来看，技术层面它解决了一个问题：有时我用推理模型并不是为了让它输出长篇大论，而是希望它能摘取信息，比如订单号、角色名字，或者演员顺场表等。传统工具很难识别同一个人，比如张三今天叫张三，明天叫三哥，有些人叫老三，无法判断是同一个人。AI具备很好的语义理解能力，可以从上下文判断并标注同一人物。但我之前遇到一个严重问题，无论怎么限制AI 的输出，它总会输出一些无关内容，比如要求输出 JSON 格式，它还会加上“好的，我收到任务了”等奇怪的信息。到目前为止，AI依然如此，很难让它只输出JSON，直到Jev模型出现。Jev模型有规定的输出模式，可以做判断、减法、打分。Clairic是Jev的一种变形，不是前沿推理大模型，甚至比Jev复杂，不仅做评判，还能摘取数据。以前要求数据员必须用标准格式，比如报销时必须按规定填写，否则财务系统无法识别。生成式 AI可以解决这类问题，但输出格式不稳定，理解过程复杂，不像简单逻辑工具，更像人脑思考再输出，过程较复杂。

Clairic模型弥补了大模型和Jev模型之间的空档。Jev模型太简单，大模型又太复杂，Clairic刚好处于中间，负责信息摘取。它的应用场景需要串联，比如先用Jev判断内容类型，再用Clairic提取信息，或顺序互换。Clairic可以从图片、文字等提取有价值信息。比如报销时，无论发票怎么贴、金额怎么写、公司名字和个人名字顺序如何，都能准确摘取关键词。然后通过Jev判断是报销、预付款还是垫款，再交给大模型处理内容。它非常适合高频、结构固定、可枚举的场景，比如退货理赔案例。我做过一个demo，发现除了这个场景，很难找到其他适用场景。演员顺场表也是一个典型应用，需要高频、结构固定、清晰的产品逻辑，不能让模型自由发挥。只要接口进来的内容都是退货，它只需提取退货信息和用户 ID等固定内容，更像写好的程序但带点智能。适用场景目前极其有限，但它是非常强大的生产力工具。如果做 harness 开发，网上能看到相关视频和面试题，我也很关注这些内容。最早做提示符时，公司写号，想变的是阅历，交给院士看也好，定个文凭。

大模型并不应该承担所有任务。比如说，查找信息时，你需要调用一个API，例如先通过GitHub的某个API获取数据，然后再用diff看下这个代码做了什么。不能每次都让大模型自己思考并调用工具，这样不仅浪费token，效率也很低。此外，大模型总是有可能超出边界。对于那些可以固定、高频触发、形成成熟SOP的流程，一定要用代码实现，而不是依赖大模型学习或依赖提示词、技能去限制它。这也是成熟harness的标志。这个时候Clairic就显得很有意思了。它的框架非常固定，不是推理模型，而是一种渐进式的模型，不是常规的推理工作流，而是单向输出内容，更像一个工具或者API，而不是LLM。因为在Jev和大模型之间，总是存在一些缺点：Jev做的东西太简单、太快，大模型又太全量，所以中间一些信息提取或复杂度的任务就被Clairic这种模型替代了。

这种模型的出现，一定是开发人员在日常AI使用过程中发现了需求。虽然harness很多东西不应该全量依赖大模型，而且大模型的稳定性也不够好。即使你限制它，它还是会出格，一旦出格就会报错，甚至可能陷入循环。因此，采用已经写死、有成熟输出形态的新奇模型，在生产业务中非常重要。在某些环节，这种模型是不可或缺的。之前没有这类产品，现在算是从Cloudflare内部应用中产生的模型需求，进而发展出一个新东西。
