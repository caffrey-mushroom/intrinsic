2. 智能企业的范式转变

a) 为什么传统数据系统难以满足企业当前的业务需求？

  • 过去20年，企业投入数万亿美元建设数据基础设施，但大部分系统只能告诉企业“过去发生了什么”。
  • 数据通常以静态报表、Dashboard 或分散系统的形式存在，需要知识工作者手动登录 Salesforce、ERP、SAP 等系统提取和整合。
  • 当业务人员需要进一步追问原因时，传统系统无法直接执行后续分析，仍需要提交工单、联系不同部门并进行大量人工沟通。
  • 因此，传统企业系统更多属于 System of Insight（洞察系统），能够展示结果，但不能主动采取行动。

b) 数据分析师 Max 的典型工作痛点是什么？

  • Max 代表企业中常见的业务数据分析师，需要对接业务、运营、财务和法务等多个部门，并向 VP 或高管交付报表和演示材料。
  • 在没有 AI 工作助手的情况下，其典型工作流程包括：
  1. 登录多个业务系统，手动拉取十几份原始数据。
  2. 将数据放入 Excel 核对，并处理十几万元级别的账务差额。
  3. 通过钉钉、飞书等工具逐一联系各部门，了解差异产生的原因。
  4. 在不同报表中反复筛选和对齐数字。
  5. 用 Excel 制作图表，再手动复制到幻灯片。
  6. 当高管要求更换分析角度时，由于实时数据已经变化，需要重新执行整个流程。
  • Max 约有60%的时间消耗在数据提取、对账、复制、排版和沟通等低价值操作上，而不是用于业务判断和战略分析。

c) 新一代智能企业的工作方式是什么？

  • 企业将从 System of Insight 转向 System of Action（行动系统）。
  • AI Agent 不仅提供洞察，还可以基于企业已有数据直接执行分析、制作 Dashboard、生成 Slides，并完成沟通和交付。
  • 理想状态下，用户只需要通过自然语言描述任务，AI Agent 就能输出一份可直接交付给 VP 的完整材料。
  • 这一转变不仅改善个人效率，也会改变企业业务流程和行业运作方式。

d) AI Agent 可以应用于哪些业务场景？

  • 销售团队：通过客户情报 Agent 获取客户支出、业务动态和可复用案例。
  • 市场营销：分析目标受众、获取市场反馈，并判断营销策略是否有效。
  • 财务团队：自动对账、趋势分析和未来销售预测，减少手工公式和报表操作。
  • 银行业：分析客户或企业存款增长模式，由多个 Agent 组合完成前期分析，员工负责最终决策。
  • 医疗行业：对审评或理赔预授权进行第一轮自动预审，筛除不符合条件的信息。
  • 零售行业：辅助新品上市、季度商业企划和经营决策。

3. Snowflake 内部应用验证与实际成效

a) Snowflake 如何验证自身 AI 产品的可用性？

  • Snowflake 内部采用 “Snow on Snow” 原则，即首先成为自家产品的客户，并在内部严格环境中验证产品。
  • 内部工具 Raven 构建于 Snowflake 平台之上，主要服务全球约6,000名销售及市场团队成员。
  • 销售、架构师和解决方案工程师可以通过自然语言向 Raven 提问，例如：
  1. 某客户每月支出主要集中在哪些领域。
  2. 公司近期有哪些使用案例可以复用于其他客户。
  3. 某项业务变化背后的原因是什么。
  • Raven 已帮助 Snowflake 节省超过1,600万美元的运营管理成本。

b) Raven 的实践说明了什么？

  • 企业级 AI 的价值不只是生成文本，而是打通企业内部数据、业务定义和工作流程。
  • 当 AI 能够理解企业上下文时，可以显著减少信息查询、跨部门沟通和重复分析的成本。
  • Snowflake 希望通过内部先行使用，验证 AI 产品在真实组织、严格权限和复杂业务环境中的稳定性。

4. 企业 AI 从 POC 走向生产的主要障碍

a) 为什么很多企业的 AI POC 容易成功，但大规模生产落地困难？

  • POC 通常数据范围有限、任务边界清晰，因此能够快速看到效果。
  • 进入企业生产环境后，如果 AI 缺乏企业上下文，就会出现以下问题：
  1. 不理解企业内部指标和业务定义。
  2. 不清楚数据表之间的真实关系。
  3. 无法遵守企业权限和治理政策。
  4. 频繁寻找错误的数据表或执行无效查询。
  5. Token 消耗和全表扫描成本快速上升。
  6. 输出看似专业、实际上与企业真实情况不符的结论。
  • 因此，生产级 AI 的关键不是简单接入一个外部大模型，而是让模型真正理解企业的数据、规则和业务流程。

b) 缺乏企业上下文会带来什么风险？

  • 例如，用户询问：“为什么第四季度实际开票金额比合作预测低15%？”
  • 缺乏企业上下文的外部 AI 可能给出“销售放缓”或“系统功能延迟”等看似合理、实际错误的答案。
  • 如果管理层根据错误结论继续投入资源，企业可能在错误方向上持续行动。
  • 当 AI 能够访问企业上下文时，可以进一步发现真实原因，例如部分合同包含内部上线免责条款，导致财务归属审核和开票延迟。
  • 这一案例说明，企业 AI 的幻觉问题不仅源于模型本身，也源于上下文缺失和架构设计不合理。

c) 将外部 Agent 通过狭窄管道连接数据仓库存在哪些问题？

  • 很多企业仅将 Snowflake 作为存储和数据管道，智能能力仍位于外部。
  • 外部 Agent 无法原生理解数据定义、元数据、历史执行记录和权限体系。
  • 每次提问时，Agent 可能反复尝试不同数据表，造成查询效率低、Token 失控和扫描成本增加。
  • 这种架构在 Demo 中可能可用，但在高并发、复杂权限和实时业务环境中容易失效。

5. Snowflake 企业级 AI 的三大核心支柱

a) Snowflake 的企业级 AI 架构优势是什么？

  • Snowflake 将其优势概括为三大支柱：
  1. 数据所在之地：企业数据原生存放于平台内部。
  2. 规则所在之处：安全、权限和治理政策与数据处于同一平台。
  3. 将 AI 带到数据中：不是将敏感数据搬到外部模型，而是让 AI 在数据环境中运行。

b) Snowflake 如何让 Agent 理解企业业务？

  • 平台可基于企业上下文、历史执行记录和元数据自动构建语义层。
  • Agent 从使用初期就能够理解企业指标、业务术语和数据表关系。
  • 当用户询问“营收是多少”时，Agent 可以直接识别营收定义并定位正确的数据表，无需反复尝试多个数据源。
  • 这种方式能够提高回答准确率，并降低无效查询和 Token 消耗。

c) AI Agent 如何继承企业的安全权限？

  • Snowflake 已具备行级和列级安全策略，AI Agent 会原生继承用户权限。
  • 某个用户只能让 Agent 访问其本人有权限查看的数据。
  • Agent 执行的查询、调用和操作均可追踪、审计。
  • 企业敏感数据、提示词和商业逻辑不会被外部基础模型用于训练。
  • 平台同时提供 Prompt Injection 防护和 Data Leakage 防护，降低提示词注入和敏感信息泄漏风险。

d) Snowflake 如何控制 AI 成本？

  • Agent 能够基于企业语义和元数据精准定位所需数据，减少错误查询和全表扫描。
  • 在部分生产环境和客户数据中，Token 使用量可降低20%至50%。
  • 成本优化并非简单减少模型调用，而是通过更准确的上下文、语义路由和数据定位提高单次调用效率。

6. Snowflake Co-work 的产品定位与工作方式

a) Co-work 与普通 Copilot 或 Chatbot 有什么区别？

  • Co-work 被定位为面向知识工作者的统一 AI 工作空间，而不是单纯的聊天机器人。
  • 它不仅能够回答问题，还可以：
  1. 接入企业数据和员工沟通上下文。
  2. 执行分析任务。
  3. 生成图表、报告和 Slides。
  4. 通过 API 连接邮件、Slack、Calendar 等外部应用。
  5. 将结果直接交付给对应的 Stakeholder。
  • 其核心价值是把“问答、分析、制作和交付”整合在同一工作流中。

b) Co-work 如何改善季度经营复盘流程？

  • 过去，Max 可能需要长达3周整合季度末 Review 所需的数据。
  • 使用 Co-work 后，只需要通过一句自然语言指令描述任务，系统即可：
  1. 自动汇总相关业务数据。
  2. 输出结论、图片和分析结果。
  3. 深入分析 AI 成本、消费增长等高管关注的问题。
  4. 主动追踪异常月份及其原因。
  5. 生成可供审阅的 Draft。
  6. 通过 Slack 或邮件发送给 VP。
  • Co-work 还可以根据 Calendar 自动创建会议，在会议邀请中写入 Agenda，并转发给管理者。

c) Co-work 是否支持自动化周期任务？

  • Co-work 已推出 Automation 功能。
  • 用户可预先设置工作流及执行频率，按每日、每周、每月或每季度自动完成任务。
  • 可应用于周报、QBR、经营状态汇报、异常提醒等固定流程。
  • 结果可通过邮件或 Slack 主动发送，减少用户手动发起和重复执行。

d) Co-work 是否支持移动办公？

  • 手机端可提供与电脑端基本一致的使用体验。
  • 用户可以在移动端查看：
  1. 已连接的服务。
  2. 历史聊天记录。
  3. 数据表格。
  4. 已生成的 SQL Query。
  • 当用户不方便打字时，可直接使用语音转文字功能。
  • 典型场景包括销售人员在拜访客户途中，临时收到 QBR 修改要求，并通过手机完成数据查询和内容调整。

7. Co-work 背后的技术架构与企业上下文能力

a) Co-work 的技术架构由哪些部分组成？

  • 会议将其描述为端到端的三层推理结构：
  1. 上层为面向用户的应用和交互工作空间。
  2. 中间层包括 API、Agent 和内置 AI Function。
  3. 底层为企业数据、语义、权限和上下文体系。
  • 内置 AI Function 可以处理 PDF 中的图片、表格和文本信息。
  • 即使采用市场上的顶尖模型，如果缺乏底层企业上下文，也无法发挥完整能力。

b) 平台如何持续构建企业上下文？

  • 平台可自动更新和维护包含最高约240万个业务相关概念的实时索引。
  • 索引由多层上下文构建而成，可同时处理结构化数据和非结构化数据。
  • 系统能够对不同类型的信息进行智能路由，并同步至企业语义层。
  • 相较于手工维护语言模型、数据说明和映射关系，该方式可以降低企业构建和维护成本。
  • 其目标是同时降低 Token 使用量并提升回答质量，使 AI 更符合生产环境要求。

c) Snowflake 如何保障企业 AI 的安全性？

  • 安全护栏覆盖：
  1. Prompt Injection 防护。
  2. Data Leakage 防护。
  3. 行级和列级权限继承。
  4. Agent 行为记录与审计。
  5. 企业敏感信息和商业逻辑不用于外部模型训练。
  • 安全与治理被视为企业 AI 进入生产的基础能力，而不是上线后的附加功能。

d) AI 工作流将如何改变数据分析师的角色？

  • Cortex 可以在早上主动推送数据对账异常。
  • 当 VP 提出复杂业务问题时，可通过 Deep Research 快速完成分析。
  • 系统能够自动生成可交互 Slides，并将 PDF 或报告通过 API、邮件附件等方式发送。
  • 数据分析师将从报表制作和数据搬运人员，转变为业务判断者和企业战略支持者。

8. 企业级 AI 系统的核心建设原则

a) 企业 AI 成功的关键是选择最强模型吗？

  • 不是。Frontier Model 已经具备代码编写、数学推理、文档分析和工具调用等强大通用能力。
  • 但企业 Workload 与通用场景存在明显差异：
  1. 企业数据是私有的，基础模型通常没有接触过。
  2. 数据访问需要遵守权限、政策和治理规则。
  3. 任务具有很强的流程和业务专属性。
  4. 企业还需要平衡成本、时延、隐私和准确率。
  • 企业应关注的不是“哪个模型最聪明”，而是“哪种模型、Context、Tools、Memory 和 Coordination 组合最适合自身 Workload”。

b) 企业级 AI 系统需要重点建设哪些能力？

  • 会议提出三个核心方向：
  1. Specialized Model：围绕特定任务训练或优化模型。
  2. Intelligent Context：为模型提供准确、精简、动态的企业上下文。
  3. Coordination：让多个 Agent 独立探索、相互质疑、验证证据并形成结论。
  • 三者分别解决质量、成本、时延、隐私和可信度问题，必须组合使用。

9. 专用模型的价值与 Text-to-SQL 实践

a) 为什么专用小模型可能优于大型通用模型？

  • 当企业具备高质量的任务数据、Reward Design 和 Validation Set 时，可以训练出更紧凑的专用模型。
  • 专用模型围绕具体 Workload 优化，有可能在特定任务上超过规模更大的通用模型。
  • 模型价值最终由实际任务表现决定，而不是由参数规模单独决定。
  • 专用模型通常还具有更低成本、更低时延和更强可控性。

b) Text-to-SQL 场景的主要难点是什么？

  • 模型不仅需要理解自然语言问题，还必须：
  1. 遵循真实数据库 Schema。
  2. 理解企业术语和数据定义。
  3. 适配 Snowflake 等平台的 SQL Dialect。
  4. 生成能够执行且具有效率的 SQL。
  5. 避免“可以执行但结果错误”的 Near Miss。
  • Near Miss 比明显报错更危险，因为错误结果可能看起来合理，进而误导业务决策。
  • 常见问题包括错误 Filter、字段含义误判、信息跨表分离，以及未理解企业内部术语。

c) Snowflake 如何训练 Text-to-SQL 专用模型？

  • 训练体系主要包括四个模块：
  1. Data：生成大量领域专属数据，使模型理解 Snowflake SQL Dialect。
  2. Knowledge：引入更接近真实场景的 SQL 数据，提高对不同 Schema 和新 Schema 的泛化能力。
  3. Reward：针对不同 SQL 可能返回相同结果的情况，设计更可信的奖励机制，避免只根据单次执行结果判断正确性。
  4. Training System：通过底层训练系统提高训练速度和迭代效率。
  • 相关训练优化系统可将训练速度提高约3.5倍，将原本约5天的训练时间缩短至1.5天以内。
  • 数据、知识、奖励和训练系统并非彼此独立，而是形成持续迭代闭环。

10. SQL Auto-completion 模型的优化效果

a) SQL 自动补全模型需要满足哪些要求？

  • 自动补全不仅要生成合法 SQL，还必须同时满足：
  1. 准确。
  2. 对用户有帮助。
  3. 响应速度足够快。
  4. 避免输出低质量建议干扰用户。
  • 在部分情况下，宁可不输出，也不应展示可能误导用户的补全内容。

b) 专用化训练带来了哪些量化改善？

  • 模型经过更具针对性的训练后：
  1. 内部 Precision 从23.4%提升至26.1%。
  2. User Acceptance 从17.8%提升至约26.4%。
  3. Inference Latency 降低约30%。
  4. 在保持体验质量的前提下，Suggestion 数量提升约30%。
  • 结果说明，模型表现的改善并非来自简单增加输出数量，而是来自数据、上下文和专用训练的共同优化。

11. Context Engineering 与 Active Memory

a) 为什么不能把所有信息一次性放入 Prompt？

  • 企业内部存在大量工具说明、日志、代码、文档和历史输出。
  • 即使大模型的 Context Length 从8K扩展到32K、128K、256K乃至更高，也无法自动判断哪些信息真正重要。
  • 如果将全部内容一次性输入，会造成：
  1. Token 消耗快速增加。
  2. 有效信息被噪声淹没。
  3. 推理速度下降。
  4. 回答准确率降低。
  • Context Engineering 的目标是让每次任务的 Working Context 足够小，同时提供足够的 Dynamic Grounding。

b) Snowflake 如何控制上下文膨胀？

  • 主要采用三类方式：
  1. 工具和 Skills 按任务需求逐步加入，而不是一次性加载所有能力。
  2. 将相对独立的 Thought 或中间结果合并，降低模型处理开销。
  3. 对长代码和大文件提供 Context Reference，由模型根据需要进一步查询，而非完整加载全部内容。
  • 这种机制使模型能够像人一样先判断哪些信息可能有用，再定向获取细节。
  • 会议展示的测试表明，经过上下文优化后，可以在提高任务正确率的同时降低整体执行成本；部分测试中成本降幅约33%。

c) 什么是 Active Memory？

  • Active Memory 的目标是让 AI 在不同 Session 之间保留可复用经验。
  • 当用户纠正一次错误后，系统希望下一次遇到相似问题时直接采用正确处理方式。
  • Memory 来源包括：
  1. 文档、博客和历史案例的显式或自动索引。
  2. 成功对话中提取的事实和处理方法。
  3. 失败对话中识别出的错误原因及修正方式。
  • 系统会在后台自动记录和组织可复用内容，减少用户重复解释。

d) Active Memory 面临哪些治理问题？

  • 每条 Memory 都需要明确：
  1. 信息来源是什么。
  2. 何时可以使用。
  3. 何时需要更新。
  4. 何时应停用或删除。
  • 企业政策、流程和业务定义会变化，旧 Memory 如果未及时更新，可能成为新的错误来源。
  • 因此，Memory 不能只是简单存储历史对话，还必须具备来源追踪、版本管理和生命周期治理能力。
  • 会议展示的多组评测中，Active Memory 在不同任务上的提升幅度约为8%、40%和73%；部分具体场景提升约18%。

e) Context Engineering 可以分为哪些层次？

  • 当前上下文管理：控制本次任务中的 Working Set，减少无关信息。
  • 语义 Grounding：在任务开始时提供与问题最相关的企业定义和资料。
  • 跨 Session Memory：将可复用的知识和经验持续保存，在未来任务中调用。
  • 三者共同实现“更少噪声、更高准确率和更低成本”。

12. 多 Agent 协同与 Hybrid Research

a) 为什么复杂企业任务需要多个 Agent 协同？

  • 复杂任务往往同时依赖企业内部结构化数据和外部实时信息。
  • 例如，评估近期监管行动对企业供应链的影响，需要同时了解：
  1. 企业内部供应商及产品依赖关系。
  2. 受影响员工和业务规模。
  3. 外部新闻、监管变化和电话会议内容。
  • 内部数据库了解企业关系，但不了解外部世界最新发生的事件。
  • Open Web Research 能发现外部事件，却不了解哪些供应商、产品和企业内部关系真正相关。
  • 因此，这类问题既不是单纯的 SQL Research，也不是单纯的 Search，而是跨领域的 Hybrid Research。

b) 多 Agent 协作最容易在哪个环节失败？

  • 很多失败并非某个 Agent 本身能力不足，而是发生在 Handoff 交接环节。
  • 典型问题包括：
  1. 数据库 Agent 找到了正确供应商，但搜索 Agent 被同名或更知名公司误导。
  2. 搜索 Agent 发现了重要外部事件，却无法转化为严格的数据库查询。
  3. 不同 Agent 分别完成了正确任务，但综合结果违反原始约束。
  4. 交接过程过度压缩信息，导致关键身份、实体关系或条件丢失。
  • 信息在交接中一旦丢失，后续推理通常无法完整恢复，因此必须进行端到端系统设计。

c) Snowflake 如何避免多个 Agent 过早形成错误共识？

  • 系统将流程分为三个阶段：
  1. 独立探索阶段：各 Agent 保留自己的搜索树、假设和随机性，不能直接改变最终结论。
  2. 辩论与验证阶段：Agent 可以查看彼此信息、指出错误，并通过实验、查询或其他证据验证观点。
  3. 最终综合阶段：只有在主要分歧得到解决后，系统才整合内容并输出最终结论。
  • 早期刻意限制 Agent 相互影响，是为了避免一个 Agent 提出错误方向后，其他 Agent 集体跟随。
  • 系统不采用简单投票，而是要求 Agent 相互质询，并对关键主张提供证据。

d) 最终答案如何保证可验证性？

  • 系统会标注每项信息的来源，包括：
  1. 企业数据库及具体查询依据。
  2. 外部网络搜索链接。
  3. 内部文档及对应段落。
  4. 不同 Agent 的分析和验证过程。
  • 设计原则是：前期保持独立探索，后期要求每项主张均有证据支持，并在充分讨论后延迟收敛。
  • 在相同模型条件下，该 Agent 架构取得约64%的任务表现，对比部分开源 Agent 框架约55%。

13. 企业 AI 系统的评估框架

a) 企业在设计 AI 系统时应回答哪些关键问题？

  • 第一个问题：现有模型是否掌握完成任务所需的全部知识，还是需要针对该任务训练专用模型？
  • 第二个问题：应向模型提供什么样的上下文，才能提升准确率并降低成本？
  • 第三个问题：在探索和执行过程中，应配置什么样的 Agent Harness、Tools 和 Evidence 机制，才能获得可信结果？

b) 企业 AI 应遵循什么总体建设思路？

  • 应围绕真实 Workload 进行建设，而不是围绕某个单一模型或 Demo 进行建设。
  • Foundation Model 会持续增强，但模型能力不会自动转化为企业成果。
  • 企业需要围绕自身数据、业务流程和任务要求，完成以下建设：
  1. 专用模型或任务适配。
  2. 企业语义和上下文体系。
  3. 权限、安全和治理机制。
  4. 跨 Session Memory。
  5. 多 Agent 协作与证据验证机制。
  6. 成本、时延和准确率的综合优化。
  • 可信企业 AI 是完整系统工程的结果，而不是单纯选择最强基础模型的结果。

14. 安全治理的下一阶段重点

a) 为什么安全与治理将成为企业 AI 的核心议题？

  • 随着 AI 能够接触越来越多的核心数据并执行更多业务操作，安全风险也将同步扩大。
  • 企业需要重点解决：
  1. 敏感数据如何被保护。
  2. 不同人员和 Agent 可以访问哪些数据。
  3. AI 执行行为如何被记录和审计。
  4. 提示词注入和数据泄漏如何防范。
  5. 企业数据是否会被外部模型用于训练。
  6. Agent 在生产环境中的权限边界如何管理。
  • 安全、权限和治理不是企业 AI 的附加模块，而是其进入生产环境和市场应用的基础前提。
  • 后续安全专题将进一步从生成式 AI 时代的企业安全角度展开讨论。

分析师：模型究竟需要学会什么？应在什么场景、什么上下文中使用？当多个Agent同时协作时，应如何达成共识并形成最终结论？

专家：我们并不是认为当前的Frontier Model不够好。恰恰相反，现在的Frontier Model非常强大，可以帮助我们编写代码、解决数学问题、分析文档、调用工具，以及处理各种任务。

但大部分Frontier Model在推出时，通常以general purpose的方式提供，即尽可能广泛地解决问题，而企业workload往往恰恰相反。

第1，企业数据是私有的，这些数据并未被Frontier Model看到。第2，访问数据时需要governance，系统必须遵循权限和政策。第3，workload具有很强的process specific属性。今天可能需要用它做deep research，研究最新内容；明天可能需要执行另一项task，例如用它来写一个……这意味着需要结合具体的task、文档和人员来解决问题。

此外，还需要考虑cost、latency、governance和privacy。如果是一个非常简单的task，却必须使用非常昂贵的模型，就可能因速度太慢而不适用；如果latency太高，也会希望系统可以更快。这些约束改变了问题本身的定义。

我们不应只关注哪个模型最聪明或最强，而应关注哪种模型、context、memory和coordination的组合最适合自身的workload。这也是今天讨论的重点，因为可信的enterprise既来自模型，也来自其周边所有系统的专门化和专业化。

我将从3个方面展开这一观点。第1，很多时候需要specialize your model，让模型针对具体workload进行学习，而不是追求通用能力。第2，需要intelligent context。这个概念已经被多次提及，我们将进一步讨论如何通过context降低cost，并解决更困难的问题。第3，需要coordination，即在存在多个Agent时，让它们相互质询、相互验证，最终输出可信的答案。

这3个方面分别解决不同的问题，只有组合起来，才能将模型的原始能力转化为企业真正关心的quality、cost、latency和privacy。

我们先从模型开始。我们并不是说小模型一定最好，而是认为，当你拥有足够好的data、reward和validation set，并且这些要素都围绕具体任务构建时，就能够训练出一个更好、更紧凑的specialized model。它在特定task上的表现完全有可能超过规模更大的general purpose模型。决定能力是否有价值的，最终是workload，而不是模型本身。

第1个要介绍的是text-to-SQL，这是一个非常典型的场景。模型不仅要理解问题意图，还要遵循真实的schema，以及Snowflake、Databricks的数据细节，并生成一条不仅能够执行，而且具有效率，甚至能够正确执行的SQL。

这里最困难的往往不是明显的SQL generation错误或error，而是near miss。它可能可以执行，也可能返回一个看起来比较正确的结果，但实际上可能完全错误。

回　答　者：例如，一些 table 可能存在错误的 filter，或因表达不完整、信息分离而被错误理解。Native schema、企业术语、dialect 等细节，也都是通用模型无法自行消化的内容。

Snowflake 的 Text-to-SQL 在该 task 的测试中，Text-to-SQL8B 在我们使用的对比中只是一个大约 32B 的模型，但与其他很多大模型相比，能够取得更高的 accuracy。同时，它的模型大概只有 300万参数，30，小于 30亿参数。当然，这并不意味着 scale 不重要。Scale 非常重要，但模型本身或模型大小本身并不能解决所有 domain data 问题。当 evaluation、dataset 和实际使用能够真正反映 workload 时，专门的数据和训练方法可以把一个最小的模型转变为更强的企业级应用。

我们如何得到这个 8B 模型？主要通过 4个模块，即 4个模块，包括 data、knowledge、reward 和 training system。

第 1层是 data。我们生成了大量 domain-specific 数据，让模型先进一步了解 Snowflake dialect。

第 2层是 knowledge。我们使用 SQL from the web 作为 ground truth 和训练数据，使其更接近真实情况，并提高模型对不同 schema 和新 schema 方案的理解。模型不仅是学习一个模板，还能够将问题重新连接到新的数据。

第 3层是 rewards。很多人都听说过 instruction-based training 等方法，但在运行 SQL 时会出现一个非常具体且有意思的现象：可能存在 2条不同的 SQL。例如，最简单的情况是，1条使用“小于等于”，另 1条使用“小于”，但在某个特定数据条目上，二者返回的结果可能相同，因为“小于等于”与“等于”的差异并未在数据中体现。此时，需要让 reward design 更加可信。我们做了大概的 vision-related present，并对一些 table 进行了大量增强，相当于 1个做、1个做 generic。

第 4层也非常重要，但很多时候会被忽略，那就是 training system。为了获得一个好的模型，需要进行大量训练。我们有自己的微软 system team，他们发明了 1个名为 Zero 的系统，即 Zero Redundancy Optimizer。它可以将训练速度提高 3.5倍，把原本大约需要 5天的训练时间缩短至 1.5天之内，并把可训练参数所能支持的上下成本从 2万扩展到 64000个 GPU。

这 4个模块并非相互独立，而是形成循环。具备良好的数据，才能形成良好的 knowledge；拥有良好的 reward design，并运行在良好的 system 上，能够加速模型迭代，最终得到 1个好的模型。

第 2个想分享的是 Snowflake 的 auto-completion model。该模型已经进入市场。模型质量不仅体现在能否生成 1段合法的 SQL。在 auto-completion task 中，原生要求是准确、有用，同时也必须足够快。低质量的体验可能会打断用户，因此有时宁可保持沉默，也不要输出内容。

在该 task 上，我们最初的模型是 1个 3B、3B 的模型，之后通过后续训练获得了 1个 4B、更 customized 或 specialized 的模型。使用这个更 specialized 的模型后，我们提升了所有指标。在 1个内部 precision test 中，我们看到我们的……

回　答　者：precision从23.4%提高至26.1%，user acceptance从17.8%提高至26.4%左右。与此同时，inference latency相比原来降低了30%，即速度提升了30%。由于模型的latency较低，我们还将suggestion的数量提高了30%，用户可以看到更多suggestion。因此，这种提升并非依靠过度输出suggestion，而是确实提升了模型数据及答案的表现。

该模型的优势非常明显，具备更高的precision、更高的accuracy以及更低的latency。这也说明，在整个训练过程中，我们为模型提供了很多有用的context。由此回到最初提出的问题：模型非常重要，但它never works alone。模型所创造的优势，是由周围的上下文等信息共同决定的。

这也引出了第2个问题，即如何进行context engineering。我们不能把所有information都放在prompt里，就像人不能把所有东西都写进脑子里。我们希望每1次工作流程的working context足够小，同时，在用户开始探索之前，为其提供足够多的dynamic grounding，并将真正有价值的经验带到下1个session。

我们希望session之间存在记忆关系。以人为例，第1次完成1个task时可能需要30分钟；第2次因为有了自己的memory，可能只需要15分钟；熟悉这个问题后，可能只需要5分钟就可以解决。

第1个问题是，Snowflake如何帮助用户解决context length增长速度的问题。行业中经常出现的情况是，由于缺少充分约束，content的增长速度远快于真正有用信息的增长速度。例如，不同工具的描述、工具的输出结果、log和工具状态都在快速增加。

模型可以处理的context length越大，就意味着可以放入更多tokens。我们看到，大模型的context length已经从8k发展至32k、128k、256k和1 million。但截至目前，它仍然存在界限，无法自动筛选哪些content是重要的，并只保留重要内容。

Snowflake Copilot通过3种方式解决context exposure问题。第1，tools和skills是iteratively added的，不会1次性加入所有可用内容。例如，在中国可以使用WeChat、各种app和百度搜索，我们不会1次性全部加入，而是根据实际需求逐次添加。

第2，我们会将不同且相对独立的thought合并处理，从而降低模型的overhead。

第3，对于大模型处理代码的场景，如果整段代码可能有500行，500行代码就足以使模型的context length达到上限。现在的做法是为模型提供1个context reference，使其能够像人一样识别可能有用的信息，再通过更多query处理各类任务。例如，针对特定信息进一步进行graph，因为模型知道当前没有这个graph。

回答者：也就是说，它会纳入更多信息，因此能更准确地判断你到底要去哪里，不需要反复阅读 instruction，也不需要处理过大的内容。这里展示的是1个 single benchmark。在配合5的情况下，连续测试3次且3次都正确，我们大概可以达到86%，成本约为3毛钱。如果采用另一种方式，大概是72%，成本是0.14。也就是说，我们的成本会降低33%，同时取得更高的结果。

第2个方面是今天会议上多次讨论的内容。它解决的是另1个问题。我们将前面的问题视为 compact efficiency，也就是压缩；这里更多解决的是，模型最初看到问题时，如何向它提供相关文字。如果不提供任何相关内容，它可能需要进行一些 trial and error；加入这些内容后，很多试错就不再需要，它可以直接判断应该选择什么样的信息。

这组数据也比较突出：我们低于3点，成本低于66，但在相同条件下取得了高出3.6倍的结果。

接下来这部分此前大概没有讲过，大家可能也是第1次看到。我们希望解决的是，在此之外，当模型看到1个问题时，是否已经通过其他方式或人工方式获得 grounding context。我们希望把 context 延伸到不同的 session 之间。

举例来说，今天它回答错了，这种情况我们2个人都可能遇到。你告诉它这里不对，并说明正确的处理方式。你希望它下1次遇到相同问题时，能够直接解决。就像1个刚入职的员工做错了事情，你当然希望他下1次能够做对。因此，我们可以引入 active memory。

Active memory 分为2条线。第1条线的第1层是一些显式索引。例如，你有一些 documents、blogs 上的 examples，它可以帮助建立 link，但不需要你显式告诉它。你的 file 会被自动记录下来，并可能在下1次使用。这是1个自动化过程，系统会在后台完成这些工作。

此外，它会从成功或失败的对话中提取可用事实，并将其记录下来。下1次处理相关问题时，这些内容就可以帮助它解决问题。

不过，memory 虽然看起来很理想，但经常面临1个问题：如何保证每1个 memory 都是准确的。你需要知道每条信息来自哪里，什么时候应该使用，什么时候应该更新或停用。

Memory 也会成为公司组织层面的问题。例如，公司过去采用某种内容，之后突然换成1个新的内容。

回答者：对于较为复杂的任务，可能不需要更新自身的 knowledge base，因为相关信息都会记载在 memory 中。在评测中，我们发现 context memory、active memory 可以使 overall 分别增加 8%、40% 和 73%。在 Netflix 方面，我们可以将其提高 18%，从而更快地获得答案，也能找到更好的信息来帮助获得答案。

由此可以看到，context engineering 包含不同方面。throughput 更多管理当前的 model context，context sense 更多管理 semantic grounding，after memory 则将 durable knowledge 或 cross-session knowledge 持续记录并应用于未来。

第3点是如何让 agent 进行协同处理。面对非常复杂的任务时，就像整个团队共同完成一项工作，但每个 agent 只负责其中一小部分。因此，需要将每个 agent 掌握的内容和收集到的信息整合起来。

可以先看一个较为简单的 summarization 问题，即如何讨论近期监管行动后其他方面的一些风险。企业内部数据库可以提供公司的 supplier、product、依赖某个 supply 的员工数量，以及特别有效的 campaign 等信息。但是，structured data 不一定能够解释过去几天或当天早上发生了什么，以及这些事件为何会导致策略调整。相关信息可能来自新闻报道，也可能来自当天早上的 phone call report，这些都不是内部数据库能够提供的。

Open Web research 的情况则相反。它可以发现外部世界刚刚发生了什么，却不知道哪一家 supplier 属于你的公司，也不了解该 supply 与公司产品之间的关系。因此，任何一方的信息都无法独立解决这个问题。

我们提出了 hybrid research 的概念。这是一个 hybrid research 问题，需要精准处理 structured constraint，以及不完整、嘈杂且不断变化的 Open Web knowledge。这既不属于 sequel research，也不属于 search，而是一个跨领域的协同处理任务。

那么，这类任务通常会在什么情况下失败？我们发现，很多失败并不是由某个单独的 agent 或某个错误的 agent 导致的，而是经常发生在 handoff 或交接环节。

例如，数据库可能已经识别出某个相关 supplier，下一个 agent 需要进行搜索，但名称相近、知名度更高的公司可能会占据搜索结果。相关 website 看起来内容丰富，提供了很多 source，但与公司真正相关的部分却失效了。

反过来的情况也会发生。例如，search 已经找到一个与公司高度相关的外部事件，却无法将这个问题转化为严格的 database query。也可能两边分别完成了正确的工作，却很难将其 bridge 起来。每个 agent 看起来都是正确的，但最终整合时却违反了最初的一些约束。这也就是为什么要做 end-to-end。

很多问题的实践都发生在系统级流程中：如何规划、如何搜索、如何进行综合，以及如何完整保留其身份信息和存储目的。

交接本身就是一种信息压缩。当信息压缩遗漏了一些细节时，就不可能通过推理将其恢复。这与人的交流类似：一个人读过很多书，在与另一个人交谈的过程中，会察觉对方的变化，并据此表达相关内容。

因此，我们认为这是一个“1”的问题。为了解决过早收敛，我们将探索与预测完全拆分。系统设置了一个门控模块，国内通常称之为 EDS，用于控制各方之间是否可以相互影响。

在探索过程中，智能体可以发出自己的信息，包括其交互内容、交接信息和相关智能体信息，但不能直接改变结果。我们是有意这样设计的，甚至会观察 AI 是否认为这种机制不公平，例如为什么在这个阶段不能读取其他智能体的信息。

这是因为智能体非常容易受到外部信息或其他观点的影响。当一个智能体提出某个方向，其他智能体跟进后，可能会沿着同一个错误方向继续探索，并重复犯同样的错误。引入随机性的目的就是规避这一问题，使各个智能体能够保留自己的搜索树和假设，并保持随机性。

进入辩论模式后，模型会允许不同智能体相互查看信息。我们不会进行一次简单投票，而是让不同智能体相互质疑。某个智能体可能会指出对方的错误，并通过实验或不同思路加以验证，同时要求对方理解其具体做法。

在完整的辩论过程中，各个智能体会逐步得出结论。只有在辩论完全结束、所有智能体都达成共识且不再存在不同意见后，系统才会进入最终预测阶段。进入预测阶段后，我们会通过综合处理整合所有内容，并最终呈现给用户。

我们还会清楚引用每项信息的来源，说明信息是否来自数据库；如果来自数据库，则说明具体如何撰写；如果来自自动网络搜索，则说明对应的链接；如果来自内部文档，则说明具体依据的是哪一段内容。

总体而言，这一设计可以概括为：早期尽量保持独立探索，后期要求每一项主张都具备证据支持并达成一致。模型整体上也会进行模型投票，让不同模型、不同智能体共同形成结论，并延迟收敛，直至真正的内容能够得到支持。
