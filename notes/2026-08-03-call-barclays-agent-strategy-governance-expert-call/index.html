巴克莱智能体应用与模型战略专家访谈纪要

1. 受访者职责与智能体治理体系

a) 受访者在巴克莱智能体相关工作中的职责是什么？

  • 纵向团队管理与技术交付
  1. 受访者现任技术总监，负责管理软件工程师和架构师团队。
  2. 团队承担解决方案前端、中台及后台的开发工作。
  3. 工作内容既包括使用AI模型或智能体辅助软件工程任务，也包括开发具备AI或智能体能力的业务解决方案。
  • 横向治理与监督
  1. 支持生成式AI和智能体新用例的准入与治理。
  2. 覆盖用例评估、试点、用例管线管理、风险评估及生产化等环节。
  3. 主要承担咨询、监督和治理职责，确保用例满足银行的安全、风险和架构要求。

2. 智能体平台部署现状与技术路线

a) 巴克莱目前有哪些智能体平台已经进入生产部署？

  • Microsoft Copilot生态
  1. 巴克莱与微软已开展多年合作，约两年前首先推出Copilot，为员工桌面办公提供大语言模型能力。
  2. 近期进一步引入Copilot Studio及相关智能体能力，允许员工通过自然语言配置和定制个人智能体。
  3. 相关能力已向员工开放约6至9个月，现有生态已形成较广泛使用并逐渐成熟。
  4. 当前主要采用两种方式：一是通过前端直接配置智能体；二是通过Copilot Studio创建更定制化的智能体。
  • 内部智能体框架
  1. 银行正在建设内部能力，以支持规模更大、标准化程度更高、复杂度更高的业务用例。
  2. 一个重点方向是内部构建多模型智能体编排器和相关框架。
  3. 另一个重点方向是围绕Anthropic Claude SDK构建类似Claude Code/Cowork的企业级智能体框架。
  4. 该框架采用智能体循环、模块化插件、可移植技能及MCP服务，计划针对特定业务部门部署。
  • 整体发展阶段
  1. 巴克莱在行业同业中大致处于中间阶段。
  2. 过去12个月进行了专项投资，正在推动智能体从早期试点加速进入生产环境。
  3. 目前尚未进入全自主软件开发阶段，暂未部署类似Devin AI的全自主开发产品。

b) 当前智能体主要面向哪些任务？

  • 工程场景
  1. 代码生成、样板代码编写和调试。
  2. 测试自愈、代码审查及功能增强。
  3. SQL查询优化等复杂度相对较低的开发工作。
  4. 从单纯的AI辅助编码，逐渐转向任务委托、任务编排和更大范围的软件开发生命周期管理。
  • 业务场景
  1. 文档处理、内容摘要和文档生成。
  2. 审计、内容编写及内部资料处理。
  3. 面向内部文档、制度和政策资料的多步骤工作流。
  4. 通过主智能体与子智能体协作，完成文档提取、摘要、判断和执行等任务。

3. 工程智能体的产品选择与覆盖规模

a) 巴克莱目前主要使用哪些AI编码工具？

  • Claude Code
  1. Claude Code是当前主要的智能体编码助手之一。
  2. 真正规模化推广始于过去6至9个月，目前约覆盖3,000至4,000名工程师。
  3. 银行正围绕Claude SDK Harness、智能体循环和插件式架构进行更广泛投入。
  4. Claude既用于工程师通过CLI或IDE进行编码，也作为SDK嵌入企业级智能体应用。
  • GitLab Duo
  1. GitLab Duo目前覆盖约22,000名工程师，应用范围明显更广。
  2. 主要用于复杂度较低的日常工程任务，如样板代码、调试、代码审查、测试自愈及功能增强。
  3. 巴克莱此前已战略性选择GitLab而非GitHub，原因包括GitLab具备完整集成的持续交付流水线等能力。
  • 内部多模型产品
  1. 银行内部还提供面向多模态生成式AI的产品。
  2. 该产品可动态调用Llama、Gemini、Anthropic及OpenAI系列模型。
  3. 产品既面向普通用户，也面向开发者，但未以插件方式直接集成至IDE，因此不属于标准代码助手。
  4. 可用于SQL优化等较简单的编码任务。
  • 暂未采用的工具
  1. 目前未使用Codex。
  2. 工程侧投入主要集中于Claude Code，并将其作为GitLab Duo之上的增强层。
  3. 巴克莱尚未部署全自主软件开发能力，而部分同业已开始探索相关方案。

b) Claude Code和GitLab Duo如何分工？

  • GitLab Duo覆盖面更广，适合低复杂度、高频、标准化的工程任务。
  • Claude Code能力更强，适合复杂编码、智能体编排和更大范围的软件开发生命周期任务。
  • 当前银行仍在判断哪些用例确实需要Claude Code许可证，以避免将高成本工具用于简单任务。
  • Claude Code并非替代GitLab Duo，而是作为能力更强、成本更高的附加层。

c) 为什么Claude Code的成本明显更高？

  • 使用成熟度不足
  1. 不同工程团队的成熟度不一致。
  2. 部分团队仅将Claude Code作为聊天机器人使用，造成Token消耗效率偏低。
  3. 项目配置、上下文管理及实施方式不理想，也会导致不必要的调用。
  • 工程规范尚未统一
  1. 团队在一致性、最佳实践、上下文摘要及开发者或智能体之间的任务交接方面仍需完善。
  2. 当前正在向BMAD或规范驱动开发等框架演进。
  3. 目标是由单个工程师借助Claude Code管理更完整的软件开发生命周期。
  • 开发方式正在升级
  1. 不能继续依赖单次或少量提示，而要通过智能体循环、意图模型和编排框架串联开发环节。
  2. 在组织学习和成熟度提升阶段，效率不足会产生额外成本。
  3. 随着治理边界、运营模式及开发规范逐渐明确，单位任务成本有望得到优化。

4. API成本、Token使用量与支出结构

a) 工程编码场景的使用成本大约是多少？

  • 当前编码智能体的预期成本约为每名开发人员每天10至15美元。
  • 积极使用Claude Code等智能体编码方案的工程师约为3,000至4,000人。
  • 单项工程任务可能消耗约100万至300万Token，明显高于一般业务执行任务。

b) 业务智能体的Token消耗量如何？

  • 文档处理、文档运行及其他执行类任务，单项任务通常消耗约2万至20万Token。
  • 相比工程任务，业务执行类任务的单次消耗和成本明显更低。
  • 部分通用智能体能力可面向银行约9万名员工开放，但不同员工的使用频率差异较大，因此难以准确估算整体使用量。

c) 中等复杂度业务用例的年度成本是多少？

  • 对于内容摘要、文档生成、审计和内容编写等中等复杂度用例：
  1. 单个解决方案通常面向约1,000至1,500名用户。
  2. 每年Token成本约为100万至150万英镑。
  • 该数据仅代表部分已落地项目，不能直接外推至整个银行。

d) 编码支出主要流向哪些模型供应商？

  • Claude Code大约占编码模型支出的70%左右。
  • 其余支出主要流向OpenAI及其他模型能力。
  • 尽管GPT系列能力有所提升，编码领域目前并未转向Claude与GPT各占一半。
  • 由于银行正围绕Claude SDK、Claude Code Harness及相关企业级框架持续投资，预计未来12至18个月使用重心会进一步向Anthropic倾斜。

e) 未来Token支出会如何增长？

  • 整体银行层面的2026年Token预算暂时无法准确估算。
  • 可以确定的是，未来6个月、12个月和18个月的Token支出将显著增长，甚至可能呈指数级增长。
  • 主要驱动因素包括：
  1. Claude Code等工程智能体许可证数量快速扩大。
  2. 智能体从工程端进一步扩展至业务端。
  3. 单个用例的复杂度、可访问范围和工作流深度持续提高。
  • Claude Code用户过去6个月已从数百人增加至3,000至4,000人。
  • 预计约6个月后可能增至6,000人，一年后可能达到9,000至10,000人。
  • 用户数即使只增长一倍，Token消耗也可能因任务复杂度提升而增长超过一倍。

5. 多模型分层与智能体编排策略

a) 巴克莱如何在Opus、Sonnet和Haiku之间分配任务？

  • 模型分层原则
  1. Opus或Sonnet等能力更强、成本更高的模型用于复杂推理及特定编排任务。
  2. Haiku等低成本模型用于任务执行、文档摘要和简单交互。
  3. 系统可向用户提供模型选择，也可通过规则由智能体编排器自动选择模型。
  • 默认模型策略
  1. Opus在大多数情况下不是默认模型。
  2. 默认通常使用Sonnet或Haiku。
  3. 只有在能力要求较高时，才将复杂任务路由至Opus。
  • 使用量与成本分布
  1. 调用量预计更多集中于Sonnet及较低层级模型。
  2. Opus调用次数较少，但单Token成本更高。
  3. 因此不同模型的调用量不会均匀分布，但最终成本分布可能比调用量更加接近。

b) 为什么主智能体与子智能体通常使用同一模型家族？

  • 同一模型家族在上下文传递、交互方式、集成和配置方面更一致。
  • 可以减少跨模型调优、调试及不可解释错误。
  • 典型模式是：
  1. 编排智能体使用Opus。
  2. 较复杂子任务使用Sonnet。
  3. 文档提取、摘要等简单任务使用Haiku。
  • 同一模型系列也有利于共享框架、工具链及治理配置。

c) 是否完全排斥跨供应商模型组合？

  • 并不排斥，但目前尚未规模化采用。
  • 在评估环节，跨供应商组合可能具有优势：
  1. 开发智能体可使用Claude系列。
  2. 负责评判输出的模型可来自其他模型家族。
  3. 不同模型能够保持上下文独立，降低评估者与开发者共享相同偏差的风险。
  • 未来在大语言模型评判、对抗性智能体、A/B测试及红蓝团队测试中，跨供应商模型可能更有价值。

6. 长上下文、缓存与存储架构

a) 长时间运行的智能体如何管理上下文？

  • 当智能体处理内部文档、政策及多步骤工作流时，不能把全部信息持续放入上下文窗口。
  • 需要在以下两层之间进行分工：
  1. 会话状态和临时存储层。
  2. RAG检索增强生成层。
  • 会话中加载或生成的资料，可通过中间智能体状态或子智能体状态保存并反复检索，避免重复处理同一文档。
  • 例如，文档的0级、1级或2级摘要可以在整个会话期间保留，无须每次重新调用解析服务。
  • 这种架构可降低上下文窗口占用和Token消耗，从而减少运行成本。

b) 提示词和工具配置如何优化Token成本？

  • 将上下文分为静态和可变两部分：
  1. 静态上下文、系统提示词和工具模式可持续保留。
  2. 可变内容根据任务需要动态加载。
  • 为MCP服务设置清晰、简洁的标签，帮助模型和编排器准确识别服务。
  • 采用插件式模块化结构，将技能、MCP服务及数据源封装为独立插件。
  • 根据任务只激活必要插件，避免一次性向模型暴露全部工具和服务。
  • 通过限制对话轮次、智能体迭代次数及工具调用次数，控制成本和失控风险。
  • 银行的关注点已从早期“先实现功能”转向“优化生产运行效率”。

c) 缓存和会话存储如何落地？

  • 基础设施通常由超大规模云服务商动态提供，不需要业务团队自行采购服务器和SSD。
  • 可采用的存储方案包括：
  1. S3存储桶：管理文档及会话期资料。
  2. Amazon ECS：承载并动态扩展执行环境。
  3. DynamoDB：保存需要缓存24小时等短周期会话信息。
  4. DuckDB：用于应用内快速、临时访问，工具运行结束后清除。
  5. PostgreSQL：保存需要更长期持久化的信息。
  • 数据生命周期可配置为仅会话期间、24小时、48小时或7天，随后自动释放。
  • 具体方案取决于工具类型、信息是否需要持久化及所需保留时间。
  • 受访者团队主要关注AWS月度账单和S3等服务的OpEx，不直接负责CPU、SSD或底层基础设施采购。

7. 模型替换成本与供应商粘性

a) 如果出现更便宜的模型，替换现有Claude或GPT是否容易？

  • 技术上可以替换，但实际操作并不容易。
  • 技术迁移成本
  1. 智能体框架、应用配置、评估和追踪体系往往与特定模型绑定。
  2. 替换模型后，需要重新调试智能体行为。
  3. 测试、评估、监控和相关能力也需重新配置。
  • 治理与采购成本
  1. 新模型需要经过采购审批。
  2. 需要完成第三方供应商风险评估。
  3. 需要获得模型风险管理、安全及技术架构部门批准。
  4. 整套方案的能力和风险也需重新评估。
  • 时间成本
  1. 新模型从评估到正式采用通常需要9至12个月。
  2. 即使低价模型具备明显成本优势，也需要将一次性迁移和评估成本纳入比较。

b) 为什么企业会倾向于继续使用同一模型家族？

  • 同一模型家族集成和调试更简单。
  • 上下文传递和智能体交互方式更加一致。
  • 可以减少跨模型运行中的随机错误和行为差异。
  • 供应商可能按Token使用量提供阶梯折扣，使用规模越大，单位价格越低。
  • 如果用量分散至多个模型家族和供应商，可能无法达到特定折扣门槛。
  • 企业还可能通过AWS、Azure等云服务商采购模型，因此模型选择会与云服务整体折扣和商业协议相互绑定。

c) 更便宜的小模型是否会成为重要趋势？

  • 当前人工成本通常仍显著高于模型成本，因此企业首先关注以模型替代人工所带来的总体节省。
  • 当容易自动化的人工环节逐渐被消除后，模型成本优化的重要性会明显上升。
  • 未来企业会更加重视：
  1. 更便宜、更小、更灵活的模型。
  2. 多模型分层和任务路由。
  3. 简单任务使用低成本模型。
  4. 复杂任务按需升级至前沿模型。
  • 部分小模型即使规模仅为前沿模型的约十分之一，仍可能实现约97%的任务效果，而成本约为前沿模型的61%。
  • 随着生产用例和智能体工作链数量增加，模型优化将对企业利润产生显著影响。

8. 中国开源模型的采用前景

a) 巴克莱目前是否使用中国开源模型？

  • 现阶段尚未使用。
  • 主要障碍包括：
  1. 中国及巴克莱业务所在国家的监管限制。
  2. 数据驻留和数据主权要求。
  3. 模型风险、安全及内部验证要求。
  4. 第三方供应商及法律责任评估。
  • 银行认可中国开源模型的成本优势，也有探索意愿，但尚未进入积极试用阶段。

b) 未来3至6个月内是否可能采用？

  • 短期内采用的可能性较低。
  • 新模型通常需要经历模型风险、内部验证、技术、安全及供应商风险等多轮评估。
  • 以Anthropic通过AWS等云服务商接入为例，整体评估耗时约9至12个月。
  • 因此，中国开源模型在短期内难以进入生产环境，实际采用时间可能晚于2027年。

c) 如果中国模型通过AWS Bedrock或Azure提供，是否会加快采用？

  • 会在一定程度上加快。
  • 超大规模云服务商可先完成第一层审查，包括：
  1. 合作关系和法律责任。
  2. 基础设施义务。
  3. 安全性和渗透测试。
  4. 模型基础评估。
  • 银行仍需针对模型本身完成第二层内部评估。
  • 云平台接入能够简化部分沟通、合同和安全评估，但不能完全免除银行自身的治理流程。

9. 智能体规模化应用的主要瓶颈

a) 限制智能体更广泛部署的首要因素是什么？

  • 首要因素并非模型能力不足，而是银行所处行业高度监管且风险厌恶。
  • 核心约束包括：
  1. 声誉风险。
  2. 网络及数据安全要求。
  3. 供应商稳定性和供应商风险管理。
  4. 架构适配和系统隔离要求。
  5. 模型是否符合银行风险承受范围。
  6. 法规遵从及合规证明能力。
  • 大量供应商会因规模、业务稳定性、安全能力或法规证明不足而被排除。

b) 评估能力为何成为瓶颈？

  • 银行同一时间只能全面评估有限数量的新模型。
  • 即使仅将模型用于研发试验，也需经过严格流程并产生评估成本。
  • 模型供应商和产品迭代速度远高于金融机构的评估及采用速度。
  • 过去9至12个月，市场模型数量和版本数量已超出许多机构能够有效跟进的范围。
  • 工程和技术团队自身成熟度仍在提升，难以及时掌握全部新能力。

c) 模型安全性是否已经成为现实风险？

  1. 智能体应设置何种能力边界。
