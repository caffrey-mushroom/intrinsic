原标题：微软离职销售专家|金融服务领域对 Azure 云平台的需求保持强劲，微软指引九月季度约 44% 至 45% 增长，生产级 AI 更侧重文档工作流与有针对性的 Copilot 采用，推理成本下降同时规模化使用维持消耗

#cloud #financials #ai-demand

Meritco 久谦 · 2026-10-22

摘要

金融服务行业的 Azure 云平台消费仍由广泛的传统工作负载支撑，同时新增的 AI收入集中在较大型的生产部署中。文档自动化和员工助理主导经常性使用，但治理、集成和容量限制延缓了从已获资金的需求到计费的转换。推理优化可以在容量扩张时降低单位成本而不减少总体消耗。

要点

  1. 从 7 月到 9 月，金融服务的 Azure 云平台需求保持强劲，由广泛的数据库、基础设施、分析、安全和应用现代化工作负载支撑，而新增的 AI 收入更多集中在数量较少的大型项目；微软公开指引九月季度按固定汇率计算的 Azure

同比增长约为 44% 至 45%

  1. 从 6 月到 9 月，AI 的生产采用有所增加，但安全审查、模型风险管理、数据集成、监管审批和遗留系统使企业规模化保持渐进；文档工作流自动化在生产成熟度和经常性 Azure

消耗中排名第一，员工知识与助理排名第二，自治业务智能体排名第三

  1. 随着客户采用更小的模型、开放权重模型、模型路由、提示优化和缓存，AI 使用增长速度越来越快于推理支出；如果推理成本下降 40% 而事务量翻倍，则在不计入额外存储、数据库、Azure AI

Search、网络和监控消耗的情况下，总推理支出仍可能约增长 20%

  1. 针对大型金融服务 AI 项目的方向性预算框架大致分配约 25% 给基础设施、15% 给模型推理、25% 给应用开发、25% 给集成与工程以及 10% 给安全与治理；计划在基础设施、模型推理和应用开发上的投资较去年约增加 25% 至

33%

  1. 对需要专用 GPU 基础设施、预配模型吞吐量或区域可用性的 7 月至 9 月部署存在 AI 容量约束，导致部分已获资金的需求被延迟，但这并不意味着被取消
  2. 自 6 月以来，金融服务客户在扩展 Copilot 时越来越倾向于基于活跃使用和可衡量的投资回报率进行选择性扩展，而不是广泛分配许可证；Microsoft 365 Copilot 的席位并不会自动提高 Azure 账单，但使用

Copilot Studio、Azure AI Foundry、Azure AI Search、Azure Functions 和数据库构建的专用工作流创造了有意义的交叉销售机会

Q:在您负责的金融服务客户中，7月至9月的实际 Azure 支出与4月至6月相比如何，也就是日历上的第三季度与第二季度相比？AI 工作负载与非 AI 工作负载有什么变化？

A:在金融服务账户中，7月至9月仍然是 Azure 需求持续的时期，且 AI 正成为越来越重要的增量增长驱动因素。在非 AI 方面，既有的消费驱动因素仍然是数据库、应用现代化、Databricks 以及更广泛的 Azure 基础设施。在AI 方面，需求越来越集中于文档智能、企业搜索和面向生产的 Copilot 界面。关键区别在于，AI 管道中的增长并不会立即转化为已计费的消费，因为安全评审、数据集成和投产审批会产生滞后。

在未对账户级数据之前，我不会给出确切的环比增长百分比。我强调的商业趋势是：AI 机会在增加，同时存在大量经常性的非 AI 工作负载作为基座。作为背景，微软在公开指引中表示，按恒定汇率计其 9 月季度的 Azure 同比增长约为 44% 到45%。这支持了更广泛的需求前景，但它并不是衡量单个账户环比支出的指标。

Q:金融行业的趋势是否与整体 Azure 趋势一致，还是存在差异？

A:金融服务与更广泛的 Azure 增长趋势是直接对齐的，但采纳的构成和节奏有些不同。金融机构对云现代化有强劲的潜在需求，特别是在数据库、分析、安全和应用基础设施方面。AI是另一个增长机会，特别是在文档处理、欺诈分析和提升员工生产力的解决方案上。金融服务不同之处在于投产部署的速度。监管要求、模型风险管理、数据治理以及与遗留系统的集成可以延长实施周期。我的判断是潜在需求仍然强劲，但 AI的消费相比监管较少的行业可能更为缓慢地放量。在没有行业特定消费数据的情况下，不应假定该行业会与 Azure 的整体增长百分比相匹配。

Q:金融行业的增长是广泛分布的还是较为集中？大多数客户都在增加支出，还是少数大型项目在推动增长？

A:我会将基础云消费的增长描述为广泛性的，但与 AI 相关的支出则更为集中。大多数成熟的金融服务客户在数据库、基础设施、分析和安全方面都有持续的 Azure 消费，形成了相对多元的基础。然而，AI支出的较大增量往往来自较少数量的客户将大规模工作负载投入生产或扩展现有部署。

区分增加消费的客户数量与推动总增长的资金规模很重要。我的预期是，少数较大的项目在增量 AI 收入中占比不成比例，而传统的云现代化则支撑着更广泛的客户群。在未审阅账户级消费分布之前，我不会为这种集中度指定精确的百分比。

Q:展望日历上的第四季度，哪些因素会让您有信心认为客户的 Azure 支出会加速、保持稳定或放缓？

A:就日历第四季度而言，即 10 月到 12 月，我的基线判断是 Azure 消费将非常稳定，并有潜在的加速可能，特别是随着已获得资金的 AI项目进入生产。让我有信心的三个因素是：已批准的预算和已承诺的迁移计划；已通过安全和模型风险审查的项目；以及可用的 Azure 容量以支持生产工作负载。

在银行和抵押贷款相关的金融服务中，传统基础设施和数据库消费提供了相对稳定的基础。上行潜力来自 AI 推理、文档处理和分析工作负载超越初始试点规模的扩展。最大的不利风险是集成延迟、采购周期以及项目推迟到 2027年。我的预期是持续增长，但生产上线的时点将决定第四季度究竟是显著加速还是仅仅维持既有轨迹。

Q:Azure 收入或增长是否存在季节性？例如，日历第四季度通常会因为 12 月休假而增长较低，工作活动下降吗？

A:Azure 支出存在一定季节性，但我不认为仅仅因为 12 月假期就会出现显著下降。Azure 主要是一个以消费为驱动的业务，生产工作负载即便在员工休假时也会继续运行。在金融服务中，交易处理、数据库、安全和面向客户的应用全年运行。

季节性对新项目部署的影响更大。由于假期安排和年终变更冻结，12 月在实施和采购方面可能更慢。另一方面，一些客户会加速迁移或在年终前使用剩余预算。根据我的经验，基础消费是稳定的，而新工作负载的上线在 12月可能会更慢。因此，我会将季节性视为一个温和的时间因素，而不是对 Azure 收入的主要阻力。

Q:对于同一组客户，到 9 月底在生产中运行的 AI 工作负载大约占多少百分比，相较于 6 月底？这一份额是在增加还是保持稳定？

A:我会将趋势描述为生产采用在增加，而不是保持稳定，尤其是在金融服务领域。重要的区分是 AI 的试验、有限的付费生产和企业级生产之间的差别。将文档智能、知识检索和客户服务应用更多地纳入实时业务流程的兴趣在增加。

在未审查相同客户群及其工作负载清单之前，我不会给出确切的 6 月到 9 月的百分比。一个只有一个生产 AI应用且有十个试点的客户，与一个运行十个生产应用的客户，其采用曲线会非常不同。生产采用在推进，有些进展推进得很快，但由于安全、模型风险、审批、数据集成以及证明可衡量 ROI 的需要，更广泛的企业级扩展仍然是渐进的。

Q:对于在7月之前已经投产的四个 AI 项目，到9月它们的每月 Azure 支出发生了怎样的变化？是加速、保持稳定还是回落？

A:对于在7月之前已投产的 AI 项目，我总体上预期到9月支出会保持稳定或更高，而不会普遍出现下降。以文档智能为例：一旦金融机构从处理有限的文档集转向处理大量的贷款申请或服务记录，通过推理、文档处理及支持数据服务的经常性 Azure消费就会增加。知识检索类应用在更多员工和部门开始使用时也可能呈现类似模式。

不过，支出并非总是加速。客户可能会优化提示、引入更小的模型或改进缓存，从而在使用量增长的同时降低单次成本。我区分工作负载采用与收入增长的概念。我可以描述扩展机制，但在没有这些四个项目的实际消费历史记录的情况下，我不会声称具体的支出变化。

Q:总体而言，支出增长是否与工作负载增长一致，还是两者可能会出现背离，因为客户选择更小的模型、开源权重模型、提示优化或其他节约成本的措施？

A:AI 工作负载增长与 Azure 支出正逐渐出现背离，因为客户在推理环节变得更高效。某金融机构的文档处理量可能翻倍，但 AI 支出增长却明显低于100%，因为它使用了更小的模型、提示优化、缓存或模型路由。客户也在为可预测的、高吞吐量任务评估开放权重模型，同时将高端模型保留用于复杂推理。

每笔交易成本降低可以加速采用，因为客户能够证明更多工作流自动化是合理的，从而产生额外的消费。我预计在许多已优化的工作负载中，AI 使用量的增长速度会快于推理支出。Azure 支出仍可能通过增加数据库、存储、搜索和相关服务而上升。

Q:对于最近的多年期 Azure 承诺，客户的实际消费是与计划的爬坡一致、超前还是滞后？为什么？

A:我会将针对多年期 Azure 承诺的消费总体描述为：对于已建立的工作负载通常与计划爬坡相符，而对于较新的举措则更具波动性。传统工作负载如数据库、基础设施和分析的消费通常更可预测，因为客户已有迁移时间表和运行要求。AI则不同：客户可能基于雄心勃勃的生产路线图对 Azure 做出承诺，但由于安全审批、数据集成、模型验证或从初始试点扩展的延迟，实际消费可能滞后。

重要的区别在于商业承诺与实际实现的消费之间。三年期的 Azure协议表明了采购意图，但随着工作负载部署并被使用，收入才会爬升。没有各客户承诺进度的实际消费细节，我不会把整个组合简单地归类为超前或滞后。最大的变量通常是生产准备状态，而不一定是需求不足。

Q:在 7 月至 9 月期间，项目，尤其是 AI 项目，是否因 Azure 容量或配额限制而受阻？该季度容量是否是一个因素？

A:是的。容量约束在 7 至 9 月季度确实相关，尤其是对需要专用 GPU 基础设施或预置模型吞吐量的 AI 工作负载。微软已公开承认，某些地区或领域的 AI需求在全球可用容量上存在超前情况。然而，公司范围的约束应与可在单个金融服务账户中验证的情况区分开来。

影响往往集中在较大的生产部署上，这类场景中客户需要保证吞吐量、特定模型可用性，或满足数据驻留要求的区域容量。传统工作负载通常较少受 GPU 约束影响。容量问题会延迟已获资金支持的 AI 需求转化为 Azure消费，但并非所有被延迟的项目都可归因于基础设施短缺。安全审查、集成准备和配额配置也能解释这些延迟。

Q:在 7 月，约有多少比例的已获资金支持的 AI 项目因任何原因被推迟？

A:我不会给出无支撑的数据百分比，但应当把被推迟的项目与被取消的项目区分开来。在金融服务领域，已获资金支持的 AI 项目可能因安全、模型风险、数据保护、采购或与 Azure 相关的问题而错期。上线推迟并不一定表明需求疲软。在 7 至 9月间，我预期复杂的面向客户的 AI 和具代理特征的工作流出现的延迟最多，而较为简单的内部生产应用遇到的阻碍较少。

要准确量化延迟，我会将该季度计划上线的已获资金项目数量与截至 9 月 30 日投入生产的项目数量进行对比。这样得到的延迟百分比比猜测更具可辩护性。

Q:当客户为 2027 年日历年做计划时，有多少 AI 资金是新增的，又有多少是从其他传统 IT 项目中重新分配的？是新钱还是内部重拨？

A:对于 2027 年日历年，我会把企业 AI 资金描述为增量投资与从现有 IT 预算重分配的组合，而非完全全新的支出。在金融服务领域，最有说服力的 AI商业案例越来越多地获得专门的业务单元资金，特别是用于文档自动化、客户服务和运营效率。同时，相当一部分资金是从现有的现代化、分析和应用开发预算中重定向的。

例如，一个已经在投资 Azure Databricks 或 Fabric 的客户可能会扩大这些举措以支持 AI，而不是创建完全独立的预算。AI正从实验性创新资金向经常性运营预算转变。在没有客户预算数据的情况下，我不会给出精确的新资金与被重分配资金的比例，但具有可衡量成本节省或收入影响的项目更有可能获得真正的增量资金。

Q:对于一个典型的大客户，总项目投资在基础设施、模型、应用、数据或集成、工程与安全之间大致如何分配？与去年或过去相比，这一构成有何变化？

A:对于典型的大型金融服务客户，一个方向性的规划模型会大致分配：约 25% 给基础设施，15% 给模型推理，25% 给应用开发，25% 给集成与工程，约 10% 给安全与治理。这代表的是总项目投资，而不仅仅是 Azure账单。基础设施涵盖计算、网络和托管。模型开支包括推理和 API 消耗。应用支出涵盖开发、工作流、集成与部署。

数据包括准备、管道、数据库和检索系统。安全包括身份、合规、合规监控和模型风险控制。在金融服务中，数据集成经常占据较大份额，因为存在遗留系统和监管要求。这些百分比是说明性的预算框架，而非经测量的平均值。一旦应用进入生产，构成可能会向经常性基础设施、推理和运营支持倾斜。今年与去年相比，对基础设施、模型推理和应用开发的规划大约增长了25% 至 33%，表明这些项目投资有显著推动。

Q:如果客户增加对基础设施的支出，Azure 应该会直接受益。对于安全和数据支出，收益是流向第三方软件提供商更多，还是流向 Azure？

A:Azure 在基础设施、模型推理和 Azure 托管的数据服务方面受益最直接。然而，需要区分总 AI 项目支出与最终成为 Azure 收入的部分。如果一家金融机构投资于 GPU 计算、Azure OpenAI、Azure SQL 或Azure AI Search，那会直接产生 Azure 的消费。当生成的应用在 Azure 上运行时，应用开发与集成也会产生 Azure 收入。对顾问、内部开发或第三方软件的支出并不必然转化为 Azure 收入。

最有意思的机会是乘数效应：成功的 AI 应用可以在计算、推理、数据库、存储和安全上同时产生经常性消费。这就是为什么将项目投入生产对 Azure 的长期增长很重要。

Q:当 AI 项目进入生产并需要更多治理、安全与数据库时，是专门的第三方软件和数据提供商受益更多，还是 Azure 自身更能从这一趋势中获益？

A:双方都有获益。Azure 通常更有利于捕获更广泛的基础设施和数据消耗基础，而专业的第三方厂商则能获得更高价值的安全与治理支出。随着 AI 在金融服务领域进入生产阶段，客户需要更强的身份控制、数据治理、访问管理、可审计性和监控。微软通过Azure 以及 Microsoft Entra ID、Defender、Purview 和 Microsoft Sentinel 等产品拥有优势，这些产品可以集成到现有的企业环境中。

第三方供应商在多云治理、数据安全态势管理、AI 模型安全以及独立风险监控方面仍然具有相关性。大型银行很少希望其整个安全架构依赖于单一云提供商。我的预期是，Azure会夺取更多底层的经常性消耗，而第三方专精厂商可能在特定安全类别中从较小的基数实现更快的增长。结果取决于客户是优先考虑集成的 Microsoft 安全栈，还是优先在多个云和 AI 环境中保持独立控制。

Q:将一个已上线的金融服务 AI 项目与一个停滞的项目比较。差别是什么，为什么有些项目会被暂停或停止？

A:把文档智能与复杂的面向客户的 AI自动化相比较。一个贷款文档提取的用例会对文档进行分类、提取信息，并将其送入现有的工作流以供人工验证。这类项目通常有明确的生产路径，因为范围狭窄、业务负责人可识别，并且可以通过处理时间、准确率和减少人工工作量来衡量成功。

相比之下，一个能够做出客户服务或信贷相关决策的自治 AI 代理更容易陷入停滞。它会引入模型风险问题、监管要求、敏感客户数据、集成复杂性，以及关于 AI 决策责任归属的疑问。最大差异不一定是技术本身，而是生产就绪度和业务归属。

能够推进的项目具有定义明确的 ROI、获批的数据访问、人工监督和有责任的执行赞助人。陷入停滞的项目可能有令人鼓舞的演示，但尚未解决运营或治理要求。这就是为什么应当将 AI 实验与实际的 Azure消耗区分开来：成功的概念验证并不会自动成为可扩展的生产工作负载。

Q:当前哪些金融服务 AI 用例正在产生最多的经常性 Azure 支出？它们主要是帮助员工、服务客户，还是在业务工作流中采取行动？

A:金融服务领域最强的经常性 Azure消耗来自于员工辅助的工作流和以文档为主的业务流程，而不是完全自治的代理。第一类是文档智能，包括抵押贷款申请、收入验证、贷后服务和合规文档。这些工作负载通过文档处理、模型推理、存储、数据库和集成服务产生经常性消耗。它们具有吸引力是因为处理量是持续的且ROI 可度量。

第二类是内部知识检索和员工 Copilot 应用，尤其面向客服团队、承保人员和运营人员。当客户使用 Azure AI Search 和托管在 Azure上的模型构建这些应用时，使用量会随员工采用而扩大。第三类是面向客户的辅助服务。该类在快速增长，但能够采取重要行动的完全自治代理仍受合规和人工审批要求的更多限制。

按生产成熟度排序，我会把文档工作流自动化放在首位，员工知识和辅助其次，自治业务代理排在第三。可持续的 Azure 消耗来自交易量最高且使用最重复的场景，而不仅仅是大量存在的 AI 试点。

Q:自三月或六月以来，客户在生产模型选择上有哪些变化？

A:自三月以来，尤其是自六月以来，最大的变化是客户正从“一模型通用”转向为特定工作负载和经济性选择模型。早期，许多企业 AI 项目默认使用可用的最大规模前沿模型，通常来自OpenAI。现在客户更为审慎：在复杂推理场景使用高能力模型，而在文档分类、提取、摘要和重复推理场景使用更小、更便宜的模型。

客户对开源权重模型的兴趣增加，因他们希望获得更多部署控制、可预测成本或特定的数据处理方式。然而在金融服务领域，模型质量、安全性、可审计性和运营支持比仅仅选择最便宜的选项更重要。每笔推理交易的成本可能下降，但更低的成本可以解锁显著更多的生产工作负载。因此模型效率并不必然减少总的Azure 消耗；它可以支持更广泛的采用。

Q:开源权重模型的工作负载实际上运行在哪里：在 Azure、Azure 虚拟机、另一家云、本地，还是混合？

A:三种部署模型都存在。对于已在 Microsoft 平台标准化的金融服务客户，Azure 往往是最实用的起点。有两种主要方式可以在 Azure 上运行开源权重模型。一种是在 Azure AI Foundry中使用托管的模型服务选项，由微软处理更多的部署基础设施；另一种是在 Azure GPU 虚拟机或 Azure Kubernetes Service 上自行托管，赋予客户对模型定制、性能和伸缩性的更大控制。

对于高度敏感的工作负载、数据主权要求以及拥有现有 GPU 基础设施的机构，本地部署仍然相关。AWS 和 Google Cloud 也是选项，尤其适用于已经建立多云环境的客户。关键区别在于托管推理与自托管计算。两者都可以通过不同的计费模式产生Azure 消耗。我不会在没有客户级数据的情况下断言精确的部署比例。方向上看，模型选择变得更灵活，而部署决策仍然受既有云承诺、安全架构和总体拥有成本的强烈影响。

Q:是否有更多客户为降低成本而转向更便宜的模型、模型路由、缓存或提示优化？这对总 Azure 账单的影响如何：是下降、持平还是继续上升？

A:是的。随着 AI 从试点进入生产，金融服务客户在优化推理成本方面变得更成熟。我看到三种方法：对常规任务使用更小、更便宜的模型；仅在必要时将复杂请求路由到更高能力的模型；以及优化提示、缓存和 token使用以减少不必要的推理。重要的区分是每笔交易的成本与总体 Azure 账单。对于使用量相对固定的既有工作负载，优化可以减少推理支出。

对于正在扩展 AI 采用的客户，更低的单元成本会使额外的用例在经济上可行。例如，如果推理成本下降 40% 但交易量翻倍，在假定工作负载构成相似的情况下，总体推理支出仍可能大约增加 20%。AI 应用还会消耗 Azure存储、数据库、Azure AI Search、网络和监控等资源。总体上，我预期每笔推理交易的成本会下降，而对积极扩展生产 AI 的客户来说，总体 Azure 消耗通常会保持稳定或增加。

Q:在 AI 交易中，Azure 相对于 AWS 和 Google Cloud 的优势是什么？为何 Azure 能赢得一些交易，而在另一些交易中落败？

A:Azure 在金融服务领域最大的竞争优势在于其与企业技术栈的集成能力，而不仅仅是拥有最好的 AI 模型。以一家已经在使用 Microsoft 365、Microsoft Entra ID、Azure SQL 和 Azure Databricks 的抵押贷款放款人为例。如果它要构建一个用于贷款处理的 AI 应用，Azure 具有天然优势，因为身份、数据访问、安全性和采购流程已经建立完备。这会减少实施摩擦并能加速投入生产部署。

当客户已深度承诺于 AWS、偏好 Google Vertex AI 与 Gemini 生态，或在其他地方能获得更优的经济性、模型性能或 GPU 可用性时，Azure 可能会失利。当客户已经在 AWS 上运营大型应用环境时，AWS 尤其强；而Google Cloud 在数据分析和以 AI 为本的开发方面具有竞争力。没有具体的成交记录，我不会把某一笔保密的胜负归因于单一因素。更清晰的经常性模式是：Azure在企业集成和运维熟悉度上获胜，而可能因既有云足迹、专门化需求、定价或容量问题而落败。

作为外部交叉验证，2026 年剑桥一项关于金融服务行业 AI 的研究发现，在金融科技受访者中 AWS 更为普遍，而在传统金融机构中 Azure 更为普遍。该研究对竞争对手和既有企业云足迹的重要性包含更多细节。

Q:你有没有参与过微软的 Forward-Deployed Engineering 团队的项目？你有直接的 Forward-Deployed Engineering 经验吗？

A:一个被正式指派的 Forward-Deployed Engineering 团队与微软的 Cloud Solution Architects、专项专家、工程团队和实施合作伙伴是有区别的。工程介入仍然可以是实质性的，可能包括解决方案架构、数据集成、安全需求和概念验证验证等工作。

Forward-Deployed Engineering 模式是将工程师更直接地嵌入到客户的实施中，帮助构建可投入生产的 AI 解决方案。这些团队旨在解决技术和商业挑战，尤其是通过缩短 AI 项目从批准到实际消费之间的时间来发挥作用。

Q:你观察到客户对微软工程或类似 Forward-Deployed Engineering 的支持有何反馈？这有帮助，还是影响不大？

A:效果取决于客户，但动手的微软工程支持通常会产生有意义的差异，尤其是在将 AI 项目从概念验证推向生产阶段时。其好处通常集中在三个方面：更快解决技术阻碍、更好地与既有 Azure 基础设施集成，以及在安全和架构决策上提高信心。

例如，某金融机构可能有一个成功的文档智能试点，但在连接遗留系统、管理敏感数据或设计可扩展的生产方案时遇到困难。直接的工程介入可以比仅靠文档和支持工单更快地解决这些问题。当障碍是实施复杂性时，嵌入的技术专长能创造最大价值。如果阻碍是预算批准、监管签字或缺乏高管赞助，单纯增加工程师并不能解决这些问题。

Q:自 6 月以来，金融服务客户是否更愿意扩展或续订付费 Copilot 部署？是什么在改变他们的决定？

A:金融服务客户在扩展 Copilot 部署方面变得更有意愿，但他们也在变得更有选择性，关于内部哪些人应获得付费许可。将许可发放给不使用它的员工是浪费资金。今年早些时候，关注点常常是试点和技术演示。自 6月以来，讨论越来越转向可衡量的采用率、生产力提升，以及这些收益是否能证明持续订阅成本的合理性。

最强的业务案例出现在那些经常处理文档、会议、研究和复杂信息的员工群体。客户正从基于热情分配许可转向基于已证明的使用情况和投资回报分配许可。我看到在有针对性的部门中扩展潜力更强，但不应假定每个试点都会成为全企业范围的推广，或续订会自动发生。

Q:同样的逻辑是否适用于其他行业——为需要的部门购买 Copilot 授权，并在使用率低的地方减少或重新分配授权？

A:是的。这种采购纪律适用于大多数行业，而不仅限于金融服务。获得最大价值的部门因行业而异。在金融服务和汽车行业，可能的使用者包括客户经理、分析师、合规团队和运营人员。在其他行业，产生价值的使用者可能是销售、咨询、法务、人力资源或项目管理等岗位。

常见模式是公司最初购买相对广泛的一组 Copilot许可以评估采用情况，然后查看活跃使用情况，识别哪些员工持续使用该产品，并评估它是否节省了大量时间。如果某个部门显示出强劲的生产力收益，客户更愿意扩展许可；如果使用率低，他们可能会重新分配许可，而不是继续为未充分利用的席位付费。已购买许可与实际交付价值的许可之间的区分对续订和扩展愈发重要。该行为在各行业普遍适用，但结果取决于谁在有意义地使用这些许可。

Q:Copilot 推广是否会导致客户购买更多 Azure 服务或构建增加其 Azure 账单的自定义 agent？

A:Copilot 可以成为额外 Azure 消耗的切入点，但其影响是间接的而非自动的。应将 Microsoft 365 Copilot 许可与自定义 AI 应用区分开来。购买更多的 Microsoft 365 Copilot席位并不会自动增加客户的 Azure 账单。

当客户发现标准的 Copilot 体验无法满足专门化工作流时，机会便出现了。一家抵押贷款机构或银行可能希望有一个能检索贷款文档、核查申请完整性并与其服务系统集成的 agent。这可能会导致在 Copilot Studio、Azure AI Foundry、Azure AI Search、Azure Functions 和数据库方面的投资。具体影响取决于解决方案的部署方式以及客户如何处理业务工作流。

真正的机会在于从员工生产力向定制的、可投入生产的业务工作流的推进。我会把这描述为一个有意义的交叉销售机会，但不应假定每次 Copilot 推广都会产生额外的 Azure 收入。决定性因素是客户是否真正构建并运营自定义工作负载。

Q:你是否看到面向客户的证据表明 Azure 的交付时间受到影响，因为容量被分配给 Copilot 或其他微软内部工作负载？

A:没有直接面向客户的证据证明 Azure 部署因微软优先支持 Copilot 或其他内部工作负载而被延迟。客户可以观察到 GPU 可用性有限、区域性容量限制、配额限制以及某些 AI服务更长的供应时间。这些限制可能会推迟有资金支持的项目或将 Azure 消耗推到更晚时期。

观察到容量短缺与知道微软如何在内部分配该容量之间存在重要区别。面向客户的延迟并不能确定其根本原因是否为 Copilot 需求、其他 Azure 客户、硬件可用性或区域性约束。容量限制确实是影响 AI部署时间的合法因素，但要将延迟特定归因于微软内部工作负载需要经核实的分配数据。

Q:你是否估算过微软在2027财年可能新增多少吉瓦的容量？基于已获资金的项目和客户部署计划，微软是否需要在2027财年剩余时间里更快地扩建容量，有哪些证据支持这一结论？

A:我预计微软将在2027财年剩余时间里继续加速AI容量的部署。在没有经过核实的基础设施数据情况下，我起初不会给出具体的吉瓦数。有三个理由支持这一方向性判断。首先，微软已公开承认存在AI容量限制，表明在某些领域需求已超过可用供给。其次，客户管道正从试验阶段向生产阶段转变，在金融服务领域这意味着经常性的推理、文档处理、Azure AI Search和数据工作负载，而不是偶发的试点活动。第三，随着推理成本下降，客户可以在更多的基于交易的业务流程中经济性地部署AI，即便计算效率提高也会产生额外需求。

最有力的支持证据是微软对基础设施的大规模投资、其公开讨论的容量限制以及不断扩展的生产级AI用例。更快的容量部署在商业上是合理的，但关键指标不仅仅是新增了多少吉瓦，而是可用的GPU容量在正确的地区变得可用并转化为付费的Azure消耗的速度。电力可用性、建设时间表和网络部署会限制微软扩充供给的速度。

Q:与AWS或Google Cloud相比，竞争对手是否因为拥有更多可用容量而在赢得AI订单上占优？

A:容量可用性会影响竞争性的AI合同，但我不会得出AWS或Google Cloud在所有情况下始终比Azure拥有更多容量的结论。关键是某个供应商在客户需要的时间是否具备特定的GPU容量、模型供给和区域可用性。如果一家金融机构有一个已获资金准备投入生产的AI项目，而Azure无法满足所需的配置时间表，这就为AWS或Google Cloud创造了机会，因为客户可能会迁移特定工作负载而不是推迟业务。

Azure仍然可以凭借既有的企业关系、微软的安全集成和商业承诺来取胜。容量已成为更重要的竞争考量，但它并非每笔交易的决定性因素。目前没有经过验证的模式表明AWS或Google Cloud因容量优势而持续在金融服务的AI交易中占优。我会将容量视为Azure在单笔交易层面的风险，而非更广泛竞争劣势的证据。
