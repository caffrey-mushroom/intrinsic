专家访谈纪要：Azure、AI应用与云竞争趋势

1. Azure Q3需求与金融行业增长特征

a) 日历年Q3（7—9月）Azure支出较Q2表现如何，AI与非AI工作负载分别有哪些变化？

  • 金融服务客户的Azure需求在Q3继续增长，AI正逐步成为增量增长的重要驱动力。
  • 非AI工作负载仍构成稳定、庞大的经常性基础，主要包括：
  1. 数据库现代化；
  2. 应用现代化；
  3. Databricks及分析平台；
  4. Azure基础设施与安全服务。
  • AI需求主要集中在：
  1. 文档智能；
  2. 企业知识搜索；
  3. Copilot；
  4. 面向生产环境的AI接口与应用。
  • AI项目管线增长不会立即转化为Azure计费收入，安全审查、数据集成、模型风险评估及生产审批均会造成时滞。
  • 专家未提供所负责客户的Q3环比增速，原因是缺少账户层面的实际使用数据。
  • Microsoft公开指引显示，9月季度Azure按固定汇率计算的同比增速约为44%—45%，可用于判断整体需求环境，但不能直接代表单个客户或金融行业的环比增速。

b) 金融服务行业的Azure趋势是否与整体市场一致？

  • 从方向看，金融服务行业与Azure整体增长趋势一致，云现代化和AI需求均较强。
  • 金融行业的基础需求集中于数据库、分析、安全和应用基础设施，AI则进一步创造增量机会，重点场景包括：
  1. 文档处理；
  2. 欺诈分析；
  3. 员工生产力工具。
  • 与监管较少的行业相比，金融行业从试点到生产部署的速度更慢，主要受以下因素影响：
  1. 监管要求；
  2. 模型风险管理；
  3. 数据治理；
  4. 遗留系统集成；
  5. 敏感数据保护。
  • 因此，金融行业底层需求依然强劲，但AI使用量增长可能更加渐进，不能简单假设其增速与Azure整体增速完全一致。

c) 金融行业的增长来自广泛客户，还是少数大型项目？

  • 传统云使用量增长较为广泛，大多数成熟金融客户都在持续使用数据库、基础设施、分析和安全服务。
  • AI增量支出相对集中，较大规模的收入增长通常来自少数已将AI工作负载投入生产或正在扩大部署范围的客户。
  • 需要区分两个概念：
  1. 增加使用量的客户数量；
  2. 对总收入增长的贡献规模。
  • 传统云现代化覆盖较广泛的客户群体，少数大型生产项目则对AI增量收入贡献更高。
  • 由于没有审查账户层面的支出分布，专家未对集中度给出具体比例。

2. Q4 Azure支出展望与季节性影响

a) 日历年Q4的Azure支出会加速、稳定还是放缓？

  • 基准判断是Q4 Azure使用量将保持稳定增长；如果已获得资金支持的AI项目顺利投入生产，则存在进一步加速的可能。
  • 判断Q4增长能否加速的三个关键因素是：
  1. 客户是否已有获批预算和明确的迁移时间表；
  2. AI项目是否已通过安全审查和模型风险审查；
  3. Azure是否具备支持生产工作负载的可用容量。
  • 银行、抵押贷款等金融客户的数据库、基础设施和核心业务系统提供了稳定的使用量基础。
  • 主要上行空间来自：
  1. AI推理；
  2. 文档处理；
  3. 数据分析；
  4. 项目从试点向大规模生产扩展。
  • 主要下行风险包括：
  1. 数据和系统集成延期；
  2. 采购周期延长；
  3. 安全或监管审批未完成；
  4. 项目推迟至2027年；
  5. 区域GPU或模型吞吐量容量不足。
  • Q4能否显著加速，核心取决于生产环境的实际上线时间，而非项目需求是否存在。

b) Azure是否存在明显的年末季节性？

  • Azure存在一定季节性，但不会仅因12月假期或员工休假而出现显著下降。
  • Azure以按使用量计费为主，金融机构的交易处理、数据库、安全系统及客户应用全年持续运行，因此底层消耗较稳定。
  • 季节性主要影响新项目的采购和部署：
  1. 假期安排会降低实施速度；
  2. 年末变更冻结可能推迟生产上线；
  3. 部分客户可能为使用剩余预算或完成年度目标而加快迁移。
  • 整体而言，12月新增上线的工作负载可能较少，但既有生产负载不会明显下降，季节性只是温和的时间因素，并非Azure收入的重大阻力。

3. AI生产部署进度与项目转化效率

a) 截至9月底，AI工作负载进入生产环境的比例是否较6月底提升？

  • 趋势明确指向生产部署和采用率提升，而非维持稳定。
  • 金融客户正在将更多文档智能、知识检索和客户服务应用纳入实际业务流程。
  • AI采用应区分三个阶段：
  1. 实验或概念验证；
  2. 有限范围的付费生产；
  3. 企业级规模化生产。
  • 生产部署虽在加快，但企业级规模化仍较渐进，主要受安全、模型风险、审批、数据集成和ROI证明要求影响。
  • 专家未给出6月至9月的具体生产化比例，因为客户拥有的生产应用和试点项目数量差异较大，必须基于同一批客户的工作负载清单进行测算。

b) 已投入生产的AI项目，其Azure支出通常如何变化？

  • 对于7月前已投入生产的项目，预计到9月支出通常保持稳定或有所增加，而非普遍下降。
  • 文档智能项目在处理更多贷款申请、服务记录或合规材料后，会增加：
  1. 模型推理；
  2. 文档处理；
  3. 数据库存储；
  4. 搜索和集成服务消耗。
  • 企业知识检索项目也会随着更多员工和部门使用而扩大Azure消耗。
  • 但支出不一定持续加速，因为客户会通过更小模型、提示词优化、缓存和模型路由降低单位成本。
  • 因此，应区分工作负载采用增长与收入增长，二者并不必然同比例变化。

c) AI工作负载增长是否会与Azure支出增长保持一致？

  • AI工作负载与推理支出正逐渐分化，使用量增长可能快于推理费用增长。
  • 例如，金融机构的文档处理量即使翻倍，AI推理支出增幅也可能明显低于100%，原因包括：
  1. 使用更小、成本更低的模型；
  2. 优化提示词和令牌使用；
  3. 引入缓存；
  4. 使用模型路由；
  5. 将开放权重模型用于高容量、可预测任务。
  • 单次交易成本下降能够提升更多场景的经济可行性，从而推动应用普及和总交易量增长。
  • 即使推理成本增速低于工作负载增速，数据库、存储、AI搜索、网络和安全服务仍可能推动Azure总账单增长。

4. 多年期Azure承诺与实际消耗进度

a) 多年期Azure承诺协议的实际消耗是否符合计划？

  • 对成熟工作负载而言，实际消耗总体符合计划爬坡进度。
  • 数据库、基础设施和分析工作负载具有明确的迁移计划和运营需求，因此消耗更可预测。
  • 对较新的AI项目而言，实际消耗存在更大不确定性，可能落后于初始承诺计划。
  • AI项目消耗滞后的主要原因包括：
  1. 安全审批；
  2. 数据集成；
  3. 模型验证；
  4. 从试点向生产扩展延迟；
  5. 容量或配额限制。
  • 三年期Azure协议体现客户的采购意向，但收入只有在工作负载实际部署和使用后才会确认。
  • AI消耗落后于计划不一定意味着需求不足，更常见的原因是生产就绪程度不够。

b) Q3获得资金支持的AI项目是否因容量或其他因素受阻？

  • Q3容量限制仍是重要影响因素，尤其针对需要以下资源的工作负载：
  1. 专用GPU基础设施；
  2. 预配置模型吞吐量；
  3. 特定区域容量；
  4. 满足数据驻留要求的本地区域资源。
  • 大型生产部署受到的影响更明显，传统云工作负载受到GPU容量约束的程度相对较低。
  • 容量不足可能导致已获资金支持的需求无法及时转化为Azure实际消费。
  • 但项目延期不能全部归因于基础设施短缺，安全审查、配额配置、数据准备和系统集成也会造成延迟。
  • 复杂的客户应用型AI和智能体工作流更容易延期，简单的内部生产应用面临的障碍相对较少。
  • 应区分项目延期与项目取消：金融行业中的多数受阻项目是上线时间延后，并不代表需求消失。

5. AI预算来源、支出结构与Azure变现路径

a) 2027年企业AI预算主要来自新增资金还是现有IT预算重分配？

  • 企业AI资金预计由新增投资和现有IT预算重新分配共同构成，不会全部来自净新增支出。
  • 具有明确业务价值的项目更容易获得业务部门专项资金，主要包括：
  1. 文档自动化；
  2. 客户服务；
  3. 运营效率提升；
  4. 可量化的成本节约或收入提升项目。
  • 相当一部分资金会从现代化改造、分析和应用开发预算中重新分配。
  • 已投资Azure Databricks或Fabric的客户，更可能在原有项目基础上扩展AI能力，而不是另行建立完全独立的预算。
  • AI预算正在从实验性创新预算，逐渐转向更稳定、可持续的运营预算。
  • 真正能够证明成本节约或收入增长的项目，最可能获得净新增资金。

b) 大型金融客户的AI项目预算大致如何分配？

  • 专家给出的方向性框架包括：
  1. 基础设施约25%；
  2. 模型推理约15%；
  3. 应用开发约25%；
  4. 集成约25%；
  5. 工程投入约25%；
  6. 安全与治理约10%。
  • 上述比例属于方向性项目规划框架，存在分类重叠，并非可直接相加的实测平均值。
  • 预算覆盖的不只是Azure账单，还包括内部开发、咨询服务、第三方软件、数据准备、安全治理及系统集成。
  • 金融行业因遗留系统和监管要求较多，数据集成通常占据较大支出。
  • 应用进入生产阶段后，支出会更多转向经常性基础设施、推理和运营支持。
  • 相较去年，基础设施、模型推理和应用开发方面的规划投入增加约25%—33%，各类AI相关投资均明显上升。

c) 哪些AI投入能够直接转化为Azure收入？

  • Azure最直接受益于：
  1. GPU和云计算基础设施；
  2. Azure OpenAI及模型推理；
  3. Azure SQL、Azure Search等托管数据服务；
  4. 存储、网络、监控和安全服务。
  • 应用开发和集成只有在最终应用部署于Azure并持续运行时，才会转化为Azure消耗。
  • 咨询服务、内部开发和第三方软件支出不会自动形成Azure收入。
  • AI生产应用具有明显的乘数效应：一个成功应用可以同时带来计算、推理、数据库、存储、搜索和安全等多层经常性消耗。
  • 因此，推动项目从概念验证进入生产，是Azure长期增长的关键。

d) AI治理和安全需求增加后，Azure还是第三方厂商更受益？

  • Azure和第三方专业厂商都会受益，但获取价值的层次不同。
  • Microsoft可通过Azure、Entra、Defender、Purview和Sentinel承接身份、数据治理、安全监控和合规需求，优势在于与现有企业环境的集成。
  • 第三方厂商在以下领域仍具重要价值：
  1. 多云治理；
  2. 数据安全态势管理；
  3. AI模型安全；
  4. 独立风险监控。
  • 大型金融机构通常不愿让整个安全架构完全依赖单一云服务商。
  • 预计Azure将承接更广泛的底层经常性用量；第三方厂商则可能从较小基数出发，在专业安全和治理细分领域实现更快增长。

6. 金融AI项目成功与停滞的关键差异

a) 为什么文档智能项目更容易上线，而复杂智能体项目容易停滞？

  • 贷款文档信息提取类项目通常更容易进入生产，原因包括：
  1. 项目范围较窄；
  2. 业务负责人明确；
  3. 可保留人工验证环节；
  4. 处理时间、准确率和人工成本节约均可衡量；
  5. 与现有业务流程的衔接较清晰。
  • 面向客户、能够自主作出服务或信贷决策的智能体更容易停滞，主要障碍包括：
  1. 模型风险；
  2. 监管要求；
  3. 敏感客户数据；
  4. 系统集成复杂；
  5. AI决策责任归属不清；
  6. 缺乏可接受的人工监督机制。
  • 项目成败的最大差异往往不是技术本身，而是生产就绪程度和业务责任归属。
  • 能够持续推进的项目通常具备明确ROI、获批数据权限、人工监督机制和高管发起人。
  • 停滞项目往往只有较好的演示效果，但尚未解决运营、治理和责任问题。
  • 成功的概念验证不会自动转化为可扩展的生产工作负载，也不会自动形成持续Azure消费。

b) 当前哪些金融AI用例产生的经常性Azure支出最多？

  • 第一类是文档智能及工作流自动化，包括：
  1. 抵押贷款申请；
  2. 收入核验；
  3. 贷款服务；
  4. 合规文档处理。
  • 此类工作负载处理量稳定、重复使用频率高、ROI容易衡量，可持续消耗模型推理、存储、数据库和集成服务。
  • 第二类是内部知识检索和员工Copilot，主要面向服务团队、承保人员和运营人员。
  • 第三类是面向客户的辅助服务，该领域正在增长，但完全自主执行重要业务决策的智能体仍受合规和人工审批要求限制。
  • 按生产成熟度和资源消耗排序：
  1. 工作流与自动化；
  2. 员工知识检索与辅助；
  3. 自主业务智能体。
  • 当前最强劲的经常性Azure消耗仍来自员工辅助型和文档密集型业务流程，而非完全自主智能体。

7. 模型选择、开放权重模型与成本优化

a) 客户的生产模型选择发生了哪些变化？

  • 客户正在放弃“单一模型满足所有需求”的方式，转向按工作负载复杂度和经济性选择模型。
  • 过去企业AI项目通常默认使用规模最大的前沿模型，尤其是OpenAI模型；目前客户更倾向于：
  1. 使用高能力模型处理复杂推理；
  2. 使用小型、低成本模型处理分类、提取、摘要和重复性任务；
  3. 通过模型路由动态选择不同模型。
  • 客户对开放权重模型的兴趣上升，主要出于：
  1. 更强的部署控制；
  2. 更可预测的成本；
  3. 特定的数据处理要求；
  4. 高容量、标准化任务的经济性。
  • 金融客户仍将模型质量、安全性、可审计性和运营支持置于单纯低价之上。
  • 单笔推理成本下降不一定降低Azure总消耗，因为更低成本可能释放更多生产场景。

b) 开放权重模型主要部署在哪里？

  • 三种部署方式均存在：
  1. Azure；
  2. AWS、Google Cloud等其他云平台；
  3. 本地部署。
  • 对已采用Microsoft技术标准的金融客户，Azure通常是最现实的起点。
  • 在Azure上的主要部署方式包括：
  1. 通过Azure AI Foundry的模型服务使用托管式部署；
  2. 在Azure GPU虚拟机或AKS上自行托管，以增强模型定制、性能和扩展控制。
  • 本地部署仍适用于高度敏感、存在数据主权要求或已拥有GPU基础设施的机构。
  • AWS和Google适合已有多云环境或其服务在成本、模型、GPU可用性方面更匹配的客户。
  • 模型部署决策主要取决于现有云承诺、安全架构、数据要求和总体拥有成本。

c) 推理成本优化会如何影响Azure总账单？

  • 客户主要通过三种方式降低推理成本：
  1. 使用更小、更便宜的模型；
  2. 仅将复杂请求路由至高能力模型；
  3. 优化提示词、缓存和令牌使用量。
  • 对使用量固定的成熟工作负载，优化可能直接降低推理支出。
  • 对快速扩张的客户，单位成本下降会使更多应用场景具备经济可行性，从而增加总交易量。
  • 例如，若推理成本下降40%，但交易量翻倍，在工作负载组合基本不变的情况下，推理总支出仍可能增加约20%。
  • 此外，AI应用还会带动存储、数据库、搜索、网络和监控消费。
  • 整体判断是：单笔交易成本将持续下降，但积极扩大AI生产部署的客户，其Azure总消耗通常保持稳定或继续增长。

8. Azure与AWS、Google Cloud的竞争格局

a) Azure赢得金融AI项目的主要原因是什么？

  • Azure的核心优势不是单一模型性能，而是与企业现有技术栈的深度集成。
  • 金融客户通常已使用Microsoft 365、Entra ID、Azure SQL及Azure Databricks，Azure可以复用现有的：
  1. 身份管理；
  2. 数据访问体系；
  3. 安全架构；
  4. 采购流程；
  5. 商业承诺。
  • 这些因素能够降低实施阻力，并缩短从试点到生产的时间。
  • 传统金融机构对Azure的采用通常更强，而金融科技公司对AWS的采用可能更普遍，现有云基础设施是项目归属的重要决定因素。

b) Azure在哪些情况下可能输给AWS或Google Cloud？

  • 若客户现有应用环境主要运行在AWS，迁移和集成成本会使AWS更具竞争力。
  • Google在数据分析、AI原生开发及Gemini/Vertex AI生态方面具有优势。
  • Azure可能因以下因素失去项目：
  1. 客户已有云基础设施偏向竞争对手；
  2. 特定模型性能要求；
  3. 定价或总体成本；
  4. GPU及区域容量可用性；
  5. 专业化技术需求。
  • Azure的优势集中于企业级集成与客户熟悉度，潜在劣势则来自容量、价格和客户既有架构。

c) 容量是否已成为云厂商竞争结果的重要因素？

  • 容量可用性正在成为更重要的竞争考量，尤其是服务商能否在客户所需时间和区域提供特定GPU、模型吞吐量及数据驻留能力。
  • 如果Azure无法按时完成资源配置，已获资金支持的客户可能将特定工作负载迁移至AWS或Google Cloud，而不是等待。
  • 但尚无经验证的规律表明，AWS或Google Cloud因容量更充足而持续赢得金融行业AI项目。
  • 容量是Azure在单个项目层面的风险，但不能据此认定Azure存在整体竞争劣势。
  • Azure仍可凭借企业客户关系、安全集成和既有商业承诺赢得项目。

9. Microsoft工程支持与FDE模式

a) 专家参与的项目是否有正式FDE团队介入？

  • 专家熟悉FDE模式，但其项目主要通过Microsoft云解决方案架构师、专业工程团队和实施合作伙伴推进，并非正式指派的前线部署工程师项目。
  • 相关工程团队主要协助解决：
  1. 数据集成；
  2. 安全要求；
  3. 架构设计；
  4. 概念验证；
  5. 生产部署。
  • FDE模式的价值在于将工程师更直接地嵌入客户实施过程，帮助客户构建可投入生产的AI解决方案，缩短项目批准与实际使用之间的时间。

b) 客户如何评价微软工程与FDE类支持？

  • 微软工程团队的直接支持通常能够显著改善AI项目从概念验证走向生产的效率。
  • 正面反馈主要集中在：
  1. 更快解决技术障碍；
  2. 更好地与现有Azure基础设施集成；
  3. 提升客户对安全和架构决策的信心。
  • 在遗留系统连接、敏感数据管理及规模化架构设计方面，工程团队直接参与比仅依赖文档和支持工单更有效。
  • 若主要障碍是实施复杂性，嵌入式工程支持能够创造较大价值。
  • 若障碍来自预算审批、监管签核或缺少高管支持，仅增加工程师无法解决问题。

10. Copilot扩张、续约与Azure交叉销售

a) 自6月以来，金融客户是否更愿意扩大或续订Copilot？

  • 客户扩大Copilot部署的意愿增强，但许可证分配更加谨慎。
  • 讨论重点已从展示技术能力转向：
  1. 实际采用率；
  2. 可衡量的生产力提升；
  3. 是否足以证明持续订阅费用的合理性。
  • 某银行项目初期约部署30名用户，是否扩大至数百名用户取决于能否证明实际价值。
  • 经常处理文档、会议、研究和复杂信息的岗位，更容易形成明确的Copilot商业价值。
  • 客户正从“基于热情广泛分配许可证”转向“根据使用率和ROI精准分配”。
  • 特定部门具备较强扩展潜力，但不能假设所有试点都会转化为全企业推广或自动续约。

b) 这种许可证管理逻辑是否适用于其他行业？

  • 同样的采购和管理原则适用于金融、汽车及其他行业。
  • 受益岗位通常包括：
  1. 客户经理；
  2. 分析师；
  3. 合规与法务人员；
  4. 运营团队；
  5. 销售和咨询人员；
  6. 人力资源和项目经理。
  • 企业通常先购买较广泛的许可证，再根据活跃使用情况和实际时间节约效果重新分配。
  • 低使用率席位可能被转给更有需求的员工，而非继续为闲置许可证付费。
  • 续约和扩展将越来越取决于活跃使用并创造实际价值的席位，而不是已购买许可证总量。

c) Copilot推广是否会直接增加Azure支出？

  • Microsoft 365 Copilot席位增加不会自动带动Azure支出。
  • Azure增量机会通常出现在标准Copilot无法满足专业业务流程后，客户开始构建定制化应用或智能体。
  • 例如，抵押贷款机构可能构建能够检索贷款文件、检查申请完整性并连接服务系统的智能体，从而带动：
  1. Copilot Studio；
  2. Azure AI Foundry；
  3. Azure AI Search；
  4. Azure Functions；
  5. Azure数据库及存储。
  • Copilot对Azure的核心价值在于，将客户从通用员工生产力场景引导至定制化、生产级、嵌入业务工作流的AI场景。
  • 这一过程具备显著交叉销售潜力，但只有客户真正构建并运行定制工作负载时，才会形成增量Azure消费。

11. Azure容量约束与2027财年扩张判断

a) 是否有证据表明微软优先保障Copilot，导致外部Azure客户交付延迟？

  • 部分客户对此存在担忧，但专家未看到直接证据证明Azure部署延迟是因为微软优先向Copilot或其他内部工作负载分配容量。
  • 客户能够观察到的现象包括：
  1. GPU供应有限；
  2. 区域容量受限；
  3. 配额限制；
  4. 特定AI服务配置周期延长。
  • 容量短缺确实可能造成资金投入延迟和项目上线推迟，但无法仅凭客户交付延期推断微软内部容量分配逻辑。
  • 根本原因还可能包括整体Azure客户需求、硬件供应和区域电力限制。

b) 微软是否需要在2027财年加快AI产能建设？

  • 专家预计微软将在2027财年剩余时间继续加快AI产能扩张，主要依据包括：
  1. 微软已公开承认AI产能受限；
  2. 客户项目正从试验转向生产；
  3. 金融行业形成经常性推理、文档处理、AI搜索和数据工作负载；
  4. 推理成本下降会提高更多应用的经济可行性，进而扩大需求。
  • 衡量扩张效果的关键不是单纯新增多少吉瓦，而是：
  1. GPU产能能否及时投产；
  2. 是否位于客户需要的区域；
  3. 是否能满足数据驻留要求；
  4. 是否能转化为实际付费Azure消费。
  • 电力供应、数据中心建设周期、GPU安装和网络部署均会限制供给扩张速度。

c) 微软2027财年可能新增多少数据中心产能？

  • 专家给出的情景估算为约1吉瓦，较宽区间为0.5—1.5吉瓦。
  • 该数字并非微软官方指引，也不是基于客户账户数据得出的结论，仅为结合客户需求、AI基础设施投资和行业趋势形成的粗略规划假设。
  • 数据中心新增1吉瓦并不等于立即获得1吉瓦可用AI算力，实际可用能力仍取决于建设、供电、GPU安装和投产进度。
  • 专家没有支持“每季度新增1—1.5吉瓦”的可验证数据，因此未进一步上调估算。

如果不审查同一批客户及其工作负载清单，我不会对6月至9月的变化给出确切百分比。要得出准确比例，必须了解这些客户具体使用了哪些工作负载。拥有1个生产级AI应用和10个试点项目的客户，与运行10个不同生产级应用的客户，其采用情况截然不同。

总体而言，生产部署正在推进，发展速度也相当快。但由于安全、模型风险、审批、数据集成等因素，以及企业需要证明可衡量的投资回报率，更广泛的企业规模化进程仍然较为渐进。

提问者：您能否举例说明，7月前已经投入生产的4个AI项目，到9月时，其每月Azure支出发生了怎样的变化？支出是在加速增长、保持稳定，还是有所回落？

提问者：下一个问题与承诺金额和实际消耗有关。对于近期签订的多年期Azure承诺协议，客户的实际消耗是符合计划爬坡进度、领先于计划，还是落后于计划？原因是什么？

AI则有所不同。客户可能基于雄心勃勃的生产部署路线图承诺使用Azure，但由于安全审批、数据集成、模型验证，或从初始试点向外扩展出现延迟，实际消耗可能滞后。

提问者：在7月至9月期间，您是否看到项目，尤其是AI项目，因Azure容量限制而被推迟？

提问者：或者是否存在配额限制？管理层曾提到，一些项目因容量限制而受阻。7月至9月期间，这一因素是否有所缓解？

不过，我会区分公司整体面临的限制与我们在各个金融服务客户中能够确认的情况。容量限制的影响更多集中在大型生产部署中，因为这类客户需要有保障的吞吐量、特定模型的可用性，或特定区域的容量，以满足其数据驻留要求。传统工作负载通常较少受到这类GPU容量限制的影响。

因此，容量限制可能导致已获得资金支持的AI需求无法及时转化为Azure实际使用量，但不能将所有项目延期都归因于基础设施短缺。安全审查、集成准备情况和配额配置等因素，也可能造成项目延期。

提问者：换一种方式来看，7月至9月期间，已获得资金支持的AI项目中，有多大比例因各种原因受阻？是否有大致数据？

回　答　者：对于我具体负责的客户组合，我不希望给出缺乏依据的百分比，但需要区分项目延期与项目取消。在金融服务领域，已获得资金支持的AI项目确实可能因安全、模型风险、数据保护、采购和Azure等因素而延期。上线时间延后并不一定意味着需求减弱。

从7月至9月的情况来看，复杂的客户应用型AI和智能体工作流可能面临较多延期，而相对简单的内部生产应用面临的障碍较少。若要准确量化，应比较该季度计划推进的已获资金支持项目数量与截至9月30日已投入生产的项目数量。这样得出的延期比例会更有依据，而不是依靠推测。

提问者：接下来想了解客户预算。客户在规划27日历年时，AI资金中有多少属于新增预算，又有多少来自其他预算？

提问者：与传统的其他IT项目相比，企业AI投入属于新增预算，还是客户从内部IT预算中重新分配的资金？

在金融服务行业，商业价值最显著的AI项目正日益获得业务部门的专项资金，尤其是文档自动化、客户服务和运营效率提升等项目。与此同时，也有相当一部分资金来自现有的现代化改造、分析和应用开发预算。例如，已经投资Azure Databricks或Fabric的客户，可能会扩展相关项目以支持AI，而不是另行设立全新的预算。

在我们的客户组合中，AI资金正在从实验性创新预算转向更具持续性的运营预算。由于缺少客户的具体预算数据，我无法准确判断新增资金与重新分配资金的比例。但具有可量化成本节约或收入提升效果的项目，预计最有可能获得真正的增量资金。

提问者：对于典型客户，其预算在基础设施、模型、应用、数据和安全方面大致如何分配？

回　答　者：您是想了解金融服务行业客户在不同项目之间的预算分配吗？

提问者：不是。我想了解一家大型客户或典型客户的整体IT预算如何在不同项目或职能之间分配。随着AI出现，与去年或更早时期相比，这种分配发生了哪些变化？

回　答　者：对于典型的大型金融服务企业，我会采用方向性的规划模型：基础设施占25%，模型推理占15%，应用开发占25%，集成占25%，工程占25%，安全与治理约占10%。

需要特别说明的是，这些比例代表项目总投资，而不仅是Azure账单。我们与客户沟通和推进实施时，基础设施通常涵盖计算、网络和托管；模型支出包括推理、API调用和应用开发；应用相关支出涵盖开发、工作流、集成和部署；数据相关支出则包括数据准备、管道和数据库。

回　答　者：检索系统、安全覆盖、身份管理、合规监控以及模型风险控制等。在金融服务领域，由于存在遗留系统和监管要求，数据集成通常占据相当大的支出比例。这些百分比仅用于说明预算框架，并非基于我所负责客户得出的实测平均值。

应用进入生产阶段后，支出结构可能转向经常性基础设施、推理和运营支持。今年与去年相比，基础设施、模型推理和应用开发方面的规划投入增加了25%至约33%。目前，这些不同项目的投资都在显著增加。

提问者：Azure的费用会受益于哪些方面投入的增加？如果客户增加基础设施支出，Azure会从中受益，对吗？安全或数据方面的投入会使第三方软件提供商受益，还是会使Azure受益？

回　答　者：Azure确实会从中受益。Azure最直接受益于基础设施、模型推理和Azure托管数据服务方面的支出。不过，需要区分AI项目支出与最终转化为Azure收入的部分。

例如，金融机构投资GPU计算、Azure OpenAI、Azure SQL或Azure Search，会直接产生Azure资源消耗。应用开发和集成也可能创造Azure收入，因为最终形成的应用会在Azure上运行。然而，咨询服务、内部开发和第三方软件方面的支出，并不会自动转化为Azure收入。

最值得关注的是乘数效应，即成功的AI应用可以同时在计算、推理、数据库、存储和安全等方面产生经常性资源消耗。因此，推动项目进入生产阶段对Azure的长期增长非常重要。

提问者：明白了。随着AI项目加速推进，治理和安全需求也在增加。这会使第三方软件提供商受益，还是也会使Azure等云平台受益？

回　答　者：抱歉，问题的最后一部分是什么？

提问者：这一趋势会……

提问者：第三方软件、安全软件或数据仓库提供商是否会更多地受益于这一趋势？还是 Azure 等云平台本身会从中受益？这一趋势是否会增加对安全数据库的需求？

回　答　者：这是一个多层面的问题。两类厂商都会受益，但 Azure 通常更有能力承接更广泛的基础设施和数据使用需求，而专业化的第三方供应商则能够获取价值更高的安全与治理支出。

在金融服务领域，随着 AI 进入生产环境，客户需要更强大的身份控制、数据治理、访问管理、可审计性和监控能力。Microsoft 拥有 Azure、Entra、Defender、Purview 和 Microsoft Sentinel 等解决方案，并可将其集成到现有的企业环境中，因此具备一定优势。

不过，第三方提供商仍然非常重要，尤其是在多云治理、数据安全态势管理、AI 模型安全和独立风险监控方面。大型银行通常不希望其整个安全架构依赖单一云服务提供商。

我预计，Azure 将承接更多底层的经常性用量，而第三方专业厂商则会从较小的业务基数出发，在特定安全类别中实现更快增长。最终哪一方更具优势，取决于客户是优先选择集成式 Microsoft 安全技术栈，还是更重视对多个云和 AI 环境实施独立控制。

提问者：我想了解哪些因素会阻碍 AI 项目进入生产阶段。能否比较一个已经上线的金融服务 AI 项目与一个停滞的项目，并说明二者产生差异的原因？为什么部分项目会暂停或停滞？

回　答　者：可以比较我在金融服务领域接触过的两类项目，即文档智能项目与更加复杂的面向客户的 AI 自动化项目。

第一类是贷款文档信息提取用例，由 AI 对文档进行分类、提取信息，再将信息发送至现有工作流程，由人工进行验证。此类项目通常具有清晰的生产落地路径，因为其范围较窄，业务负责人也较为明确。

回　答　者：我们清楚参与人员，也清楚协作对象，因此可以衡量项目成效，例如处理时间、准确性和人工工作量的减少。相比之下，如果由自主AI智能体作出客户服务或信贷相关决策，项目更容易停滞，因为这会给整个团队和公司带来模型风险方面的担忧，同时还涉及大量监管要求、敏感客户数据、集成复杂性，以及AI决策责任归属等问题。

最大的差异未必在于技术本身，而在于生产就绪程度和业务责任归属。能够持续推进而未陷入停滞的项目，通常具有明确的ROI、经过批准的数据访问权限、人工监督机制，以及承担责任的高管发起人。停滞的项目往往拥有前景良好的演示，但尚未解决运营或治理要求。

因此，我会区分AI实验与实际的Azure消耗。成功的概念验证通常不会自动转化为可扩展的生产工作负载。

提问者：您已经提到了几个用例。当前，哪些金融服务AI用例产生的经常性Azure支出最多？这些用例主要是辅助员工、服务客户，还是在业务工作流中采取行动？

回　答　者：我将这些用例分为3类。目前，金融服务领域最强劲的经常性Azure消耗，主要来自员工辅助型工作流和文档密集型业务流程，而非完全自主的智能体。

第2类是内部知识检索和员工Copilot，尤其适用于服务团队、承保人员和运营人员。当客户基于Azure AI搜索和Azure托管模型构建这些应用时，相关使用量会随着员工采用率的提升而扩展。

第3类是面向客户的辅助服务。这类用例正在显著增长，但对于采取重要行动的完全自主智能体，合规要求仍构成较大限制，而且仍需要人工审批。因此，如果进行排序，文档相关用例会排在首位。

回　答　者：从生产应用和成熟度来看，第1类是工作流和自动化，第2类是员工知识与辅助，第3类是自主业务智能体。其中，工作流和自动化的交易量最高，也是使用最广泛、重复使用频率最高的领域。这不仅仅是开展若干AI试点项目，而是能够持续推动Azure资源消耗。

提问者：明白。下一个问题与模型选择有关。自3月或6月采用Anthropic以来，客户对生产环境模型的选择发生了哪些变化？

回　答　者：自3月以来，特别是到6月，我看到的最大变化是，客户正在放弃由单一模型满足所有需求的方式，转而根据具体工作负载和经济性选择模型。

此前，许多企业AI项目默认采用规模最大的前沿模型，主要是OpenAI。现在，客户的选择更加审慎。他们会使用高容量模型处理复杂推理任务，同时采用规模更小、成本更低的模型完成文档分类、信息提取、摘要或重复性推理等任务。

客户对开放权重模型的兴趣也在上升，特别是在需要更强部署控制、更可预测的成本或特定数据处理方式时。不过，在金融服务领域，模型质量、安全性、可审计性和运营支持仍然远比单纯选择最便宜的方案重要。

这对Azure的影响仍然非常重要。虽然单笔交易的推理成本可能下降，但更低的成本能够释放更多重要的生产工作负载。因此，模型效率提升并不一定意味着Azure总资源消耗下降，反而可以支持更广泛的应用。

提问者：这些开放权重模型的工作负载实际上运行在哪里？是在Azure、Azure虚拟机、其他云平台，还是本地部署？

回　答　者：这3种部署模式都存在。对于已经采用Microsoft标准体系的金融服务客户而言，Azure通常是最实际的起点。

在Azure上运行开放权重模型主要有2种方式。第1种是使用Azure Foundry中的模型服务选项，由Microsoft负责更多部署基础设施。第2种是在Azure GPU虚拟机或AKS上自行托管，这使客户能够更好地控制模型定制、性能和扩展。

本地部署对于高度敏感的工作负载仍然具有较强的相关性。

回　答　者：对于有数据主权要求、已具备 GPU 基础设施的机构，AWS 和 Google 也是可选方案，尤其适合已经建立多云环境的客户。关键区别在于，Azure 主要提供托管式推理，而其他方案则涉及自托管计算。两者都可以产生 Azure 消耗，但采用不同的计费模式。由于缺少这些客户在部署层面的数据，我无法给出准确的占比。从整体趋势来看，客户在模型选择上正变得更加灵活，但部署决策仍在很大程度上受到现有云服务承诺、安全架构和总体拥有成本的影响。

提问者：您是否观察到越来越多的客户转向成本更低的模型，或者通过模型路由和提示词优化来降低成本？这会对客户的 Azure 总账单产生什么影响？账单会下降、保持不变，还是继续增长？
